# msr_image — 장비 FTP 부하 감소 설계

- 작성일: 2026-08-10
- 상태: 설계 확정, 구현 전
- 범위: 이미지 서빙 경로가 계측 장비 FTP 서버에 여는 **세션 수**를 줄입니다. 캐시
  계층, 이미지 계약, `download_all` 배치 로직은 바꾸지 않습니다.

## 1. 배경 — 왜 지금 이 문제인가

계측 장비의 FTP 서버는 동시 세션 수에 상한이 있고, **엔지니어들이 각자 도구로 같은
장비에 접속해 데이터를 수집합니다.** 즉 우리가 쓰는 것은 공용 희소 자원이며, 우리가
세션을 더 열수록 사람들의 수집 작업이 밀립니다. `SKEWNONO_TOOL_FTP_CONCURRENCY=6`
을 작게 유지해 온 이유가 이것입니다.

2026-08-10 실측(`scripts.measure_msr_image_ftp`, 프록시 경유)에서 cold fetch 1장이
133 ms 이고 그중 connect+login 이 94 ms(71%)로 나왔습니다. 이 숫자만 보면 커넥션
풀링이 최대 레버로 보입니다. **그러나 풀링은 유휴 세션을 붙들어 장비 슬롯을
점유하므로, 위 제약 아래에서는 반대 방향입니다.** 풀링은 채택하지 않습니다.

같은 제약으로 보면 실제 문제는 로그인 비용이 아니라 **우리가 여는 세션의 개수**이며,
현재 그 개수를 아무것도 세지 않는 경로가 있습니다.

## 2. 현재 무엇이 장비에 접속하는가

| 경로 | 예산 | 실제 상한 |
| --- | --- | --- |
| warm job (`POST /api/msr-images` → `download_all`) | Redis 로 워커 간 `max_jobs=2` × `ftp_concurrency=6` | 12 (전 장비 합산, 장비별 아님) |
| cold GET (`GET /api/msr-image` 캐시 미스 → `fetch_image`) | **없음** | 무제한 |

`routes.py` 의 serve 경로는 캐시가 비면 요청 안에서 장비에 직접 접속합니다. 이때
세션을 세는 주체가 없습니다.

### 2.1 예산이 거꾸로 작동합니다

`useMsrImageWarmer.runWarm` 의 `catch` 는 429(`too_many_jobs`)를 죽은 장비와 똑같이
처리해 `status = 'gaveup'` 으로 떨어뜨립니다. 그리고 `SemImage.vue` 의
`holdForWarm` 은 `status === 'warming'` 일 때만 이미지를 보류합니다.

따라서 **warm job 상한에 걸리는 순간 — 즉 장비가 가장 바쁠 때 — 화면의 모든 이미지가
예산 없는 cold GET 으로 동시에 쏟아집니다.** 부하를 묶으려고 만든 상한이, 걸리는
순간 무제한 경로를 여는 스위치가 되어 있습니다.

기존 코드도 이 동작을 인지하고 있습니다(그 `catch` 의 주석: *"the per-image request
path — cache-miss fetch plus auto-retry — still runs and may well win"*). 당시에는
의도된 fallback 이었고, 장비가 공용 자원이라는 제약을 넣으면 성립하지 않습니다.

### 2.2 재시도가 중복을 만듭니다

`useAutoRetrySrc` 는 `<img>` 오류를 2.5초·5초 뒤 재시도합니다(`IMAGE_RETRY_DELAYS_MS`).
느린 이미지 1장은 첫 요청이 끝나기 전에 두 번째·세 번째 요청을 부르고, 캐시는 아직
비어 있으므로 **같은 파일에 대해 최대 3개의 세션**이 열립니다. 장비가 느릴 때, 즉
이미 혼잡할 때만 골라서 그렇게 됩니다.

## 3. 결정 요약

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 커넥션 풀링 | **하지 않습니다** | 유휴 세션이 장비 슬롯을 점유합니다. 실측이 준 94 ms 는 레이턴시 관점의 이득이고, 공용 자원 제약 아래에서는 순손실입니다. |
| warm 429 처리 | `gaveup` 대신 **backoff 재시도**, 이미지는 계속 보류 | §2.1. 가장 큰 증폭원이고 가장 작은 변경입니다. |
| cold GET 중복 | 캐시키별 **프로세스 내 single-flight 락** | §2.2. 같은 파일에 대한 동시 요청을 1회 방문으로 합칩니다. |
| 자동 재시도 횟수 | **2회 유지** (줄이지 않습니다) | §5.3. |
| 장비별 세션 예산 | **하지 않습니다** | §5.4. |
| Redis 분산 락 | **하지 않습니다** | §5.4. |
| `create_bounded` 원자화 | **하지 않습니다** | 비원자성은 문서화된 의도적 절충이며(job 몇 개 초과, key 만료로 자가 교정), §2.1 과 규모가 다릅니다. |

## 4. 설계

두 변경은 서로를 싸게 만듭니다. **P1 은 cold GET 이 발생하는 빈도**를 줄이고, **A 는
발생한 것들의 중복**을 없앱니다. 하나만 하면 각각 절반의 효과입니다.

### 4.1 P1 — warm 거부를 기다림으로 바꿉니다

대상: `front-dev-home/app/composables/useMsrImageWarmer.ts`,
`front-dev-home/app/utils/imageWarm.ts`.

`runWarm` 의 실패 처리를 **거부(429)와 그 외**로 나눕니다.

- **429 이면서 본문 `code === "too_many_jobs"`** — `gaveup` 이 아니라 `warming` 을
  유지한 채 jittered backoff 후 POST 를 다시 시도합니다. 이미지는 계속 보류되므로
  cold GET 이 나가지 않습니다.
- **그 외 오류**(죽은 장비, 만료된 job, 그리고 **rate-limit 429**) — 지금처럼
  `gaveup`. 기다려도 나아질 것이 없거나, 재시도가 상황을 악화시키는 경우입니다.

**상태 코드만으로 판별하면 안 됩니다.** `/api/*` 에는 20 req/5s 애플리케이션 전역
rate limit 이 걸려 있고 그것도 429 를 반환합니다. warm 폴링이 600 ms 간격이므로
이미지 GET 과 겹치면 실제로 도달할 수 있는 한도이며, 그 429 에 재시도로 답하면
이미 제한당한 클라이언트가 요청을 더 보내는 꼴이 됩니다. job 상한 거부만
`{"error": "too many active downloads", "code": "too_many_jobs"}` 를 실어 보내므로
(`routes.py:272`), 그 `code` 가 유일하게 안전한 판별자입니다.

두 경우를 가르는 근거가 다릅니다. 429 는 **일시적이고 자가 해소되는** 상태(앞선
job 이 끝나면 슬롯이 납니다)인 반면, 나머지는 그렇지 않습니다.

경계값:

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 재시도 단위 | POST 부터 다시 (`startDownloadAll` → 폴링 루프 전체) | 429 는 job 이 생성되지 않았다는 뜻이므로 폴링할 job_id 자체가 없습니다. |
| backoff | 1s → 2s → 4s, 각 회차에 ±25% jitter | 여러 사용자가 같은 순간 거부당했을 때 동시에 재시도하지 않도록 합니다. |
| 총 대기 상한 | 기존 `WARM_CEILING_MS = 15_000`, 기존 `startedAt` 기준 | 이미 "언제까지 기다릴 것인가" 를 정한 값이고, 두 번째 상한을 만들면 둘이 어긋납니다. |
| 상한 초과 | `gaveup` | 지금과 같습니다. 이 경우에만 cold GET 으로 떨어집니다. |

상한 판정은 `nextWarmState` 를 거치지 않고 `Date.now() - startedAt >= WARM_CEILING_MS`
를 직접 씁니다. `nextWarmState` 는 폴링 응답(`poll`)을 인자로 받는데 429 경로에는
그 응답이 없기 때문입니다. 상한 **값**은 공유하되 판정 지점만 둘입니다.

`startedAt` 은 기존대로 `runWarm` 진입 시점이므로, backoff 대기 시간도 이 예산에서
함께 차감됩니다. 즉 재시도가 총 대기를 늘리지 않습니다.

### 4.2 A — serve 경로 single-flight

대상: `back_dev_home/msr_image/single_flight.py`(신규, 약 40줄),
`back_dev_home/msr_image/routes.py`(한 블록 교체).

serve 경로의 `fetch_image` + `cache.put` 쌍을 캐시키별 락으로 감쌉니다. **락 안에서
캐시를 다시 읽는 것이 이 패턴의 정확성 근거입니다** — 그것이 없으면 대기자들이
순서대로 장비에 다녀가므로, 직렬화만 시키고 부하는 그대로입니다.

```python
with fetch_gate(cache_key(locator)):     # 같은 이미지끼리만 직렬화
    hit = cache.get(locator)             # 앞 요청이 이미 채웠는가?
    if hit is not None:
        return hit                       # 장비에 가지 않습니다
    fetched = data.fetch_image(locator)
    cache.put(locator, fetched)
    return fetched
```

결정 사항:

- **키는 `cache_key(locator, preview=False)`** 입니다. preview 요청도 결국 같은 원본
  1장을 장비에서 받으므로, 장비 방문을 기준으로 합쳐야 `?preview=1` 과 원본 다운로드가
  동시에 들어와도 세션이 하나입니다. TIFF→WebP 변환은 우리 CPU 비용이지 장비 부하가
  아니므로 락 밖에 둡니다.
- **이미지별 락**입니다. 전역 락 하나면 서로 다른 이미지끼리 줄을 서서 갤러리 로딩이
  직렬화됩니다.
- **타임아웃을 두지 않습니다.** fetch 는 이미 `ftp_timeout`/`host_timeout` 으로
  묶여 있어 락이 무한정 잡히지 않고, 대기자가 기다리는 것이 바로 의도한 동작입니다.
  타임아웃을 넣으면 "포기하고 나도 장비에 간다" 가 되어 목적을 되돌립니다.
- **캐시 계층이 아니라 라우트에 둡니다.** `ImageCache` 는 저장소이고 "누가 장비에
  다녀올 것인가" 는 저장소의 관심사가 아닙니다. 캐시에 넣으면 `DiskImageCache` 와
  `MinioImageCache` 양쪽에 같은 조율 로직이 복제됩니다.
- **warm job 은 감싸지 않습니다.** 이미 배치(세션 1개로 N장)라 dedup 이 얻을 것이
  없고, job 과 GET 이 같은 게이트를 두고 경합하면 job 이 GET 을 기다리는 역전이
  생깁니다.
- **Redis 를 쓰지 않습니다.** 워커 간 중복은 워커 수만큼 남지만, 무제한이 워커 수로
  바뀌는 것만으로 증폭이 사라지고 나머지는 MinIO 캐시가 감당합니다.

락 사전은 무한정 자라면 안 되므로, 마지막 사용자가 빠져나갈 때 항목을 제거합니다
(참조 수를 세고 0이면 삭제). 캐시키는 MSR·파일명 조합이라 상한이 없습니다.

## 5. 검토된 대안과 기각 사유

### 5.1 커넥션 풀링

실측이 지목한 최대 레버였으나 §1 의 제약과 정면으로 충돌합니다. 또한 실측이 프록시
경유였으므로 94 ms 에는 HTTP 왕복이 섞여 있어, FTP 세션을 재사용해도 그 부분은 남습니다.
즉 실제 이득은 94 ms 보다 작고 비용은 장비 슬롯 점유입니다.

### 5.2 cold miss 를 warm job 에 enqueue 하고 202 반환

부하는 최소가 되지만 프론트 계약이 바뀌고 `useAutoRetrySrc` 를 다시 써야 합니다.
P1+A 를 넣고도 부하가 남을 때 다시 봅니다.

### 5.3 자동 재시도 2회 → 1회

A 가 들어가면 **재시도가 싸집니다** — 재시도 요청이 진행 중인 fetch 에 합류해 캐시
결과를 받으므로 장비 세션이 늘지 않습니다. 그 상태에서 횟수를 줄이면 장비 부하는
그대로인데 `이미지 없음` 판정만 빨라져 사용자 경험만 나빠집니다. 유지합니다.

### 5.4 장비별 세션 예산 (in-process 세마포어 또는 Redis counting semaphore)

가장 확실하게 상한을 보장하는 방법이지만 **대기·타임아웃·기아 처리**를 새로
들여옵니다. P1 이 증폭의 근원을 없애고 A 가 중복을 없앤 뒤에도 부하가 관측될 때
판단할 일입니다. 그때는 warm 과 cold 가 **함께 소비하는** 장비별 예산이어야 하며,
한쪽만 묶으면 §2.1 과 같은 우회가 다시 생깁니다.

## 7. 성공 기준

1. warm job 상한에 걸린 상태에서 갤러리를 열어도 cold GET 이 쏟아지지 않습니다
   (기다렸다가 캐시 적중).
2. 같은 이미지에 대한 동시 요청 N개가 장비 방문 1회로 합쳐집니다.
3. 이미지 계약(`GET /api/msr-image` 응답 헤더·바이트), 캐시 키, warm job 동작이
   그대로입니다.
4. 집에서 Redis 없이 전체 스위트가 통과합니다.

## 8. 이 문서가 바꾸지 않는 것

- `download_all` 의 배치·동시성 로직
- `ImageCache` 인터페이스와 두 구현
- `_SECONDS_PER_IMAGE`, `ftp_concurrency` 등 2026-08-10 실측으로 확정한 상수
- `create_bounded` 의 비원자성 (문서화된 의도적 절충)
- vendored `ftp_handler` (이번 범위에 라이브러리 변경이 없습니다)
