# BM/PM 장비 Up 게이트 & PM 집중 관리 — 설계 spec

- 작성일: 2026-05-31
- 대상: CD-SEM 함대(fleet), 팹(fab) 단위
- 라우트: `/ebeam/cd-sem/[fab]/pm-planning`
- 원천 이슈: `docs/issues/tool_monitoring/tool_up_rules.txt`
- 브레인스토밍 결정 기록: `docs/issues/tool_monitoring/tool_up_brainstorm.md`
- 공유 코어: `docs/superpowers/specs/2026-05-31-tool-skew-mgmt-design.md`
  (스큐 코어 엔진 — consensus·skew·epoch). 본 기능은 그 스펙이 미뤄둔
  **"응용 ②: PM MDC·CD_MONITORING 목표값 사전 산출"**의 구체화입니다.

## 1. 목적과 푸는 문제

엔지니어는 BM/PM마다 Data를 직접 확인하고 장비 Up/Down을 결정합니다. HW 엔지니어가
점검을 마치면 App(MI) 엔지니어에게 Data 확인을 요청하는데, App 엔지니어가 부재하면
확인 주체가 없어 **장비 Up이 지연**되는 통증이 있습니다.

동시에, 지금까지는 PM 시 **그 장비 자기 기준**으로만 전후 값이 spec range에 들면
Up 했기 때문에, 장비는 안정적으로 운영되지만 **시간이 지나도 fleet 간 스큐가
개선되지 않는** 단점이 있습니다.

본 대시보드는 두 출력으로 이 둘을 동시에 풉니다.

- **(가) Up 게이트** — 방금 BM/PM을 마친 **한 장비**를 지금 Up할지 즉시 판정합니다.
  자기 참조적 판정이므로 App 엔지니어 없이 HW 엔지니어가 단독 Up할 수 있습니다.
- **(나) 집중 관리 대상 선정** — **함대 전체**를 빔 조건별로 줄세워 다음 PM 때 중앙으로
  당길 장비를 계획합니다.

## 2. 핵심 긴장 — 두 조건의 충돌

| 조건 | 내용 | 방향 |
| --- | --- | --- |
| 1. 연속성 | BM/PM 전후 계측 데이터가 spec range 안에서 유지 | "변하지 마라"(자기 baseline) |
| 2. 수렴 | fleet 중앙값에서 먼 장비를 median 쪽으로 유도 | "변해라"(fleet median) |

의도적 MDC 조정은 전후 delta를 만드므로, **"언제 안정성보다 수렴을 우선하는가"**가
이 설계의 심장입니다. 해법은 **바깥쪽 N개 장비만 중앙으로 당기는 순위 기반
접근**입니다. 전 장비가 median을 쫓으면 표적이 흔들려 진동하지만, 바깥 N개만 당기면
분포가 매 PM 사이클마다 좁아지기만 하여 수렴합니다.

## 3. 페이지 구조

- **라우트:** `/ebeam/cd-sem/[fab]/pm-planning` — 팹 스코프, `skew-check`의 형제 페이지.
- **헤더:** 기존 `EbeamMetaBar` 패턴(제목·토글·통계·freshness).
- **레이아웃 (A · 스택):** 상단에 얇은 **Up 게이트 스트립**, 그 아래 full-width
  **집중 관리 본문**. `skew-check`의 위→아래 섹션 스택 패턴과 동형입니다. 게이트는
  단일 장비 즉시 확인(짧음), 집중 관리가 페이지의 주 작업(넓음)이라는 위계를 반영합니다.

## 4. 섹션 (가) — Up 게이트 (장비별·즉시)

### 4.1 하드 게이트 (통과 시 HW 단독 Up)

장비 선택 → **판정 카드**. 다음 두 조건을 **모두** 만족할 때만 통과합니다.

- (a) **CD_MONITORING 계측값이 그 장비의 per-tool spec range 안**.
- (d) **BSM(빔 형상 radar)이 spec range 안**.

둘 다 자기 참조적(그 장비 자신의 spec)이라 fleet 비교나 App 엔지니어 판단 없이도
판정됩니다 → 통증 해결.

### 4.2 게이트는 사후값을 본다 (delta는 게이트가 아님)

- 게이트는 **PM 사후(post-PM) 값이 spec range 안인지**만 봅니다. **전후 delta는
  게이트 조건이 아닙니다.**
- 근거: delta를 게이트로 쓰면 (i) 약간 벗어났다가 PM으로 **개선되어 range 안으로
  들어온** 경우와 (ii) 의도적 **MDC 수렴 조정**이 모두 게이트에서 실패합니다. 둘 다
  Up을 막아선 안 됩니다.
- 따라서 (c) **MDC 변화**는 게이트 항목이 아니라 **context**(epoch 마커·수렴 추천의
  이력 입력)로만 표시합니다. 전후 delta도 정보로만 보여줍니다.

### 4.3 advisory 신호 (Up을 막지 않음)

- 판정 카드 옆에 그 장비의 **max-axis fleet skew**(§5.1)를 chip으로 함께 표시합니다.
- **Up을 막지 않습니다.** advisory 임계선을 넘으면 다음 PM **집중 후보로 적재만**
  합니다(양산은 계속 돌려야 하므로 지금 Up은 보류하지 않음).

### 4.4 제외

- (e) 특수각은 deferred(기존 스큐 스펙과 동일).

## 5. 섹션 (나) — 집중 관리 대상 선정 (함대·다음 PM)

### 5.1 순위 점수 — max-axis skew

- 코어 엔진은 셀`(빔 × 축[X/Y] × cd_band × epoch)`마다 **tool skew = consensus 대비
  잔차(nm)**를 줍니다. CD_MONITORING은 16nm 단일 대역이므로 본 기능에서 cd_band는
  사실상 단일 대역으로 collapse됩니다.
- **순위 최소 단위 = 빔 조건(500V·800V).** 한 빔 안에서 X·Y 두 잔차를 하나의 순위
  점수로 합칩니다:

  > **score(tool, beam) = max(|skew_X|, |skew_Y|)**  — "최악 축"

- 채택 이유: 순위 점수와 드릴다운의 "이 축을 고쳐라"가 **같은 숫자**이므로, HW
  핸드오프("어느 코일을 칼리브레이션?")가 모호하지 않습니다. 유클리드/평균은 어느
  한 축도 단독으로 나쁘지 않은데 순위만 높아지는 모호함이 생깁니다.

### 5.2 선정 규칙 — 임계 게이트 → bottom-N

- **2단계 선정.** (1) advisory **임계선을 넘은 장비만** 후보 풀에 넣고, (2) 그 풀에서
  점수 상위 **최대 N대**를 빔별 집중 대상으로 지명합니다.
- 자기-제한 성질: 함대가 수렴해 전부 임계선 안에 들면 후보가 자연히 비어, 이미 좋은
  장비를 불필요하게 당기지 않습니다(무조건 bottom-N의 진동·낭비 회피).
- HW가 빔·축별로 칼리브레이션하므로 "이 장비의 800V·Y가 멀다"가 실행 단위입니다.
  축(X/Y)은 **드릴다운**으로 펼칩니다.
- 지명은 **HW 협의 후 확정** — 시스템은 후보를 제시하고 사람이 결정합니다.

### 5.3 N과 임계값 — knob + 기본값

- **N**(기본 3)과 **advisory 임계값**은 엔지니어 **knob(조절 가능) + 기본값(우리가
  지정)**입니다. 코어의 `tolerance` knob 철학과 동일하게 **클라이언트에서 재계산**하여,
  knob을 돌릴 때 재요청 없이 즉시 순위·후보를 다시 그립니다.
- 임계값은 **빔별 기본값**을 제공합니다(500V·800V의 skew 스케일이 다르므로 단일
  글로벌 nm은 한 빔을 오판정).

### 5.4 수렴 추천의 해상도

- 셀(빔×축)별로 `현재값 · fleet median(목표) · 부호 있는 gap`과 MDC·BSM 과거 epoch
  이력을 나란히 제시하고, 방향은 **정성 화살표**("median보다 +0.4nm 높음 → 낮추는
  쪽") 수준으로 둡니다.
- **MDC는 절대 목표값이 아닙니다.** 하드웨어 리세팅을 하면 default가 완전히 새로
  잡히므로 MDC 이력은 주로 *그 장비 자신의 이력 관리*용입니다. HW 세팅이 이미 최적이고
  **최종 출력값만 옮기면 될 때** MDC를 조정하며, 이때 타겟값을 제시할 수는 있으나
  그것이 최종 목표는 될 수 없습니다.
- "권고 MDC 수치 산출"은 회귀모델·office 실데이터가 필요하므로 deferred. 계약에는
  자리만 예약합니다(가짜 수치를 만들지 않음).

## 6. API 계약 & swap surface (Phase-1 ↔ office)

- 신규 피처 폴더 `back_dev_home/ebeam/<...>/pm_planning/` 에 `routes.py` + `data.py` +
  `contracts.py` + `__fixtures__/` 를 두며, 기존 hitachi 피처 패턴을 그대로 따릅니다.
- **스큐 코어(consensus·skew·epoch)를 계약으로 공유**합니다. finder(`/skew-check`)와는
  별도 라우트로 분리하되 같은 코어 출력을 입력으로 받습니다.
- **BSM·MDC는 기존 hardware 피처 데이터를 입력으로 재사용**합니다(중복 생성 금지).
- **신규 필드:** per-tool **spec range**(CD_MONITORING + BSM 상·하한)를 **hardware 피처
  계약에 추가**하고, `pm-planning`이 계약으로 소비합니다. spec range 원천은 기존
  per-tool spec(office 시스템)입니다.
- 계약이 노출하는 것:
  - 게이트: 장비별 `cd_monitoring_value` + `spec_range`, `bsm_in_spec`,
    `gate_verdict`, `advisory_skew`(max-axis), `epoch_markers`, `prev_post_delta`(참고).
  - 집중 관리: 빔×축별 raw skew(부호 있음), `current_consensus`/`median`,
    빔별 기본 `threshold`, 기본 `N`, `mdc_history`/`bsm_epoch_history`(이력).
- **클라이언트 계산:** 순위 점수(max-axis)·임계 게이트·bottom-N·knob 재계산은 모두
  **클라이언트**가 수행합니다. 엔진은 raw skew와 기본값만 내려보냅니다.
- Phase-1은 mock 출력 + 계약 + UX만 증명합니다. 실제 통계 구현은 office에서 `data.py`
  스왑으로 교체하며, "추천이 옳다"는 검증은 office 실데이터로 별도 수행합니다.

## 7. 범위 경계

### 7.1 v1 포함

- 섹션 (가) Up 게이트: 사후값 ∈ per-tool spec(CD_MON + BSM), advisory chip(비차단).
- 섹션 (나) 집중 관리: max-axis 순위, 임계 게이트→bottom-N, N·임계 knob, 축 드릴다운,
  수렴 추천(정성 화살표 + epoch 이력).
- **X/Y 축만**, 양팹 공용, 레이아웃 A(스택).

### 7.2 Deferred (후속)

- 권고 MDC 수치 자동 산출(회귀모델·office 데이터 필요; 계약에 자리만 예약).
- 특수각 전용 검증.
- 알람 발송 채널.

### 7.3 열린 결정 (구현 단계에서 확정)

- N·빔별 임계값의 구체 기본 수치(mock에서 임시값, office에서 보정).
- cd_band collapse 확인(CD_MONITORING 단일 대역 가정의 mock 표현).
- 수렴 추천 패널의 epoch 이력 표시 깊이(몇 epoch까지).

## 8. 고려된 대안

| 접근 | 내용 | 판정 |
| --- | --- | --- |
| 순위 점수 = 유클리드 √(X²+Y²) | X/Y 평면 벡터 크기 | 기각 — 단독으로 안 나쁜 축이 순위 올림, HW 핸드오프 모호 |
| 순위 점수 = 두 축 평균 | (\|X\|+\|Y\|)/2 | 기각 — 한 축만 심하게 멀 때 희석되어 과소평가 |
| 선정 = 무조건 bottom-N | 임계 무시, 항상 N대 | 기각 — 함대가 좋아져도 계속 N대를 끌어들여 진동·낭비 |
| 선정 = 임계 게이트 → bottom-N | 임계 통과 후보 중 상위 N | **채택** — 자기-제한, 수렴 시 후보 자연 소멸 |
| 게이트 = 전후 delta | 변화량으로 Up 판정 | 기각 — 개선·의도적 MDC 수렴까지 차단 |
| 게이트 = 사후값 ∈ spec | 자기 참조 spec range | **채택** — App 엔지니어 없이 판정, 수렴 조정과 양립 |
| 레이아웃 = 통합 그리드(C) | 한 표에 게이트+랭킹 | 기각 — 단일 장비 즉시 판정 집중도 약화, BSM radar 압축 곤란 |
| 레이아웃 = 스택(A) | 게이트 상단 스트립 + 집중 본문 | **채택** — 시간적 분리 반영, skew-check 패턴 동형 |

## 9. 되돌리기 어려운 이유

이 설계는 **(1) 게이트가 사후값만 본다**(delta 비차단)와 **(2) 하나의 max-axis
지표가 게이트 advisory와 집중 순위를 동시에 구동**한다는 두 약속을 계약·UI에 박습니다.
한 번 mock·office 양쪽과 Nuxt 페이지에 자리 잡으면, 게이트에 delta 조건을 끼워넣거나
지표를 합성 점수로 바꾸는 일은 계약·UI·backend를 함께 갈아엎는 비용을 부릅니다.
특히 "게이트는 delta를 막지 않는다"는 원칙은 맥락 없이는 과해 보이므로 — 왜 변화량을
안 막는가 — 그 근거(개선·의도적 수렴 조정을 차단하지 않기 위함)를 여기 명시해 둡니다.
