# 동료 기여 안내

SKEWNONO 는 장비별 작업 공간의 **허브**입니다. 사용자는 장비를 고르고 그 장비의
작업 공간에 들어갑니다. 동료는 아래 두 방향 중 하나로 참여합니다. 최종 반영은
저장소 소유자가 결정하고, **동료가 만든 것이 깨져도 SKEWNONO 는 뜬다**는 것이 두
방향 모두의 전제입니다.

| 방향 | 코드가 사는 곳 | SKEWNONO 와 공유하는 것 | 안내 |
| --- | --- | --- | --- |
| 저장소 안에서 기여 | 이 저장소의 `backend/contrib/<slug>/` 와 `apps/<slug>/` | 신원, API, 배포, 요청 제한 | [`in-repo/`](in-repo/README.md) |
| 별도 공간에서 개발 후 링크 | 동료의 저장소와 서버 | 진입 주소와 메뉴 한 줄 | [`linked/`](linked/README.md) |

각 폴더에는 안내(`README.md`)와 동료의 사내 LLM 에 넣을 규약(`AGENTS.md`)이 한 장씩
있습니다. `AGENTS.md` 는 자기 작업 폴더에 복사해서 `<...>` 자리를 채우는 템플릿입니다.

## 어느 쪽인가

- SKEWNONO 의 데이터(`/api/*`)와 신원을 그대로 쓰고, 배포를 SKEWNONO 와 같이 타도
  되면 **저장소 안**입니다.
- 자기 데이터로 자기 도구를 만들고, 스택과 배포 주기를 따로 가져가고 싶으면
  **별도 공간**입니다.
- 나중에 옮길 수 있습니다. 진입 주소가 SKEWNONO 쪽에 고정되어 있어서 위치가 바뀌어도
  사용자가 북마크한 링크는 그대로입니다.

## 두 방향에 공통인 규칙

### 진입 주소는 `/<slug>` 입니다

작업 공간이 어디에 있든 SKEWNONO 안에서는 `/<slug>` 로 들어갑니다. 구현은 두 파일입니다.

- `frontend/app/pages/<slug>.vue` 한 장. 실제 위치로 보내는 일만 합니다.

  ```vue
  <script setup lang="ts">
  // /<slug> 는 SKEWNONO 쪽에 고정된 주소이고, 작업 공간의 실제 위치는 아래입니다.
  await navigateTo('<실제 URL>', { external: true })
  </script>

  <template>
    <div />
  </template>
  ```

- `frontend/app/utils/headerNav.ts` 의 `HEADER_LINKS` 에 `to: '/<slug>'`, `group: 'lab'`
  항목 한 줄. 실험실 메뉴 노출이 여기서 파생됩니다. 메뉴 항목은 `NuxtLink` 로
  그려지므로 `to` 에 외부 URL 이나 정적 파일 경로를 직접 넣으면 라우터가 가로채
  404 가 납니다. 항상 위 페이지를 거칩니다.

승격되어 정식 화면이 되면 그 페이지 파일을 진짜 구현으로 바꾸면 됩니다. 주소는 안
바뀝니다.

### 슬러그

슬러그 하나가 폴더 이름, API 경로, 페이지 경로, 활동 로그 키를 모두 정합니다.

- 백엔드 폴더와 API 접두어는 **snake_case** 입니다: `backend/contrib/my_tool/`,
  `/api/my_tool/...`.
- 페이지 경로는 **kebab-case** 입니다: `/my-tool`. 활동 로그가 페이지 경로의 `-` 를
  `_` 로 바꾸고 API 경로는 첫 세그먼트를 그대로 쓰므로, 이렇게 해야 둘이 같은
  `my_tool` 로 모입니다. 한 번 기록된 슬러그는 되돌릴 수 없습니다.
- `_` 로 시작하는 폴더는 공유 plumbing 으로 취급되어 등록되지 않습니다.
- `frontend/app/pages/` 의 기존 이름과 겹치지 않는지 먼저 봅니다. 백엔드 슬러그 충돌은
  부팅 로그에 남지만, 페이지 경로 충돌은 개발 서버 경고 한 줄뿐입니다.

### 반입 경로

사무실에서는 GitHub 로그인이 되지 않으므로 PR 흐름이 성립하지 않습니다.

1. `main` 에서 브랜치를 만들어 작업하고 **commit 합니다.** `git status` 가 깨끗해야
   합니다. `format-patch` 와 `bundle` 은 commit 된 변경만 담고, 작업 트리의 변경은
   조용히 빠집니다.
2. `git format-patch main` 또는 `git bundle create <slug>.bundle main..HEAD` 로 묶어
   소유자에게 넘깁니다. 사내 공유 경로에 bare 저장소를 두고 그곳에 push 해도 됩니다.
   `git diff --stat main...HEAD` 를 같이 넘기면 수신 쪽이 완전성을 맞춰볼 수 있습니다.
3. 소유자가 사무실에서 받아 검토하고, 집에서 `main` 에 올립니다.

별도 공간 방향이면 SKEWNONO 쪽에 넘기는 것은 위 두 파일뿐입니다.

### 소유자 검토

소유자는 **patch 전체**를 봅니다. 자기 폴더 안은 동작과 게이트 통과 여부만 보고, 각
안내의 "손대는 줄" 표 밖으로 나온 공유 파일 변경은 줄마다 이유를 확인합니다. 이유는
patch 의 `MIGRATION.md` 에 적혀 있어야 합니다.

### 사내 LLM 컨텍스트

동료는 사내 LLM 과 함께 코딩합니다. 작업을 시작할 때 다음을 컨텍스트에 넣습니다.

- 자기 폴더의 `AGENTS.md` (이 폴더의 템플릿을 복사한 것)
- 해당 방향의 안내 `README.md`
- 저장소 안 방향이면 루트 `AGENTS.md`, 화면을 SKEWNONO 안에 만들면 `DESIGN.md`

LLM 이 공유 코드를 고치자고 제안하는 것을 막는 방법은 문서를 늘리는 것이 아니라
**읽는 범위를 자기 폴더와 이 파일들로 좁히는 것**입니다.
