02 / 확립한 것

3-Phase 배포 전략

집(오프라인), 회사 로컬, 회사 운영망 세 곳에서 같은 코드가 돕니다. 바뀌는 것은 환경변수뿐입니다. 집에서는 Flask가 5050 포트에서 메모리 상의 mock 모듈을 읽어주고, 회사에서는 같은 Flask가 Redis와 OpenSearch를 읽습니다. Nuxt는 어느 쪽이든 /api/*로만 이야기하므로 프론트엔드는 자기가 어느 환경에 있는지 알 필요가 없습니다.

PHASE 1 · 완료

집 / 오프라인

개인 PC에서 완전 오프라인으로 개발합니다. Flask mock 서버가 메모리 상의 Python 모듈에서 데이터를 만들어주므로 DB도 네트워크도 필요 없습니다.

NUXT_API_TARGET=http://localhost:5050
SKEWNONO_DATA_PROVIDER=mock
PHASE 2 · 진행 중

회사 / 로컬

사내망에서 같은 Flask가 Redis·OpenSearch·MinIO를 봅니다. 기능별로 하나씩 환경변수를 office로 돌리며 검증합니다.

SKEWNONO_SEM_LIST_PROVIDER=office
SKEWNONO_STORAGE_PROVIDER=office
PHASE 3 · 예정

회사 / 운영

사내 프라이빗 클라우드에 올립니다. Flask가 빌드된 Nuxt 정적 파일까지 함께 서빙하므로 배포 대상은 하나입니다.

http://sknn.skhynix.com
내부망 전용 · 외부 노출 없음
03 / 확립한 것

Ports & Adapters 어댑터 구조

기능마다 폴더가 하나씩 있고 그 안에 routes.py, contracts.py, data.py, 그리고 providers/mock.py와 providers/office.py가 들어갑니다. data.py는 환경변수를 보고 둘 중 하나를 고르는 디스패처이며 절대 손대지 않습니다. 회사에서 할 일은 office.py 한 파일을 채우는 것뿐이고 응답 모양은 contracts.py가 강제합니다.

Nuxt 화면
환경을 알지 못함
$fetch('/api/…')
→
routes.py + data.py
단계가 바뀌어도 그대로
contracts.py 로 모양 고정
→
providers/
여기만 갈아끼웁니다
mock.py ↔ office.py
전 단계 공통 — 고칠 일 없음 교체 지점 — 회사에서 채우는 유일한 파일

office.py는 사내 스키마가 들어가므로 git에서 제외했습니다. 대신 뼈대만 담은 office_example.py를 20개 기능 전부에 두고 회사에서 복사해서 쓰는 방식으로 정리했습니다.

상태 관리와 데이터 조회

Pinia는 쓰지 않았습니다. 화면 간 공유 상태는 Nuxt의 useState로, 새로고침을 견뎌야 하는 값은 usePersistedState 팩토리 하나로 모았습니다. 원래 localStorage를 직접 만지는 컴포저블이 8개 흩어져 있었는데 하나로 합쳤습니다.

서버 조회는 useAsyncData에 리소스별 캐시 키를 붙여 여러 화면이 같은 요청을 나눠 쓰도록 했습니다.

테스트와 문서

기능마다 계약 테스트가 있어서 mock과 office 어댑터가 같은 모양을 뱉는지 확인합니다. 환경변수를 office로 바꾸고 테스트가 통과해야만 실제 전환을 승인합니다.

문서는 OpenWiki가 하루 두 번 자동으로 갱신하므로, 코드가 바뀌면 설명도 따라옵니다.

04 / 화면 구성

메뉴 구조와 페이지

메뉴는 장비 종류(CD-SEM, HV-SEM)와 Fab을 축으로 잡고 그 아래 7개 탭을 두었습니다. CD-SEM과 HV-SEM은 같은 컴포넌트를 공유하므로 장비가 늘어나도 화면을 새로 만들 필요가 없습니다.

TAB 01

장비 상태

Fab별 장비 목록과 가동 상태, 장비 IP·버전 정보를 한 화면에서 확인합니다.

TAB 02

Recipe 현황

장비별 Recipe 보유 현황과 Storage 점유, PPID 사용 불가 구간을 봅니다.

TAB 03

Recipe 검색

Recipe 조회·비교, Lateral 조회, 측정 이력, Open 조회, TAT 분석을 묶었습니다.

TAB 04

H/W 관리

BSM·FDC·MDC·Beam Shape·Resolution 등 하드웨어 지표를 시계열로 추적합니다.

TAB 05

디바이스 통계

DRAM·NAND·New Memory별 Recipe/Parameter 현황과 계측 룰 위반을 추적합니다.

TAB 06

스큐 관리

장비 간 측정 편차를 fleet 합의값 대비 residual로 분해해 확인합니다.

TAB 07

스큐보아

측정 결과·웨이퍼 맵·MSR 이미지·상관 분석을 한 워크스페이스에 모았습니다.

05 / 기능 목록
