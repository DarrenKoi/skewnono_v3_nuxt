사무실(Office) OpenSearch index — recipe IDP 버전 이력

"Lateral check"(횡전개 점검) 화면의 소스입니다. 답하려는 질문은 하나입니다 —
**이 recipe 를 fab 안의 어느 장비가, 어떤 IDP 버전으로 보유하고 있는가.**

Index(alias)
  cdsem_idp_ver -> tool_type "cd-sem"
  hvsem_idp_ver -> tool_type "hv-sem"

문서 1건 = **(recipe, version) 한 쌍** 입니다. 한 recipe 의 full_name 을 검색하면 그
recipe 의 버전 이력 전체가 나오고, version 이 가장 높은 것이 현재 버전입니다.

사용 field

  full_name -> text: 사용자가 검색한 recipe 이름. 정확 일치는 full_name.keyword 로
                     겁니다. 기본 mapping 은 analyzed text 라 term 은 아무것도
                     매칭하지 않고 match 는 토큰이 겹치는 다른 recipe 까지 잡습니다.
  fab_name -> text: fab 필터. **대문자로 저장**되어 있습니다. fab_name.keyword 사용.
  version -> long: IDP 버전. 클수록 최신입니다.
  modified -> date: 해당 버전이 생성된 시각.
  eqp_id -> text(다중값): 이 버전을 명시적으로 보유한 장비 목록(보유).
                          값이 1개면 list 가 아니라 bare string 으로 돌아오므로
                          두 형태를 모두 받아야 합니다.

  parameters -> object: {parameter 이름: 측정 point 수}. 아래 "parameters blob 구조".
  parameters_list -> string(다중값): parameter 이름을 **측정 순서**로 적은 목록입니다
                     (office 확인 2026-08-10). parameters 의 key 순서와 **다릅니다** —
                     아래 "순서는 parameters_list 가 정합니다" 절을 보십시오.
  raw_data -> object: parameter 별 상세 row. ``Mother_Para`` 가 여기 있습니다
              (office 확인 2026-08-10). 아래 "raw_data — mother 의 출처" 절.

가져오지 않는 field

  parameters, parameters_list, raw_data
                       -> **이 화면(lateral check)이** 읽지 않는 object blob 입니다.
                          버전 200건치를 함께 내리면 응답이 그것만으로 커집니다.
                          ※ device-statistics 는 반대로 이 셋이 필요합니다.
                            아래 "두 번째 소비자" 절을 보십시오.
  not_found_eqp_id -> 미보유 목록. **의도적으로 읽지 않습니다.** 보유 판정은
                      "명시적 eqp_id 등재" 와 "최근 측정 실행 이력" 의 합집합인데,
                      recipe 를 실제로 실행한 장비를 미보유로 표시할 수는 없으므로
                      이 부정 목록이 실행 증거를 뒤집게 두지 않습니다.

조회 방법

1. full_name.keyword + fab_name.keyword 로 버전 문서를 최대 200건(MAX_VERSION_DOCS)
   가져옵니다. 한 recipe 가 이보다 많은 버전을 가지는 것은 예상 밖이므로, 상한에
   걸리면 조용히 자르지 않고 truncation 을 감지합니다.
2. 두 번째 신호로 meas_hist_* 의 최근 30일(MEAS_HISTORY_DAYS) 창에서 같은
   fab/full_name 의 eqp_id.keyword distinct 값을 구합니다. 이것이 하한선입니다 —
   recipe 를 실행한 장비는 미보유로 표시될 수 없습니다. IDP 이력에 없는 장비는
   발견된 최신 버전을 받고, 명시적 IDP 버전 등재가 항상 우선합니다.
3. 장비 명부(eqp_id / model / vendor / available)는 **이 index 에서 오지 않습니다.**
   sem_list 로 해결합니다(docs/datatables/hitachi/sem_list.txt). 이 index 는 장비별
   보유/버전/시점만 결정합니다. 명부를 자체 공급하면 같은 fab 인데 장비 재고 화면과
   장비 수가 달라지고, 어느 쪽이 맞는지 판별할 수 없게 됩니다.

두 번째 소비자 — device-statistics 의 파라미터 개수 (user-confirmed 2026-07-30)

이 index 는 소비자가 둘이고, **필요한 field 가 서로 반대**입니다. lateral check 는
parameters 를 버리고 보유/버전만 보지만, device-statistics 는 parameters 가 목적입니다.

- 조인 키: sknn-planstep-r3 의 recipe_id 가 이 index 의 full_name 과 같은 값입니다
  (docs/datatables/hitachi/planstep_r3.txt). 정확 일치는 full_name.keyword 로 겁니다.
- **가장 높은 version 문서 1건만** 필요합니다. 버전 이력 전체를 받는 lateral check 와
  달리, 여기서는 recipe 당 최신 1건의 parameters 로 para_* 개수를 집계합니다.
- 따라서 질의는 recipe 당 `full_name.keyword` term + `version` desc 정렬 + `size: 1` 로
  좁히고, `_source` 도 필요한 field 로 제한합니다 — `parameters`,
  `parameters_list`, 그리고 `raw_data` 는 **통째로가 아니라** `raw_data.Parameter` /
  `raw_data.Mother_Para` / `raw_data.Region` 세 경로만.

주의 — payload. device 1개가 recipe 를 100~200개 가지므로(docs/datatables/hitachi/
recipe_params.txt), recipe 마다 parameters blob 을 받으면 위 "200건이면 응답이
커진다" 경고가 device 단위로 그대로 재현됩니다. 최신 1건 제한과 _source 제한은
선택이 아니라 필수입니다. 실제 blob 크기와 recipe 당 파라미터 개수는 사무실에서
확인합니다:

    .venv/bin/python -m scripts.probes.probe_planstep_r3

parameters blob 구조 (user-confirmed 2026-07-30)

**dict[str, int]** 입니다 — key 가 파라미터 이름, value 가 측정 point 수입니다.

    {"WAFER": 13, "EDGE": 16, ...}

계약 두 형태가 모두 이 dict 하나에서 나옵니다.

  RecipeParamsRow.parameters   -> [{"name": k, "point_count": v}, ...]
                                  dict entry 1개 = ParameterRow 1개입니다.
  RecipeInfoRow.para_*         -> **value(point 수)의 구간별 파라미터 개수**입니다
                                  (2026-08-10 합의). 이름의 숫자는 구간의 상한입니다.

                                      x <= 5        para_5
                                      5 < x <= 9    para_9
                                      9 < x <= 13   para_13
                                      13 < x <= 16  para_16
                                      16 < x        para_over_16

                                  다섯 구간이 point 수 전체를 덮으므로 **모든
                                  파라미터가 정확히 한 버킷**에 들어갑니다.
                                  para_all 은 그 합이자 파라미터 총 개수입니다.

즉 para_* 는 **파라미터 타입별 개수가 아니라 point 수 구간별 개수**입니다.
"para_16" 이 타입 코드처럼 보이지만 16 은 측정 point 수의 상한이며,
타입(WAFER / LEVEL / EDGE / EDGE_EX / OTHER)과는 다른 축이므로 섞으면 안 됩니다.

정정 이력 (2026-08-10) — 그 전까지는 point 수가 **정확히** 16/13/9/5 인 것만
셌습니다. 확인된 실물 한 건이

    {"EDGE": 10, "LEVEL": 4, "WAFER": 10}

으로 나오면서 그 정의가 무너졌습니다. 세 값 모두 네 숫자 밖이라 이 recipe 는
para_all 까지 0 이 되고, 화면의 100% 누적 막대는 빈 칸이 됩니다. 값이 point 수라는
것은 같은 날 재확인되었으므로 읽는 쪽의 버그가 아니라 정의의 문제였습니다.

구간으로 바꾸면서 오래 열려 있던 질문 하나도 닫혔습니다 — para_all 을 "전체
파라미터 수" 로 쓸지 "버킷 합" 으로 쓸지. 구간이 전체를 덮으므로 **두 값은 이제
같습니다.**

경계는 코드 한 곳에 있습니다: `back_dev_home/ebeam/device_statistics/para_buckets.py`
(프론트엔드 거울은 `app/utils/paraTrendSeries.ts` 의 PARA_KEYS).

para_* 는 측정 파라미터만 셉니다 (user-confirmed 2026-08-10)

  Dummy 와 Align 은 CD 를 재는 파라미터가 아니라(recipe_params.txt) point 수가
  1~3 이며, "얼마나 많이 쟀는가" 의 답에 들어가지 않습니다. 따라서 para_* 버킷
  집계에서 빠집니다. 아래 "16 초과는 2~5%" 도 이 둘을 빼고 센 값입니다.

  판정은 **이름 + 맨 앞** 입니다 (user-confirmed 2026-08-10). 이 둘은 가끔
  나타나고 나타날 때는 parameters_list 의 맨 앞에 오므로, 뒤쪽에 있는 같은
  계열 이름("CD_ALIGN")은 진짜 측정 파라미터로 봅니다. 그래서 이 필터는
  **parameters_list 로 순서를 맞춘 뒤에** 걸어야 합니다 — 순서가 없으면 아무것도
  못 걸러내지만, 엉뚱한 파라미터를 지우는 것보다는 낫습니다.

  거르는 자리는 para_buckets.measurement_parameters 하나입니다. count_points 가
  point 수가 아니라 **{이름: point 수}** 를 받는 것이 그래서입니다 — 이름을 안
  받으면 부르는 쪽이 거르기를 잊을 수 있고, 그 실수는 예외가 아니라 "para 합계가
  조금 크다" 로만 나타납니다.

16 point 초과는 드물고 몰려 있습니다 (user-confirmed 2026-08-10)

  16 point 를 넘는 파라미터는 **전체 파라미터의 2~5%** 이고, 그것이 **전체
  recipe 의 3%** 에 몰려 있습니다. 즉 그 3% 의 recipe 는 파라미터가 거의 전부
  16 을 넘고, 나머지 97% 의 recipe 에는 그런 파라미터가 아예 없습니다.

  그 3% 는 웨이퍼 전면을 훑는 특수 측정 job 입니다 — recipe 이름에
  "_*CDU"/"_FULL"/"_HALF"/"_MTX" 가 들어 있는 것들이고(끝이 아니라 포함입니다 —
  "_BCDU_NEW" 처럼 꼬리가 붙습니다; recipe_params.txt), 파라미터당 point 수가
  정상 recipe 와 자릿수부터 다릅니다.

  따라서 para_over_16 구간은 **대부분의 recipe 에서 비어 있는 것이 정상**입니다.
  화면이 그 빈 구간을 "값이 0" 으로 그리지 않고 아예 그리지 않는 이유가 이것입니다.

  mock 은 이 비율에 맞춰 다시 잡았습니다 (recipe_population.py 의
  _JUDGE_EXEMPT_RATIO = 0.03 + _apply_sweep_jobs). 그 전에는 recipe 의 약 75% 가
  16 초과 파라미터를 갖고 있어 실물의 25배였습니다.

순서는 parameters_list 가 정합니다 (office 확인 2026-08-10)

``parameters`` dict 의 key 순서는 **측정 순서가 아닙니다.** 같은 문서가

    parameters      = {"EDGE": 10, "LEVEL": 4, "WAFER": 10}
    parameters_list = ["WAFER", "LEVEL", "EDGE"]

로 옵니다 — 정확히 반대입니다. 화면(recipe drill)은 위에서부터 읽히므로 dict 순서를
그대로 쓰면 **가장 먼저 재는 WAFER 가 목록 맨 아래**로 갑니다.

정정 이력: 2026-08-05 기록은 "dict 의 key 순서가 곧 recipe 가 적어 둔 순서" 라고
보고 어댑터의 이름순 정렬을 걷어냈습니다. 절반만 맞았습니다 — 정렬하지 말아야
한다는 것은 맞고, 순서의 출처가 그 dict 라는 것은 틀렸습니다. 어댑터는 이제
``parameters_list`` 로 재배열합니다(`_ordered_parameters`). 목록에 없는
parameter 는 버리지 않고 뒤에 붙입니다 — 두 field 가 어긋날 때 파라미터가 화면에서
사라지는 편이 순서가 어긋나는 것보다 나쁘기 때문입니다.

raw_data — mother 의 출처 (office 확인 2026-08-10)

parameter 별 상세 row 가 담긴 object 이고, **``Mother_Para`` 가 여기 있습니다.**
확인된 형태는 row dict 의 list 입니다.

    raw_data = [
      {"Parameter": "WAFER", "Mother_Para": True,  "SEQ": 1, "Region": 1, ...},
      {"Parameter": "LEVEL", "Mother_Para": False, "SEQ": 2, "Region": 1, ...},
      ...
    ]

**``Region`` 도 여기 있고, 그것이 SEQ 그룹의 키입니다** (user-confirmed
2026-08-18). 같은 Region 인 row 들이 한 image definition 을 공유하며 화면에는
"1/8, 2/8, 3/8 …" 으로 보입니다. device-statistics 는 이 묶음으로 son 에게 mother
의 cap 을 물려줍니다 — 없으면 WAFER(13) mother 의 son 인 CELL_SP·LWR 이 이름이
OTHER 라는 이유로 _other(9)에 걸려 고칠 수 없는 위반이 됩니다
(docs/datatables/hitachi/recipe_params.txt 의 "SEQ 그룹" 절).

이것으로 오래 열려 있던 문제가 닫힙니다. 그전까지 ``Mother_Para`` 는 장비 FTP 의
``.idp`` 원본 파일에서만 읽을 수 있다고 보았고(recipe_idp.txt), device 4000개 ×
recipe 100~200개 규모에서는 그 경로를 쓸 수 없어 device-statistics 의
mother_normal 버킷을 비워 두고 있었습니다. recipe-search 의 recipe-open 이 FTP
파싱의 대안으로 쓰는 것과 같은 blob 입니다.

★ 통째로 받으면 안 됩니다. recipe 1건의 parameter 표 전체이고 device 당 recipe
  100~200 개가 곱해집니다 — 위 payload 주의가 그대로 적용됩니다. 어댑터는
  ``_source`` 를 ``raw_data.Parameter`` / ``raw_data.Mother_Para`` /
  ``raw_data.Region`` 세 경로로 좁혀 배열 구조만 유지한 채 세 컬럼만 받습니다.

★ bool 로 실려 오는지 확인이 필요합니다 (OFFICE-VERIFY). ``.idp`` 파서 쪽은 진짜
  bool 이지만(recipe_idp.txt), 적재를 거치며 문자열이 되었을 수 있습니다.
  ``bool("False")`` 가 True 라서 그냥 캐스팅하면 **모든 parameter 가 mother** 가
  됩니다. 어댑터의 `_flag` 는 알려진 표기만 받고 나머지는 "모름"으로 둡니다.

★ 주차 스냅샷 호환 — 2026-08-10 이전에 쓰인 주차 스냅샷에는 para_over_16 키가
  없습니다. 트렌드 화면은 8주 전까지 거슬러 읽으므로, 없는 키는 **0 으로** 읽어야
  합니다(그대로 더하면 합계가 통째로 NaN 이 됩니다). 프론트엔드 세 곳이 그렇게
  하고 있고 테스트가 그 경로를 잡고 있습니다.

OFFICE-VERIFY — key 의 세분도. 확인된 예시 key 가 "WAFER", "EDGE" 처럼 타입 단어
그대로였습니다. key 가 항상 이 타입 수준이면 파라미터 개별 이름이 없다는 뜻이고,
그때는 프론트엔드의 longest-prefix 타입 파생(EDGE_EX > EDGE > WAFER > LEVEL >
OTHER)이 할 일이 없어지며 **outlier 뷰와 bloated recipe 신호가 입력을 잃습니다**
(recipe_params.txt 의 mock 생성 규칙 2·3번이 그 신호를 전제로 합니다). 반대로
"EDGE_EX_R" 처럼 접두사 뒤가 더 붙는 key 가 섞여 있으면 지금 계약이 그대로
성립합니다. probe 가 실제 key 목록을 출력하므로 첫 실행에서 확정됩니다.

시각(timezone)

사무실 index 공통으로 offset 없는 KST wall-clock 입니다. 프론트가 로컬 시각으로
포맷하므로, 응답의 recipe_generated_at 에는 명시적으로 +09:00 을 붙입니다. Z 로
붙이면 12:00 KST 가 12:00 UTC 로 태깅되어 KST 브라우저에서 21:00 으로 — 9시간 늦게
표시됩니다.

OFFICE-VERIFY: modified 가 offset 없이 저장된다는 것은 meas_hist index 의 관례를
따른 **가정**입니다. 적재 쪽이 Z 접미사를 붙여 쓰고 있으면 9시간 어긋납니다.
사무실 첫 실행 때 실제 modified 값 하나를 눈으로 확인합니다.
