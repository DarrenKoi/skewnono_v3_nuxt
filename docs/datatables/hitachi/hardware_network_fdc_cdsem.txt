the doc from opensearch.
fields are like this, 

eqp_id:str,
eqp_model_cd:str
fab_name:str
eqp_ip:str
fdc_key:str -> "SPMVoltages", "LaserPower", "ContactpinConductionInfo", "TemperatureEChuck"
timestamp:str "2026-06-17T09:20:00"
values:list (starts with fdc_key) -> 
['TemperatureEChuck', '0', '1', '23.39053']
['TemperatureEChuck', '0', '2', '23.35351']
['TemperatureEChuck', '0', '3', '23.31353']
일정 시간 간격으로 1, 2, 3에서 여러 측정 값 존재 timestamp 모두 다름.
주기적으로 장비의 세 위치에 대한 온도를 측정
===
['SPMVoltages', '0', 'B', '7', '1', '1', 'spline', '-0.2', '0', '-0.4', '0.0', '-1.2',.... 100개량 이어짐]
['SPMVoltages', '0', 'A', '6', '1', '1', 'quartic', '-0.2', '0', '-0.4', '0.0', '-1.2',.... 100개량 이어짐]
'A' 'B' 'C' 구분, string (spline, quartic,..)은 판정이 아니라 피팅 모델 이름 (office 확인 2026-09-28). 그 뒤 숫자는 측정 값들 (항상 107개, office 확인 2026-09-28). 
'A', 'B', 'C'와 판정 (pline, quartic) 사이에 숫자 7, 6, 1, 1, 도 변함. 아직 무슨 의미인지는 파악 못함.
====
['LaserPower', '0', '0.78', '0.73', '341990938', '46504250']
'0'뒤에 2개의 쌍 (x, y)로 이루어짐 각각 스케일이 다른게 포인트. 아직 무슨 의미인지 파악 못함. 둘 다 의미있는 측정 value로 추정
====
['ContactpinConductionInfo', '0', 'A', '5', 'NonConduction', '-25.5', '-0.9', '24.6', '25,0', '182501']
['ContactpinConductionInfo', '0', 'B', '3', 'Conduction', '-5.0', '-5.0', '0.0', '5.0', '182671']
'A'/'B'/'C' 뒤의 정수 (위 '5', '3') 는 pin 번호 1-25 입니다 (user-confirmed 2026-09-28).
판정은 Conduction / UnstableConduction / NonConduction 세 값 (office 확인 2026-09-28). 

A, B, C들은 주기적으로 한번씩 측정되기 때문에 timestamp상 서로 근접한 상태

doc 하나는 고유의 eqp_id, timestamp, values를 가짐. 

========================================================================
어댑터 소비 규약 (hardware/fdc office adapter)
========================================================================

Index -> network_fdc_cdsem   (CD-SEM 전용)
조회   -> eqp_id.keyword term + timestamp range, timestamp 오름차순
상한   -> MAX_FDC_DOCS = 10000 (요청 1회당). 가장 바쁜 장비는 30일에 16.5k 건이라
          (office 확인 2026-09-28) 한 번에 담기지 않습니다. 요청이 상한을 채우면 창을
          반으로 나눠 다시 묻고, 1시간 창에서도 채우면 에러를 냅니다.
중복   -> 같은 _id 의 byte 동일 문서가 rollover alias 의 두 backing index 에 함께
          있습니다 (office 확인 2026-09-28). 어댑터가 (eqp_id, fdc_key, timestamp,
          values) 기준으로 중복을 제거합니다.

가져오는 field (명시 목록 — 새 적재 컬럼이 모든 doc 에 딸려오지 못하게)
  eqp_id, eqp_model_cd, fab_name, eqp_ip, fdc_key, timestamp, values

.keyword 를 쓰는 이유 (office 확인 2026-07-23)

  이 index 는 ops_index_mgmt/network_fdc_cdsem.py 가 **명시 mapping 없이** 만듭니다.
  따라서 dynamic mapping 이 모든 문자열을 text + .keyword 로 잡습니다. 정확 일치는
  eqp_id.keyword 를 써야 하고, bare field 에 terms 집계를 걸면 fielddata 에러가
  납니다.

  ★ 형제 index 인 sharpness_monitor_cdsem 을 따라하지 마십시오. 그쪽은 외부에서
  관리되며 ip 가 bare keyword 로 명시 매핑되어 있어 규칙이 정반대입니다.

timestamp

  진짜 date 타입이라 bare field 로 range·sort 가 됩니다. offset 없는 KST wall clock
  이며 라우트의 naive start/end 와 같은 기준이라 양쪽이 like-for-like 로 비교되고,
  원본 문자열이 차트까지 그대로 도달합니다. Z 접미사가 붙어 저장되면 창이 9시간
  밀립니다.

fdc_key 검증

  위에 적힌 4종(TemperatureEChuck, SPMVoltages, LaserPower,
  ContactpinConductionInfo)만 통과시킵니다. 모르는 key 가 오면 프론트 파서가 본 적
  없는 shape 이 index 에 늘어난 것이므로, 빈 차트를 그리지 않고 에러를 냅니다.

eqp_id 표기

  실제 저장된 값은 6MCDE305 형태입니다. Hardware 화면의 장비 선택기가 이 index 와
  같은 철자(= 그 장비의 sem_list row 값)를 넘기지 않으면 term 이 아무것도 잡지
  못합니다. 어댑터의 __main__ 을 돌리면 실제 mapping, 존재하는 eqp_id 값, 그리고
  어느 절이 결과를 비우는지 확인할 수 있습니다.

CD-SEM 전용: fdc 는 normalizers.CDSEM_ONLY_SERVICES 에 없으므로, HV-SEM 장비는
에러가 아니라 "매칭 0건" 이라는 정상적인 빈 결과가 됩니다.

========================================================================
실측 특성 (office 확인 2026-09-28)
========================================================================

hardware_fdc_sce_characterization.md 를 사무실 LLM 이 90일치 실데이터로 돌린 결과
입니다. mock (backend/ebeam/hardware/providers/fdc/mock.py) 도 같은 값으로 맞췄습니다.

공통
  - 문서 수: 가장 바쁜 장비가 30일에 16.5k 건 (key 4종 합계). 10000 상한을 넘습니다.
  - 중복: 같은 _id 의 byte 동일 문서가 두 backing index 에 있습니다. 제거 대상입니다.
  - values[1] 은 항상 '0' 입니다. 무시합니다.
  - key 커버리지는 모델별로 다릅니다. 빈 sub-tab 은 정상입니다.
      CG6300          : 4종 모두
      GT2000 / GT2000S: ContactpinConductionInfo 없음
      CG5000          : SPMVoltages 만
    (CG6320/CG6340/CG6360/CG6380 은 CG6300 과 같다고 가정 - OFFICE-VERIFY)

TemperatureEChuck
  - 주기: 장비별 중앙값 4-16분.
  - 한 주기의 위치 1/2/3 은 +-30초 안에 기록되며 timestamp 가 같은 적은 없습니다.
  - 위치 간 offset 은 0.02 도 미만입니다. 절대 온도를 한 축에 그립니다.
  - drift 는 일평균이 담고 있습니다. BM/PM marker 는 유지할 가치가 있습니다.
  - 장비 간 편차가 장비 내 noise 의 15배입니다. fab 단위 ranking/heatmap 이 의미가
    있습니다 (미구현 - .scratch/fdc-fleet-view/ 참고).

SPMVoltages
  - profile 길이는 항상 107 입니다.
  - 채널 A/B/C 는 같은 timestamp 를 쓰지 않습니다. 주기는 시간 창으로 묶습니다.
  - 채널을 2개만 내는 장비가 있습니다.
  - 단위 scale 이 장비마다 100배까지 다릅니다. 장비 간 원본 profile 을 비교하지 않고,
    그 장비의 중앙 profile 대비 편차를 추세로 봅니다.
  - spline / quartic 은 피팅 모델 이름입니다. 합격/불합격 판정이 아닙니다.
  - BM/PM 에서 갈리는 scalar 는 찾지 못했습니다 (step 이 noise 이하). 미결입니다.
  - values[3..5] ('7','1','1') 의 의미와 profile 모양은 아직 모릅니다 - OFFICE-VERIFY.

LaserPower
  - x1/y1 은 안정적인 신호입니다. x2/y2 의 drift 는 noise 입니다.
  - 화면은 x1/y1 의 기준선 대비 % 만 봅니다. fleet 비교도 x1/y1 만 의미가 있습니다.
  - 네 숫자가 무엇인지 설명한 문서는 없습니다. 라벨은 x1/y1 그대로 둡니다.

ContactpinConductionInfo
  - 판정 어휘: Conduction / UnstableConduction / NonConduction.
  - 판정 뒤 처음 4개 숫자의 spread (max - min) 가 등급을 가릅니다.
    Conduction 중앙값 6.4, NonConduction 중앙값 38.0, 경계 약 15-20.
  - 마지막 숫자는 채널별로 단조 증가하는 counter 입니다 (event 당 +1). 원값이 아니라
    증가율을 봅니다.
  - 등급별 비율, UnstableConduction 의 spread 대역, 콤마 소수점 ('25,0') 빈도는
    아직 모릅니다 - OFFICE-VERIFY.

========================================================================
typed side-field (write 시점 파생, office 확인 2026-09-28)
========================================================================

values 는 위치 기반 문자열 list 라 OpenSearch 가 위치별로 집계하지 못합니다. 그래서
사무실 FDC 적재 task 가 values 는 그대로 두고 아래 typed field 를 _source 에 함께
씁니다. 이 저장소의 기준 구현은 ops_index_mgmt/network_fdc_cdsem.side_fields 입니다.

  fdc_key                   field          type (dynamic)    출처
  TemperatureEChuck         temp_pos       long              values[2] (1-3)
                            temp_c         float             values[3]
  LaserPower                laser_x1       float             values[2]
                            laser_y1       float             values[3]
  SPMVoltages               spm_channel    text + .keyword   values[2]
                            spm_judgement  text + .keyword   values[6] (피팅 모델 이름)
  ContactpinConductionInfo  pin_channel    text + .keyword   values[2]
                            pin_no         long              values[3] (1-25)
                            pin_judgement  text + .keyword   values[4]
                            pin_spread     float             max - min of values[5:9]
                            pin_counter    long              values[9]

  - index 는 dynamic mapping 그대로입니다. 문자열 field 는 eqp_id 처럼 .keyword 로
    집계합니다.
  - SPM 은 숫자 field 가 없습니다. 장비마다 단위 scale 이 100배까지 달라 fab 비교를
    하지 않습니다.
  - pin_counter 는 채널별 단조 증가 counter (event 당 +1) 입니다. 원값이 아니라
    증가율을 봅니다.
  - 이전 문서에는 field 가 없습니다. backfill 이 아직 없어 fleet 화면은 배포 후
    약 30일에 걸쳐 채워집니다.
  - 중복 문서: 평균은 byte 동일 중복에 영향이 없지만, 문서 수 기반 비율은 ~1% 부풀려
    집니다. fleet 집계는 Contactpin 수를 cardinality(timestamp) 로 셉니다 (_id 가
    fab_eqp_key_timestamp 라 timestamp 하나가 곧 중복 제거된 문서 하나).
  - pin_judgement 철자: 사무실 회신이 field 목록에는 pin_judgement, 집계 예시에는
    pin_judgment 로 적었습니다 - OFFICE-VERIFY.
  - 화면용 per-tool 어댑터(fdc/office_example.build_fdc_docs)는 이 field 를 가져오지
    않고, fleet 어댑터(build_fdc_fleet, fdc/fleet.py)만 집계합니다.
