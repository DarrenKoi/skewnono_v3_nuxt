사무실(Office) Redis — fab 별 recipe 이름 목록

Recipe 검색 화면의 **검색 대상**입니다. 측정 이력(meas_hist)을 검색하는 것이 아니라,
이 목록의 recipe 이름 문자열만 검색합니다. 측정된 적 없는 recipe 도 목록에는 존재하기
때문입니다.

저장 형태: Redis **hash**, tool family 별로 하나씩.

Key -> "v3_cdsem_unique_rcp_list"  : CD-SEM
Key -> "v3_hvsem_unique_rcp_list"  : HV-SEM

hash field -> fab 이름의 **소문자** 표기. 예: "m14a", "m16b", "r3"
               (office 확인 2026-08-07 — 아래 주의 1 참고)
hash value -> 그 fab 의 recipe 이름 list

  {"m14a": ["1/AC_M2_TAT", "1/AC_M3_CD", ...], "r3": [...]}

주의

1. field 가 소문자입니다. 화면과 routes 는 대문자(M14A)를 쓰므로, 소문자 변환은
   Redis 경계(어댑터)에서만 일어나고 그 위 계층으로는 새어나가지 않습니다.
   응답은 호출자가 보낸 대문자 표기를 그대로 되돌려 줍니다.

   이 소문자 규칙은 **적재 job 쪽에서 지켜야 하는 계약**입니다. 2026-08-07 에
   실제로 field 가 대문자로 적재되어 검색이 전건 무응답이었고, DB 를 소문자로
   재생성해 해결했습니다(office 확인 2026-08-07). 증상이 에러가 아니라 **빈
   결과**인 점이 이 사고의 함정입니다 — 어댑터는 field 부재를 "그 fab 에 recipe
   가 없다"는 정상 응답으로, key 부재만 인프라 장애(502)로 구분하기 때문입니다.
   같은 증상을 다시 만나면 `HKEYS` 로 실제 적재 표기부터 확인하십시오.
2. value 의 직렬화 형식이 고정되어 있지 않습니다. 적재 job 에 따라 JSON
   (["a", "b"]) 일 수도 Python repr (['a', 'b']) 일 수도 있어 어댑터가 둘 다
   파싱합니다. 마지막 수단으로 콤마 분리도 시도합니다 — recipe 이름에는 "/" 와
   "_" 는 있어도 콤마는 없으므로 안전한 fallback 입니다.
3. recipe 이름은 "class/recipe" 형태를 포함합니다. meas_hist 의 full_name 과 같은
   체계입니다.

Recipe 위치 registry (user-confirmed 2026-07-29)
================================================

Recipe 이름 목록과 별개로, recipe 파일의 **위치**와 **보유 장비**를 fab 별 hash
2개가 직접 들고 있습니다. recipe open 이 이 둘로 .idp 경로를 조립하므로,
측정된 적 없는 recipe 도 열어볼 수 있습니다.

Key -> "v3_{cdsem|hvsem}_rcp_loc_{fab}"       : recipe 파일 위치
Key -> "v3_{cdsem|hvsem}_tools_in_rcp_{fab}"  : 그 recipe 를 보유한 장비 목록

  {fab} 은 fab 이름의 **소문자** 표기입니다(unique_rcp_list 의 hash field 와
  같은 규칙이지만, 여기서는 field 가 아니라 **key 이름**의 일부입니다).
  이 두 registry 도 2026-08-07 에 소문자로 재생성되어 있음을 확인했습니다
  (office 확인 2026-08-07). 카탈로그와 함께 바꿔야 하는 이유는 실패 방식이
  다르기 때문입니다 — 카탈로그가 대문자면 검색이 빈 결과가 되고, registry 가
  대문자면 검색은 정상인데 **자세히 보기(recipe open)만** meas_hist fallback
  으로 넘어갑니다(`_bail` 로그만 남고 응답은 200 이라, 측정 이력이 있는 recipe
  는 여전히 열리므로 화면상으로는 정상으로 보입니다).

hash field -> full_name ("class_name/recipe_name")
hash value -> rcp_loc      : [idw_name, idp_name]  (경로 문자열 2개, 순서 고정)
              tools_in_rcp : [eqp_id, ...]

주의

1. rcp_loc 의 value 는 **위치로 읽습니다**(0번 idw, 1번 idp). 항목이 2개보다
   적으면 어댑터는 이 소스를 포기하고 meas_hist 로 넘어갑니다. 3개 이상이면
   앞의 2개(idw, idp)만 쓰고 나머지는 무시합니다.
2. class_name 은 두 hash 어디에도 없습니다. full_name 의 "/" 앞부분이 곧
   class_name 이므로(meas_hist.txt), 조회에 쓴 key 에서 그대로 떼어 씁니다.
3. tools_in_rcp 는 eqp_id 를 주지만 FTP 는 eqp_ip 로 접속합니다. sem_list
   roster 로 eqp_id -> eqp_ip 를 해석하며, 두 소스의 eqp_id 표기는 동일합니다
   (user-confirmed 2026-07-29). roster 에 없는 eqp_id 는 "표기가 다르다"가
   아니라 "roster 에 그 장비가 없다"는 뜻입니다.
4. value 직렬화 형식은 unique_rcp_list 와 같은 규칙으로 파싱합니다(JSON ->
   Python repr -> 콤마 분리).

recipe 자세히 보기 / 비교

자세히 보기(recipe open)는 위 registry 2개로 .idp 경로를 조립해 장비 FTP 에서
파일을 받아 파싱합니다(docs/datatables/hitachi/recipe_idp.txt). 비교(compare)는 아직
mock 을 그대로 re-export 하고 있습니다 — 열람에서 파생되는 관계를 유지하기
위해 재구현하지 않았습니다.

연결 설정

REDIS_HOST / REDIS_PORT / REDIS_PASSWORD (back_dev_home/.env).
