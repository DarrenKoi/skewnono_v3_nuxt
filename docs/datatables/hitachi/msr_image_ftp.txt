측정 이미지 소스 — 장비 FTP 직접 조회 (OpenSearch/MinIO 아님)

MSR 측정 이미지는 데이터베이스에 적재되지 않습니다. **장비 자체의 FTP 서버**에만
있으므로, 백엔드가 장비로 FTP 세션을 열어 목록을 받고 파일을 중계합니다.

경로 구조

  root       : /HITACHI/DEVICE/HD
  이미지 폴더 : /HITACHI/DEVICE/HD/{class_name}/images/{msr}
  이미지 파일 : /HITACHI/DEVICE/HD/{class_name}/images/{msr}/{name}
  cond 사이드카: /HITACHI/DEVICE/HD/{class_name}/images/{msr}/.{name}/cond.txt

cond 는 이미지 1장당 1개인 숨김 사이드카입니다. 파일이 아니라 **점(.)으로 시작하는
폴더** 안에 cond.txt 로 들어 있습니다 — /dir/foo.jpeg 의 cond 는
/dir/.foo.jpeg/cond.txt 입니다. 이미지와 cond 를 항상 쌍으로 요청합니다.

  ⚠ 그 숨김 폴더가 **디렉터리 목록에 그대로 나옵니다** (office 확인 2026-08-10).
    이름이 .foo.jpeg 라 확장자로는 이미지와 구분되지 않습니다. 즉 목록을 확장자로만
    거르면 이미지 개수가 두 배가 되고, 그 절반은 RETR 시 550 을 돌려줍니다
    (디렉터리이므로). 목록 필터는 확장자와 **점 시작 여부를 함께** 봐야 합니다.
    최초 발견: 실측 스크립트 B 단계가 .S12_A0001-01AP.jpeg 에서 ImageNotFound.

class_name 과 msr 은 meas_hist 문서의 같은 이름 field 에서 옵니다
(docs/datatables/hitachi/meas_hist.txt).

파일 확장자

  .jpeg, .jpg, .tif, .tiff 를 모두 목록에 넣습니다.
  장비는 JPEG 프리뷰와 TIFF 원본을 함께 서빙하고, minio_pkl 의 mp_image_name 컬럼이
  **양쪽을 모두** 참조합니다(office 확인 2026-07-24: 한 MSR 에서 jpeg 26 / tif 13).
  jpeg 만 필터하면 TIFF 가 통째로 보이지 않게 됩니다 — 첫 사무실 점검에서 39장 중
  13장이 "없는 파일" 로 잡힌 원인이 이것이었습니다.

파일 이름 (HV-SEM, user-confirmed 2026-08-08)

  HV-SEM 은 targeting point 하나를 여러 장으로 찍어 공유 stem 에 -U/-T/-M/-L
  suffix 를 붙입니다 (예: S04_M0004-01MP-U.jpeg). 어떤 구성원은 .jpeg 없이
  .tif 만 존재하고, 같은 sub-position 이 JPEG 프리뷰와 TIFF 원본 **양쪽으로
  함께** 나열되기도 합니다 (-U.jpeg + -U.TIF, user-confirmed 2026-08-24 —
  pickle 의 4-image U/U/L/L row 로 확인, 대문자 .TIF 표기 관찰; 정확한 표기
  집합은 OFFICE-VERIFY). 어댑터의 확장자 필터는 이미 lower() 후 비교하므로
  대문자 표기도 통과합니다. 이 feature 의 요청 경로는 이름을 **불투명 문자열**로만
  다루므로(정확 일치 fetch, hyphen 은 validate_segment 통과) 코드 변경 없이
  동작합니다 — 어떤 이름을 요청할지는 msr_file 의 mp_image_names 목록이
  정합니다(docs/datatables/hitachi/msr_file_pickle.txt 의 어댑터 규약).

경로 표기 주의

FTP 목록(NLST)은 **전체 경로**를 돌려줍니다. 프론트로 내려보내는 계약은 basename
이고, 프론트가 그 basename 을 다시 보내면 백엔드가 전체 경로를 재조립합니다.
목록 단계에서 basename 으로 잘라야 이 왕복이 성립합니다.

전송 경로 (플랫폼별)

  사무실 로컬 PC(Windows) : 장비로의 직접 FTP egress 가 막혀 있어 방화벽이 없는
                            호스트의 HTTP proxy 를 경유합니다.
  클라우드(Phase 3, Linux) : 장비로 직접 내려받습니다.

두 클래스는 같은 인터페이스를 노출하므로 import 하는 줄만 다릅니다. 선택은 import
시점에 platform.system() 으로 이루어집니다.

보안 — SSRF 가드

백엔드는 클라이언트가 보낸 IP 로 FTP 세션을 엽니다. 따라서 eqp_ip 는 IPv4 형식
검증과 (설정된 경우) 허용 subnet 검사를 반드시 통과해야 합니다. class_name / msr /
name 세 조각도 경로에 그대로 끼워지므로 "/", "\", "..", 제어문자, 앞뒤 공백을
거부합니다. 이 세 값은 FTP 경로이자 이미지 캐시의 파일 시스템 key 이므로, 검증
실패는 두 곳 모두를 탈출시킵니다.

대량 내려받기

한 번의 fleet 호출이 파일들을 n 개 연결로 분산합니다. 연결 1개가
[img1, cond1, img2, cond2, ...] 순서로 받으므로, cond 가 도착하는 즉시 그 이미지를
방출할 수 있습니다. cond RETR 이 실패해 콜백이 오지 않는 경우는 같은 연결의 다음
이미지가 도착하는 것으로 cond 단계 종료를 판정합니다.

검증 방법

msr_image 어댑터를 직접 실행하면(python -m ...providers.office) minio_pkl 의
df_result_data 에 적힌 mp_image_name 집합과 장비 FTP 가 실제로 서빙하는 목록을
대조합니다. pickle 이름은 확장자가 없을 수 있고 대소문자가 다를 수 있으므로 stem
매칭까지 시도합니다. 장비에만 있고 pickle 에 없는 파일(extra)은 보통 정상입니다.

실측 타이밍 (office 확인 2026-08-10, scripts.probes.measure_msr_image_ftp)

  connect + login  : 94 ms   (중앙값)
  cold fetch 1장   : 133 ms  (login 94 + 이미지·cond 전송 39)
  download_all 1장 : 0.20 s  (동시성 6)
  동시성 6 vs 1    : 2.0배

  성격이 예상과 반대입니다. 이미지는 작고 링크는 빨라서 **비용의 71%가 전송이 아니라
  login** 입니다. "장비가 multi-MB TIFF 를 서빙하니 1장에 수 초" 라는 가정으로
  잡았던 _SECONDS_PER_IMAGE = 5.0 은 12배 과대했고, 실측 후 0.4 로 내렸습니다.

  따라서 이 경로의 최적화 레버는 전송 속도가 아니라 **세션 재사용**입니다. 지금은
  이미지 1장마다 새 세션을 열어 매번 94 ms 를 냅니다.

  TIFF 가 섞인 MSR 은 아직 이 측정에 포함되지 않았습니다 — 위 숫자는 측정에 쓰인
  MSR 의 파일 구성에 대한 값입니다. OFFICE-VERIFY: TIFF 비중이 높은 MSR 에서 전송
  비중이 얼마나 오르는지.

  MinIO 캐시 PUT (office 확인 2026-08-10)

    이미지 1장 캐시 쓰기 : 16 ms
    같은 실행의 fetch    : 78 ms   (연결당 21% 추가)

    캐시 쓰기는 FTP 워커 스레드 안에서 일어나 그 연결의 다음 RETR 을 막습니다.
    실측상 그 비용이 fetch 의 21% 라 파이프라이닝은 하지 않기로 했습니다. 같은
    노력을 커넥션 풀링(login 이 cold fetch 의 71%)에 쓰는 편이 4배 낫습니다.

    측정은 <prefix>_measure/ 아래에만 쓰고 반환 전에 지웁니다. 실제 image_cache/
    에 쓰지 않는 이유는 정리 단계가 purge(0) 으로 접두어 전체를 쓸기 때문입니다 —
    실제 접두어였다면 그 한 줄이 사용자들의 캐시를 통째로 지웠을 것입니다.
