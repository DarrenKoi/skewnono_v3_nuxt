chat RAG — 근거 검색 인덱스와 figure 저장소 (OpenSearch + MinIO)

출처: 사내 RAG 인덱스입니다. 문서(매뉴얼·회의록·메일·리포트)를 chunk 단위로
색인하고 k-NN 으로 검색하며, chunk 가 그림에서 추출된 경우 해당 그림의 webp
파일이 MinIO 에 따로 보관됩니다. 검색 결과의 애플리케이션 측 계약은
back_dev_home/chat/knowledge/contracts.py 의 Evidence 이고, office 어댑터가
raw hit 을 이 모양으로 정규화합니다.

(설계 user-confirmed 2026-08-04. k-NN 질의 자체는 사내에서 동작 확인됨을
user-confirmed 로 받았습니다. Embedding/rerank 모델 계열(BGE-M3,
bge-reranker-v2-m3)과 검색 방식(2-leg hybrid)은 user-confirmed 로 닫혔습니다
— 아래 "검색 방식" 절 참고. 인덱스 이름, host, figure bucket 이름은 아직
OFFICE-VERIFY 이며 이 문서에 적지 않습니다 — credential 과 사내 식별자는
저장소에 commit 하지 않습니다.)

무엇이 Evidence 한 행이 되는가
- 검색 결과 chunk 1건이 Evidence 1행입니다. 한 검색당 최대 5행이며 상한은
  애플리케이션이 정합니다(모델이나 어댑터가 늘릴 수 없습니다).
- source_type 은 manual / meeting / email / report 중 하나이며, 호출된 검색
  함수가 찍습니다. hit 안의 값을 신뢰하지 않습니다.
- 접근 권한 필터(AccessScope: user_id/groups/fabs)는 질의 단계에 들어갑니다.
  검색 후 Python 필터링으로 보완하는 것은 계약 위반입니다.

필드
| 필드 | 규칙 |
| --- | --- |
| source_id | 재색인 후에도 유지되는 stable ID. revision 이 바뀔 때만 변합니다. |
| source_type | manual / meeting / email / report |
| title | 노출 승인된 제목만 |
| snippet | 승인된 최소 근거 text. 원문 전체가 아닙니다. |
| revision | manual/report revision, 없으면 None |
| occurred_at | 정규화된 ISO-8601 기준일, 없으면 None |
| section | section provenance, 없으면 None |
| page | 1-based page 번호, 없으면 None |
| region | 승인된 page region reference, 없으면 None |
| locator | 안정된 논리 참조 `manual:<doc_id>#page=<page>`. URL 이나 filesystem/MinIO 경로가 아닙니다. |
| figure_id | 그림 chunk 의 불투명(opaque) 토큰. text/table chunk 는 None. |
| score | ranking 진단값, 없으면 None |

사무실 manual 검색이 실제로 돌려주는 필드 (office 확인 2026-08-27)
- 사내 RAG 의 `src/retrieve/serve.py:search_manuals()` 는 hit 마다 정확히
  다음 8개를 돌려줍니다: `source_id`, `title`, `snippet`, `section`, `page`,
  `figure_id`, `score`, `element_type`.
  - `figure_id` 는 text/table chunk 에서 null, figure chunk 에서만 값이
    있습니다.
  - 파일시스템의 `image_path` 는 절대 돌려주지 않습니다 — seam 을 넘는 것은
    `figure_id` 뿐입니다.
- 따라서 Evidence 의 `revision`, `occurred_at`, `region`, `locator` 는
  manual 에서 모두 None 입니다. 어댑터 `_to_evidence()` 는 optional 키를
  `.get` 으로 읽으므로 키가 아예 없어도 None 으로 매핑되고, office.py 가
  채워 넣을 필요가 없습니다. (매뉴얼은 개정되지 않으므로 revision 이 없는
  것은 예상과 일치합니다 — user-confirmed 2026-08-06.)
  - OFFICE-VERIFY: office.py 가 `source_id`/`page` 로 `locator`
    (`manual:<doc_id>#page=<page>`) 를 파생할지는 미정입니다. 확정 전까지
    mock 의 manual fixture 는 raw hit 과 같이 None 을 냅니다.
- `element_type` 은 raw hit 에는 실려 오지만 Evidence 로 내보내지 않고
  어댑터에서 버립니다 — 아래 "`element_type`" 절 참고.

figure_id — 저장소 키가 아니라 토큰입니다
- figure_id 는 그림을 식별하는 불투명 문자열입니다. bucket, prefix, 경로
  구분자, .webp 확장자를 **포함하지 않습니다**. 인덱스는 맨 id 만 내보냅니다.
- 형식은 `{doc_id}_p{page}_i{idx}` 입니다(office 확인 2026-08-19).
  실제 예: `CG6300_1.HHTSEM_SYSTEM_p100_i0`
  - doc_id 에 **점(.) 이 들어갑니다**. `CG6300_1.HHTSEM_SYSTEM` 처럼 장비
    모델과 문서 이름이 점으로 이어집니다.
  - page 는 1-based page 번호이고, idx 는 그 page 안에서 추출된 그림의
    0-based 순번입니다. 한 page 에 그림이 여러 개면 i0, i1 … 로 늘어납니다.
- 키 조립은 전적으로 서버가 합니다(back_dev_home/chat/figures.py):
  `{client prefix}/hitachi_sem/manual_figures/{figure_id}.webp`.
- 서버는 저장소에 닿기 전에 `^[A-Za-z0-9._-]{1,128}$` 로 id 를 검증하고,
  추가로 `..` 를 포함한 id 를 거부합니다.
  따라서 경로가 섞인 id 를 내보내는 hit 은 오류가 아니라 그냥 렌더되지 않는
  그림이 됩니다. 색인 쪽에서 형식을 지키는 것이 유일한 방어선입니다.
  - 점을 허용하는 charset 은 2026-08-19 에 넓혔습니다. 그전 규칙
    `^[A-Za-z0-9_-]{1,128}$` 은 위 실제 예를 **거부**합니다. mock fixture 의
    id 에는 점이 없었으므로 집에서는 전부 통과하고 사무실에서만 모든 그림이
    404 나는 형태였습니다 — 조용히 렌더만 안 되므로 오류로 드러나지 않습니다.
  - 점을 허용하면 `..` 가 charset 만으로는 걸러지지 않으므로 이름으로 따로
    거부합니다. 앞머리 점(`.`, `.foo`)도 거부합니다 — 맨 `.` 하나가 charset
    을 통과해 MinIO 경로에서는 `.../..webp` 키로 저장소까지 갔습니다
    (2026-08-27, 디스크 경로는 containment 검사로만 살아남던 것). slash 는
    charset 과 Flask routing 양쪽에서 막히고, 디스크 경로는 조립된 경로가
    figures 디렉터리 안인지 다시 확인합니다.
- 이 규칙이 locator 와 다른 이유: locator 는 사람이 읽는 참조라 절대
  저장소 경로가 되면 안 되고, figure_id 는 반대로 애플리케이션이 저장소
  접근으로 바꾸는 유일한 값이라 형식을 좁게 고정해야 합니다.

figure 제공 (디스크 2026-08-19, MinIO 2026-08-27 구현 완료)
- `GET /api/chat/figures/<figure_id>` 는 **구현되어 있습니다**. route 는
  back_dev_home/chat/routes.py 의 chat_figure, 저장소 접근은
  back_dev_home/chat/figures.py 의 read_figure() 한 곳입니다. 응답 형태는
  back_dev_home/msr_image/routes.py 의 serve_image_route 를 따릅니다 —
  Response(bytes, mimetype="image/webp") + Cache-Control.
- 저장소는 **knowledge provider 를 따라갑니다**. 별도 selector 가 없습니다:
  figure_id 는 그것을 만든 인덱스에 대해서만 의미가 있고(사내 ingestion 이
  인덱스와 그림 객체를 같이 씁니다), "사무실 인덱스 + 디스크 그림" 은 누구도
  원할 수 없는 조합이기 때문입니다.
  | SKEWNONO_CHAT_KNOWLEDGE_PROVIDER | 저장소 | 객체 |
  | --- | --- | --- |
  | mock (집) | 디스크 | `{SKEWNONO_CHAT_FIGURES_DIR}/{figure_id}.webp` |
  | office | MinIO | `{client prefix}/{SKEWNONO_CHAT_FIGURE_PREFIX}{figure_id}.webp` |
- 디스크(mock): SKEWNONO_CHAT_FIGURES_DIR 이 그림 디렉터리의 절대 경로입니다.
  설정하지 않으면 그 배포에는 그림 저장소가 없다는 뜻이고 404 를 돌려줍니다.
  오류가 아닙니다 — 그림 추출 없이 색인한 매뉴얼은 정상 상태이고, SPA 는
  썸네일 없이 인용만 렌더합니다.
- MinIO(office) 실제 배치 (office 확인 2026-08-27):
    user/2067928/hitachi_sem/manual_figures/CG6300_1.HHTSEM_SYSTEM_p100_i0.webp
    ^bucket ^client prefix ^SKEWNONO_CHAT_FIGURE_PREFIX (기본값)  ^figure_id
  - 사용자 namespace `2067928/` 는 MinIO client 의 **자체 기본 prefix**
    (minio_handler 의 PREFIX / MINIO_PREFIX)이고, 앱은 그 아래 키만 넘깁니다:
    `MinioObject().get("hitachi_sem/manual_figures/<id>.webp")`.
  - msr_image 의 image cache 와 **반대 규약**입니다. 그쪽은 client prefix 를
    비우고(use_prefix(None)) `2067928/image_cache/` 를 자기 prefix 에 적습니다.
    둘 다 동작하며, 섞는 것이 함정입니다 — SKEWNONO_CHAT_FIGURE_PREFIX 에
    `2067928/` 를 적으면 `2067928/2067928/...` 으로 겹쳐 모든 그림이 404
    납니다. (이전 문서의 `user/2067928/figures/` 예시는 이 이유로 폐기.)
  - SKEWNONO_CHAT_FIGURE_BUCKET 은 보통 비웁니다 — client 기본 bucket 이
    `user` 이고 그림이 거기 있습니다. SKEWNONO_CHAT_FIGURE_PREFIX 기본값은
    `hitachi_sem/manual_figures/` 이며 앞 slash 제거·뒤 slash 하나로
    정규화합니다. `hitachi_sem/` 은 tool family 축이라 다른 family 의 그림은
    다른 prefix 로 가지 다른 bucket 으로 가지 않습니다.
  - MinIO 오류 중 NoSuchKey/NoSuchObject/NotFound 는 그냥 miss(404)이고,
    그 밖의 오류(예: scoped credential 의 AccessDenied)도 404 이지만 warning
    로그를 남깁니다 — 남기지 않으면 bucket 설정 오류가 "그림을 추출하지 않은
    매뉴얼" 과 구분되지 않습니다.
- 응답: 200 은 image/webp 바이트와 `Cache-Control: public, max-age=3600`
  입니다. 추출된 그림은 불변이고 답변 하나가 여러 장을 인용하므로, 캐시가
  없으면 대화를 되짚어 볼 때마다 전부 다시 받습니다.
- 실패는 전부 404 입니다: 형식에 맞지 않는 id, 저장되지 않은 그림,
  저장소 미설정이 모두 같은 응답입니다. 어떤 경우인지 구분해서 알려주지
  않는 것은 의도된 것입니다 — 구분하면 figure_id 존재 여부를 확인하는
  수단이 됩니다.
- 인가는 "인증된 사용자면 통과"입니다(user-confirmed 2026-08-04). /api/* 는
  이미 신원 gate 뒤에 있으므로 추가 확인을 하지 않습니다.
  남는 위험: 검색은 AccessScope 로 걸러지지만 이 endpoint 는 걸러지지
  않으므로, group/fab 제한 매뉴얼의 **그림**은 figure_id 를 아는 사람이면
  그룹 밖에서도 받을 수 있습니다. 그림 자체가 접근 제한 정보를 담는 것이
  확인되면 이 결정을 다시 봐야 합니다.

한국어와 영어를 항상 함께 (user-confirmed 2026-08-04)
- 사용자는 한 질문 안에서 두 언어를 섞습니다("얼라인 alarm 리셋"). 코퍼스도
  섞여 있습니다. 따라서 한 번의 요청이 두 언어를 동시에 만족시켜야 합니다.
- 한 언어만 만족시키는 요청은 오류를 내지 않고 recall 만 조용히 반토막
  냅니다 — 빈 결과와 진짜 miss 를 구분할 수 없습니다.
- k-NN leg 는 BGE-M3 dense 를 사용합니다(user-confirmed 2026-08-06). BGE-M3 는
  multilingual 이므로 한/영 동시 요건이 이 leg 에서 충족됩니다. multilingual
  여부는 더 이상 OFFICE-VERIFY 가 아닙니다.
- lexical/BM25 leg 는 Nori analyzer 를 확보했습니다(user-confirmed
  2026-08-06). OpenSearch 기본 standard analyzer 는 한글을 한 글자씩 쪼개
  쓸모 있는 매칭이 나오지 않으므로, 한국어 text 필드에는 Nori 를 명시적으로
  지정합니다.
- 질의를 언어 판별해서 한쪽으로 분기하거나 번역해서 보내지 않습니다. 섞인
  질문을 더 나쁜 단일 언어 질문으로 바꾸는 일입니다.

검색 방식 — 2-leg hybrid + 크로스인코더 rerank (user-confirmed 2026-08-06/07)
- 검색은 Nori BM25 ⊕ BGE-M3 dense 의 2-leg hybrid 입니다. BGE-M3 의 sparse
  representation 은 쓰지 않습니다 — dense 하나로 이미 multilingual 요건을
  만족하므로 sparse leg 를 더해 얻는 이득보다 왕복 비용이 큽니다.
- Hybrid 결과 중 후보 20~30건(`SKEWNONO_CHAT_KNOWLEDGE_CANDIDATES`, 기본
  24, 5~50 으로 clamp)을 뽑아 `bge-reranker-v2-m3` 크로스인코더로 재점수화한
  뒤, 점수순 정렬 후 상한 5행으로 절단합니다. 정렬과 절단은 애플리케이션
  (tracked 계약 절반)이 소유하며 모델이나 어댑터가 늘릴 수 없습니다.
- 크로스인코더는 후보 수에 선형으로 비쌉니다. 20~30 으로 시작해 사무실에서
  실측하며, 50 은 체감될 수 있습니다.

모델 호출 위치 — C2 (user-confirmed 2026-08-07)
- BGE-M3 embedding 과 `bge-reranker-v2-m3` rerank 는 사내 API 로 제공됩니다.
  `office.py` 가 이 API 를 **직접** 호출합니다(C2). OpenSearch 의 ML Commons
  remote connector 로 클러스터가 직접 호출하게 하는 경로(C1)는 보류입니다 —
  `plugins.ml_commons.trusted_connector_endpoints_regex` 에 사내 host 가
  등록되어 있지 않습니다(office 확인 2026-08-07).
- C2 는 tool 호출 1회당 Flask 왕복 3회(embedding → OpenSearch → rerank)입니다.
  C1 으로 전환하면 왕복이 1회로 줄지만, 클러스터 cluster-wide 설정 변경 권한과
  운영 협의가 선행되어야 합니다. 전환 시 바뀌는 범위는 gitignored `office.py`
  의 `_execute()` 와 `_rerank()` 뿐이며, 추적되는 계약(`chat_rag_contract.txt`
  의 필드, `Evidence` 12필드)은 바뀌지 않습니다.

RAG 공개 API 와 호출 방식 (office 확인 2026-08-27, handoff:
docs/datatables/chat/chat_office_adapter_handoff.txt)
- RAG 는 별도 git 저장소이며 `back_dev_home/chat/_rag/` 에 checkout 해 두고
  같은 프로세스에서 import 합니다(`chat/rag.py`). 서비스 경계가 없습니다.
- 공개 함수 셋:
  - `src.retrieve.serve.search_manuals(query, scope, limit=, index_dir=)`
    → hit list(위 8개 필드). hybrid + bge-reranker-v2-m3 rerank 까지 끝난
    결과이므로 어댑터 `_rerank()` 는 hit 의 `score` 를 그대로 돌려주는
    항등 함수입니다(C1 과 같은 모양). `limit` 은 후보 수(기본 24)입니다.
  - `src.retrieve.agent.rewrite_query(question) -> str` — agent loop 전 1회.
    LLM 이 약어를 풀고 한/영 용어를 짝지어 검색용 질의를 만듭니다.
  - `src.retrieve.agent.generate_follow_ups(question, answer, sources)
    -> list[str]` — 답변 후 1회, 다음 질문 3~5개.
- 인덱스 위치는 `index_dir` 인자로 넘깁니다. RAG 의 기본값은 상대 경로
  `"index"` 이므로 chat 은 항상 절대 경로(`SKEWNONO_RAG_INDEX_DIR`, 미설정이면
  `{checkout}/index`)를 넘깁니다.
- OFFICE-VERIFY: `search_manuals` 의 `scope` 인자가 질의 단계 필터로 실제
  쓰이는지(매뉴얼은 현재 권한 제한이 없어 무시해도 결과는 같음), 그리고 RAG 가
  timeout/권한 오류를 `TimeoutError`/`PermissionError` 로 올리는지. 현재
  `_translate_error()` 는 그 둘만 구분하고 나머지는 전부 `KnowledgeUnavailable`
  입니다.
- 집(mock)과의 차이: mock 의 `rewrite_query` 는 고정 약어·번역 표, `generate_follow_ups`
  는 인용 제목에서 만든 질문 3개입니다. 모양만 같고 내용은 표 lookup 입니다.

`element_type` — raw hit 에는 실려 오지만 Evidence 로 내보내지 않음
- 인덱스는 chunk 마다 `element_type` 을 갖고, 사무실 `search_manuals()` 는
  이를 hit 에 실어 돌려줍니다(office 확인 2026-08-27). 그러나 검색 엔진
  내부 값이며 애플리케이션 `Evidence` 계약에는 없는 필드입니다. 어댑터
  `_to_evidence()` 가 seam 에서 버리며, 프론트로 끌어올리면 안 됩니다.
  그림 여부는 `element_type` 이 아니라 `figure_id` 의 null 여부로 읽습니다.
- 현재 어휘는 `paragraph`, `procedure`, `warning`, `caution`, `alarm`,
  `parameter`, `table`, `parts_list`, `troubleshooting`, `figure_caption`,
  `figure_description` 11종입니다. 라벨링이 망설여지는 원인은 어휘 자체가
  아니라 하나의 열거형에 축이 네 개(형태·기능·안전 등급·도메인 개체) 눌려
  있는 것입니다 — 경고가 포함된 절차 단계, 파라미터 표, 알람 대처 표처럼
  동시에 참인 chunk 에서 거짓 선택을 강요합니다.
- 축을 분리한 `block_type`(형태) / `intent`(기능, 다중 가능) /
  `safety_level`(원문 머리말 그대로, OFFICE-VERIFY) / `is_generated`(bool,
  우선순위 최상) / `alarm_codes`(추출 필드, 라벨이 아님) 로의 재구성을
  권고합니다. 강제는 아닙니다 — 자세한 근거는
  `docs/superpowers/specs/2026-08-07-chat-rag-manuals-design.md` 5.1절을
  참고합니다.
- `is_generated` 를 최우선으로 두는 이유는 나머지와 성격이 다르기 때문입니다.
  틀려도 검색 품질만 나빠지는 다른 축과 달리, 이것은 기계가 생성한 문장을
  사람이 쓴 근거로 인용하는 문제이며 나중에 소급 판별할 수 없습니다.
- `alarm_codes` 는 확정된 ALID 집합을 담습니다 — `9006`(align),
  `9007`·`9035`(meas), Hitachi 한정입니다.
- `safety_level` 은 OFFICE-VERIFY 입니다. 매뉴얼이 ANSI Z535.6 계열 머리말
  (DANGER / WARNING / CAUTION / NOTICE)을 쓰는지 미확인입니다.

범위 — 매뉴얼 1종 우선
- 이번 연결은 매뉴얼(manual) 1종만 대상입니다. 매뉴얼은 개정되지 않습니다
  (user-confirmed 2026-08-06) — revision 우선순위, superseded 문서 제외는
  매뉴얼 범위에서는 해당 없습니다.
- 회의록·메일·리포트는 뒤로 미룹니다. 메일·회의록은 수신자/참석자 단위
  권한이라 authoritative access resolver 가 선행되어야 하며, 현재
  `AccessScope` 는 `groups`/`fabs` 가 빈 list 입니다.

집(mock)과의 차이 — back_dev_home/chat/knowledge/providers/mock.py
- mock 은 __fixtures__/knowledge/*.json 에 대한 토큰 집합 교집합 검색입니다.
  embedding 유사도가 아니므로 semantic 매칭이 없고, score 는 사무실의 float
  거리와 달리 작은 정수입니다.
- fixture 는 한국어와 영어를 일부러 섞어 둡니다. 영어 전용 mock 이면 사무실
  인덱스가 답하는 한국어 질문에 집에서는 빈 결과가 나오고, 모든 집 세션이
  실제와 다른 검색 경로를 상대로 개발하게 됩니다.
- manual fixture 의 revision/occurred_at/region/locator 는 사무실 raw hit 과
  같이 전부 None 입니다(위 "사무실 manual 검색이 실제로 돌려주는 필드" 절).
  meeting/email/report fixture 는 아직 사무실 형태를 모르므로 그대로입니다.
- figure_id 는 manual fixture 3건에만 채워져 있고 나머지는 None 입니다.
  뒤에 실제 MinIO 객체나 .webp 파일은 없습니다 — 값은 여전히 불투명
  토큰입니다.
  다만 **형식은 사무실 것을 그대로 따릅니다**: `{doc_id}_p{page}_i{idx}`,
  doc_id 는 점을 포함한 합성값(예: `SYN6300_1.EBEAM_ALARM_p12_i0`)이고
  `_p{page}` 는 그 record 의 page 필드와 일치시킵니다.
  점 없는 예전 id(`fig-alarm-r2-p12`)를 2026-08-19 에 바꾼 이유는, 그 형태가
  "serving charset 에서 점을 빼도 된다"를 가르쳤고 실제로 그렇게 좁혔다가
  집에서는 전부 통과하고 사무실에서만 모든 그림이 404 나는 상태를 만들기
  때문입니다. 형식만 진짜이고 내용은 합성입니다.
