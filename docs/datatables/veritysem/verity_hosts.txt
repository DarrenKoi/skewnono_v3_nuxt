사무실(Office) Redis — VeritySEM 장비 host 명부 + tool version (user-confirmed 2026-10-23)

Provision 의 v3_df_provision_hosts 와 같은 계열의 key 입니다(../provision/provision_hosts.txt).
차이는 하나입니다. VeritySEM 은 **tool IP 가 곧 data IP** 이므로 data_ip 컬럼이 따로
없고, eqp_ip 하나로 장비와 데이터에 모두 접속합니다. 그래서 이 계열에는 Provision 처럼
"data IP 가 확인되었는가" 를 나타내는 ip_note 도 없습니다.

저장 형태: Redis, pandas DataFrame 을 parquet 직렬화(sem_list 와 같은 방식).

Key 1 -> "v3_df_verity_hosts"   : host 명부 (아래 대부분이 이 key 의 설명)
Key 2 -> "v3_df_verity_version" : 장비(tool) version 과 tool 쪽 접속 여부 (맨 아래 절)

용도: **읽기 전용** 입니다. 갱신 주기 (user-confirmed 2026-10-23):

    Key 1 v3_df_verity_hosts   : 매시 23분
    Key 2 v3_df_verity_version : 매일 09:10

규모 (office 확인 2026-10-23): 54 대. v3_df_sem_list 의 VERITY* 54 대와 **정확히 일치**하며
eqp_id 는 Key 1 안에서 유일합니다. 행 수는 장비 반입에 따라 바뀌므로 고정값으로 가정하지
않습니다. 같은 실행 기준 분포:

    available : On 51 / Off 3  (Key 1 과 Key 2 의 available 개수가 같습니다)
    veridity  : On 44 / Off 1 / "-" 9   (Off 1 대 = Veridity 가 있으나 그 실행에서 접속 불가)
    Off 3 대 중 2 대는 Veridity 가 없는("-") 장비입니다.

컬럼 정보 (8개, 문자열)

| 컬럼 | 뜻 |
| --- | --- |
| eqp_id | v3_df_sem_list 의 eqp_id |
| eqp_model_cd | v3_df_sem_list 의 eqp_model_cd |
| fab_name | v3_df_sem_list 의 fab_name |
| eqp_ip | 장비 IP 이자 data IP (Provision 과 달리 둘이 같습니다) |
| output_path | 측정 결과 위치. 항상 "/D_Drive/Output" |
| veridity_path | Veridity 리포트 위치. 45 대는 "/C_Drive/Veridity/Reports", 9 대는 "" |
| available | "On" / "Off" — output_path 목록 조회 성공 여부 |
| veridity | "On" / "Off" — Veridity/Reports 목록 조회 성공 여부. veridity_path 가 "" 인 장비는 설계상 "-" 입니다 |
| checked_at | 마지막 점검 실행의 UTC ISO timestamp. 화면에는 KST 로 표시합니다 |

경로: 장비 화면에서 D:\Output 으로 보이는 결과 폴더가 FTP 에서는 /D_Drive/Output 입니다.
경로는 행의 값을 그대로 씁니다 — 지금은 모든 행이 같지만 상수로 박아 두지 않습니다.

available 과 veridity 는 서로 다른 폴더를 잽니다. 측정 결과를 꺼낼 수 있는지는
available 이 말하고, veridity 는 별개의 리포트 폴더입니다. veridity 는 세 값입니다 —
"On", "Off"(Veridity 가 있으나 접속 실패), "-"(Veridity 가 없는 장비, 장애 아님).
SKEWNONO 백엔드는 "-" 를 "" 로 바꿔 상태 표시 없이 — 로 보여 줍니다. "Off" 로 바꾸지
않습니다 — 그러면 Veridity 가 없는 9 대가 장애로 보입니다.

OFFICE-VERIFY

- Veridity 리포트의 내용·형식과 SKEWNONO 에서의 쓰임.

Key 2 -> "v3_df_verity_version" (user-confirmed 2026-10-23)

| 컬럼 | 뜻 |
| --- | --- |
| eqp_ip | 장비 IP. **eqp_id 컬럼은 없습니다** — v3_df_sem_list 의 eqp_id -> eqp_ip 를 다리로 eqp_ip 로 join 합니다(Provision 의 version key 와 같은 방식). eqp_ip 는 유일합니다 (user-confirmed 2026-10-23) |
| version | 장비의 /D_drive/Qrelease/current_version.ini 원문. 형식 Ver_<maj>_<min>_<pat>_<build>_Win7, "" = probe 실패 |
| available | "On" = 그 ini 다운로드 성공 (tool 쪽 접속 여부) |

두 key 의 available 은 이름이 같지만 다른 것을 잽니다(Key 1 = /D_Drive/Output 목록, Key 2 =
version ini). SKEWNONO 백엔드는 읽자마자 data_available / tool_available 로 이름을 바꿉니다.

SKEWNONO 소비처 (sem_list, 2026-10-23 구현, 사무실 검증 대기)

VeritySEM 은 v3_df_sem_avail 이 아니라 이 두 key 로 판정합니다 (user-confirmed 2026-10-23).
Provision 과 같은 구조이며 규칙만 다릅니다 — VeritySEM 에는 ip_note 가 없으므로:

1. GET /api/sem-list (장비 리스트) — v3_df_sem_list 의 VERITY* 행 중 Key 1 에 있는 행.
   available 은 Key 1 의 available(Output 목록) 입니다. Off 여도 장비 리스트에 남습니다.
2. GET /api/sem-list/pending (미연결 장비) — Key 1 에 없는 VERITY* 행. 지금은 54 대가 모두
   Key 1 에 있으므로 보통 비어 있습니다. 비어 있지 않다면 신규 반입 장비이거나 Key 1 이
   Redis 에 없는 경우(이때는 boot/app 로그에 경고가 남습니다)입니다.

장비 리스트는 Data / Tool / Veridity 상태와 version 을, 미연결 화면은 같은 값을(없으면 —)
보여 주며 checked_at 은 KST 로 표시합니다. 구현은 backend/sem_list/MIGRATION.md 의
PROVISION / VeritySEM 절을 참고합니다.

FTP 접속 (tool_files, 2026-10-23 구현)

계정은 rtauser 입니다 (user-confirmed 2026-10-23, 비밀번호는 사무실 .env 에만 둡니다).
파일 이름은 latin-1 로 읽습니다 — byte 그대로 통과시키며 UTF-8 로 decode 하지 않습니다
(user-confirmed 2026-10-23). SKEWNONO_TOOL_FTP_ENCODING=latin-1 하나로 Hitachi 와 같이 덮입니다.
로그인 폴더는 OFFICE-VERIFY 입니다.

디스크 여유 공간 (storage, office 확인 2026-10-26)

장비 FTP 서버는 디스크 여유 공간을 알려 주지 않습니다. scripts/probes/ftp_space_probe.py 로
AVBL / SITE DF / SITE DISKFREE 를 경로 없이, 그리고 /D_Drive · /C_Drive 에 붙여 보냈고 모두
응답이 없었습니다. 따라서 CD-SEM·HV-SEM 처럼 FTP 만으로 storage 를 수집할 수 없으며, 장비 쪽
예약 작업(wmic 결과를 파일로 남기기)이 필요합니다. VeritySEM storage 는 보류 상태입니다
(user-confirmed 2026-10-26). 출력 원문(FTP 서버 종류, SYST/FEAT 응답)은 받지 않았습니다.
