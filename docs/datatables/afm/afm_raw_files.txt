AFM 장비 raw 파일 — ETL 이전 원본 (Redis/MinIO 적재 형태 아님)

이 문서는 각 AFM 장비에서 추출한 **raw 파일**의 구조입니다. 사무실 agent 가
skewnono-pjt-shared/AFM/ 의 raw 데이터를 보고 확인한 내용이며(office 확인
2026-10-02, 회신 3회), 회신 원문은 docs/afm/office-data-findings.md 에 그대로 있습니다.

웹이 실제로 읽을 것은 이 raw 파일이 아니라 ETL 이후의 적재물입니다 — Redis 색인
(측정 목록 + MinIO 경로)과 MinIO 객체(상세·Profile·이미지). 그 형태는 ETL 이
끝난 뒤 다시 회신받기로 했으므로 **아직 미정**입니다. key 이름·형식·dtype 이
정해지면 이 폴더에 적재 형태 문서를 따로 추가합니다. 질문서는
docs/afm/to-questionnaire-afm.md 입니다.

표기: [확인] = office 확인 2026-10-02, [가정] = OFFICE-VERIFY.
      [정정] = 앞선 회신의 내용을 뒤의 회신이 바꾼 곳.


가장 중요한 규칙 — 파일의 유무는 recipe 설정이 정합니다 [확인]

  data CSV·profile txt·이미지 가운데 무엇이 있는지는 전부 **recipe 설정**에
  달려 있습니다. point 수(1~36 실측)와 Site ID 컬럼의 유무도 recipe 가 정합니다. 파일이 없는 것은 오류가 아니라 **정상 상태**이므로, 웹은 부재를
  빈 화면으로 보여 주어야 하고 오류로 다루면 안 됩니다.

  같은 원리가 파일 안에도 적용됩니다. 아래가 모두 실측되었습니다 [확인]:
    - Summary 가 아예 없는 파일
    - method 명 줄만 있고 표가 없는 빈 Summary
    - 표가 없는 빈 Data
    - 빈 값인 Last Pick Up Time / Last Put Back Time


D1 장비 목록

  장비 ID   fab    근거
  MAP608    PKG    [가정] docs/afm/tool_info.txt 뿐입니다. 회신은 이 장비의 fab 을 말하지 않았습니다.
  MAPC01    R3     [확인] 코드로 확인
  5EAP1501  M15    [확인] 코드로 확인

  ⚠ raw 데이터 어디에도 fab 필드가 없습니다 [확인]. fab 은 장비 ID 에서 대응표로
    붙여야 하고, 그 대응표가 어디에 실릴지는 미정입니다.
  ⚠ 이전 mock 의 대응(R3→MAP608, M12→MAPC01, M15→5MAPT01)은 틀렸습니다.
    5MAPT01 이라는 장비는 없습니다.


D2 측정 식별자 — 파일명

  파일명은 `#` 으로 필드를 구분하고, 장비마다 **필드 순서가 다릅니다** [확인].
  값이 없는 자리는 NA 입니다.

  MAP608   : #YYMMDD#hhmmss#RECIPE#SAMPLE_ID#LOT_ID#hhmmss#.csv
  MAPC01   : #YYMMDD#hhmmss#RECIPE#SLOT#NA#NA#SAMPLE_ID_Info.csv
  5EAP1501 : #YYMMDD#HHMMSS#RECIPE#SAMPLE_ID#LOT_ID#NA#...csv

  - MAP608 은 시각이 두 번 나오고, **마지막 시각이 측정 시작 시각**입니다 [확인].
    **오래된 데이터는 그 자리가 NA** 인 경우가 있습니다 [확인] — 측정 시작 시각을
    이 필드에서만 얻으면 오래된 측정은 시각이 없습니다.
    첫 번째 시각이 무엇인지(저장 시각인지 종료 시각인지)는 회신에 없습니다 [가정].
  - **recipe 명에 공백·괄호·소문자가 들어갈 수 있고, 세 장비 공통입니다** [확인].
    실측: `Fi-Tapping TEST`, `RQQA_PFH_MONF (1)`, 5EAP1501 의 `xy scanner opm`,
    `zeroscan 5point pm`.
    그 밖에 실측된 recipe 명: BSOXCMP_CORRELATION_36PT, RL1A_LPCCMP_CMPWEAK2,
    RX1A_M0A_COT_X_PDG, VED_BS_TOP01. 어느 장비의 recipe 인지는 5EAP1501 의 둘 외에는
    회신에 없습니다 [가정].
    파일명이 측정의 키이고 웹은 그 키를 URL 경로에 넣으므로 URL 인코딩이 필요합니다.
    MinIO 객체 key 와 Redis key 에 들어갈 때도 같은 주의가 필요합니다.
  - MAPC01 은 LOT_ID 자리가 NA 입니다. lot 을 다른 곳(Info 섹션 등)에서 얻을 수
    있는지는 미정입니다 [가정] — mock 은 lot_id 를 "NA" 로 둡니다.
  - MAPC01 만 SLOT 필드가 따로 있습니다. 나머지 두 장비의 slot 이 SAMPLE_ID 안에
    들어 있는지는 미정입니다 [가정].
  - 5EAP1501 의 `...` 는 회신에서 생략된 부분입니다. 마지막 `#` 와 `.csv` 사이에
    무엇이 오는지 모릅니다 [가정] — mock 은 비워 둡니다.
  - SAMPLE_ID 의 생김새, 재측정 시 파일명이 겹치는지는 회신에 없습니다 [가정].
  - **시간대는 미정**입니다 (2차 회신이 남은 미정으로 명시).

  ⚠ 한 파서로 세 장비를 읽을 수 없습니다. 다섯 번째 필드가 MAP608·5EAP1501 에서는
    LOT_ID 이고 MAPC01 에서는 NA 이며, 네 번째 필드는 SAMPLE_ID 또는 SLOT 입니다.


D3 측정 상세 — CSV

  CSV 한 파일이 섹션 셋입니다 [확인].

    Info    : key, value
    Summary : MEAN / STDEV / MIN / MAX / RANGE
    Data    : 측정 point 하나가 한 행

  장비별 유무 [정정]:
    1차 회신은 "MAPC01 은 data CSV 가 없다"고 했으나, 2차 회신이 **MAPC01 에도
    recipe 에 따라 data CSV 가 있다**고 바로잡았습니다. 장비가 아니라 recipe 가
    정합니다(맨 위 규칙).
    5EAP1501 은 profile txt 가 없습니다(1차 회신). 이것도 장비의 성질이 아니라
    그 장비에서 도는 recipe 의 설정일 수 있습니다 [가정].

  측정 컬럼 — recipe 마다 다릅니다 [확인]. 실측된 것:

    Left_H (nm) / Right_H (nm) / Ref_H (nm)
    Dishing_H (nm)
    Bottom_H (nm) / Top_H (nm)               (BSOXCMP_CORRELATION_36PT)
    Ref_Range (nm) / Left_TRIM_H (nm)
    ROUGHNESS_RANGE (nm) / Ra (nm) / Rq (nm)
    Pad_1_H (nm) ...                         (MAP608)
    1_Minimum (nm) ~ 51_Minimum (nm)         (5EAP1501)
    RZ1_Minimum (nm) ...                     번호 컬럼에 접두가 붙은 변형
    Line1_Residue_H                          (RL1A_LPCCMP_CMPWEAK2) Line1_* 접두 계열
    SITE19_21_..                             (RX1A_M0A_COT_X_PDG) 이름이 잘려 전달됨

    - 전부 `nm` 를 포함합니다 [확인]. 이름에 nm 가 든 컬럼만 고르는 웹의 시계열
      필터는 그대로 동작합니다.
    - "등"이 붙어 있어 이 목록이 전부는 아닙니다. 웹은 컬럼 이름을 고정하면 안 됩니다.
    - 회신은 `Ref_Range/Left_TRIM_H (nm)` 처럼 묶어 적었습니다. `/` 로 나눈 각각이
      `(nm)` 를 단 별개 컬럼이라고 읽었습니다 [가정]. `1~51_Minimum (nm)` 도 1번부터
      51번까지 컬럼 51개로 읽었습니다 [가정].
    - `Line1_Residue_H` 는 회신에 `(nm)` 없이 적혔습니다. 앞선 회신의 "전부 nm
      포함"에 따라 `(nm)` 가 붙는다고 보았습니다 [가정]. `SITE19_21_..` 의 나머지
      이름은 모릅니다 [가정] — mock 은 `SITE19_21_H (nm)` 로 둡니다.
    - 어느 컬럼이 어느 recipe·장비의 것인지는 위에 괄호로 적은 것 외에는
      회신에 없습니다 [가정].
    - 컬럼 이름이 `SITE` 로 시작할 수 있습니다. 웹이 `Site` 로 시작하는 키를 위치
      컬럼으로 추정하면 안 됩니다.
    - 번호가 붙은 컬럼은 문자열 정렬로 `10_…` 이 `1_…` 앞에 옵니다. 웹은 자연
      순서로 다시 놓습니다(frontend/app/utils/afmExport.ts 의 collectColumns).

  Summary block [확인]:
    - CSV 헤더에 Site 컬럼은 없습니다. 각 섹션 앞에 이름 줄이 있고, 파서가 그것을
      Site 필드로 저장합니다. 그 이름은 **method 명**입니다.
    - **한 파일에 Summary block 이 여러 개**일 수 있습니다.
      실측: Profile_LEFT_UL + Profile_RIGHT_UL.
    - Summary 가 없는 파일, method 명 줄만 있는 빈 Summary 도 있습니다(맨 위 규칙).

  Data 행 [확인]:
    point 수   : recipe 마다 다르며 **1 ~ 36** 까지 실측되었습니다.
    Site ID    : 위치 식별자. 예 `0001_X000_Y000`, `0002_X002_Y-001` (음수 가능).
                 MAPC01 profile 파일명의 Site 부분과 **일치**합니다 — 측정 위치 하나의
                 profile 을 찾는 연결 키입니다.
                 ⚠ **세 장비 모두 recipe 에 따라 있거나 없습니다** [정정: 2차 회신은
                   "컬럼 존재"라고만 했습니다]. 있는 것이 확인된 recipe:
                   BSOXCMP_CORRELATION_36PT, RL1A_LPCCMP_CMPWEAK2, RX1A_M0A_COT_X_PDG.
                   없는 recipe 에서 위치와 profile 파일을 무엇으로 가리키는지는
                   회신에 없습니다 [가정] — mock 은 `0001` 같은 순번만 씁니다.
    Site X     : Site ID 와 함께 있거나 없다고 보았습니다 [가정]. 값의 단위는 회신에
                 없습니다 [가정: Site ID 의 X 숫자와 같은 die 번호].
    Site Y     : 위와 같습니다.
    State      : **COMPLETED, FAILED, STOPPED 3종으로 확정**되었습니다.
                 STOPPED 는 드문 예외가 아니라 여러 recipe 에서 나옵니다
                 (VED_BS_TOP01, Fi-Tapping TEST 등).
                 [정정] 2차 회신의 `COMPLITED` 는 오타였습니다.
    Method_ID  : recipe 에 따라 **숫자**입니다. 그 밖의 recipe 에서는 숫자가 아닙니다
                 [가정: method 명 문자열]. 타입이 섞이므로 parquet 적재 시 dtype 에
                 주의해야 합니다.
    Valid      : 컬럼 존재. **FALSE 인 실물은 아직 보지 못했습니다** (남은 미정) —
                 FALSE 의 표기(FALSE / False / 0 / 빈 값)를 모릅니다.

  ⚠ Site 가 두 축입니다. Summary 의 `Site` 는 method 명이고 Data 의 `Site ID` 는
    위치입니다. 1차 회신만으로는 둘을 같은 값으로 보았으나 다릅니다 [정정].

  Info [확인]: Last Pick Up Time 과 Last Put Back Time 은 **빈 값일 수 있습니다**.
    이 둘이 Info 의 key 라는 것과 빈 값의 표기는 회신에 명시되지 않았습니다 [가정].

  회신에 없는 것 [가정]: Info 의 나머지 key, Data 행의 나머지 컬럼, `<측정명>_Valid`
  의 존재, Summary 가 장비 값인지 계산값인지와 STDEV 의 ddof, 유효값 제외 규칙,
  method block 하나가 Site 마다 몇 행을 내는지, 여러 block 이 같은 컬럼을 갖는지.


D4 Profile — txt

  2D 격자 txt 입니다 [확인].

    헤더 : Data Size / Surface Size / X·Y·Z unit
    본문 : 탭으로 구분한 X  Y  Z

  장비별 격자 [확인]:
    MAP608 : 512 × 64, 단위 um / um / nm
    MAPC01 : 격자가 다양합니다. 1024×1 ~ 16384×1 등이며 **1D 와 2D 가 섞여** 있습니다.
             파일명에 Site ID 가 들어 있습니다(D3 의 Data 행 참고).
    5EAP1501 : profile 없음

  ⚠ 단위가 **파일마다 다릅니다** — um / nm / pm / Pixel. 반드시 헤더에서 읽어야
    하고, 장비나 축 이름으로 단위를 정해 두면 안 됩니다 [확인].
  ⚠ 현재 계약(`AfmProfilePoint` = x, y, z)에는 단위를 실을 자리가 없습니다. ETL 이
    단위를 통일해 주지 않는다면 profile 응답에 단위를 추가해야 합니다 — 적재 형태가
    회신되면 결정합니다.

  회신에 없는 것 [가정]: profile 파일명의 Site ID 밖 부분, MAP608 의 profile
  파일명도 Site ID 를 쓰는지, MAPC01 의 2D 격자 크기, 격자 간격·원점,
  leveling/flattening 여부, 오류·포화 값의 표현.


D5 이미지

  webp 변환본이 있습니다. TIFF 는 문제가 되지 않습니다 [확인] — 브라우저가 TIFF 를
  못 그리는 문제는 webp 변환본으로 해결됩니다. 유무는 recipe 설정이 정합니다(맨 위 규칙).

  회신에 없는 것 [가정]: 종류(Height·align·tip·capture)별 파일명 규칙.


mock 반영 (backend/afm/providers/mock.py)

  위 [확인] 항목은 mock 이 그대로 재현하고 backend/afm/tests/
  test_mock_office_facts.py 가 고정합니다. [가정] 항목은 mock 의 docstring 에
  OFFICE-VERIFY 로 나열되어 있습니다.

  mock 이 일부러 다르게 두었거나 지어낸 곳:
    - recipe 명은 위 D2 에 적은 여덟 개만 실제이고 나머지는 지어냈습니다. 어느
      recipe 가 어느 장비·컬럼·method·파일 종류·point 수를 갖는지도, 괄호로 확인된
      셋의 컬럼과 Site ID 유무를 빼면 지어낸 대응입니다(mock 의 RECIPES 표).
    - point 가 하나인 측정의 STDEV 는 0 으로 냅니다. 실제 표기는 모릅니다.
    - Summary 없는 파일과 표 없는 Data 는 열두 파일에 하나꼴로 냅니다. 실제 비율은 모릅니다.
      "method 명 줄만 있는 빈 Summary"는 행 목록으로는 "Summary 없음"과 구분되지
      않아 같은 모양으로 냅니다.
    - Valid 는 일부를 False 로 냅니다. 실물은 아직 TRUE 만 보았습니다.
    - Profile 좌표는 um/um/nm 로 읽히는 값 하나로 통일했습니다. 계약에 단위 필드가
      없어 파일별 단위 차이를 재현할 수 없습니다.
    - Summary 는 그 block 의 Data 행에서 직접 계산합니다(STDEV 는 ddof=1).
      실제 계산 규칙은 모릅니다.
