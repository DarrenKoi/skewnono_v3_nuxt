AFM 장비 raw 파일 — ETL 이전 원본 (적재 형태는 afm_redis.txt)

이 문서는 각 AFM 장비에서 추출한 **raw 파일**의 구조입니다. 사무실 agent 가
skewnono-pjt-shared/AFM/ 의 raw 데이터를 보고 확인한 내용이며(office 확인
2026-10-02, 회신 4회), 회신 원문은 docs/afm/office-data-findings.md 에 그대로 있습니다.

웹이 실제로 읽는 것은 이 raw 파일이 아니라 ETL 이후의 적재물입니다 — Redis 색인
(측정 목록 + MinIO 객체 key)과 MinIO 객체(상세·Profile·이미지). 그 key 이름·형식·열은
**afm_redis.txt** 에 있습니다(user-confirmed 2026-10-06). 이 문서는 그 값들이 어디서
왔는지 — 파일명의 필드, CSV 의 섹션, profile 의 격자 — 를 설명합니다. 아직 답을 받지
못한 질문은 docs/afm/to-questionnaire-afm.md 하나에 모여 있고, 받은 답의 반영 현황은
docs/afm/office-data-findings.md 끝에 있습니다.

표기: [확인] = office 확인 2026-10-02, [가정] = OFFICE-VERIFY.
      [정정] = 앞선 회신의 내용을 뒤의 회신이 바꾼 곳.


가장 중요한 규칙 — 무엇이 있는지는 recipe 설정이 정합니다 [확인]

  data CSV·profile txt·이미지 가운데 무엇이 있는지, point 가 몇 개인지(1~36 실측),
  Site ID 를 기록하는지는 전부 **recipe 설정**에 달려 있습니다. 장비가 정하지
  않습니다. 파일이 없는 것은 오류가 아니라 **정상 상태**이므로, 웹은 부재를 빈
  화면으로 보여 주어야 하고 오류로 다루면 안 됩니다.

  같은 원리가 파일 안에도 적용됩니다. 아래가 모두 실측되었습니다 [확인]:
    - Summary 가 아예 없는 data CSV (Info 뒤에 바로 Data)
    - method 명 줄만 있고 표가 없는 빈 Summary block
    - 표가 없는 빈 Data
    - 측정 컬럼이 없는 block (중단된 측정의 뒤쪽 block)
    - 빈 문자열인 Info 값 (Carrier ID, Last Pick Up Time, Last Put Back Time 등)

D2 측정 식별자 — 파일명

  파일명은 `#` 으로 필드를 구분하고, 장비마다 **필드 순서가 다릅니다** [확인].
  값이 없는 자리는 NA 입니다.

  MAP608   : #YYMMDD#hhmmss#RECIPE#SAMPLE_ID#LOT_ID#hhmmss#.csv
  MAPC01   : #YYMMDD#hhmmss#RECIPE#SLOT#NA#NA#<원본 파일명>_Info.csv   (Info, 항상 있음)
             #YYMMDD#hhmmss#RECIPE#SLOT#NA#NA#<원본 파일명>.csv        (data, recipe 에 따라)
  5EAP1501 : #YYMMDD#HHMMSS#RECIPE#SAMPLE_ID#LOT_ID#NA#<원본 파일명>.csv

  실측 예 [확인]:
    MAPC01   #260709#033958#RL1C_L1_XDEC_5MM_LINE#01#NA#NA#RL1C078.01.csv
    5EAP1501 #261001#023441#VM_GTFILLOX_5PT_R1#5PNN1768.05$5PNN1768#NA#VM_GTFILLOX_5PT_R15PNN17685PNN178.05.csv
             (회신 그대로입니다. `$` 는 `#` 의, 끝의 `5PNN178.05` 는 `5PNN1768.05` 의
              오타입니다 [확인 2026-10-06]. SAMPLE_ID=5PNN1768.05, LOT_ID=5PNN1768 입니다.)

  MAP608 [확인]:
    - 첫 번째 시각은 **세션(폴더) 시작 시각**입니다. 같은 세션의 여러 측정이
      **공유**하므로 date#time 만으로는 측정이 구분되지 않습니다.
    - 마지막 시각이 **측정 시작 시각**입니다. 오래된 데이터는 그 자리가 NA 입니다.
    - 시작 시각의 확실한 원천은 **Info 섹션의 Start Time** 입니다. 뒤 시각이 NA 인
      실측에서 Start Time 이 첫 시각과 일치하는 것을 확인했습니다.

  MAPC01 [확인, 정정 포함]:
    - `_Info.csv` 는 지금까지 **모든 측정에 있습니다**. data CSV 는 recipe 에 따라 있고,
      같은 이름에서 `_Info` 를 뺀 것입니다.
    - 마지막 세그먼트는 장비의 원본 파일명이라 recipe 마다 다릅니다.
    - LOT_ID 자리는 NA 이고, lot 은 **Info 섹션의 `Lot ID`** 에 있습니다
      (info CSV 안, 예: `Lot ID,MON69683`).
    - [정정] **측정 한 건 = 앞 4필드(date#time#recipe#slot)** 입니다(적재 검증 완료).
      같은 sample 이 하루에 여러 번 다시 측정되며(모니터링 recipe), 측정마다 info CSV 가
      있고 **시각으로만** 구분됩니다. 시각이 다른 info(124557)와 profile(132331)은 같은
      측정의 파일이 아니라 서로 다른 측정입니다 — sample 이나 날짜로 파일을 묶으면
      다른 측정이 섞입니다.

  5EAP1501 [확인]:
    - 끝부분은 RECIPE+LOT+SAMPLE 을 **구분자 없이 이어 붙인** 원본 파일명입니다.
      `_SOP_LEFT_UR` 같은 접미가 붙기도 합니다(선택).
    - SAMPLE_ID 는 `<lot>.<nn>` 형태입니다(예 `5PNN1768.05`).
    - ⚠ `.nn` 은 **웨이퍼 슬롯이 아닐 수 있습니다** — `.05` 와 Slot 5 가 맞지 않는 실측이
      있습니다 [확인 2026-10-06]. 슬롯은 Info 의 `Sample Location` (`Slot N`)에 있습니다.

  공통:
    - **recipe 명에 공백·괄호·소문자가 들어갈 수 있고, 세 장비 공통입니다** [확인].
      실측: `Fi-Tapping TEST`, `RQQA_PFH_MONF (1)`, 5EAP1501 의 `xy scanner opm`,
      `zeroscan 5point pm`. 파일명이 측정의 키이고 웹은 그 키를 URL 경로에 넣으므로
      URL 인코딩이 필요합니다. MinIO 객체 key 와 Redis key 에서도 같습니다.
    - 그 밖에 실측된 recipe 명: BSOXCMP_CORRELATION_36PT, RL1A_LPCCMP_CMPWEAK2,
      RX1A_M0A_COT_X_PDG, VED_BS_TOP01, RL1C_L1_XDEC_5MM_LINE(MAPC01),
      VM_GTFILLOX_5PT_R1(5EAP1501).
    - **시간대는 미정**입니다. 장비 현지 시각이며 KST 로 추정합니다 [가정].
    - MAP608 의 SAMPLE_ID 형태, 재측정 시 MAP608·5EAP1501 의 파일명이 겹치는지는
      회신에 없습니다 [가정].

  ⚠ 한 파서로 세 장비를 읽을 수 없습니다. 다섯 번째 필드가 MAP608·5EAP1501 에서는
    LOT_ID 이고 MAPC01 에서는 NA 이며, 네 번째 필드는 SAMPLE_ID 또는 SLOT 입니다.
  ⚠ 측정을 가리는 필드도 장비마다 다릅니다. MAP608 은 뒤 시각(또는 sample)까지 봐야
    하고, MAPC01 은 앞 4필드입니다.


D3 측정 상세 — CSV

  CSV 한 파일이 섹션 셋입니다 [확인].

    Info    : key, value. 값은 빈 문자열일 수 있습니다.
    Summary : MEAN / STDEV / MIN / MAX / RANGE
    Data    : 측정 point 하나가 한 행

  Info 의 key 는 측정에 따라 **두 가지 구성**입니다 [user-confirmed 2026-10-06].
  아래는 파일에 적힌 순서입니다.
    15키: Lot ID, Recipe ID, Carrier ID, Sample Location, Sample ID,
          Data Save Location, Start Time, End Time, Tip ID, Tip Cassette ID,
          Tip Port No, Tip Slot No, Last Pick Up Time, Last Put Back Time, Tip Width
    13키: Port No, Carrier ID, Slot No, Lot ID, Sample ID, Recipe ID, Tip ID,
          Tip Cassette ID, Tip Port No, Tip Slot No, Last Pick Up Time,
          Last Put Back Time, Tip Width
  - 13키에는 `Sample Location`·`Start Time`·`End Time`·`Data Save Location` 이 없고,
    대신 `Port No`·`Slot No` 가 있습니다.
  - `Sample Location` 의 값 안에 `Slot N` 이 있습니다(실제 웨이퍼 슬롯) [확인].
  - 장비별 분포 [user-confirmed 2026-10-06]: 5EAP1501 은 15키 위주, MAPC01 은 13키
    위주, MAP608 은 혼재입니다. 어느 장비도 한 구성만 갖는다고 볼 수 없습니다.
  - 한 장비 안에서 구성을 가르는 것(recipe·시기·파일 종류)과 비율, `Port No`·
    `Slot No`·`End Time`·`Data Save Location`·`Tip *` 의 값 생김새는 모릅니다
    [OFFICE-VERIFY].
  - ⚠ 웹은 key 를 정해 두지 않습니다. 상세 화면은 **있는 key 만** 보여 주고, 빈 값은
    null 로 받습니다(JSON 응답이 key 를 정렬하므로 화면 순서는 파일 순서가 아니라 A–Z). key 를 이름으로 읽는 곳은 13키에 없는 key 가
    빠져도 동작해야 합니다(시계열의 `Start Time` 은 목록의 날짜로 대신합니다).
  MAPC01 의 info CSV 는 **Data 섹션에 `FileName` 열**이 있어 point 번호(`_0001`)와
  파일을 잇지만, 현재 적재에서는 제외됩니다 [확인 2026-10-06].

  측정 컬럼 — recipe 마다 다릅니다 [확인]. 실측된 것:

    Left_H (nm) / Right_H (nm) / Ref_H (nm)
    Dishing_H (nm)
    Bottom_H (nm) / Top_H (nm)               (BSOXCMP_CORRELATION_36PT)
    Ref_Range (nm) / Left_TRIM_H (nm)
    ROUGHNESS_RANGE (nm) / Ra (nm) / Rq (nm)
    Pad_1_H (nm) ...                         (MAP608)
    1_Minimum (nm) ~ 51_Minimum (nm)         (5EAP1501) — 컬럼 51개
    RZ1_Minimum (nm) ...                     번호 컬럼에 접두가 붙은 변형
    Line1_Residue_H (nm)                     (RL1A_LPCCMP_CMPWEAK2) Line1_* 접두 계열
    SITE19_21_H (nm)                         (RX1A_M0A_COT_X_PDG)

    - 전부 `nm` 를 포함합니다 [확인]. 이름에 nm 가 든 컬럼만 고르는 웹의 시계열
      필터는 그대로 동작합니다.
    - "등"이 붙어 있어 이 목록이 전부는 아닙니다. 웹은 컬럼 이름을 고정하면 안 됩니다.
    - 묶어 적힌 표기(`1~51_…`, `Ref_Range/Left_TRIM_H (nm)`)를 각각 `(nm)` 를 단
      별개 컬럼으로 읽은 것이 맞다고 확인받았습니다 [확인].
    - 컬럼 이름이 `SITE` 로 시작할 수 있습니다. 웹이 `Site` 로 시작하는 키를 위치
      컬럼으로 추정하면 안 됩니다.
    - 번호가 붙은 컬럼은 문자열 정렬로 `10_…` 이 `1_…` 앞에 옵니다. 웹은 자연
      순서로 다시 놓습니다(frontend/app/utils/afmExport.ts 의 collectColumns).

  Block [확인]:
    - CSV 헤더에 Site 컬럼은 없습니다. 각 섹션 앞에 이름 줄이 있고, 파서가 그것을
      Site 필드로 저장합니다. 그 이름은 **method 명**입니다.
    - **한 파일에 block 이 여러 개**일 수 있습니다(실측: Profile_LEFT_UL +
      Profile_RIGHT_UL). Summary 뿐 아니라 **Data 도 block 마다 나뉩니다**.
    - 한 block 은 측정 point 마다 Data 행을 하나 냅니다.
    - **block 마다 컬럼이 다를 수 있습니다.** 실측된 것은 두 번째 block 에 측정 컬럼이
      없고 State 가 STOPPED 인 경우입니다. 빈 Summary block 도 있습니다.
    - ⚠ **Summary block 과 Data block 은 순서(위치)로 맞춥니다.** Method ID 가 같은지로
      맞추면 안 됩니다.

  Data 행 [확인]:
    Point No   : point 번호. **위치 키**입니다 — `Point No`=1 ↔ 파일명 `_0001` ↔
                 info CSV 의 FileName 열 `_0001` (4자리, 선행 0).
    Site ID    : 위치 식별자. 예 `0001_X000_Y000`, `0002_X002_Y-001` (음수 가능).
                 **세 장비 모두 recipe 에 따라 있거나 없습니다.** 있는 것이 확인된
                 recipe: BSOXCMP_CORRELATION_36PT, RL1A_LPCCMP_CMPWEAK2, RX1A_M0A_COT_X_PDG.
    Site X     : Site ID 안의 X 숫자와 같습니다(`0002_X002_Y-001` → 2). **단위 없음.**
    Site Y     : 위와 같습니다(→ -1).
    State      : **COMPLETED, FAILED, STOPPED 3종으로 확정.** STOPPED 는 여러 recipe 에서
                 나옵니다(VED_BS_TOP01, Fi-Tapping TEST 등).
                 [정정] 2차 회신의 `COMPLITED` 는 오타였습니다.
    Method ID  : recipe 에 따라 **숫자**(실측 `2`)이거나 **문자열**(실측 `L1_XDEC_5MM_LINE`,
                 recipe RL1C_L1_XDEC_5MM_LINE)입니다. 타입이 섞이므로 parquet 적재 시
                 dtype 에 주의해야 합니다. block 을 가리는 키로 쓰면 안 됩니다(위 ⚠).
                 컬럼 이름이 `Method_ID` 인지 `Method ID` 인지는 회신마다 달랐습니다
                 [가정: mock 은 `Method_ID`].
    Valid      : 컬럼 존재. **FALSE 인 실물은 아직 없습니다**(미실측) — FALSE 의 표기를
                 모릅니다.

  Summary 값 [확인]: point 가 하나인 측정은 STDEV=0.0, RANGE=0.0 입니다(1PT 실측).

  ⚠ Site 가 두 축입니다. Summary 의 `Site` 는 method 명이고 Data 의 `Site ID` 는
    위치입니다 [정정: 1차 회신만으로는 같은 값으로 보았습니다].

  회신에 없는 것 [가정]: Data 행의 나머지 컬럼, `<측정명>_Valid`
  의 존재, Summary 가 장비 값인지 계산값인지와 STDEV 의 ddof, 유효값 제외 규칙.


  block 과 행 [확인 2026-10-06, 정정]:
    - 적재된 Data 행은 **`Site` 열에 자기 block 의 method 명**을 갖습니다. block 은 그
      열로 가립니다 — 행의 순서로 추측하지 않습니다.
    - **repeat recipe** 는 한 block 안에서 같은 point 를 되풀이해 측정합니다
      (실측 4 Site × 2 반복 = 8행). "같은 point 가 다시 나오면 다음 block" 이라는 규칙은
      틀립니다.
    - 측정이 중단되면 **측정하지 못한 point 의 행은 없습니다.** STOPPED 행으로 채우지
      않습니다.
    - 측정하지 못한 칸은 공백 한 칸이고 `NaN`·`-` 는 없습니다.
    적재 형태의 나머지는 afm_redis.txt 3.1 에 있습니다.


D4 Profile

  raw 는 2D 격자 txt 입니다 [확인].

    헤더 : Data Size / Surface Size / X·Y·Z unit
    본문 : 탭으로 구분한 X  Y  Z

  파일명 — 위치 키로 끝납니다 [확인]:
    Site ID 없는 recipe : ..._0001_Height.txt                      (`_<Point No>`)
    Site ID 있는 recipe : ..._0004_X000_Y-002_0002_Height.txt      (`_<Site ID>_<4자리>`)
    세 장비 공통이 아니라 **recipe 의존**입니다 — Site ID 를 기록하는 recipe 만 파일명에
    site 가 들어갑니다. 뒤의 4자리(`0002`)는 **그 Site 안의 point 번호**입니다
    [확인 2026-10-06]. 한 Site 에 point 가 여럿일 수 있습니다(실측 예
    `0001_X-001_Y-001_0014`).

  장비별 격자 [확인]:
    MAP608 : 512 × 64, 단위 um / um / nm
    MAPC01 : 격자가 다양합니다. 1024×1 ~ 16384×1 등이며 **1D 와 2D 가 섞여** 있습니다.
    5EAP1501 : profile 없음

  적재 형태 [확인] — ETL 이후:
    - **X / Y / Z parquet** 입니다. 1D 도 같은 형태이고 **Y = 0 으로 고정**됩니다.
    - 단위는 **통일하지 않습니다.** 파일별로 유지하며 객체 metadata 로 함께 적재합니다:
        XUnit, YUnit, ZUnit, DataSize, SurfaceSize
    - 1D / 2D 는 **DataSize** 로 구분합니다(예: `1024 x 1`).
    - 단위는 um / nm / pm / Pixel 가운데 하나이고 파일마다 다릅니다. 장비나 축 이름으로
      단위를 정해 두면 안 됩니다.
    - **Pixel 의 길이 환산은 미정**입니다(원본에 근거가 없음). Pixel 축은 길이로 바꾸지
      않고 Pixel 그대로 보여 줍니다.

  회신에 없는 것 [가정]: metadata 가 MinIO 객체의 user metadata 인지 parquet 파일의
  metadata 인지, SurfaceSize 의 값 형식, MAPC01 의 2D 격자 크기, 격자 간격·원점,
  leveling/flattening 여부, 오류·포화 값의 표현.


D5 이미지

  webp 변환본이 있습니다. TIFF 는 문제가 되지 않습니다 [확인] — 브라우저가 TIFF 를
  못 그리는 문제는 webp 변환본으로 해결됩니다. 유무는 recipe 설정이 정하고, 파일명의
  위치 키 규칙은 profile 과 같습니다(D4).

  원본 TIFF 는 MinIO 에 저장되어 있고, 사용자가 웹에서 내려받을 수 있어야 합니다
  [user-confirmed 2026-10-03]. 화면에는 webp 변환본을 그리고, 다운로드는 원본을 그대로
  (변환 없이) 내보냅니다.

  회신에 없는 것 [가정]: 종류(Height·align·tip·capture)별 파일명의 나머지 부분.
  원본 TIFF 의 MinIO bucket·key 규칙, 원본 파일명이 webp 변환본과 확장자만 다른지,

  capture 에도 TIFF 원본이 있는지(현재는 Result 이미지에만 있다고 가정).


웹 계약에 반영된 것 (backend/afm)

  - profile 응답은 point 목록과 함께 `meta` 를 싣습니다 — `AfmProfileMeta`
    (x_unit, y_unit, z_unit, data_size, surface_size). provider 함수는
    `get_profile_meta(filename, point, tool_name)` 이고 office adapter 는 위의
    XUnit·YUnit·ZUnit·DataSize·SurfaceSize 를 이 키로 옮깁니다.
  - 화면은 축과 Excel 헤더에 그 단위를 그대로 씁니다. data_size 가 한 줄(`1024 x 1`)
    이라고 하면 히트맵 대신 선 그래프로 그립니다. data_size 를 읽을 수 없을 때만
    "Y 가 한 값뿐인가"로 판단합니다.
  - 원본 TIFF 다운로드는 `GET /api/afm/files/<filename>/tiff/<name>` 입니다. provider
    함수는 `get_tiff_original(filename, name, tool_name)` 이고 `AfmOriginalFile`
    (filename, content_type, data) 을 돌려줍니다. `name` 은 `tiff_dir_list` 의 표시용
    이름이며, 저장 key 로 바꾸는 일은 office adapter 가 맡습니다. Result 이미지 목록의
    각 항목은 이 주소를 `original_url` 로 싣습니다. 측정 하나의 원본 전체는
    `GET /api/afm/files/<filename>/tiff.zip` 으로 한 번에 받습니다(route 가 위 두 함수로
    조립하므로 office 함수가 따로 없습니다).
  - `AfmMeasurementRow` 는 Redis 명세에 맞추었습니다(afm_redis.txt). 상세의
    summary·data 는 detail parquet 의 열 구성을 받을 때까지 그대로 둡니다. 특히
    **Data 행이 어느 block 에 속하는지**를 담을 자리가 아직 없습니다 — Method ID 로는
    가릴 수 없으므로 그 열 구성이 확인되면 정합니다.

    - 세션(MAP608)은 측정 3건, 재측정(MAPC01)은 3회로 고정했습니다. 실제 크기는 모릅니다.
    - Site 당 point 2개는 recipe 하나(VED_BS_TOP01)에만 두었습니다.
    - 숫자가 아닌 Method ID 는 recipe 명에서 첫 토막을 뺀 것으로 만듭니다. 실측 한 건이

    - Summary 는 그 block 의 Data 행에서 직접 계산합니다(STDEV 는 ddof=1).
      실제 계산 규칙은 모릅니다.
    - Pixel 축의 값은 표본의 순번입니다.
