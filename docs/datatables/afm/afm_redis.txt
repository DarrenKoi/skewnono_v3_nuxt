AFM 적재 형태 — Redis 색인 + MinIO 객체 (ETL 이후, 웹이 실제로 읽는 것)

각 AFM 장비의 raw 파일(afm_raw_files.txt)을 ETL 이 적재한 결과입니다. Redis 가 측정
목록과 MinIO 객체 key 를 갖고, 본문(상세·profile·이미지)은 MinIO 에 있습니다.
소비 feature 는 `afm` 이고 adapter 는 backend/afm/providers/office_example.py 입니다.

표기: [명세] = user-confirmed 2026-10-06 (사무실 적재 명세 전달, 5차),
      [확인] = office 확인 2026-10-06 (실제 적재물을 보고 답한 6차 회신),
      [확인 7차] = office 확인 2026-10-07 (7차 회신),
      [확인 8차] = office 확인 2026-10-07 (8차 회신, 전부 실측 기반),
      [확인 9차] = office 확인 2026-10-07 (9차 회신),
      [가정] = OFFICE-VERIFY.
회신 원문은 docs/afm/office-data-findings.md, 남은 질문은 docs/afm/to-questionnaire-afm.md 에
있습니다. adapter 자체는 아직 사무실에서 실행해 보지 않았습니다.


공통 규칙 [명세]

  값 직렬화 : pandas `DataFrame.to_parquet()` → bytes.
              예외는 `afm_tool_recipes` 하나이며 JSON 문자열입니다.
  자료형    : 모두 Redis **hash** 입니다.
  hash field: 장비명 문자열입니다 — `MAP608`, `MAPC01`, `5EAP1501`.
              `afm_d1_tools` 만 field 가 `all` 하나입니다.
  갱신 단위 : 장비(field) 하나 = DataFrame 전체를 **통째로 다시 씁니다.**
              행 단위 key 는 없습니다. TTL 도 없습니다.
  갱신 주기 : **30분**입니다. 측정이 끝난 뒤 통상 30분 안에 목록에 나타납니다 [확인].
  읽기      : `hget` → `pd.read_parquet(io.BytesIO(raw))`.
  결측      : **빈 값은 null** 입니다. 웹 응답으로 내보낼 때 NaN 을 null 로 바꿔야
              합니다(그대로 두면 JSON 이 깨집니다).
  쓰기 금지 : 웹은 MinIO 에 **쓰지 않습니다.** 적재는 ETL 만 합니다.
  복구      : Redis 가 유실되어도 MinIO 객체 key 만으로 D2 를 다시 만들 수 있습니다.
  보존      : **3개월**로 확정되었습니다 [확인]. 지울 때 **MinIO 객체를 먼저, Redis 행을
              나중에** 지웁니다. 그 사이에는 목록에는 있는데 객체가 없는 측정이
              생기므로, 웹은 객체가 없는 것을 오류가 아니라 "없음"으로 다룹니다.

  사용 key 4개 [명세 + 확인]:

    afm_d1_tools          장비 목록 (아래 1)
    afm_d2_measurements   측정 이력 (아래 2)
    afm_tool_recipes      recipe 명의 JSON 배열. 측정 검색의 Recipe 필터에 읽어도
                          됩니다. 웹은 아직 읽지 않습니다(목록에서 직접 모읍니다).
                          hash field 가 장비명인지는 회신에 없습니다 [가정].
    afm_download_history  다운로드 이력 parquet. **웹은 읽지 않습니다.**


1. afm_d1_tools — 장비 목록

  hash, field 는 `all` 하나뿐입니다 [명세]. 실제 값 [확인]:

    id        name      fab   alias
    MAP608    MAP608    ''    null
    MAPC01    MAPC01    ''    R3
    5EAP1501  5EAP1501  ''    M15

  - `id` 는 **대문자 그대로**입니다(장비명과 같습니다).
  - `fab` 은 **빈 문자열**입니다. 언제 채워질지는 회신에 없습니다.
  - `alias` 는 **fab 이 아니라 추출 파이프라인이 장비에 붙인 코드명**입니다. fab 인지는
    원본에 근거가 없습니다 [확인 9차].
  - **fab 은 적재물 어디에도 없으므로 고정 표로 붙입니다** [user-confirmed 2026-10-07]:
    MAP608 = PKG, MAPC01 = R3, 5EAP1501 = M15. adapter 는 `fab` 이 비어 있으면 이 표에서
    채우고 `alias` 는 읽지 않습니다.

  웹 계약 `AfmToolRow` 로는 id→id(소문자로 — 화면의 장비 주소가 소문자입니다),
  name→name·label, fab(없으면 위의 표)→fab 으로 옮깁니다.

  ⚠ 화면의 장비 목록은 frontend 에 고정된 표(useAfmToolData.ts)를 쓰고
    `/api/afm/tools` 를 부르지 않습니다. 그 표도 같은 대응입니다.


2. afm_d2_measurements — 측정 이력

  hash, field = 장비명(`MAP608`, `MAPC01`, `5EAP1501`) [명세].
  값은 그 장비의 **측정 전체 목록을 DataFrame 하나로** 담은 parquet bytes 입니다.

  열:

    unique_key      측정키. 파일명의 `#` 필드입니다(아래 "측정키"). 장비 안에서 유일 [확인].
    filename        **data CSV 의 원본 파일명 전체**입니다. data CSV 가 없는 측정만
                    info CSV(`..._Info.csv`)의 이름입니다. 장비 안에서 유일합니다
                    (전수 확인, 중복 0건) [확인].
    date            YYMMDD
    formatted_date  YYYY-MM-DD **또는 null**
    recipe_name
    lot_id          MAPC01 도 채워져 있습니다 — 파일명의 `NA` 가 아니라 Info 의
                    `Lot ID` 입니다 [확인].
    slot_number     **앞에 0 이 없는 숫자 문자열**입니다(`5`, `10`, `21`) — 파일명의
                    두 자리(`.05`)와 다릅니다. **null 인 행이 있습니다** [확인 9차].
                    **Info `Sample Location` 의 `Slot N`** 에서 옵니다(실제 웨이퍼
                    슬롯). 그것을 읽지 못한 측정만 파일명의 `.nn` 꼬리로 채웁니다
                    [확인]. `.nn` 은 슬롯과 다를 수 있습니다 — 5EAP1501 에서 `.05` 와
                    Slot 5 가 맞지 않는 실측이 있습니다. **웹이 파일명에서 슬롯을
                    읽으면 안 됩니다.**
    time            **HHMMSS 6자리** 또는 null. 값 `NA` 도 null 로 취급합니다.
                    파일명의 **첫 시각**이므로 MAP608 에서는 **세션 시작 시각**이고,
                    같은 세션의 측정들이 같은 `time` 을 갖습니다. 측정마다의 시각은
                    측정키의 6번째 필드입니다 [확인].
    measured_time   **그 측정의 시작 시각**입니다. 2026-10-07 에 추가되었습니다
                    [확인 7차]. MAP608 의 6번째 필드는 오래된 파일만이 아니라 최근
                    파일의 절반쯤(29/46)에서 `NA` 이므로, `time` 만으로는 MAP608 측정의
                    절반 이상이 세션 시각에 모입니다.
                    값 [확인 8차]:
                      - **`HHMMSS` 6자리**, 선행 0 포함(전수 확인).
                      - MAP608 의 6번째 필드가 `NA` 이면 **Info 의 `Start Time`** 에서
                        만듭니다. 그 값은 세션 시각과 다릅니다(실측 `time`='014148' →
                        `measured_time`='022914').
                      - `Start Time` 이 없는 **13키 Info 의 측정은 null** 입니다(6건).
                      - MAPC01·5EAP1501 은 `time` 과 전수 일치합니다.
                    adapter 는 빈 값을 null 로 내고 화면은 null 이면 `time` 을 씁니다.
    measured_info   열은 있으나 **항상 null** 입니다 [확인].
    tool_name       대문자 그대로 [확인].
    fab
    point_count     int **또는 null**. **실제로 스캔한 위치 수**(profile·tiff 파일 수)
                    입니다 [확인 7차]. recipe 가 정한 수도, points 의 행 수도 아닙니다.
                      - repeat recipe: 4 Site × 14 point = **56** (행은 112, recipe 의
                        point 는 14).
                      - 중단된 측정은 작아집니다. 실측 분포 2, 3, 5, 8, 14, 43, 55, 56.
                      - 첫 point 에서 중단되어 tiff·profile·capture 가 0건인 측정은 null.
                      - profile 도 Result 이미지도 남기지 않는 recipe 는 측정이
                        끝났어도 null 입니다 [확인 9차].

  `tool_id` 열은 **없습니다** [확인]. 계약의 `tool_id` 는 adapter 가 장비명을 소문자로
  바꿔 채웁니다.

  팁 열 9종 — **2026-10-07 에 적재되었습니다** [확인 7차: 아래 이름 그대로, 구현·테스트
  완료]. 팁 모니터링 화면(`/afm/<장비>/tips`)이 장비의 모든 측정을 한 번에 읽는 열입니다.
  값은 상세(`detail_points`)와 **같은 첫 data CSV** 에서 계산하므로 목록과 상세가
  어긋나지 않습니다.

    tip_id               Info `Tip ID` 그대로 (text, 없으면 null)
    tip_cassette_id      Info `Tip Cassette ID` 그대로
    tip_port_no          Info `Tip Port No` 그대로
    tip_slot_no          Info `Tip Slot No` 그대로
    last_pick_up_time    Info `Last Pick Up Time` 그대로. Home 의 요청(Q58)으로 추가된
                         열입니다 [확인 9차]. 팁 단위 값이라 한 팁의 측정이 모두 같은
                         값을 갖고, 바뀌면 팁을 다시 집은 것입니다. 빈 값은 null.
    tip_width            Info `Tip Width`. **float64** 이고 기록이 없는 측정(`NaN`)은
                         NaN 입니다 [확인 7차]. adapter 는 NaN 을 null 로 냅니다.
    approach_count_mean  data 전체 행의 `Approach Count` 평균 (float)
    mileage_mean         data 전체 행의 `Mileage` 평균 (float). `Mileage` 는 **팁 단위
                         누적값**이라 한 팁을 쓰는 동안 커지기만 하고, 다른 슬롯의
                         팁으로 바뀌면 리셋됩니다 [확인 7차: DT-NCHR_CM slot 9 → slot 1
                         에서 1430483 → 3520]. 같은 팁에서 값이 줄어든 일은 0건이고
                         리셋은 늘 슬롯 변화와 함께였습니다. 리셋 뒤 첫 값은 0 이
                         아닙니다(3520). 단위는 미정입니다(um 추정) [확인 8차].
                         장비 재시작·수동 초기화 때의 동작은 **미실측**입니다.
    not_completed_count  `State` 가 COMPLETED 가 아닌 행 수 (int)
    invalid_count        `State` 가 COMPLETED 이고 `Valid` 가 FALSE 인 행 수 (int)

  뒤의 넷은 data 행이 없는 측정(info 만 있는 측정)에서 null 입니다. 블록(`Site`)을
  가리지 않고 한 측정의 모든 행을 셉니다 — 시계열 비교의 장비 건강과 같은 정의입니다.
  mock 도 각 측정의 상세(Info·data 행)에서 같은 정의로 계산해 채웁니다.
  과거 측정도 **소급해 채워져 있습니다.** 목록의 보존은 3개월이라 팁 이력도 3개월까지
  입니다. `Tip Width` 에는 단위가 붙지 않고, `State` 는 3종뿐입니다 [확인 8차].
  관측된 `Tip ID` 는 **8종**이고 이름에 `MCNT` 가 든 것은 2종입니다. 나머지 6종의 폭이
  팁마다 다른지는 미정입니다. **5EAP1501 의 `OMCL-AC160TS` 는 `Tip Width` 가 대부분 NaN**
  이라, 폭이 있는 측정이 5건 미만이면 화면은 폭 관리선을 내지 않습니다 [확인 8차].
  판정 기준 [user-confirmed 2026-10-06]: 팁 종류(`Tip ID`)별로 묶고, spec 은 아직 정하지
  않아 같은 종류 측정의 중앙값 ± 3σ(σ는 MAD 기반) 밖을 이상치로 봅니다. 팁의 상태는
  그 팁의 최근 5건으로 정합니다(2건 이상 밖 = 이상, 1건 = 주의) [웹이 정한 규칙].
  7차 회신으로 바뀐 두 곳 [확인 7차]:
    - `Tip Width` — MCNT 가 아닌 종류는 폭이 사실상 상수라 종류 단위 관리선이 맞습니다.
      **MCNT 계열만 33.96~39.11 로 퍼지고 같은 슬롯에서도 오르내리므로**(마모가 아니라
      측정 오차로 추정) 관리선을 **팁(카세트·포트·슬롯) 단위**로 긋습니다. 화면은
      `Tip ID` 에 `MCNT` 가 들어 있으면 MCNT 계열로 봅니다 [가정: 이름으로 가립니다].
    - `Mileage` — 누적값이므로 관리선을 긋지 않고 판정에서 뺍니다. 사무실도 동의했습니다
      (관측 전수에서 모든 recipe 가 팁 단위 누적, "리셋 없는 종류" 0건) [확인 8차].
  팁이 바뀐 지점 [확인 7차]: 교체를 적은 기록은 없습니다. `Tip ID`·`Tip Cassette ID`·
  `Tip Port No`·`Tip Slot No` 가운데 하나가 달라졌거나 **Mileage 가 리셋된** 자리가
  팁이 바뀐 지점입니다.
  [확인 8차] Info 의 `Last Pick Up Time`·`Last Put Back Time` 은 **팁 단위 값**입니다 —
  같은 팁의 연속 측정 4건(02:50~06:31)이 모두 Pick Up 01:33:39 였습니다. 값이 갱신되면
  팁을 다시 집은 것입니다. 재시작·수동 초기화가 미실측이므로 Mileage 감소는 그것만으로
  보지 말고 **팁 값 변화나 Pick Up 갱신과 묶어** 보라는 권고를 받았습니다. 화면
  (시계열 비교의 세로선)은 팁 값이 달라진 자리, 또는 팁 값은 같은데 Mileage 평균이
  줄고 Pick Up 이 바뀐 자리에 긋습니다. 목록에 `last_pick_up_time` 이 생겨 팁 모니터링도
  같은 규칙을 씁니다 [확인 9차].
  현장에서 팁을 바꾸는 기준 숫자(Mileage·Approach Count 한계 등)는 **없습니다**
  [확인 9차]. 통계 관리선이 유일한 기준입니다.

  파일 목록 7종 — 모두 list[str] 이고, 원소는 **MinIO 객체 key 전체**입니다
  (prefix `2067928/` 포함). **빈 리스트 = 파일 없음**입니다 [명세].

    data_dir_list     상세 parquet
    profile_dir_list  profile parquet
    tiff_dir_list     Result 이미지(webp) **와 원본 TIFF** [확인]
    align_dir_list    align 이미지 (webp) **와 원본 `.bmp`** [확인 8차]. 측정마다 1~4장
                      이고 이름은 `1_Result.webp` 꼴 — 위치 키가 없습니다 [확인 9차].
    tip_dir_list      tip 이미지 (webp) **와 원본 `.png`** [확인 8차]. **두 계열**입니다
                      [확인 7차, 6차 답 정정]: point 마다 `_C_PR` 한 장(2440×1832
                      grayscale, 약 2.5MB)과 측정마다 `C_Result` 한 장(448×336 RGB, 약
                      440KB). 크기는 [확인 8차]. 원본은 `_C_PR` 이 `.png`,
                      `C_Result` 가 `.bmp` 입니다 [확인 9차].
    capture_dir_list  capture 이미지 (webp) **와 원본 `.png`** [확인 8차]. **point 마다
                      한 장**이고 이름은 종류 없이 위치 키로 끝납니다(`…_0001.webp`)
                      [확인 9차].

  원본은 **webp 와 이름이 같고 확장자만 다릅니다** — 네 종류 모두 [확인 9차].
  Result 이미지는 위치마다 한 장이고 repeat recipe 도 Site × point 마다 한 장입니다.
  측정 한 건의 webp 는 실측 최대 **133장**(MAP608 `WID_REAL`), 원본까지 189 객체입니다
  [확인 9차]. 그래서 `afm` 은 `msr_image` 처럼 사용자당 5초 50회 요청 제한의 예외입니다
  (backend/__init__.py 의 `_EXEMPT_BLUEPRINTS`, user-confirmed 2026-10-07).
    raw_dir_list      원본 csv / txt

  ⚠ `data_dir_list` 가 비어 있지 않다고 "측정 데이터 있음"이 아닙니다 [확인]. data CSV 가
    없는 측정(MAPC01 의 info 만 있는 측정)도 `detail_information.parquet` **하나**를
    갖습니다. adapter 는 `detail_points.parquet` 이 목록에 있을 때만 `has_data` 를 켭니다.
  ⚠ 원본 TIFF 는 `tiff_dir_list` 에 webp 와 함께 들어 있습니다 [확인]. 확장자는
    **`.tiff`** 입니다 [확인 7차]. **5EAP1501 은 현재 원본이 0개**이지만 초기 적재에서
    빠진 것이고(mirror 에 원본 206개), 다시 적재될 예정입니다 [확인 7차]. 화면의 이미지
    목록에는 webp 만 올리고, TIFF 는 다운로드로만 제공합니다. 원본은 webp 와 이름이
    같고 확장자만 다릅니다 [확인 9차].
  ⚠ **align·tip·capture 의 원본도 각자의 목록에 들어 있고, TIFF 가 아닙니다** — align 은
    `.bmp`, tip 과 capture 는 `.png` 입니다 [확인 8차]. 그래서 adapter 는 확장자를 나열하지
    않고 **`.webp` 가 아닌 것을 모두 원본**으로 보아 이미지 목록과 `has_image`·`has_align`·
    `has_tip` 판단에서 뺍니다. 원본 다운로드는 네 종류 모두에 있습니다 — 이미지 하나의
    원본, 그리고 열린 탭의 원본 전체를 묶은 zip. 원본은 webp 의 이름에서 확장자만 바꿔
    찾습니다.
  ⚠ 예전 요구사항(docs/afm/개발요구.txt)의 `["no files"]` 표지는 **쓰지 않습니다.**
  ⚠ parquet 의 list 열은 `pd.read_parquet` 에서 list 가 아니라 numpy 배열로 돌아옵니다.
  ⚠ 추출에 실패한 측정은 목록에 **들어오지 않습니다** [확인]. "파일이 원래 없음"과
    "추출 실패"는 목록에서 구분할 수 없습니다.

  `recipe_name`·`lot_id` 가 null 인 행은 지금 0건이고, `NA` 라는 글자가 값으로 들어가는
  칸은 없습니다 [확인 9차]. `formatted_date`·`time` 이 null 이 되는 조건은 회신에 없습니다
  [가정].
  규모 [확인 9차, 약 1주일 표본]: MAP608 67행 / 7일 / 하루 16건(최대 30), MAPC01 108행 /
  7일 / 21건(최대 62), 5EAP1501 28행 / 6일 / 11건(최대 12). 3개월치의 크기는 미정입니다.
  보존 3개월은 **측정 시각** 기준입니다.

  측정키 (unique_key) [명세]

    앵커(CSV) 그룹의 전체 6필드 키입니다.

      date#time#recipe#slot#lot#measured          (MAPC01 은 **앞 4필드**)

    예: 261001#070028#NA_NECKING_SLIM#5NNN0336.01#5NNN0336#NA

    파일명(afm_raw_files.txt D2)에서 맨 앞의 `#` 과 7번째 필드(원본 파일명)를 뺀
    것입니다. MAPC01 이 4필드인 까닭은 그 장비의 측정 한 건이 date#time#recipe#slot
    이기 때문입니다(같은 문서 D2).


3. MinIO 객체

  key 패턴 [명세] : 2067928/afm/<TOOL>/<측정키>/<파일명>

    상세    : detail_information.parquet
              detail_summary.parquet
              detail_points.parquet
    profile : profile_<원본이름>.parquet
    이미지  : <파일명>.webp  (Result 는 같은 목록에 원본 TIFF 도 있습니다)

  bucket 은 `user`, `2067928/` 는 minio_handler 의 기본 prefix 와 같은 값입니다. Redis 의
  key 가 이미 그 prefix 를 포함하므로, 읽을 때는 **client 의 prefix 를 비워야** 합니다
  (`MinioObject(prefix="")`). 기본 prefix 를 그대로 두면 `2067928/2067928/...` 가 되어
  전부 404 입니다. 측정키에는 recipe 명이 들어가므로 key 에 공백·괄호가 있을 수 있습니다.

  3.1 상세 — **모든 값이 문자열로 적재됩니다** [확인]

    숫자도 문자열입니다 — 측정값은 `"79.24"`, `Point No` 도 `"1"` 입니다. adapter 는
    단위가 붙은 열(`... (nm)`, `X (um)`)과 `Point No`·`Site X`·`Site Y` 를 숫자로,
    `Valid`·`<측정명>_Valid` 를 bool 로 바꿉니다. 그 밖의 열은 문자열 그대로 둡니다.

    detail_information.parquet
      열은 `name`, `value` 둘입니다(`key` 가 아닙니다). Info 의 한 줄이 한 행입니다.
      빈 값은 **빈 문자열 `''`** 입니다. adapter 는 그것을 null 로 바꿉니다.
      행의 구성은 13키·15키 두 가지입니다(afm_raw_files.txt D3) — adapter 는 key 를
      고르지 않고 적재된 행을 그대로 넘깁니다.
      슬롯은 `Sample Location` 의 값 안에 `Slot N` 꼴로 들어 있습니다. 값 전체는
      **`Port 1 Slot 10`** 꼴이고(MAP608·5EAP1501), MAP608 에서는 `Stage` 도 관측됩니다
      — 그때는 슬롯이 없습니다. **MAPC01 은 Info 에 `Sample Location` key 가 없고**
      슬롯은 `Slot No` 에 있습니다 [확인 9차].
      MAPC01 info CSV 의 Data 섹션에 있는 `FileName` 열(위치 키 매핑)은 **현재 적재에서
      제외**되어 있습니다.

    detail_summary.parquet
      `Site`(method 명) · `ITEM`(MEAN/STDEV/MIN/MAX/RANGE) + 측정 컬럼입니다.
      Summary 가 없는 측정은 **0행짜리 객체가 있습니다(열도 없습니다).** 중단된 측정도
      Summary 가 "없는" 것이 아니라 **빈 block(0행 parquet)** 입니다 [확인 7차].
      data CSV 가 없는 측정(MAPC01 info-only)은 **객체 자체가 없습니다.**
      값은 points 처럼 **문자열**이고, 통계는 **장비가 쓴 값 그대로**입니다(적재할 때
      계산하지 않습니다) [확인 9차]. adapter 는 points 와 같은 변환을 적용합니다.
      한 측정 안에서 두 block 이 같은 method 명을 가진 적은 없습니다 [확인 9차].

    detail_points.parquet
      측정 한 번이 한 행입니다. 열 이름은 raw CSV 그대로이며 **`Point No`, `Site ID`**
      는 이 철자입니다(공백, 밑줄 아님).

      **`Site` 열이 그 행의 block(method 명)입니다.** Summary 의 `Site` 와 같은
      이름이므로 block 은 이 열로 가립니다. 행의 순서나 "같은 point 가 다시 나오면 다음
      block" 같은 추측은 **쓰면 안 됩니다**:
        - repeat recipe 는 **한 block 안에서 같은 point 가 되풀이**됩니다
          (실측: 4 Site × 2 반복 = 8행). 반복 번호를 담은 열은 **없고**, 행은 모든
          Site 를 **한 바퀴 돈 뒤 다시 돕니다** [확인 7차]. 바퀴는 `Sample Count` 로
          구분할 수 있습니다(실측 4 → 5). 반복이 없는 recipe 에서는 `Sample Count` 가
          **한 측정 안에서 바뀌지 않고**(4종 전수), 첫 값은 측정마다 다릅니다(1~47).
          Site ID 가 있어도 반복이 없으면 바뀌지 않습니다(WID_11KEY) — **Site ID 유무는
          반복 여부가 아닙니다** [확인 8차]. profile·이미지는 반복마다 따로 있지 않고
          같은 이름 하나입니다.
        - 측정이 중단되면 **측정하지 못한 point 의 행은 아예 없습니다**(STOPPED 행으로
          채우지 않습니다). `State` 가 STOPPED 인 행은 **중단된 그 point 하나**입니다
          [확인 7차].

      측정하지 못한 칸은 **공백 한 칸 `' '`**, 그때 `<측정명>_Valid` 는 **`''`** 입니다.
      `NaN` 이나 `-` 는 없습니다. adapter 는 둘 다 null 로 내보냅니다(0 이나 False 가
      아닙니다).

      열 이름은 **`Method ID`**(공백)입니다 [확인 7차].
      `Valid` 가 FALSE 인 실물은 **여전히 없습니다**(CSV 263개 전수 0건) [확인 7차].
      그래서 FALSE 의 표기는 모릅니다 [가정: adapter 는 대소문자 무관 `true`/`false`
      만 읽고 나머지는 null]. `Sample Count` 가 무엇을 세는 값인지는 모릅니다.

  3.2 위치 키와 파일명 [확인]

    위치 키 = Site ID 가 있으면 `<Site ID>_<Point No 4자리>`, 없으면 4자리 point 번호.

      0001_X-001_Y-001_0014        (Site ID 있는 recipe)
      0001                         (없는 recipe)

    마지막 4자리는 **그 Site 안의 point 번호**가 맞습니다. profile 과 Result 이미지의
    이름은 `_<위치 키>_Height` 로 끝납니다.

    ⚠ **MAPC01 의 profile·이미지 이름은 `filename` 으로 시작하지 않습니다** — 5번째·
      6번째 필드가 다릅니다. "`filename` 에서 `_Info`·`.csv` 를 뺀 것으로 시작한다"는
      규칙은 MAPC01 에서 깨지므로, 어느 point 의 파일인지는 **이름의 끝**으로만 찾습니다.
      그 두 필드에 무엇이 들어가는지는 회신에 없습니다 [가정: mock 은 lot 을 넣습니다].

    tip 이미지는 `_C_PR`(point 마다)과 `C_Result`(측정마다 한 장)로 끝납니다
    [확인 7차]. `_C_PR` 앞이 위치 키입니다 — Site ID 가 없는 recipe 도 4자리 point
    번호가 들어갑니다(`…_0001_C_PR.webp`) [확인 8차]. 화면은 `_<위치 키>_C_PR` 에서
    point 를 읽고 `C_Result` 는 point 없는 이미지로 둡니다.
    align 은 `1_Result.webp` ~ (측정마다 1~4장, 위치 키 없음), capture 는 `…_0001.webp`
    (종류 없이 위치 키로 끝남, point 마다)입니다 [확인 9차]. 화면은 capture 에서 point 를
    읽고 align 은 point 없는 이미지로 둡니다.

  3.3 Profile [확인]

    X / Y / Z parquet 입니다. 단위(XUnit·YUnit·ZUnit·DataSize·SurfaceSize)는 **MinIO
    객체의 user metadata** 이고 parquet 파일의 metadata 가 **아닙니다.** key 는 소문자로
    저장됩니다 — `x-amz-meta-xunit`, `x-amz-meta-datasize` 등. 그래서 단위는 객체를
    내려받지 않고 stat 한 번으로 읽습니다.

    아래는 2026-10-06 회신입니다 [user-confirmed].

    - 웹의 히트맵이 읽는 것은 **고른 point 하나의 Profile 스캔(D4)** 이고, 원본 txt 를
      적재한 `profile_<원본이름>.parquet` 객체 **하나**입니다. 상세 화면의 Site 지도
      (디바이스 배치)는 이것과 별개로 `detail_points` 의 `Site ID`·`Site X`·`Site Y` 를
      씁니다.
    - 열은 `X` float64 · `Y` float64 · `Z` float64 입니다. Z 는 Height 이고 1D 에서는
      Y 가 0 으로 고정됩니다.
    - Z 는 **원본 그대로**입니다. leveling 을 하지 않고, 값이 없는 표본은 NaN 입니다.
    - 단위는 객체 metadata 에 있고 **파일마다 다르며 통일하지 않습니다.** 예:
      `xunit=MicroMeter`, `yunit=MicroMeter`, `zunit=NanoMeter`. um / nm / pm / Pixel 이
      섞여 있으므로 축 라벨과 값의 해석은 반드시 metadata 에서 읽습니다.
    - 1D / 2D 는 `datasize` 의 `<폭> x <높이>` 로 가릅니다. 높이가 1 이면 웹은 라인
      프로파일로 그립니다.
    - 2D 격자 크기는 `512x64`, `2048x256` 입니다. 5EAP1501 은 profile 자체가 없습니다.
      [가정: 회신은 크기만 나열했습니다. 512x64 가 MAP608, 2048x256 이 MAPC01 이라고
      읽었습니다.]
    - 웹은 표본이 (x, y) 격자를 정확히 채우고 축이 균등 간격일 때 셀로 그리고, 아니면
      실제 좌표에 점으로 그립니다. 이상치 필터를 거친 뒤 count / min / max / mean 을
      보여 줍니다.

    남은 [가정] (OFFICE-VERIFY):
    - metadata 의 단위 **철자**. 위 예는 `MicroMeter`·`NanoMeter` 인데 웹은 받은 글자를
      그대로 축 이름에 씁니다(`um` 만 `μm` 로 바꿉니다). 실제 값이 긴 이름이면 라벨이
      `X (MicroMeter)` 로 나옵니다. 값의 전체 목록이 필요합니다.
    - NaN 이 얼마나 자주, 어떤 모양(흩어진 점인지 줄 단위인지)으로 나오는지.

    ⚠ **2048x256 은 524,288 점**입니다. 표본 하나가 JSON 객체 하나, 차트 요소 하나라서
    그대로 보내면 응답이 수십 MB 가 되고 히트맵을 그리다 탭이 멈춥니다. 그래서 route 가
    `backend/afm/profile_sampling.py` 의 `thin_profile` 로 65,536 점 이하가 되게 행·열을
    같은 간격으로 솎아서 보냅니다(2048x256 → 683x86). 평균을 내지 않고 **골라내기만**
    하므로 Z 는 여전히 원본 값이고 NaN 도 그대로 NaN 입니다. 응답의 `total` 이 파일의
    점 수, `count` 가 보낸 점 수이고, 화면은 둘이 다르면 그 사실을 표시합니다. 통계
    (count / min / max / mean)와 xlsx 내보내기는 **솎은 표본** 기준이므로 한 점짜리
    spike 는 빠질 수 있습니다. 전체 값이 필요하면 원본 파일을 받습니다.

  남은 [가정]: 3개월치가 쌓였을 때 장비 하나의 DataFrame 크기.

      중단되어 파일이 없는 측정(point_count=null)과, 도중에 중단되어 `point_count` 가
      recipe 보다 작은 측정도 mock 에는 없습니다 — mock 의 중단은 뒤쪽 block 뿐입니다.
    - repeat recipe 는 4 Site × 1 point × 2 바퀴(8행, point_count 4)입니다. 실측
      (4 × 14 × 2 = 112행, 56)보다 작습니다.
    - `Mileage` 의 증가 속도(분당 240)와 팁 하나가 4일 유지된다는 것, MCNT 가 아닌
      종류의 폭(70, OMCL-AC160TS 는 7)은 지어냈습니다. `Last Put Back Time` 이 Pick Up
      7분 전이라는 것도 지어냈습니다.

      adapter 가 같은 표로 채웁니다.
    - 이미지는 webp 가 아니라 자리 표시 SVG 입니다.
    - null 인 `slot_number` 와 `Sample Location` 의 `Stage` 를 내지 않습니다. Site 의

      (실측 최대 133장).
