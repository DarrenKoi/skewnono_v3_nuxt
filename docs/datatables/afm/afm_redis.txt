AFM 적재 형태 — Redis 색인 + MinIO 객체 (ETL 이후, 웹이 실제로 읽는 것)

각 AFM 장비의 raw 파일(afm_raw_files.txt)을 ETL 이 적재한 결과입니다. Redis 가 측정
목록과 MinIO 객체 key 를 갖고, 본문(상세·profile·이미지)은 MinIO 에 있습니다.
소비 feature 는 `afm` 이고 adapter 는 backend/afm/providers/office_example.py 입니다.

표기: [명세] = user-confirmed 2026-10-06 (사무실 적재 명세 전달, 5차),
      [확인] = office 확인 2026-10-06 (실제 적재물을 보고 답한 6차 회신),
      [가정] = OFFICE-VERIFY.
회신 원문은 docs/afm/office-data-findings.md, 남은 질문은 docs/afm/to-questionnaire-afm.md 에
있습니다. adapter 자체는 아직 사무실에서 실행해 보지 않았습니다.


공통 규칙 [명세]

  값 직렬화 : pandas `DataFrame.to_parquet()` → bytes.
              예외는 `afm_tool_recipes` 하나이며 JSON 문자열입니다.
  자료형    : 모두 Redis **hash** 입니다.
  hash field: 장비명 문자열입니다 — `MAP608`, `MAPC01`, `5EAP1501`.
              `afm_d1_tools` 만 field 가 `all` 하나입니다.
  갱신 단위 : 장비(field) 하나 = DataFrame 전체를 **통째로 다시 씁니다.**
              행 단위 key 는 없습니다. TTL 도 없습니다.
  갱신 주기 : **30분**입니다. 측정이 끝난 뒤 통상 30분 안에 목록에 나타납니다 [확인].
  읽기      : `hget` → `pd.read_parquet(io.BytesIO(raw))`.
  결측      : **빈 값은 null** 입니다. 웹 응답으로 내보낼 때 NaN 을 null 로 바꿔야
              합니다(그대로 두면 JSON 이 깨집니다).
  쓰기 금지 : 웹은 MinIO 에 **쓰지 않습니다.** 적재는 ETL 만 합니다.
  복구      : Redis 가 유실되어도 MinIO 객체 key 만으로 D2 를 다시 만들 수 있습니다.
  보존      : **3개월**로 확정되었습니다 [확인]. 지울 때 **MinIO 객체를 먼저, Redis 행을
              나중에** 지웁니다. 그 사이에는 목록에는 있는데 객체가 없는 측정이
              생기므로, 웹은 객체가 없는 것을 오류가 아니라 "없음"으로 다룹니다.

  사용 key 4개 [명세 + 확인]:

    afm_d1_tools          장비 목록 (아래 1)
    afm_d2_measurements   측정 이력 (아래 2)
    afm_tool_recipes      recipe 명의 JSON 배열. 측정 검색의 Recipe 필터에 읽어도
                          됩니다. 웹은 아직 읽지 않습니다(목록에서 직접 모읍니다).
                          hash field 가 장비명인지는 회신에 없습니다 [가정].
    afm_download_history  다운로드 이력 parquet. **웹은 읽지 않습니다.**


1. afm_d1_tools — 장비 목록

  hash, field 는 `all` 하나뿐입니다 [명세]. 실제 값 [확인]:

    id        name      fab   alias
    MAP608    MAP608    ''    null
    MAPC01    MAPC01    ''    R3
    5EAP1501  5EAP1501  ''    M15

  - `id` 는 **대문자 그대로**입니다(장비명과 같습니다).
  - `fab` 은 **빈 문자열**입니다. 언제 채워질지는 회신에 없습니다.
  - `alias` 에 들어 있는 값이 fab 이름과 같습니다(MAPC01=R3, 5EAP1501=M15 는
    afm_raw_files.txt D1 의 확인된 대응 그대로이고, fab 을 모르는 MAP608 만 null).
    그래서 adapter 는 `fab` 이 비어 있으면 `alias` 를 fab 으로 씁니다
    [가정: alias 가 fab 을 뜻한다는 것은 Home 의 해석입니다].

  웹 계약 `AfmToolRow` 로는 id→id(소문자로 — 화면의 장비 주소가 소문자입니다),
  name→name·label, fab(없으면 alias)→fab 으로 옮깁니다.

  ⚠ 화면의 장비 목록은 frontend 에 고정된 표(useAfmToolData.ts)를 쓰고
    `/api/afm/tools` 를 부르지 않습니다. 그 표는 MAP608 을 `PKG`(추정)로 묶습니다.


2. afm_d2_measurements — 측정 이력

  hash, field = 장비명(`MAP608`, `MAPC01`, `5EAP1501`) [명세].
  값은 그 장비의 **측정 전체 목록을 DataFrame 하나로** 담은 parquet bytes 입니다.

  열:

    unique_key      측정키. 파일명의 `#` 필드입니다(아래 "측정키"). 장비 안에서 유일 [확인].
    filename        **data CSV 의 원본 파일명 전체**입니다. data CSV 가 없는 측정만
                    info CSV(`..._Info.csv`)의 이름입니다. 장비 안에서 유일합니다
                    (전수 확인, 중복 0건) [확인].
    date            YYMMDD
    formatted_date  YYYY-MM-DD **또는 null**
    recipe_name
    lot_id          MAPC01 도 채워져 있습니다 — 파일명의 `NA` 가 아니라 Info 의
                    `Lot ID` 입니다 [확인].
    slot_number     **Info `Sample Location` 의 `Slot N`** 에서 옵니다(실제 웨이퍼
                    슬롯). 그것을 읽지 못한 측정만 파일명의 `.nn` 꼬리로 채웁니다
                    [확인]. `.nn` 은 슬롯과 다를 수 있습니다 — 5EAP1501 에서 `.05` 와
                    Slot 5 가 맞지 않는 실측이 있습니다. **웹이 파일명에서 슬롯을
                    읽으면 안 됩니다.**
    time            **HHMMSS 6자리** 또는 null. 값 `NA` 도 null 로 취급합니다.
                    파일명의 **첫 시각**이므로 MAP608 에서는 **세션 시작 시각**이고,
                    같은 세션의 측정들이 같은 `time` 을 갖습니다. 측정마다의 시각은
                    측정키의 6번째 필드입니다 [확인].
    measured_info   열은 있으나 **항상 null** 입니다 [확인].
    tool_name       대문자 그대로 [확인].
    fab
    point_count     int **또는 null**

  `tool_id` 열은 **없습니다** [확인]. 계약의 `tool_id` 는 adapter 가 장비명을 소문자로
  바꿔 채웁니다.

  파일 목록 7종 — 모두 list[str] 이고, 원소는 **MinIO 객체 key 전체**입니다
  (prefix `2067928/` 포함). **빈 리스트 = 파일 없음**입니다 [명세].

    data_dir_list     상세 parquet
    profile_dir_list  profile parquet
    tiff_dir_list     Result 이미지(webp) **와 원본 TIFF** [확인]
    align_dir_list    align 이미지 (webp)
    tip_dir_list      tip 이미지 (webp)
    capture_dir_list  capture 이미지 (webp)
    raw_dir_list      원본 csv / txt

  ⚠ `data_dir_list` 가 비어 있지 않다고 "측정 데이터 있음"이 아닙니다 [확인]. data CSV 가
    없는 측정(MAPC01 의 info 만 있는 측정)도 `detail_information.parquet` **하나**를
    갖습니다. adapter 는 `detail_points.parquet` 이 목록에 있을 때만 `has_data` 를 켭니다.
  ⚠ 원본 TIFF 는 `tiff_dir_list` 에 webp 와 함께 들어 있습니다 [확인]. **5EAP1501 은 현재
    원본이 0개**입니다. 화면의 이미지 목록에는 webp 만 올리고, TIFF 는 다운로드로만
    제공합니다. 원본의 확장자와, 어느 webp 의 원본인지 가리는 규칙은 회신에 없습니다
    [가정: webp 와 이름이 같고 확장자만 `.tif`/`.tiff`].
  ⚠ 예전 요구사항(docs/afm/개발요구.txt)의 `["no files"]` 표지는 **쓰지 않습니다.**
  ⚠ parquet 의 list 열은 `pd.read_parquet` 에서 list 가 아니라 numpy 배열로 돌아옵니다.
  ⚠ 추출에 실패한 측정은 목록에 **들어오지 않습니다** [확인]. "파일이 원래 없음"과
    "추출 실패"는 목록에서 구분할 수 없습니다.

  `formatted_date`·`time`·`point_count` 가 null 이 되는 조건, `slot_number` 값의 꼴
  (`05` 인지 `5` 인지)은 회신에 없습니다 [가정].

  측정키 (unique_key) [명세]

    앵커(CSV) 그룹의 전체 6필드 키입니다.

      date#time#recipe#slot#lot#measured          (MAPC01 은 **앞 4필드**)

    예: 261001#070028#NA_NECKING_SLIM#5NNN0336.01#5NNN0336#NA

    파일명(afm_raw_files.txt D2)에서 맨 앞의 `#` 과 7번째 필드(원본 파일명)를 뺀
    것입니다. MAPC01 이 4필드인 까닭은 그 장비의 측정 한 건이 date#time#recipe#slot
    이기 때문입니다(같은 문서 D2).


3. MinIO 객체

  key 패턴 [명세] : 2067928/afm/<TOOL>/<측정키>/<파일명>

    상세    : detail_information.parquet
              detail_summary.parquet
              detail_points.parquet
    profile : profile_<원본이름>.parquet
    이미지  : <파일명>.webp  (Result 는 같은 목록에 원본 TIFF 도 있습니다)

  bucket 은 `user`, `2067928/` 는 minio_handler 의 기본 prefix 와 같은 값입니다. Redis 의
  key 가 이미 그 prefix 를 포함하므로, 읽을 때는 **client 의 prefix 를 비워야** 합니다
  (`MinioObject(prefix="")`). 기본 prefix 를 그대로 두면 `2067928/2067928/...` 가 되어
  전부 404 입니다. 측정키에는 recipe 명이 들어가므로 key 에 공백·괄호가 있을 수 있습니다.

  3.1 상세 — **모든 값이 문자열로 적재됩니다** [확인]

    숫자도 문자열입니다 — 측정값은 `"79.24"`, `Point No` 도 `"1"` 입니다. adapter 는
    단위가 붙은 열(`... (nm)`, `X (um)`)과 `Point No`·`Site X`·`Site Y` 를 숫자로,
    `Valid`·`<측정명>_Valid` 를 bool 로 바꿉니다. 그 밖의 열은 문자열 그대로 둡니다.

    detail_information.parquet
      열은 `name`, `value` 둘입니다(`key` 가 아닙니다). Info 의 한 줄이 한 행입니다.
      빈 값은 **빈 문자열 `''`** 입니다. adapter 는 그것을 null 로 바꿉니다.
      행의 구성은 13키·15키 두 가지입니다(afm_raw_files.txt D3) — adapter 는 key 를
      고르지 않고 적재된 행을 그대로 넘깁니다.
      슬롯은 `Sample Location` 의 값 안에 `Slot N` 꼴로 들어 있습니다(값 전체의
      모양은 회신에 없습니다 [가정]).
      MAPC01 info CSV 의 Data 섹션에 있는 `FileName` 열(위치 키 매핑)은 **현재 적재에서
      제외**되어 있습니다.

    detail_summary.parquet
      `Site`(method 명) · `ITEM`(MEAN/STDEV/MIN/MAX/RANGE) + 측정 컬럼입니다.
      Summary 가 없는 측정은 **0행짜리 객체가 있습니다(열도 없습니다).**
      data CSV 가 없는 측정(MAPC01 info-only)은 **객체 자체가 없습니다.**
      값이 points 처럼 문자열인지는 회신에 없습니다 [가정: 문자열로 보고 같은 변환을
      적용합니다. 숫자여도 그대로 통과합니다].

    detail_points.parquet
      측정 한 번이 한 행입니다. 열 이름은 raw CSV 그대로이며 **`Point No`, `Site ID`**
      는 이 철자입니다(공백, 밑줄 아님).

      **`Site` 열이 그 행의 block(method 명)입니다.** Summary 의 `Site` 와 같은
      이름이므로 block 은 이 열로 가립니다. 행의 순서나 "같은 point 가 다시 나오면 다음
      block" 같은 추측은 **쓰면 안 됩니다**:
        - repeat recipe 는 **한 block 안에서 같은 point 가 되풀이**됩니다
          (실측: 4 Site × 2 반복 = 8행).
        - 측정이 중단되면 **측정하지 못한 point 의 행은 아예 없습니다**(STOPPED 행으로
          채우지 않습니다).

      측정하지 못한 칸은 **공백 한 칸 `' '`**, 그때 `<측정명>_Valid` 는 **`''`** 입니다.
      `NaN` 이나 `-` 는 없습니다. adapter 는 둘 다 null 로 내보냅니다(0 이나 False 가
      아닙니다).

      회신에 없는 것 [가정]: `Method ID` / `Method_ID` 의 철자, `Valid` 가 FALSE 일 때의
      표기(adapter 는 대소문자 무관 `true`/`false` 만 읽고 나머지는 null), repeat 의 반복
      행을 가리는 열과 행의 순서, repeat recipe 의 `point_count` 가 point 수인지 행
      수인지, 중단된 block 에 남는 행의 수.

  3.2 위치 키와 파일명 [확인]

    위치 키 = Site ID 가 있으면 `<Site ID>_<Point No 4자리>`, 없으면 4자리 point 번호.

      0001_X-001_Y-001_0014        (Site ID 있는 recipe)
      0001                         (없는 recipe)

    마지막 4자리는 **그 Site 안의 point 번호**가 맞습니다. profile 과 Result 이미지의
    이름은 `_<위치 키>_Height` 로 끝납니다.

    ⚠ **MAPC01 의 profile·이미지 이름은 `filename` 으로 시작하지 않습니다** — 5번째·
      6번째 필드가 다릅니다. "`filename` 에서 `_Info`·`.csv` 를 뺀 것으로 시작한다"는
      규칙은 MAPC01 에서 깨지므로, 어느 point 의 파일인지는 **이름의 끝**으로만 찾습니다.
      그 두 필드에 무엇이 들어가는지는 회신에 없습니다 [가정: mock 은 lot 을 넣습니다].

    회신에 없는 것 [가정]: align·tip·capture 이미지의 이름 규칙과 장수.

  3.3 Profile [확인]

    X / Y / Z parquet 입니다. 단위(XUnit·YUnit·ZUnit·DataSize·SurfaceSize)는 **MinIO
    객체의 user metadata** 이고 parquet 파일의 metadata 가 **아닙니다.** key 는 소문자로
    저장됩니다 — `x-amz-meta-xunit`, `x-amz-meta-datasize` 등. 그래서 단위는 객체를
    내려받지 않고 stat 한 번으로 읽습니다.

    아래는 2026-10-06 회신입니다 [user-confirmed].

    - 웹의 히트맵이 읽는 것은 **고른 point 하나의 Profile 스캔(D4)** 이고, 원본 txt 를
      적재한 `profile_<원본이름>.parquet` 객체 **하나**입니다. 상세 화면의 Site 지도
      (디바이스 배치)는 이것과 별개로 `detail_points` 의 `Site ID`·`Site X`·`Site Y` 를
      씁니다.
    - 열은 `X` float64 · `Y` float64 · `Z` float64 입니다. Z 는 Height 이고 1D 에서는
      Y 가 0 으로 고정됩니다.
    - Z 는 **원본 그대로**입니다. leveling 을 하지 않고, 값이 없는 표본은 NaN 입니다.
    - 단위는 객체 metadata 에 있고 **파일마다 다르며 통일하지 않습니다.** 예:
      `xunit=MicroMeter`, `yunit=MicroMeter`, `zunit=NanoMeter`. um / nm / pm / Pixel 이
      섞여 있으므로 축 라벨과 값의 해석은 반드시 metadata 에서 읽습니다.
    - 1D / 2D 는 `datasize` 의 `<폭> x <높이>` 로 가릅니다. 높이가 1 이면 웹은 라인
      프로파일로 그립니다.
    - 2D 격자 크기는 `512x64`, `2048x256` 입니다. 5EAP1501 은 profile 자체가 없습니다.
      [가정: 회신은 크기만 나열했습니다. 512x64 가 MAP608, 2048x256 이 MAPC01 이라고
      읽었습니다.]
    - 웹은 표본이 (x, y) 격자를 정확히 채우고 축이 균등 간격일 때 셀로 그리고, 아니면
      실제 좌표에 점으로 그립니다. 이상치 필터를 거친 뒤 count / min / max / mean 을
      보여 줍니다.

    남은 [가정] (OFFICE-VERIFY):
    - metadata 의 단위 **철자**. 위 예는 `MicroMeter`·`NanoMeter` 인데 웹은 받은 글자를
      그대로 축 이름에 씁니다(`um` 만 `μm` 로 바꿉니다). 실제 값이 긴 이름이면 라벨이
      `X (MicroMeter)` 로 나옵니다. 값의 전체 목록이 필요합니다.
    - NaN 이 얼마나 자주, 어떤 모양(흩어진 점인지 줄 단위인지)으로 나오는지.

    ⚠ **2048x256 은 524,288 점**입니다. 표본 하나가 JSON 객체 하나, 차트 요소 하나라서
    그대로 보내면 응답이 수십 MB 가 되고 히트맵을 그리다 탭이 멈춥니다. 그래서 route 가
    `backend/afm/profile_sampling.py` 의 `thin_profile` 로 65,536 점 이하가 되게 행·열을
    같은 간격으로 솎아서 보냅니다(2048x256 → 683x86). 평균을 내지 않고 **골라내기만**
    하므로 Z 는 여전히 원본 값이고 NaN 도 그대로 NaN 입니다. 응답의 `total` 이 파일의
    점 수, `count` 가 보낸 점 수이고, 화면은 둘이 다르면 그 사실을 표시합니다. 통계
    (count / min / max / mean)와 xlsx 내보내기는 **솎은 표본** 기준이므로 한 점짜리
    spike 는 빠질 수 있습니다. 전체 값이 필요하면 원본 파일을 받습니다.

웹 계약에 반영된 것 (backend/afm)

  - `AfmMeasurementRow` 의 `formatted_date`·`time` 은 `str | None`, `point_count` 는
    `int | None` 입니다. `raw_dir_list` 가 있습니다. `measured_info` 는 빈 문자열입니다.
  - 계약의 `*_dir_list` 는 객체 key 가 아니라 그 **basename** 입니다. 화면이 저장
    구조를 알 필요가 없고, 한 측정의 폴더 안에서 이름은 겹치지 않기 때문입니다.
    이름을 key 로 되돌리는 일은 adapter 가 그 측정의 Redis 행에서 합니다.
  - 상세의 data 행은 `Site`(block)를 갖고, 화면은 그 열로 block 을 나눕니다
    (frontend `utils/afmPoints.ts` 의 `blockOf`). 측정하지 못한 칸은 null 입니다.
  - 이미지의 point 는 이름의 끝에서 읽습니다(frontend `imagePoint`).
  - `information` 은 `dict[str, str | None]` 입니다. key 는 적재된 그대로이고(13키·15키),
    빈 값은 null 입니다. 화면은 있는 key 만 보여 줍니다.
  - 이미지 route 는 provider 가 str 을 주면 SVG 로, bytes 를 주면 webp 로 내보냅니다.
    mock 은 자리 표시 SVG 를, office adapter 는 저장된 webp 를 그대로 줍니다.
  - adapter 는 장비 하나의 DataFrame 을 60초 동안 프로세스 안에 둡니다. 상세 화면 한
    번이 같은 hash field 를 여러 번 읽기 때문입니다. 갱신이 30분 주기이므로 충분합니다.
