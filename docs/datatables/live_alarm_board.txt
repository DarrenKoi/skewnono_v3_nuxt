사무실(Office) Redis — 실시간 알람 보드

장비 실시간 알람입니다. 다른 feature 와 달리 **읽기 소스가 원천이 아닙니다.**
Redis 는 사내 alarm API 앞에 놓인 짧은 캐시이고, 화면을 여는 요청이 곧 갱신
트리거입니다. 해당 fac_id 의 캐시가 CACHE_TTL_SEC(20초)보다 오래됐을 때만,
그리고 락을 잡은 요청 하나만 사내 API 를 호출합니다.

  page --(캐시 만료 + 락 획득)--> 사내 alarm API --> Redis 보드 --> 화면
  page --(캐시 유효)--------------------------------> Redis 보드 --> 화면

보는 사람이 몇 명이든 사내 API 호출은 fac_id 당 20초에 한 번이 상한입니다.
아무도 페이지를 열지 않으면 호출은 0 입니다. 예전에는 별도 스케줄러가 15초마다
polling 했으나, 그 방식은 아무도 보지 않는 새벽에도 계속 호출했고 배포 대상이
하나 더 필요했습니다.

조회 함수

  office_utils.live_alarm.get_live_alarms(fac_id) -> pd.DataFrame

  인자는 fac_id 하나뿐입니다. 조회 구간(window)을 지정할 수 없습니다.

Key 구조

  prefix : skewnono:live_alarm
  events : skewnono:live_alarm:{fac_id}:events   (ZSET)
  meta   : skewnono:live_alarm:{fac_id}:meta     (string, JSON)
  lock   : skewnono:live_alarm:{fac_id}:lock     (string, SET NX EX)

  fac_id -> "M16", "R3" 등 대문자 표기의 **fac 단위** 코드입니다.
            fab_name("M16A", "R4")이 아닙니다 — 사내 API 가 fac 단위로 받기
            때문에 캐시도 같은 단위로 잡습니다. M16A/M16B/M16C 가 하나의
            항목을 공유하고, R3/R4 도 하나를 공유합니다.
            R3 는 fac_id 와 fab_name 이 같아지는 유일한 값이라, R3 만으로는
            이 구분이 드러나지 않습니다.
  lock   -> 값은 요청마다 만드는 임의 토큰입니다. 성공하면 토큰이 일치할 때만
            지우고(다른 요청의 락을 지우지 않기 위함), 실패하면 풀지 않고 TTL
            로 만료시켜 재시도 backoff 로 씁니다.

fab 귀속은 Redis 가 아니라 sem_list roster 가 정합니다. 알람 row 에는 fab
컬럼이 없고 EQP_ID 만 있으므로, reader 가 sem_list 에서
EQP_ID -> (fab_name, tool_type) 을 찾습니다. EQP_ID 문자열을 파싱하지 않습니다.
roster 에 없는 EQP_ID 의 알람은 화면에서 빼되 unmatched_count 로 셉니다 —
그냥 버리면 roster 구멍과 조용한 fab 이 똑같아 보이기 때문입니다.

"설정 안 됨" 판정도 roster 가 합니다. 해당 fab 에 그 tool 종류가 하나도 없으면
not_configured 입니다. 예전의 registry SET 은 사라졌습니다 — 사내 API 호출이
fac 단위 하나로 통합되면서, fab 별로 따로 설정할 것이 남지 않았습니다.

events ZSET

  member -> 알람 이벤트 1건의 JSON
  score  -> occurred_epoch (epoch seconds). 갱신 시 한 번만 파싱해 넣습니다.

  ZSET 은 **누적**됩니다. 매 갱신마다 덮어쓰지 않고 더합니다. member 가 정규화
  JSON 이라 같은 이벤트를 다시 넣어도 무해하고, 이렇게 해야 사내 API 가 "지금
  발생 중" 만 돌려주더라도 최근 10분 보드를 만들 수 있습니다.

  OFFICE-VERIFY: get_live_alarms(fac_id) 가 과거 몇 분까지 돌려주는지는 아직
  확인되지 않았습니다. 10분 이상 돌려주면 장애 후 보드가 스스로 복구되고,
  "현재 발생 중" 만 돌려주면 장애 구간만큼 보드에 구멍이 남습니다. 어느 쪽이든
  코드는 동작하지만, 복구 가능 여부가 달라집니다.

이벤트 field

  id -> string: "{eqp_id}|{alid}|{occurred_at}" 조합. 중복 제거 키입니다.
  eqp_id -> string: 장비 ID
  alid -> string: 알람 ID
  alarm_name -> string: 알람 이름
  occurred_at -> string: "YYYY-MM-DD HH:MM:SS+09:00" (offset 명시)
  occurred_epoch -> int: ZSET score 와 같은 값
  recipe_id -> string
  operation_desc -> string
  lot_type_cd -> string

  선택 컬럼이 DataFrame 에서 NaN 으로 오면 빈 문자열로 바꿉니다. 그대로 두면
  str(NaN) 이 "nan" 이라 화면에 그 글자가 찍힙니다.

meta (JSON)

  fetched_at -> 사내 API 조회에 **성공한** 마지막 시각(epoch). 이 값으로 피드가
                살아 있는지 판정합니다. 실패했을 때는 갱신하지 않습니다 —
                데이터가 없는데 최신으로 보이는 상태를 만들지 않기 위해서입니다.

시간 창

  CACHE_TTL_SEC = 20          : 한 번 조회한 결과를 재사용하는 기간
  LOCK_TTL_SEC = 20           : 진행 중 표시 겸 실패 후 재시도 backoff
  BOARD_WINDOW_SEC = 600      : 화면이 보여주는 구간(최근 10분)
  FUTURE_TOLERANCE_SEC = 300  : 미래로 이만큼 넘게 찍힌 이벤트는 버립니다
  PRUNE_SEC = 900             : 이보다 오래된 member 를 삭제
  TTL_SEC = 86400             : key 자체의 만료

  PRUNE_SEC 은 반드시 BOARD_WINDOW_SEC 이상이어야 합니다. 더 짧으면 아직
  화면에 보여주고 있는 이벤트를 지웁니다 — contracts.py 가 import 시점에
  assert 로 검사합니다.

  조회 구간은 [now - BOARD_WINDOW_SEC, now + FUTURE_TOLERANCE_SEC] 입니다.
  상한을 +inf 로 두지 않는 이유는, 상위 시스템 시계가 앞서 있으면 먼 미래로
  찍힌 이벤트 하나가 보드 맨 위에 영구히 고정되기 때문입니다.

시계(clock)

  now 는 Redis 의 TIME 을 씁니다. prune 도 같은 시계를 기준으로 하므로 두 쪽이
  경계에 대해 이견을 가질 수 없습니다. 애플리케이션 서버 시각을 쓰면 두 서버의
  시차만큼 어긋납니다.

연결 설정

  REDIS_HOST / REDIS_PORT / REDIS_PASSWORD (back_dev_home/.env)

  reader 전용 LIVE_ALARM_REDIS_* 변수는 없어졌습니다. 스케줄러와 SKEWNONO 가
  서로 다른 db 에 앉아 조용히 빈 보드가 되는 사고가 원천적으로 불가능합니다 —
  쓰는 쪽과 읽는 쪽이 같은 프로세스이기 때문입니다.
