사무실(Office) OpenSearch index — R3 공정 스텝 계획(plan step)

device-statistics 의 recipe 관련 화면(recipe-statistics, recipe-trend)의 소스입니다.
답하려는 질문은 하나입니다 — **이 device 가 어떤 공정 스텝을, 몇 번째 순서로, 어떤
recipe 로 측정하는가.**

Index -> sknn-planstep-r3

문서 1건 = **(prod_id, oper_seq, samp_seq) 한 스텝** 입니다.

**이 index 는 R3 / 연구개발 전용입니다.** M 계열 양산 fab 의 공정 스텝은 이 index 에
없고 OpenSearch `ebeam_tas_lot_hist` 에서 가져옵니다 —
docs/datatables/ebeam_tas_lot_hist.txt 의 "device-statistics — M fab 스텝" 절을
보십시오. 두 경로의 차이가 커서 어댑터도 갈라집니다.

  구분          R3 (이 문서)              M fab (ebeam_tas_lot_hist)
  키            prod_id = lot_cd+"_BASE"  lot_cd 그대로 (접미사 없음)
  fab field     det_fac_id                fab_id / fab_name
  스텝 이름     oper_desc                 oper_det_desc
  순서          oper_seq, samp_seq        **없음** (event_tm 시간순으로 대체)
  측정 대상     skip_yn == "Y"            최근 3개월 창의 unique oper_det_desc
  파라미터      cdsem_idp_ver (공통)      cdsem_idp_ver (공통)

사용 field (user-confirmed 2026-07-30)

  det_fac_id -> string: fab 대표 코드. 이 index 는 "R3" 단일 값입니다.
                        (device_desc 계열의 fac_id 와 같은 의미이나 이름이 다릅니다.)
  prod_id -> string: 제품 ID. 예 "REXA_BASE".
                     **device code(lot_cd) + "_BASE" 형태입니다.** 접미사 "_BASE" 는
                     해당 device 의 process integration 기본 설정(basic setting)을
                     뜻하며, 제품 이름에 관례적으로 붙습니다. 따라서 device code 는
                     prod_id 에서 "_BASE" 접미사를 떼어 얻습니다.
  oper_id -> string: operation(공정) ID.
  main_oper_id -> string: 대표 operation ID. 여러 sample 스텝이 하나의 main operation
                          아래로 묶입니다.
  main_oper_yn -> string: "Y" | "N". 이 row 가 main operation 인지 여부입니다.
  oper_desc -> string: operation 설명. 화면에 보여주는 스텝 이름입니다.
                       예 "CBL ETCH CD", "ISO PTN CD(E)"
                       (user-confirmed 2026-08-09).
                       공정 접두사(OPER_PREFIX_ORDER — ebeam_tas_lot_hist.txt)로
                       시작해 **띄어쓰기로 이어지는** 문자열이며, 띄어쓰기가
                       여러 번 들어가는 것이 보통입니다. "/" 는 쓰이지 않습니다
                       — 슬래시가 들어가는 것은 recipe_id(full_name) 쪽입니다.
                       이름 전체를 괄호로 감싸지 않습니다. 닫는 괄호는 추가계측
                       꼬리 "CD(E)" 에만 붙습니다.
  oper_seq -> int: operation(공정) 순서.
  samp_seq -> int: sample 순서. 같은 oper_seq 안에서의 측정 순서입니다.
  eqp_id -> string: 장비 ID.
  recipe_id -> string: recipe 식별자. **다른 DB 의 full_name 과 동일한 값**입니다 —
                       cdsem_idp_ver.full_name 과 이 값으로 조인합니다.
                       이름이 "_*CDU"(패턴 — _WCDU/_FCDU/_BCDU …) 또는
                       "_FULL"/"_HALF"/"_MTX" 로 끝나면 CDU·full/half-map·
                       matrix 측정 job 으로, 계측 룰 판정 범위와 point_count
                       outlier 기준선 양쪽에서 제외됩니다. CDU 는 목록이 아니라
                       패턴인 것이 중요합니다 — 앞 글자는 어떤 map 을 재는지를
                       뜻할 뿐이라 종류가 늘 수 있습니다
                       (_WCDU/_FCDU/_FULL user-confirmed 2026-08-04,
                       _HALF/_BCDU/_MTX user-confirmed 2026-08-05
                       — recipe_params.txt).
  bak_eqp_yn -> string: "Y" | "N". 백업 장비 지정 여부입니다.
  bak_eqp_id_lval -> string: 백업 장비 목록을 슬래시로 이어붙인 문자열입니다.
                             예 "MCD018 / MCD018 / ...". 단일 문자열이므로 장비별로
                             쓰려면 분리해야 합니다.
  skip_yn -> string: "Y" | "N". **"Y" 가 현재 측정 중인 스텝입니다** (아래 주의 참고).
  eqp_grp_id -> string: 장비 그룹 ID. 예 "G-MCD-01".
  reticle_id -> string: 레티클 ID.
  chg_tm -> string: 변경 시각. 예 "2025-07-17T12:26:01" — offset 없는 KST
                    wall-clock 입니다.

조회 방법 (device-statistics 기준)

1. device code(lot_cd)에 "_BASE" 를 붙여 prod_id 를 만들고 그 값으로 스텝을
   가져옵니다. 반대로 index 에서 device 목록을 얻을 때는 prod_id 에서 "_BASE" 를
   떼어냅니다.
2. **prod_id -> oper_seq -> samp_seq 순서로 정렬**합니다(user-confirmed
   2026-07-31). 뒤의 두 값이 공정 흐름의 순서이고, 맨 앞의 prod_id 는 여러
   device 를 한 번에 질의할 때 device 별 스텝이 뒤섞이지 않게 합니다. 문서 반환
   순서에 의존하면 안 됩니다.
3. **skip_yn != "Y" 로 걸러 skip 되지 않은 스텝**의 oper_desc 와 recipe_id 를
   얻습니다. 아래 ★ 절을 반드시 먼저 읽으십시오 — `== "N"` 이 아닙니다.
4. 파라미터 개수(para_*)는 이 index 에 없습니다. 3번에서 얻은 recipe_id 를
   cdsem_idp_ver 의 full_name 과 조인해 **가장 높은 version** 문서의 parameters 에서
   구합니다 (docs/datatables/idp_ver.txt 참고).

즉 device-statistics 의 office 경로는 3-hop 입니다.

    r3_device_grp (Redis)           -> lot_cd
      + "_BASE"                     -> prod_id
    sknn-planstep-r3 (OpenSearch)   -> prod_id/oper_seq/samp_seq 정렬,
                                       skip_yn != "Y" -> oper_desc, recipe_id
    cdsem_idp_ver (OpenSearch)      -> full_name == recipe_id, 최신 version
                                       -> parameters -> para_* 집계

★ skip_yn — "Y" 만 제외하고 판정은 반드시 != "Y" (user-confirmed 2026-07-31)

이름 그대로 **"Y" 가 skip(측정하지 않음)** 입니다. 그리고 값은 **세 가지**입니다 —
"Y", "N", 그리고 **빈 값**(둘 다 아님). 따라서 "측정 중인 스텝" 을 고르는 조건은

    skip_yn != "Y"        (O)
    skip_yn == "N"        (X — 빈 값인 스텝이 통째로 사라집니다)

입니다. 긍정 비교로 쓰면 빈 값 스텝이 조용히 빠지고, 그 손실은 예외가 아니라
"숫자가 좀 작다" 로만 나타나 발견이 아주 늦습니다.

정정 이력: 2026-07-30 에 이 문서는 **"Y 가 현재 측정 중"** 이라고 기록했습니다.
2026-07-31 에 철회되었습니다 — 반대였습니다. 이 극성은 avail_recipe 와
mother_normal 버킷을 동시에 뒤집으므로 어댑터와 mock 양쪽에서 각각 함수
하나(`_is_measuring`)로 모아 두었습니다. 다시 뒤집지 마십시오.

사무실 실행으로 재확인할 때는 scripts/probe_planstep_r3.py 의 skip_yn 분포와
recipe_id 채움 비율을 함께 봅니다. "Y"/"N" 두 버킷의 합이 전체 문서 수보다 작으면
그 차이가 빈 값입니다.

화면의 네 버킷 — 스텝을 어떻게 나누는가 (user-confirmed 2026-08-04)

recipe-statistics / recipe-trend 화면(comparison.vue)은 스텝을 네 버킷으로 나눠
보여줍니다. 이 index 에 버킷 컬럼이 있는 것이 아니라 **스텝 이름과 recipe 이름에서
어댑터가 파생**합니다.

  all            모든 Step. Full job 과 Sample job 을 함께 포함합니다.
  only_normal    skip 되지 않은(skip_yn != "Y") Step 중 스텝명 끝이
                 **순수한 CD** 인 것.
                 "CD(E)", "CD(F)", "CD(BENDING)" 처럼 괄호가 붙으면 제외합니다.
                 실제 스텝명은 "CBL ETCH CD" 처럼 띄어쓰기로 이어지고 추가계측만
                 "ISO PTN CD(E)" 처럼 괄호로 닫히므로, 닫는 괄호를 벗긴 뒤 마지막
                 토큰이 정확히 "CD" 인지로 판별합니다.
                 괄호 꼬리는 한 글자(E/F)만이 아니라 **단어**일 수 있습니다 —
                 "CD(BENDING)" 이 확인된 예입니다 (user-confirmed 2026-08-05).
                 판별 규칙이 꼬리의 길이를 가정하지 않는 것이 그래서 중요합니다.
  mother_normal  only_normal 과 **같은 스텝 필터**를 쓰고, 거기서 **mother
                 파라미터를 1개 이상 가진 recipe** 만 남깁니다. para_16/13/9/5
                 집계도 mother 파라만 셉니다.
                 이 버킷은 스텝을 더 좁히는 것이 아니라 **한 단계 아래(파라미터)로
                 들어갑니다** — CONTEXT.md 의 "mother_normal = Main(Mother 파라
                 view)" 가 그 뜻입니다. mother 판별은 이 index 가 아니라 idp
                 쪽입니다 (아래 "mother_para 출처" 참고).
  only_sample    **recipe 이름**이 "_S" 또는 "SE" 로 끝나는 Step. 축이 스텝명이
                 아니라 recipe 이름인 것이 핵심이며, 끝자리 고정(anchored)이어야
                 합니다 — 이름 어디든 "SE" 를 찾으면 PHASE/BASE/SET 같은 평범한
                 단어까지 Sample 로 잡힙니다. 스텝 코드(괄호 앞)로 판단하면
                 오검출이 생긴다는 담당자 확인이 있었습니다.

only_normal / mother_normal 은 skip 을 **멤버십에서** 거르므로, 이 두 버킷의
avail_recipe 는 항상 total_recipe 와 같습니다. all / only_sample 에서만 두 값이
갈립니다 (user-confirmed 2026-08-04).

정정 이력 (2026-08-04): 2026-07-31 기록은 only_normal 을 "스텝명에 CD 가 포함된
Step" 으로, mother_normal 을 "skip 되지 않은 순수 CD 스텝" 으로 적었습니다. 둘 다
틀렸습니다 — 전자는 "CD(E)"/"CD(F)" 인 **추가계측까지 Main 으로** 셌고, 후자는
mother 파라미터를 전혀 보지 않았습니다. 두 버킷은 같은 스텝 필터를 공유하며
mother 로만 갈립니다.

mother_para 출처 — 해결됨 (office 확인 2026-08-10)

  Mother_Para 는 **파라미터 1개당 bool** 입니다 (docs/datatables/recipe_idp.txt,

    cdsem_idp_ver.raw_data     -> parameter 별 row. **Mother_Para 가 여기 있습니다**
    cdsem_idp_ver.parameters   -> {name: point_count}. mother 를 담을 자리가 없음
    장비 FTP 의 {idp_name}.idp -> 같은 값의 원본 (recipe 1건당 파일 1개)

  2026-08-04 기록은 FTP 파일이 "유일한 확인된 출처" 라고 적었습니다. 틀렸습니다 —
  같은 index 의 다른 field 를 아무도 열어 보지 않았을 뿐입니다. device 4000개 ×
  recipe 100~200개 규모에서 FTP 를 못 쓰는 것은 그대로이지만, 이제 그 경로가
  필요 없습니다. 자세한 형태와 payload 주의는 docs/datatables/idp_ver.txt 의
  "raw_data — mother 의 출처" 절에 있습니다.

  어댑터는 플래그를 **읽지 못한 경우**와 **읽었는데 True 가 하나도 없는 경우**에
  각각 다른 경고를 남기고, 두 경우 모두 이 버킷을 비웁니다 (규칙을 그대로 적용한
  결과입니다 — only_normal 로 슬쩍 대체하면 요약은 숫자를 내는데 health 는 판정할
  파라미터가 없어 0/0 이 되는, 두 표면이 어긋난 화면이 됩니다).

한 device 의 문서 수 — 2000건을 넘습니다 (office 확인 2026-08-10)

device RJ1B(prod_id "RJ1B_BASE")가 어댑터의 2000건 상한에 걸려 화면에
upstream_data_error 로 떨어졌습니다. 즉 **한 device 의 plan step 문서는 최소
2000건** 입니다.

이 숫자가 "device 당 recipe 100~200" 과 어긋나 보이는 것이 요점입니다. 이 index 의
문서 1건은 **측정 recipe 가 아니라 plan step** 이고, 한 device 의 공정 계획에는
skip_yn == "Y" 인 스텝과 같은 recipe 를 재사용하는 스텝이 함께 들어 있어 문서 수가
recipe 수보다 한 자리수 배 많습니다. mock(providers/recipe_population.py)은 스텝과
recipe 를 1:1 로 만들어 device 당 175~200 개만 내므로, 이 축에서 mock 은 실물보다
열 배 좁습니다.

어댑터의 상한은 2000 -> 10000(OpenSearch `index.max_result_window` 기본값)으로
올렸습니다. 단발 search 로 가져올 수 있는 천장이 거기라 **숫자를 더 올리는 것으로는
다음 번을 넘길 수 없고**, 10000 을 치면 search_after 페이지네이션이 필요합니다.

아직 모르는 것: 실제 최대 문서 수, 그리고 2000+ 가 정상 계획 크기인지 아니면
(oper_seq, samp_seq) 가 중복 적재된 것인지. `scripts/probe_planstep_r3` 의 [4]
단계가 device 별 문서 수를 출력하므로 사무실에서 한 번 확인하십시오.

주의 — mock 과 다른 점

- **문서 수 규모**: 위 절 참고. mock 은 device 당 175~200 스텝, 실물은 2000+ 입니다.
- **skip_yn 값 도메인**: 이 index 는 "Y"/"N"/**빈 값** 세 가지이고,
  mock(providers/statistics.py)은 과거 "Yes"/"No" 두 가지만 생성했습니다. mock 은
  2026-07-30 에 "Y"/"N" 으로, 2026-07-31 에 빈 값까지 섞도록 맞췄습니다 — 빈 값을
  만들지 않으면 `== "N"` 으로 잘못 쓴 코드가 집에서는 멀쩡히 통과합니다.
- **키 축**: 계약(RecipeInfoRow)은 lot_cd 로 키를 잡지만 이 index 에는 lot_cd 컬럼이
  없습니다. prod_id 에서 접미사를 떼어 lot_cd 를 만들어야 합니다.
- **fac_id 이름**: 계약은 fac_id, 이 index 는 det_fac_id 입니다.
- 계약에 대응이 없는 field: main_oper_id, main_oper_yn, bak_eqp_yn,
  bak_eqp_id_lval, eqp_grp_id, reticle_id. 화면이 필요해지면 계약을 넓히면 됩니다.

표기 규칙

string field 의 정확 일치·집계는 mapping 이 analyzed text 인 경우 `.keyword`
subfield 를 써야 합니다(prod_id.keyword, recipe_id.keyword 등). 실제 mapping 은
사무실에서 확인합니다 — probe 스크립트가 field 별로 어느 쪽을 써야 하는지 출력합니다.
