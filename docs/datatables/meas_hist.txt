스큐보아와 측정 이력 확인 화면에서 사용할 측정 이력 mock data
pd.DataFrame 기준으로 한 row는 "장비가 특정 lot에 특정 recipe를 실행한 1회 측정 이력"입니다.

Recipe 검색(recipe-search)은 이 측정 이력 row를 기본 검색 대상으로 사용하지 않습니다.
Recipe 검색에서는 Redis에서 받은 recipe_name 문자열 목록만 검색하고, 상세 열람은 recipe_idp.txt 구조를 사용합니다.
스큐보아에서는 MSR 존재 여부, align 결과, 측정 시간으로 측정 상태를 판단합니다.

Column -> Type: Value 설명

id -> string: mock row 고유 ID = msr
fac_id -> string: fab 대표 코드. 예: M10, M11, M14, M15, M16, R3
                  (M12는 실재하지 않습니다 — sem_list.txt 참조, user-confirmed 2026-08-03)
fab_name -> string: 실제 화면에서 선택하는 fab 이름. 예: M16A, M16B, R3, R4
vendor_nm -> string: 장비 vendor. HITACHI, AMAT
eqp_id -> string: 장비 ID. sem-list mock data의 eqp_id와 같은 형식을 사용
eqp_model_cd -> string: 장비 모델. 예: CG6300, CG6380, TP4000, VERITYSEM_5
lot_cd -> string: 디바이스/개발 lot 코드. R3/R4는 r3_device_grp, M fab은 device_desc 형식을 따름
lot_id -> string: 실제 측정 lot ID. lot_cd + 숫자 suffix로 생성. 예: RAEA240031, 4MJ240882
class_name -> string: recipe class 또는 layer group. 예: ADI, AEI, OVL, GATE, CNT, QC, DEF, EDGE
recipe_name -> string: recipe 파일명 기준 이름. 예: ADI_CD_BIAS_001, QC_DAILY_MATCH_007
full_name -> string: class_name/recipe_name 조합. 예: ADI/ADI_CD_BIAS_001
timestamp -> datetime64[ns]: 측정 대표 시각. 화면 정렬 기준으로 쓰며 보통 end_time과 같은 값
start_time -> datetime64[ns]: 측정 시작 시각
end_time -> datetime64[ns]: 측정 종료 시각
meastime -> int64: 측정 소요 시간. 단위는 second이며 end_time - start_time 값
msr -> string: MSR raw data 식별자. 예: 20260428_ADI_CD_BIAS_001_RAEA240031_ECXDX123
msr_check -> string: MSR 파일 존재 여부. Yes, No
align_fail -> string: align 결과. Pass, Fail, NA
total_images -> int64: 측정 대상 image 전체 개수
fail_images -> int64: 실패 image 개수
fail_ratio -> float64: fail_images / total_images 를 백분율로 나타낸 값. 0.0 ~ 100.0 (4.57 은 4.57%)
idp_name -> string: recipe idp 파일 경로. 예: /Recipe/ADI/ADI_CD_BIAS_001.idp
idw_name -> string: recipe idw 파일 경로. 예: /Recipe/ADI/ADI_CD_BIAS_001.idw
minio_msr -> minio에 msr data 원본 저장 경로 
minio_pkl -> minio에 msr 후처리 된 pkl 저장 경로

Mock data 생성 규칙

1. eqp_id, eqp_model_cd, vendor_nm, fac_id, fab_name은 sem-list mock data에서
   먼저 고른 장비 row를 기준으로 복사합니다. 지어내지 않습니다. 생성 순서는
   장비 → lot → recipe 이며, lot은 그 장비가 선 fab(fac_id)의 것만 고릅니다.
   sem_list mock은 eqp_id가 중복될 수 있으므로 첫 행이 이기도록 dedupe합니다.
2. tool_type은 장비 모델로 결정합니다. CG, GT 계열은 cd-sem, TP 계열은 hv-sem으로 둡니다.
3. lot_cd는 fac_id와 맞게 생성합니다. R3/R4는 r3_device_grp의 lot_cd처럼 R로 시작하는 4자리 코드, M fab은 device_desc처럼 숫자 또는 알파벳 prefix를 포함한 3~4자리 코드로 둡니다.
4. lot_id는 lot_cd가 앞에 보이도록 생성합니다.
5. full_name, idp_name, idw_name은 같은 class_name과 recipe_name에서 파생합니다. recipe 변수명을 따로 만들지 말고 recipe_name을 기준으로 만듭니다. fullname = f"{class_name}/{recipe_name}" 형태를 가집니다.
6. timestamp는 최근 180일 안에서 생성합니다. (장비별 뷰가 90일 조회를
   지원하므로 60일로는 부족합니다.) meastime은 end_time - start_time입니다.
   timestamp는 기본적으로 end_time과 같게 둡니다. meastime은 recipe baseline
   × fab 배수 × 장비 speed × jitter 로 만들며, 장비 항이 있어야 장비별
   TAT 지수가 잡음이 아닌 신호가 됩니다.
7. msr은 날짜, recipe_name, lot_id, eqp_id를 포함해서 unique하게 만듭니다.
8. msr_check가 No이면 측정 raw data가 없는 상태이므로 스큐보아에서 문제가 있는 row로 보여줄 수 있어야 합니다.
9. align_fail이 Fail이거나 msr_check가 No이면 fail_ratio를 높게 생성합니다. 정상 row는 보통 0 ~ 15% 범위, 문제 row는 15 ~ 80% 범위로 둡니다.
10. fail_images는 int(total_images * fail_ratio / 100)으로 계산하고, fail_ratio는 최종적으로 fail_images / total_images * 100으로 다시 계산합니다.

검색/화면 사용 기준

Recipe 검색 기본 검색 대상: Redis recipe_name 문자열
스큐보아 기본 판단 대상: msr_check, align_fail, total_images, fail_images, fail_ratio, meastime, timestamp
공통 필터 후보: fac_id, fab_name, tool_type, eqp_model_cd, lot_cd, class_name

  eqp_ip        -> text

사무실 사용 주의사항

1. text field 는 tokenize 되므로 exact match/aggregation 은 반드시 .keyword
   서브필드를 사용합니다 (class_name.keyword, recipe_name.keyword,
   full_name.keyword, fab_name.keyword, eqp_id.keyword).
2. mock 과 달리 OpenSearch 문서에는 lot_cd, tool_type, vendor_nm, id 컬럼이
   없습니다. tool_type 은 index(alias) 로 구분하고, lot_cd 는 별도 소스에서
   해결합니다(아래 device 카탈로그 참고).
3. recipe TAT 집계는 raw row 를 내려받지 않고 서버측 aggregation 으로
   계산합니다: ranking = composite(full_name.keyword) 를 after_key 로 전체
   페이지 순회(+ sum(meastime), top_hits 서브집계) 후 Python 에서 정렬 —
   terms 집계는 size 상한에서 잘리고 sum 정렬 시 근사치라 사용하지 않음,
   summary = sum(meastime)+value_count(meastime)+cardinality(full_name.keyword),
   daily-trend = date_histogram(day, extended_bounds 로 빈 날 0 채움).
   /devices 의 lot_id 집계도 동일하게 composite 전체 순회입니다(top-N 없음).
4. anchor(날짜 선택 상한) = 두 alias 전체의 max(timestamp). recipe_tat 과
   fail_issue office adapter 가 공유 모듈(_office_meas_hist.py)의 캐시된
   anchor 를 함께 사용하므로 recipe-status 페이지의 탭 간 데이터 기준
   날짜가 항상 일치합니다.
5. fail_issue 집계도 raw row 없이 서버측 aggregation 으로 계산합니다:
   align fail = term(align_fail.keyword == "Fail") filter 집계
   (NA 는 별도 filter 집계), meas fail = range(fail_ratio > 15.0,
   MEAS_FAIL_THRESHOLD — YAML 계약 고정값) filter 집계.
   ranking = composite(full_name.keyword) 전체 순회 후 fail 0건 recipe 는
   제외(triage 테이블), (fail count, fail rate) 내림차순 정렬.
   sample_eqp_ids 는 fail filter 집계 안의 terms(eqp_id.keyword) — mock 과
   동일하게 "실패한 row 의 장비"만 샘플링. meas ranking 의 avg_fail_ratio
   는 전체 그룹 대상 avg(fail_ratio) (실패 subset 만의 평균이 아님).
   /devices = composite(lot_id.keyword) + align/meas filter 집계를 bridge 로
   lot_cd 별 roll-up, align+meas 합산 fail 순 정렬.
6. meas_hist feature(측정 이력 검색, raw row) office 전략: 문서에 없는
   4개 계약 필드는 조회 시 파생 — id = msr, tool_type = 검색한 alias
   (양쪽 검색 시 hit 의 _index 이름에서 cdsem/hvsem 판별), lot_cd = bridge
   매핑(미매핑은 "" 로 표기, row 는 버리지 않음), vendor_nm = eqp_model_cd
   prefix 파생(VERITY* → AMAT, 그 외 → HITACHI). retention 60일 창은
   anchor(max timestamp) 기준. 페이지네이션은 from/size + track_total_hits
   (from+size ≤ 10000 = index.max_result_window). recipe 필터는
   recipe_name/full_name .keyword 에 case_insensitive wildcard(*단편*).
   ★ 적재(ingestion) 선행 조건: q 자유 검색은 search_all wildcard 필드
   (meas_hist/opensearch_query.py 의 SEARCH_ALL_MAPPING +
   build_search_all_value) 를 loader 가 색인해야 동작 — 필드가 없으면
   q 조건은 아무 문서도 매칭하지 않습니다(에러는 아님).

device 카탈로그(디바이스별 화면)용 lot_cd 해결

- meas_hist_* 에는 lot_cd 가 없습니다. 현재 생산 중인 device 목록은 아래
  두 소스를 join 해서 만듭니다.
  - Redis "device_desc" DataFrame -> lot_cd 카탈로그(메타데이터).
  - OpenSearch "ebeam_tas_lot_hist" index 의 최근 60일(event_tm) unique
    lot_cd -> "현재 생산 중" 판단(오래된 lot_cd 제거).
  자세한 스키마는 device_desc.txt, ebeam_tas_lot_hist.txt 참고.
