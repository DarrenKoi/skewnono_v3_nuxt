사무실(Office) OpenSearch index — 팹 시스템 측정 이력(lot 단위 이력)

recipe_tat 등 대시보드에서 "현재 생산 중인 device(lot_cd)" 목록을 만드는 데
사용합니다. device_desc(Redis) 는 폐기된 lot_cd 까지 모두 담고 있으므로, 최근
활동이 있는 lot_cd 만 이 index 로 걸러냅니다.

Index -> ebeam_tas_lot_hist

핵심 사용 field
  event_tm -> date: 이벤트 시각. 기간(range) 필터 기준 time_field
  lot_id   -> 개별 lot ID. meas_hist_* 문서의 lot_id 와 동일 체계 —
              meas_hist 에는 lot_cd 가 없으므로 이 index 가 유일한
              lot_id <-> lot_cd 변환 다리(bridge)입니다.
  lot_cd   -> 측정된 lot 의 device 코드. unique 목록이 "현재 생산 중" 집합.
              **여기에는 prod_id 나 "_BASE" 접미사가 없습니다** — sknn-planstep-r3
              와 달리 lot_cd 가 그대로 들어 있어 변환이 필요 없습니다.

공정 스텝 field (user-confirmed 2026-07-30)

  fab_id       -> string: fab 대표 코드. **upstream 이 쓰는 이름**입니다.
                          우리 코드에서 fab_id 는 금지된 오칭이라 fab_name 으로
                          바꿔 왔지만(storage/recipe_tat/fail_issue/pm_planning),
                          그 규칙은 우리 필드 이름에 대한 것입니다. 이 index 가
                          저장하는 이름은 fab_id 이므로 질의할 때는 이 이름을
                          그대로 씁니다.
  fab_name     -> string: fab 세부 표현. fab_id 보다 granular 합니다
                          (예: fab_id M16 <-> fab_name M16A/M16B/M16C).
                          우리 화면의 granular 필터 기준 키입니다.
  main_oper_id -> string: 대표 operation ID.
  oper_id      -> string: operation(공정) ID.
  oper_det_desc -> string: operation 상세 설명. **M fab 스텝 이름의 소스**입니다
                           (R3 의 oper_desc 에 대응).
  eqp_id       -> string: 장비 ID.
  recipe_id    -> string: recipe 식별자. 다른 DB 의 full_name 과 동일 체계이므로
                          cdsem_idp_ver.full_name 과 조인할 수 있습니다.

주의: **이 index 에는 공정 순서(sequence)가 없습니다.** R3 의 sknn-planstep-r3 는
oper_seq / samp_seq 를 갖지만 여기에는 대응 field 가 없습니다. 따라서 M fab 스텝은
순서로 정렬할 수 없고, 필요하면 event_tm 으로 시간순을 대신 씁니다.

조회 방법(recipe_tat office adapter 기준)

1. ops_store 의 OSSearch.range_dataframe_all(time_field="event_tm", days=60)
   로 최근 60일 구간을 DataFrame 으로 받습니다.
2. lot_id -> lot_cd 매핑(dict)을 만듭니다. 이 bridge 가 /devices 집계
   (meas_hist 를 lot_id 로 집계 후 device 로 roll-up)와 lot_cd 드릴다운
   (선택한 lot_cd -> lot_id 집합 -> terms(lot_id.keyword) 필터)을 지탱합니다.
3. lot_cd 컬럼의 unique 값이 "현재 생산 중" device 집합입니다 — 최근 60일
   window 에 없는 lot_id 는 매핑이 없어 자연히 탈락합니다.
4. 이 집합을 Redis "device_desc"(그리고 R3 는 r3_device_grp)와 join 해서
   화면에 표시할 device 메타데이터를 붙입니다.
5. lot_cd 별 row 수는 최근 60일 활동량(activity count)으로 쓸 수 있습니다.

주의: 이 index 는 measurement 단위로 매우 클 수 있습니다. unique lot_cd 만
필요하다면 lot_cd.keyword 에 대한 terms aggregation 이 전체 row 를 내려받는
range_dataframe_all 보다 가볍습니다(인덱스 규모에 따라 선택).

조회 방법(device-statistics — 카탈로그 필터, user-confirmed 2026-08-04)

recipe_tat 과 같은 이유로 device-statistics 의 device 목록(r3-device-grp /
device-desc 응답)도 이 index 로 거릅니다 — Redis 카탈로그는 폐기된 lot_cd 까지
담고 있으므로, 최근 90일 창(아래 스텝 조회와 같은 창)의 unique lot_cd 와
교집합을 취해 "현재 생산 중" 만 목록에 남깁니다. 구현은
back_dev_home/ebeam/cdsem/device_statistics/providers/office_example.py 의
_active_lot_cds 입니다. meas_hist 화면의 device 목록과 같은 원천이라 두 화면의
집합이 어긋나지 않습니다. 60일(recipe_tat)과 90일(device-statistics)은 근거가
달라 상수를 공유하지 않습니다.

같은 집계의 doc_count 가 곧 lot_cd 별 측정 건수(활동량)입니다 — 위 L52 의
activity-count 용법. device-statistics 의 GET /meas-activity 가 fab_id term
+ 90일 창으로 좁힌 이 순위를 meas_count 내림차순으로 내려 주고, 화면의
빠른 필터 "측정 상위 N"(10/25/50)이 그것을 소비합니다 (user-confirmed
2026-08-04). OFFICE-VERIFY: R3 문서의 fab_id 값이 "R3" 인지 첫 실행에서
확인 — 아니면 R3 순위만 빈 배열이 됩니다.

조회 방법(device-statistics — M fab 스텝, user-confirmed 2026-07-30)

device-statistics 의 공정 스텝 소스는 fab 계열에 따라 **둘로 갈립니다**.

  R3 / 연구개발 -> sknn-planstep-r3      (docs/datatables/planstep_r3.txt)
  M 계열 양산   -> ebeam_tas_lot_hist    (이 문서)

M fab 경로는 다음과 같습니다.

1. **최근 3개월**(약 90일) 구간을 event_tm 으로 자릅니다. recipe_tat 의 60일과
   다른 창이므로 상수를 공유하지 마십시오. 3개월을 쓰는 근거는 "그 안에는 fab 에서
   최소 한 번의 공정이 돌았을 것" 이라는 가정입니다 — 이 창을 좁히면 스텝이 통째로
   비는 device 가 생깁니다.
2. fab_id 로 대상을 좁힙니다.
3. lot_cd 별로 **oper_det_desc 의 unique 값**을 모읍니다. 이것이 그 device 의
   공정 스텝 목록입니다. 순서 field 가 없으므로 정렬 기준은 없고, 필요하면
   event_tm 시간순으로 대신합니다.
4. 각 스텝의 recipe_id 를 함께 가져옵니다. 파라미터 개수는 R3 와 동일하게
   recipe_id -> cdsem_idp_ver.full_name 최신 version 의 parameters 에서 구합니다
   (docs/datatables/idp_ver.txt).

주의 — payload. 3개월 × measurement 단위이므로 전체 row 를 내려받는 방식은
위험합니다. "lot_cd 별 unique oper_det_desc" 는 nested terms aggregation
(lot_cd.keyword -> oper_det_desc.keyword)으로 구하는 것이 range_dataframe_all
보다 훨씬 가볍습니다. 위의 60일 경고가 90일에서는 그만큼 더 강하게 적용됩니다.

스텝 정렬 — 공정 접두사 순서 (user-confirmed 2026-07-30)

순서 field 가 없으므로 oper_det_desc 앞머리의 공정 접두사로 정렬합니다. 확정된
순서는 다음이며, 구현은 back_dev_home/ebeam/cdsem/device_statistics/oper_order.py
(`OPER_PREFIX_ORDER`, `sort_oper_descs`)에 있습니다.

    ISO, CW, BG, MBO, BLC, POM, PRW, NW, GT, CBL,
    SNC, M0C, SNC2, SN, ILD, M2, M2C, M3, M4, RDL

    예: "SNC2(CELL OPEN ETCH CLN CD)" -> 접두사 "SNC2"

주의 — **longest-prefix** 로 매칭해야 합니다. 목록에 SNC / SNC2 / SN 이 함께 있고
M2 / M2C 도 함께 있어서, 앞에서부터 startswith 로 처음 맞는 것을 고르면 "SNC2..."
가 SNC 나 SN 으로 잡혀 엉뚱한 자리에 놓입니다. 예외 없이 순서만 조용히 틀리므로
발견이 늦습니다. 프론트엔드 파라미터 타입 파생(EDGE_EX > EDGE)과 같은 함정입니다.

주의 — 목록에 없는 접두사는 버리지 않고 맨 뒤로 보냅니다(`UNKNOWN_RANK`). 새 공정이
생겼을 때 화면에서 스텝이 사라지는 것이 가장 나쁜 실패입니다. `unknown_prefixes()`
가 미등록 접두사를 돌려주므로 목록 갱신 시점을 알 수 있습니다.

★ **화면 표기 의무.** 이 순서는 근사입니다 — 실제 공정 순서는 **tool 마다 다릅니다**.
따라서 이 정렬을 쓰는 화면은 **"운영 공정 순서를 반영하지 않는다"** 는 것을 반드시
명시해야 합니다. 명시하지 않으면 사용자가 화면 순서를 실제 공정 순서로 신뢰하게
되고, 그것은 이 데이터가 보장하지 않는 주장입니다.

주의 — 계약 공백. RecipeInfoRow 는 oper_seq / samp_seq 를 요구하지만 이 index 에는
그 값이 없습니다. 위 접두사 순서로 합성하는 것이 현재 계획이며(oper_seq 는 접두사
rank, samp_seq 는 그 안에서의 일련번호), 확정 전까지는 OFFICE-VERIFY 입니다.
