사무실(Office) OpenSearch — 장비 정비(BM/PM) 실적 + 계획

BM/PM 화면 하나가 index 두 개를 함께 읽습니다. 조회하는 어댑터도
providers/bm_pm 하나이므로 스키마 문서도 하나로 둡니다.

  fab_inform_notes      -> 실제로 일어난 정비(실적). 구간 = down_dt ~ equp_dt
  tool_maintenance_plan -> 앞으로 할 정비(계획). 구간 = tool_start_tm ~ tool_end_tm

두 index 는 짝을 이루므로, 같은 timeline 에 올릴 때 어느 쪽이 계획이고 어느 쪽이
실적인지 시각적으로 구분해야 합니다.

########################################################################
[1] fab_inform_notes — 정비 실적 및 엔지니어 작업 note
########################################################################

장비가 down 된 시점부터 up 될 때까지의 정비(BM/PM) 이벤트 한 건이 문서 한 개
입니다. 정비 사유·조치 내용은 엔지니어가 직접 작성한 자유 서술 text 로 들어
옵니다.

Index -> fab_inform_notes (alias)
  backing index  : fab_inform_notes-000001 (rollover family fab_inform_notes-*)
  shards/replicas: 2 / 1
  rollover       : write index 가 1,000,000 docs 도달 시
  retention      : backing index 를 1095d(3년) 후 삭제
  setup script   : ops_index_mgmt/fab_inform_notes.py
  _id            : doc_id (bulk_index_dataframe(id_field="doc_id",
                   op_type="create") — 재적재 시 중복이 에러로 드러납니다)

field 목록 (ops mapping 기준, 19개)

  aufnr          -> text : 이 note 의 고유 번호. 문서를 사람이 식별·추적하는
                          기준 키입니다.
  doc_id         -> text : 색인 시 _id 로 사용되는 dedup 키.
  down_dt        -> date : 장비 down 시각 (정비 시작).
  equp_dt        -> date : 장비 up 시각 (정비 종료, 실제).
  up_dt          -> date : 쓰지 않습니다. 비워 둔 채로 두고 화면·조회 어디에도
                          쓰지 않습니다. 값이 채워져 있는 문서가 있어도
                          신뢰하지 않습니다. 장비의 실제 up 시각은 equp_dt 이고,
                          앞으로의 정비 계획은 tool_maintenance_plan index 에
                          있습니다.
  hub_load_tm    -> date : 시스템(HUB)에 적재된 시각. 이벤트 발생 시각이 아니라
                          수집 시각이므로 기간 필터 기준으로 쓰지 않습니다.
  eq_event       -> text : 장비 이벤트 구분. pm_type 이 비어 있는 경우가 있어
                          화면에 함께 표시해야 합니다. tool_maintenance_plan 의
                          event_name 과 같은 성격의 정보이며 field 이름만
                          다릅니다.
  pm_type        -> text : PM 유형. 비어 있을 수 있습니다(eq_event 로 보완).
  eqp_id         -> text : 장비 ID. 조회(필터) 키.
  fab_name       -> text : fab 이름. 조회(필터) 키.
  fac_id         -> text : tool_maintenance_plan 에도 같은 이름으로 있는
                          field 입니다. 다만 그쪽의 det_fac_id(= 이 index 의
                          fab_name)에 해당하는 field 는 이 index 에 없습니다.
                          fab 단위보다 상위 구분으로 보이므로 필터·join 에는
                          쓰지 않고 fab_name 을 씁니다(타 feature 규칙과 동일).
  lot_id         -> text : 관련 lot ID. 화면 표시 대상.
  last_recipe_id -> text : 직전 recipe ID. 화면 표시 대상.
  note_comment   -> text : 엔지니어 자유 서술 note. 화면 표시 대상.
  zzproblem      -> text : 엔지니어 자유 서술 note(문제 현상). 화면 표시 대상.
  hltext         -> text : 엔지니어 자유 서술 note. 화면 표시 대상.
  interval_a     -> text : 미확인.
  noti_no        -> text : 미확인(통지 번호로 추정되나 확인 필요).
  oper           -> text : 미확인(공정 oper 로 추정되나 확인 필요).

조회 방법

  검색·필터는 fab_name 과 eqp_id 를 기준으로 겁니다. 두 field 모두 dynamic
  mapping 으로 들어온 text 이므로, 정확 일치(term)·집계에는 .keyword subfield
  (`fab_name.keyword`, `eqp_id.keyword`)를 사용합니다. 부분 검색이 필요할 때만
  분석된 본 field 를 씁니다.

  기간 필터의 time_field 는 down_dt(정비 시작) 입니다. hub_load_tm 은 적재
  시각이라 "언제 정비했는가"와 어긋납니다.

  진행 중(아직 up 안 된) 건은 equp_dt 가 비어 있는 문서로 판별합니다. 예정
  시각은 이 index 에서 얻지 않습니다(up_dt 사용 안 함).

화면 표시 field

  lot_id, pm_type, last_recipe_id, note_comment, zzproblem, hltext 가 주 표시
  대상이고, pm_type 이 비는 경우가 있으므로 eq_event 도 함께 표시합니다.

주의

  note_comment / zzproblem / hltext 는 엔지니어가 직접 쓴 자유 서술이라 길이가
  길고 개행(newline)이 많이 섞여 있습니다. 표(table) 셀에 그대로 넣으면 행 높이
  가 무너지므로 요약/펼치기 또는 pre-wrap 처리가 필요합니다.

  이 세 field 는 mapping 에서 nori analyzer 가 걸린 text 이고 .keyword subfield
  는 ignore_above: 8192 입니다(한글 UTF-8 3 bytes 기준 Lucene 32766 byte term
  한도 회피). 8192자를 넘는 note 는 .keyword 값이 아예 생성되지 않으므로,
  정렬·정확 일치·중복 제거를 이 field 로 하면 긴 note 가 조용히 누락됩니다.
  그런 용도에는 aufnr / doc_id 를 쓰십시오.

  date 4종(down_dt, equp_dt, up_dt, hub_load_tm)만 명시 mapping 되어 있고,
  나머지 column 은 dynamic mapping(text + .keyword, ignore_above 256)입니다.
  새로 추가되는 ISO timestamp column 이 생기면 fab_inform_notes.py 의
  DATE_FIELDS 에 넣고 재색인해야 date 로 잡힙니다 — dynamic date detection 은
  yyyy/MM/dd 계열만 인식하므로 그대로 두면 text 가 됩니다.

########################################################################
[2] tool_maintenance_plan — 정비 예정 작업 계획
########################################################################

BM/PM 중 "앞으로 할 일(future work)"을 담습니다.

Index -> tool_maintenance_plan (alias)
  backing index  : tool_maintenance_plan-000001
                   (rollover family tool_maintenance_plan-*)
  shards/replicas: 2 / 1
  rollover       : write index 가 1,000,000 docs 도달 시
  retention      : backing index 를 1095d(3년) 후 삭제
  setup script   : ops_index_mgmt/tool_maintenance_plan.py
  _id            : doc_id (bulk_index_dataframe(id_field="doc_id",
                   op_type="create"))

field 목록

  [장비·조직 식별]
  det_fac_id     -> text : fab 구분. fab_inform_notes 의 fab_name 과 같은 값
                          입니다(이름만 다름). fab 단위 조회·join 키.
  fac_id         -> text : 두 index 에 같은 이름으로 있는 field 입니다. 다만
                          det_fac_id 는 이 index 에만 있고 fab_inform_notes 에는
                          없습니다. 상위 구분으로 보이므로 fab 단위 선택에는
                          쓰지 않고 det_fac_id 를 씁니다.
  eqp_id         -> text : 장비 ID. fab_inform_notes.eqp_id 와 같은 체계이므로
                          장비 단위 join 키로 그대로 쓸 수 있습니다.
  eqp_model_cd   -> text : 장비 model 코드.
  maker_cd       -> text : vendor(제조사) 코드.

  [시각]
  chg_tm         -> date : 이 문서의 main timestamp. 기간(range) 필터 기준
                          time_field 로 씁니다.
  tool_start_tm  -> date : 작업 시작 시각. tool_end_tm 과 함께 계획 구간을
                          이룹니다(정비 전후 구간 표시·overlay 용).
  tool_end_tm    -> date : 작업 종료 시각.
  ll_dt          -> date : 보통 비어 있습니다. 쓰지 않습니다.
  limit_dt       -> date : 보통 비어 있습니다. 쓰지 않습니다.
  org_dt         -> date : 보통 비어 있습니다. 쓰지 않습니다.
                          (세 field 는 mapping 에만 있고 값이 거의 없으므로
                           화면·조회 어디에도 넣지 않습니다)

  [작업 내용]
  work_item_nm   -> text : 작업 항목 이름. 엔지니어 서술이므로 nori analyzer +
                          .keyword subfield(ignore_above: 8192)로 mapping 되어
                          있습니다.
  event_name     -> text : 이벤트 이름. fab_inform_notes 의 eq_event 와 같은
                          성격의 정보이며 field 이름만 다릅니다. 두 index 를
                          함께 보여줄 때는 한 열(column)로 합쳐 표시합니다.
  work_user_cd   -> text : 작업자 코드.

  doc_id 는 색인 시 _id 로 쓰입니다(fab_inform_notes 에서는 field 로도 노출).

mapping 주의

  ops_index_mgmt/tool_maintenance_plan.py 가 template 에 명시한 것은 date 6종
  (tool_start_tm, tool_end_tm, ll_dt, limit_dt, org_dt, chg_tm)과 note 1종
  (work_item_nm) 뿐입니다. 나머지 text field 는 dynamic mapping(text +
  .keyword, ignore_above 256)으로 생깁니다.

  새로 들어오는 ISO timestamp column 이 있으면 DATE_FIELDS 에 추가하고
  재색인해야 date 로 잡힙니다 — dynamic date detection 은 yyyy/MM/dd 계열만
  인식하므로 그대로 두면 text 가 됩니다. 반대로 긴 서술형 column 이 생기면
  NOTE_FIELDS 에 넣어 nori + .keyword(8192) 를 받게 합니다.

조회 방법

  기간 필터의 time_field 는 chg_tm 입니다. 특정 구간에 걸치는 정비 계획을
  찾을 때는 tool_start_tm/tool_end_tm 에 대한 range 조합을 씁니다.
  text field 의 정확 일치·집계에는 .keyword subfield 를 씁니다
  (`det_fac_id.keyword`, `eqp_id.keyword`). dynamic 으로 생기는 text 는
  ignore_above 256, work_item_nm 만 8192 입니다.

########################################################################
[3] 두 index 의 연결 — join 키와 함정
########################################################################

  장비 기준 join 은 eqp_id 로 그대로 됩니다. fab 기준은 이름이 어긋납니다 —
  계획(tool_maintenance_plan)은 det_fac_id, 실적(fab_inform_notes)은 fab_name
  이며 값은 같습니다.
  join·필터 코드에서 가장 실수하기 쉬운 지점이므로, office adapter 에서
  contracts 로 정규화할 때 det_fac_id 를 fab_name 으로 맞춰 내보내는 편이
  안전합니다(프로젝트 규약상 fab_name 이 표준 키, fac_id 계열은 그대로
  노출하지 않습니다).

  fac_id 는 두 index 에 같은 이름으로 있어 join 키로 쓰고 싶어지지만, fab
  단위보다 상위 구분으로 보이므로 단독 키로 쓰지 않습니다. 이름이 같은 쪽
  (fac_id)은 granularity 가 맞지 않고, granularity 가 맞는 쪽(det_fac_id ↔
  fab_name)은 이름이 다르다는 점이 이 한 쌍의 함정입니다.

  이벤트 구분은 event_name(계획) ↔ eq_event(실적) 로 이름만 다릅니다. 화면
  에서는 한 열로 합쳐 보여줍니다.

  시간축은 두 index 의 의미가 다릅니다. 계획 쪽은 chg_tm 기준 문서에 계획 구간
  tool_start_tm~tool_end_tm, 실적 쪽은 down_dt~equp_dt 입니다. 같은 timeline 에
  올릴 때 계획/실적을 시각적으로 구분해야 합니다.

########################################################################
[4] 어댑터 소비 규약 (hardware/bm_pm office adapter)
########################################################################

한 어댑터가 두 index 를 각각 1회씩 조회해 past / future 두 묶음과 파생 cards 를
돌려줍니다. 상위 dispatcher 가 normalizers.bm_pm_history_payload 로 감쌉니다.
anchor 는 요청의 end datetime 입니다.

--- 실적 쪽 (fab_inform_notes) ---

조회
  index      -> fab_inform_notes
  term       -> eqp_id.keyword (dynamic mapping 이라 .keyword 가 필요합니다)
  time_field -> down_dt (정비 시작). hub_load_tm 은 적재 시각이라 쓰지 않습니다.
  창          -> anchor 기준 과거 180일 (PAST_DAYS)
  상한        -> MAX_ROWS = 1000, 페이지네이션 없이 1회 요청.
                한 장비가 반년에 정비 1000건을 넘긴다면 가정이 깨진 것이므로,
                잘린 이력을 조용히 보여주지 않고 에러를 냅니다.

가져오는 field (명시 목록 — 새 적재 컬럼이 row 에 딸려오지 못하게)
  eqp_id, down_dt, equp_dt, hub_load_tm, pm_type, eq_event,
  lot_id, last_recipe_id, note_comment, zzproblem, hltext

일부러 읽지 않는 field
  up_dt   -> 유지되지 않는 예정 field 입니다. 계획은 tool_maintenance_plan 에
             있습니다.
  fac_id  -> fab 보다 거친 구분이고 join 키도 아닙니다.
  ll_dt / limit_dt / org_dt -> 보통 비어 있습니다.

--- 계획 쪽 (tool_maintenance_plan) ---

조회
  index      -> tool_maintenance_plan
  term       -> eqp_id.keyword
  time_field -> tool_start_tm (작업 시작). 문서 자체의 timestamp 인 chg_tm 이 아니라
                계획 구간의 시작으로 거릅니다 — 화면이 묻는 것은 "언제 작업하는가"
                이지 "언제 등록됐는가" 가 아니기 때문입니다.
  창          -> anchor 기준 미래 90일 (FUTURE_DAYS)
  상한        -> MAX_ROWS = 1000, 페이지네이션 없이 1회 요청.

가져오는 field (명시 목록)
  eqp_id, tool_start_tm, tool_end_tm, chg_tm, event_name,
  work_item_nm, work_user_cd

fab 단위 구분은 det_fac_id 입니다(fab_inform_notes 의 fab_name 과 같은 값). fac_id
는 두 index 에 같은 이름으로 있지만 더 상위 구분이므로 선택에 쓰지 않습니다.

--- 공통 ---

안전 장치

  hit 의 eqp_id 가 요청한 장비와 다르면 즉시 에러를 냅니다. term 이 의도보다 넓게
  매칭됐다는 뜻(대개 .keyword mapping drift)이고, 그대로 두면 다른 장비의 정비
  이력이 이 장비 이름 아래 표시됩니다.

시각 표시

  저장된 값을 **재포맷만** 하고 변환하지 않습니다. 저장된 wall clock 이 표에 그대로
  도달해야, 두 index 가 어떤 표기를 쓰든 overlay marker 와 차트 x 값이 어긋나지
  않습니다. 파싱 실패한 값은 예외를 던지지 않고 문자열 그대로 흘려보냅니다 —
  표시용 timestamp 하나가 탭 전체를 비우게 두지 않기 위해서입니다. 표를 정렬하는
  두 field 는 row mapper 에서 따로 검증합니다.

UNVERIFIED (첫 사무실 실행 때 확인)

  두 index 가 network_fdc_cdsem 처럼 offset 없는 KST wall
  clock 으로 저장하는지 아직 검증되지 않았습니다. Z 접미사가 붙어 있으면 모든 창이
  9시간 밀립니다. 어댑터의 __main__ 이 원본 저장값과 재포맷값을 나란히 출력하므로,
  탭을 신뢰하기 전에 그것부터 돌립니다.

  ★ 별도의 두 번째 시각 함정(요청 쪽): 프론트가 new Date().toISOString() 을 보내고
  라우트는 Z 만 떼므로, 어댑터가 받는 anchor 는 실제로 UTC wall clock 입니다(KST
  보다 9시간 뒤). 증상은 "가장 최근 ~9시간의 정비가 탭에서 빠져 보임" 입니다.
  fdc 어댑터와 공유하는 문제이며 bm_pm 이 만든 것은 아닙니다.
