device-statistics 의 recipe-params mock data 입니다.

device(lot_cd) 1개는 recipe 100~200개를 가지며, recipe 1개는 파라미터 다수를
측정합니다. 파라미터마다 측정 point 수가 다릅니다. 프론트엔드 ruleEngine.ts 의
RecipeInput 형태와 1:1 로 맞춰 raw 로 내려보냅니다. 위반(R3 cap)·outlier 판정은
프론트엔드가 client-side 로 수행합니다 (백엔드는 raw 만 제공).

GET /api/cdsem/device-statistics/recipe-params?lot_cds=R000,R001

응답: RecipeParamsRow 배열 (recipe 당 1행)

컬럼 -> 타입: 설명

lot_cd -> string: device 식별자. r3-device-grp / device-desc 의 lot_cd 와 조인됩니다.
recipe_id -> string: recipe 식별자. 형식은 RCP-<lot_cd>-NNN 입니다.
fac_id -> string: fab 코드. R3 또는 M11~M16 입니다.
ctn_desc -> string: recipe 설명 문자열입니다.
prod_catg_cd -> string: 제품 카테고리. DRAM, NAND, FLASH, Tech, Advanced 중 하나입니다.
recipe_class -> string: Main 또는 Sample 입니다 (D2).
family -> string: Core, Pool, VG_RTC_Cubic 중 하나입니다 (D3).
phase -> string|null: t-EV, EV, TV, PV 또는 null 입니다 (D3).
memory_class_auto -> string: DRAM, NAND, unknown 중 하나입니다. Tech/Advanced 는 unknown(수동) 입니다 (D7).
parameters -> records: 측정 파라미터 배열입니다. 각 원소는 {name, point_count, mother} 입니다.
                       **순서가 의미를 갖습니다** — recipe 가 파라미터를 적어 둔
                       순서 그대로이며, WAFER 계열이 맨 앞에 오는 것이 관례입니다
                       (user-confirmed 2026-08-05). 어댑터는 이 순서를 바꾸지
                       않습니다. 이름순으로 정렬하면 "WAFER" 가 알파벳상 거의
                       끝이라 가장 중요한 파라미터가 목록 맨 아래로 밀립니다 —
                       office 어댑터가 실제로 그랬고 2026-08-05 에 걷어냈습니다.

parameters 원소
name -> string: 파라미터 이름. 타입은 longest-prefix(EDGE_EX > EDGE > WAFER > LEVEL)로 파생되며, 그 외는 OTHER 입니다.
point_count -> int: 해당 파라미터의 측정 point 수입니다.
mother -> bool: 이 파라미터 자신이 mother 인지입니다 (idp 의 Mother_Para, office 확인 2026-07-28).

측정이 아닌 파라미터 — DUMMY / ALIGN (user-confirmed 2026-08-05)

둘 다 실물에 있는 파라미터 이름이며, **CD 를 재는 파라미터가 아닙니다**.

  DUMMY  자리를 채우는 placeholder. 재는 대상 자체가 아닙니다.
  ALIGN  정렬(addressing)용. 측정이 아니라 측정을 위한 준비라, 그 point 수는
         "얼마나 많이 쟀는가" 라는 질문의 답에 들어가면 안 됩니다. 설비 알람도
         align(9006)과 meas(9007)를 다른 사건으로 셉니다.

빠지는 자리가 서로 다르니 함께 보아야 합니다.

  outlier(outlierDetect.isOutlierExemptParam)
      DUMMY·ALIGN **둘 다** 중앙값 기준선에서도 초과 목록에서도 빠집니다.
      남겨 두면 ALIGN 의 큰 point 수가 기준선을 끌어올려 정상 파라미터의 진짜
      과다 측정이 문턱 아래로 숨습니다.

  판정(계측 룰)
      DUMMY **만** 면제입니다 — Sample 셀의 name_override 에 cap=None 으로
      들어 있습니다 (providers/rules.py). Sample 셀은 _other cap 이 0 이라
      면제가 없으면 DUMMY 가 point 1 만 있어도 항상 위반이고, 그 위반은 recipe
      를 고쳐 없앨 수 있는 종류가 아니라 고칠 수 있는 진짜 위반을 밀어냅니다.
      ALIGN 은 아직 판정 면제가 아닙니다 — 요청 범위가 outlier 집계였습니다
      (OFFICE-VERIFY: Sample recipe 의 ALIGN 이 위반으로 잡히는지 미확인).

두 자리를 한 스위치로 묶지 않은 것은 성격이 다르기 때문입니다 — outlier 는
서술적 통계, cap 은 규범입니다. 묶으면 룰 한 칸을 고칠 때 중앙값 기준선까지
따라 움직입니다.

이름 매칭은 룰 데이터의 affix 와 같은 의미입니다: 그 낱말로 시작하거나 끝나면
해당, 이름 한복판에 우연히 든 것은 제외.

mother 컬럼 — 무엇에 쓰이는가 (user-confirmed 2026-08-04)

son 파라미터는 mother 와 **같은 image** 에서 자기 cd_value 를 얻으므로 측정
시간(TAT)을 움직이는 것은 mother 수입니다. 그래서 comparison 화면의
mother_normal 버킷은 이 플래그로 파라미터를 좁혀서

  - para_16/13/9/5 (Lot 요약의 "para 분포"·"para 합계")
  - 계측 룰 검증 (health / violations / 판정 범위)
  - 측정 프로파일 (중앙값 / outlier)

셋을 **모두** 같은 mother 집합 위에서 계산합니다. 프론트엔드에서는
utils/lotHealth.ts 의 scopeRecipesToBucket 한 곳이 이 좁히기를 담당하며, 세
소비처가 같은 배열을 받습니다 — 각자 좁히게 두면 언젠가 한쪽만 고쳐져 표 한
행의 열들이 서로 다른 모수집단을 말하게 됩니다.

mother 를 가진 파라미터가 하나도 없는 recipe 는 mother_normal 버킷에 아예
들어가지 않습니다 (recipe 와 파라미터 **양쪽**을 좁힙니다).

★ 출처 미해결 (2026-08-04) — 이 컬럼은 **사무실에서 아직 채울 수 없습니다.**

  Mother_Para 가 확인된 유일한 곳은 장비 FTP 의 {idp_name}.idp 원본 파일이고
  (docs/datatables/recipe_idp.txt), 이 응답의 parameters 원천인
  cdsem_idp_ver.parameters 는 {name: point_count} 라 플래그를 담을 자리가
  없습니다. recipe 1건당 파일 1개를 내려받아야 하므로 device 4000개 규모에서는
  그 경로를 쓸 수 없습니다.

  어댑터는 blob 이 [{name, point_count, ...}] 형태로 바뀌어 플래그를 실어 주면
  그대로 읽고(키 후보: mother / Mother_Para / mother_para), 아니면 경고 로그를
  남기고 mother 를 전부 false 로 둡니다. 그 경우 mother_normal 버킷은 비어
  있게 되며, 이는 규칙을 데이터에 그대로 적용한 결과입니다.
  해결 후보는 device_statistics/MIGRATION.md 의 "mother_para 출처" 절입니다.

recipe 이름 접미사 — 특수 측정 job
(_WCDU/_FCDU/_FULL user-confirmed 2026-08-04,
 _HALF/_BCDU/_MTX 및 "_*CDU" 패턴 user-confirmed 2026-08-05)

실물 recipe 이름은 "_S"/"SE"(Sample) 외에 아래로 끝날 수 있습니다.

  "_*CDU"   CDU(CD uniformity) 측정 job. **목록이 아니라 패턴입니다** — 앞
            글자는 어떤 map 을 재는지를 뜻할 뿐이고(W=wafer, F=field, B=…)
            종류가 늘 수 있습니다. 확인된 예: _WCDU, _FCDU, _BCDU.
  "_FULL"   full-map 측정 job.
  "_HALF"   half-map 측정 job.
  "_MTX"    matrix 측정 job.

CDU 를 패턴으로 적어 두는 것이 중요합니다. 처음에는 _WCDU/_FCDU 만 열거했고,
그래서 실물의 _BCDU 가 어느 제외 경로에도 걸리지 않고 분석에 그대로 섞여
들었습니다 (2026-08-05). 접미사를 하나씩 세는 방식 자체가 이 데이터에 맞지
않습니다.

이 접미사는 이름의 일부라서 cdsem_idp_ver.full_name 조인 키를 깨지 않습니다.
recipe_class 파생 규칙(_S/SE)과도 겹치지 않으므로 서로 간섭하지 않습니다.

이 job 들은 웨이퍼를 통째로 훑는 것이 목적이라 **측정 규모가 정상 recipe 와
다른 차원**입니다. 그래서 프론트엔드의 두 분석 모두에서 빠집니다.

  판정(lotHealth.isExemptJob) — 계측 룰 판정 범위에서 **분자·분모 모두**
      제외합니다. gray(분모에 남는 판정 보류)와 다릅니다.
  outlier(outlierDetect)     — point_count 중앙값 **기준선에서도**, 초과 표시
      대상에서도 제외합니다. 남겨 두면 이 job 들의 큰 point_count 가 기준선을
      끌어올려 정상 recipe 의 진짜 과다 측정이 문턱 아래로 숨습니다.

Mock 생성 규칙
1. lot_cd 별 결정론적 seed(statistics._seed_for)로 recipe·parameter 를 생성합니다.
2. 약 8% recipe 는 기타(OTHER) 파라미터가 많은 bloated recipe 입니다 (D10 신호 검증용).
3. 약 5% recipe 는 EDGE point 수가 또래 대비 큰 outlier 를 포함합니다 (outlier 뷰·R3 cap 검증용).
4. 약 10% recipe 는 특수 측정 job 접미사(_WCDU/_FCDU/_BCDU/_FULL/_HALF/_MTX)를 갖고,
   그 recipe 의 point_count 는 정상 recipe 의 8배입니다 (판정·outlier 두 제외 경로
   검증용). 이 목록은 **표본**일 뿐 판정 기준이 아닙니다 — 기준은 위의 "_*CDU"
   패턴이고, _BCDU 를 표본에 넣어 둔 이유는 열거 목록에 없던 이름이 실제로 새어
   나갔기 때문입니다.
   배율 자체는 OFFICE-VERIFY 입니다 — "자릿수가 다르다" 는 성질만 재현하고
   절대값은 흉내 내지 않습니다. 배율이 1 이면 제외 규칙을 지워도 테스트가 조용히
   통과하므로, 이 값은 장식이 아니라 회귀의 조건입니다.
5. Sample recipe 에는 DUMMY(point 1)와 ALIGN(point 40)이 붙습니다. 값을 이렇게 고른
   것은 두 제외 경로가 집에서 **눈에 보이게** 하기 위해서입니다 — DUMMY 1 은
   Sample 셀 cap 0 을 곧바로 넘어 판정 면제가 빠지면 위반 수가 늘고, ALIGN 40 은
   정상 중앙값(약 6)의 문턱을 훌쩍 넘어 outlier 제외가 빠지면 Sample recipe 마다
   초과가 하나씩 생깁니다. 값은 OFFICE-VERIFY 이고, point_count 는 rng 가 아니라
   고정값입니다 — rng 를 한 번이라도 더 굴리면 lot 단위로 공유되는 seed 때문에
   뒤따르는 recipe 의 파라미터가 전부 다른 값이 됩니다.
   Sample 에만 붙이는 것은 확인된 사례가 거기이기 때문입니다(Main recipe 에도
   있는지는 OFFICE-VERIFY). 프론트엔드의 outlier 제외는 recipe 종류를 보지 않으므로
   어디에 있든 똑같이 걸립니다.
6. 약 85% recipe 만 mother 파라를 갖고(보유 시 파라미터의 25~45%), 나머지 15% 는
   mother 가 없어 mother_normal 버킷에서 빠집니다 — "recipe 도 좁힌다" 는 규칙이
   집에서 실제로 실행되게 하려는 것입니다. 이 비율은 OFFICE-VERIFY 입니다(실물
   미확인). mother 보유 여부는 recipe-statistics 의 버킷 멤버십과 **같은 원천**
   (recipe_population 의 RecipeIdentity)에서 나오므로 두 표면이 갈라지지 않습니다.


========================================================================
사무실(Office) 파생 규칙 — 어댑터가 각 컬럼을 무엇에서 만드는가
========================================================================

이 응답에는 **원천 컬럼이 그대로 있는 값이 하나도 없습니다.** recipe 목록은
공정 스텝 index 에서, 파라미터는 IDP index 에서 오고, 분류 컬럼 네 개는
device 의 ctn_desc / recipe 이름에서 파생됩니다. 근거 없이 값을 지어내지 않는
것이 규칙이므로, 판별할 수 없는 값은 빈 문자열이나 null 로 둡니다.

원천 (docs/datatables/planstep_r3.txt, ebeam_tas_lot_hist.txt, idp_ver.txt)

  recipe 목록  -> R3: sknn-planstep-r3 / M fab: ebeam_tas_lot_hist
  parameters   -> cdsem_idp_ver, full_name == recipe_id 의 최신 version

컬럼별 파생 규칙 (user-confirmed 2026-07-31)

  recipe_id     -> 스텝의 recipe_id 그대로. 같은 recipe 가 여러 스텝에 걸리면
                   행은 한 번만 냅니다(계약 단위가 recipe 이므로).
  ctn_desc      -> 그 recipe 가 걸린 **공정 스텝 이름**(R3 oper_desc /
                   M fab oper_det_desc). 문장을 지어내지 않습니다.
  prod_catg_cd  -> r3_device_grp 의 값. M fab device 는 이 컬럼이 없어
                   ""(빈 문자열)이며, 따라서 memory_class_auto 는 unknown 입니다.
  recipe_class  -> **recipe 이름이 "_S" 또는 "SE" 로 끝나면 Sample**, 아니면 Main.
                   끝자리 고정(anchored) 규칙입니다 — 이름 어디든 "SE" 를 찾으면
                   PHASE/BASE/SET 같은 평범한 단어가 전부 Sample 로 잡히고,
                   recipe_class 가 곧 프론트 cap 선택 축(D2)이라 위반 판정까지
                   뒤집힙니다. 스텝 코드(괄호 앞)로 판단하지 않습니다 —
                   오검출 가능성이 있다는 담당자 확인이 있었습니다.
  family        -> device 의 ctn_desc 에 "pool"/"풀" 이 있으면 Pool, 나머지는
                   전부 Core. **VG_RTC_Cubic 은 발행하지 않습니다** — 원천에서
                   판별할 근거가 없어, 틀린 분류보다 미분류를 택했습니다.
                   근거가 생기면 office 어댑터의 _family_of 만 고칩니다.
  phase         -> device 의 ctn_desc 에서 파싱합니다. "t-EV"/"tev" 를 "EV"
                   보다 먼저 봐야 합니다(부분 일치 함정).
                   OFFICE-VERIFY: 원천에 실제로 있는 "p-EV" 는 계약 Literal
                   (t-EV/EV/TV/PV)에 없어 현재 null 이 됩니다. 화면에 필요하면
                   계약을 넓혀야 합니다.

파라미터 이름의 세분도 — OFFICE-VERIFY

idp_ver.txt 와 같은 경고입니다. parameters blob 의 key 가 "WAFER"/"EDGE" 처럼
타입 단어뿐이면 위 26행의 longest-prefix 타입 파생이 할 일이 없어지고, 위 Mock
생성 규칙 2·3번이 전제하는 **bloated recipe·outlier 신호가 입력을 잃습니다.**
첫 사무실 실행에서 실제 key 목록을 확인하십시오.
