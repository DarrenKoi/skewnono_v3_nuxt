컬럼 이름 정규화

  "meas_condition mag", "meas_condition vac", "meas_condition pixel"). 어댑터는 읽는

  "object" 컬럼은 Python 내장 이름과 겹치므로 계약에서는 object_type 으로 옮깁니다.
  "class"(exe_detail_info) 도 예약어라 class_name 이 됩니다.

  mp_image_name 은 01 하나가 아니라 NN 번호가 붙어 여러 개 존재할 수 있습니다
  (no_of_mp_image 만큼 — HV-SEM 다중 이미지, user-confirmed 2026-08-08).
  화면 계약은 2026-08-08 부터 **컬럼 전부**를 `mp_image_names` 목록(NN 순서)으로
  내려보내며, `mp_image_name_01` 은 대표 1장으로 유지됩니다(항상 목록의 첫
  원소). 2026-08-08 이전에는 대표 1장만 실어 스큐보아가 HV-SEM 의 나머지
  이미지를 볼 수 없었습니다.

  세 필드(no_of_mp_image / mp_image_name_01 / mp_image_names)는 어댑터에서
  **한 목록으로부터 파생**합니다. 원시 컬럼을 따로따로 읽으면 `mp_image_name
  01` 이 비고 02 부터 채워진 행에서 셋이 어긋나, 화면이 이미지를 들고 있으면서
  "대표 이미지 없음" 을 보여 줍니다. OFFICE-VERIFY: 빈 01 은 관측된 적이
  없으나 예외 상황으로 가능하다고 봅니다(2026-08-10). 원시 값이 파생값과

========================================================================
어댑터 소비 규약 (tttm / pm_planning — 장비 그룹 CD 통계)
========================================================================

msr_file 은 MSR 1건을 열지만, tttm 과 pm_planning 은 **장비 그룹 전체의 최근
실행**을 열어 (장비 × beam × 방향) 별 대표 CD 를 만듭니다. 공용 코드는
back_dev_home/ebeam/_office_msr_cd.py 입니다.

읽는 컬럼 — "parameter", "cd_value", "meas_condition vac".

1. 표본 단위는 **점이 아니라 실행(run)** 입니다.
   MSR 1건에는 측정점이 수백 개 있고 같은 웨이퍼라 서로 상관되어 있습니다
   (rho 약 0.8). 점을 독립 표본으로 세면 표준오차가 10~25배 작아져 **모든
   장비쌍이 유의하게 스큐된 것으로** 나옵니다. 따라서 run_median() 이 실행
   1건을 숫자 1개로 접은 뒤에야 장비 단위 통계가 그 값을 봅니다.
   (docs/research/2026-08-16-skew-tttm-feasibility.md 2.4절)

2. 그 grain 은 다시 **parameter 단위**입니다.
   한 실행 안에 공칭 CD 가 다른 parameter 가 여러 개 들어 있습니다(3.2절).
   실행 단위로 한 번 더 중앙값을 내면 31 nm feature 와 68 nm feature 가 섞여
   엉뚱한 CD 대역(cd_band)에 들어가고, 그 셀의 action limit(CD 의 1 %)이
   아무도 측정하지 않은 패턴 크기 기준으로 그려집니다.

3. beam condition 은 "meas_condition vac" 에서 나옵니다 — 500 -> "500V".
   pickle 이 싣는 유일한 beam 속성이므로 라벨은 전압에서 멈춥니다. 사무실
   MDC 키는 optics 접미사까지 답니다("500V_HR_0Deg"). 같은 전압의 optics 두
   모드는 서로 다른 beam 이므로, **optics 를 추측해서 라벨을 늘리면 안 됩니다.**

4. ★ 측정 방향(X/Y)을 싣는 컬럼은 **없습니다** (2026-08-18 확인 — 이 문서의
   컬럼 목록과 meas_hist.txt 어디에도 없습니다).
   계약(tttm/contracts.py, pm_planning/contracts.py)의 axis 는
   Literal["X","Y"] 이므로 채울 값이 반드시 있어야 하는데, 현재는 parameter
   **이름**에서 되찾습니다(`CD_X`, `..._Y`, HORIZ/VERT). 이름에서 읽을 수
   없으면(`Para_13` 처럼) 그 행은 **버립니다**. 기본값 "X" 를 넣지 않는
   이유는, 계약상 측정된 사실과 구분이 되지 않아 X 셀이 두 방향을 모두
   담게 되고 그러면 방향별 드리프트 — TTTM 이 찾으려는 바로 그것 — 이
   평균으로 지워지기 때문입니다.
   ★ 방향은 parameter **이름에 들어 있습니다**. 다만 그 이름 짓는 방식이
   recipe·fab 마다 **매우 다양합니다** (user-confirmed 2026-08-18). 그래서
   내장 정규식표만으로는 적중률이 낮고, 사무실에서 실제 이름을 보고
   SKEWNONO_AXIS_PARAM_MAP 으로 채우는 것이 정상 절차입니다. 표를 못 채웠다고
   해서 잘못 채운 것보다 나쁘지는 않습니다 — 못 채우면 셀이 비고 화면이
   그렇다고 말하지만, 잘못 채우면 아무 말 없이 틀립니다.

   이름이 다양하므로 이 환경변수는 **glob 도 받습니다.** fab 하나에 정확한
   이름 40개를 적는 대신 보통 패턴 2~3개로 끝납니다.

     SKEWNONO_AXIS_PARAM_MAP="*_HOR=X,*_VER=Y,Para_13=X"

   정확한 이름이 glob 보다 우선하므로, 가족 규칙은 두고 예외 하나만
   따로 고칠 수 있습니다. 각 어댑터의 __main__ 진단이 그 fab 의 parameter
   어휘 전체와 해석 결과를 출력하고, 붙여 넣을 수 있는 환경변수 한 줄까지
   만들어 줍니다.

   또 하나 (user-confirmed 2026-08-18): CD 모니터링 recipe 의 parameter 도
   **다른 측정에서 쓰는 평범한 이름들**입니다. 모니터링 전용 어휘가 따로
   있지 않으므로, 위 표 하나가 두 화면 모두를 커버합니다.
