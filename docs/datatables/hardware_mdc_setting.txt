dict of dict format

{'eqp_id': {beam conditions: str}}

예를 들어,
{'4CCD6701': {
        '800V_HR_0Deg': '1.004984',
        '800V_HR_90Deg': '1.005625',
        '500V_HR_0Deg': '1.004096',
        '500V_HR_90Deg': '1.003888'
    }
}

each eqip id는 beam 종류과 값이 모두 다름
특정 장비는 더 많은 beam 종류를 가지고 있기도 함.
3000V, Valley 모드등 존재 

자주 바뀌지는 않지만 장비간 skew를 확인하는데 중요한 요소 

MDC : Meas Data correction

MDC 수치를 바꿈으로 인해 측정 결과값이 달라짐. result = MDC * actual measurement data

MDC는 절대 수치로 다른 장비의 수치와 같다고 해서 그 두 장비가 같다고 말할 수 없음
하지만 값이 비슷할 수록 장비의 h/w setting이 유사하다고 유추 가능.

MinIO에는 날짜별로 기록하여 추적 가능하도록 함
redis에는 가장 최근 mdc 값들을 fab_name 별로 저장

    그러므로 SCE 의 graceful-empty 규칙을 여기로 그대로 복사하면 안 됩니다.

      MDC  : hash field 없음 / 아카이브 파일 없음  -> **비정상**. 수집이 실패했거나
             적재가 밀린 상태입니다.

    에는 반드시 드러나야 합니다. 그러지 않으면 실제 수집 장애가 "원래 이 fab 은
    데이터가 없나 보다" 로 조용히 묻힙니다 — MDC 는 장비간 skew 판단의 근거이므로
    낡은 값이나 없는 값을 눈치채지 못하는 것이 가장 나쁜 실패 방식입니다.

builder 2개

========================================================================
어댑터 소비 규약 (tttm / pm_planning — epoch 경계)
========================================================================

hardware/mdc 탭은 MDC **값**을 보여 줍니다. tttm 과 pm_planning 은 같은 소스에서
**언제 바뀌었는지**를 읽습니다. 공용 코드는 back_dev_home/ebeam/_office_mdc.py
이며, 날짜별 MinIO 아카이브에서 연속한 두 수집일을 비교해 변경점을 찾습니다.
Redis 스냅샷은 오늘 값만 담고 있어 차분할 상대가 없으므로 여기서는 읽지 않습니다.

왜 필요한가 — `result = MDC × actual` 이므로 MDC 를 고치면 장비가 움직이지
않았는데도 그 장비의 측정값이 움직입니다. 경계를 넘어 pool 한 장비간 스큐는
**보정계수 변경을 장비 차이로 보고합니다.** 그래서 tttm 의 셀은 epoch 로 키가
잡히고, 셀의 창은 그 (beam, 방향)에 대한 이 fab 의 최근 MDC 변경일에서
시작합니다.

키 분해 — "800V_HR_0Deg" -> beam "800V_HR" + 회전 "0Deg".

  0Deg -> axis "X", 90Deg -> axis "Y" 로 매핑합니다.
  ★ OFFICE-VERIFY: 이 접미사가 **이미지 회전**인지 **측정 방향**인지 아직
    확인되지 않았습니다(feasibility 문서 6절 4번). 계약의 axis 축이 여기에
    걸려 있으므로, 회전으로 판명되면 모든 셀의 axis 가 다른 뜻이 됩니다.
    고칠 곳은 _office_mdc.py 의 split_condition() 한 곳입니다.
  접미사가 회전이 아닌 키(예: 맨 3000V)는 axis 를 None 으로 돌려주고 호출부가
  버립니다. 추측해서 채우지 않습니다.

전압 접두사 매칭 — 측정 행은 전압까지만 알 수 있으므로(msr_file_pickle.txt 참고)
경계 매칭은 **전압 접두사**로 합니다. Valley 설정 변경이 500V epoch 전체를
리셋하게 되어 경계가 넓어지지만, 넓어지는 방향이 안전합니다. 넘어도 됐을 비교를
막을 뿐, 변경을 가로지르는 비교를 허용하지는 않습니다.

조회 창 — pm_planning 은 측정 창(30일)과 **분리해서** 240일을 봅니다. MDC 는
"자주 바뀌지는 않는" 값이라 30일 창에서는 거의 모든 장비의 epoch 이력이 비고,
`mdc_changed` 배지가 "한 달 안에 안 바뀜"이 아니라 "한 번도 안 바뀜"으로
읽히기 때문입니다.
