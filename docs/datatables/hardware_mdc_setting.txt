dict of dict format

{'eqp_id': {beam conditions: str}}

예를 들어,
{'4CCD6701': {
        '800V_HR_0Deg': '1.004984',
        '800V_HR_90Deg': '1.005625',
        '500V_HR_0Deg': '1.004096',
        '500V_HR_90Deg': '1.003888'
    }
}

each eqip id는 beam 종류과 값이 모두 다름
특정 장비는 더 많은 beam 종류를 가지고 있기도 함.
3000V, Valley 모드등 존재 

자주 바뀌지는 않지만 장비간 skew를 확인하는데 중요한 요소 

MDC : Meas Data correction

MDC 수치를 바꿈으로 인해 측정 결과값이 달라짐. result = MDC * actual measurement data

MDC는 절대 수치로 다른 장비의 수치와 같다고 해서 그 두 장비가 같다고 말할 수 없음
하지만 값이 비슷할 수록 장비의 h/w setting이 유사하다고 유추 가능.

MinIO에는 날짜별로 기록하여 추적 가능하도록 함
redis에는 가장 최근 mdc 값들을 fab_name 별로 저장

  - Redis key 이름 — 최신 스냅샷, field = fab_name
  - MinIO 경로 규칙 — 날짜별 이력

  "Redis 최신 스냅샷 + MinIO 날짜별 이력" 이라는 구조 자체는 SCE 와 같습니다.
  이미 연결된 hardware_sce_setting.txt 의 형태를 그대로 따르는 것이 가장 안전
  합니다.
    Redis : hash key "sce_info", field = fab_name
    MinIO : hitachi_sem/cdsem/sce_info/YYYY/MM/DD/{fab_name}.json
  수집 주기가 규칙적이지 않다면 SCE 처럼 날짜를 계산하지 말고 폴더를 탐색합니다.

구현할 것: builder 2개

  build_mdc_settings(eqp_id, fab_name, as_of) -> {eqp_id: {beam_condition: str}}
    선택 장비 **와 같은 fab 의 형제 장비들**의 as-of 스냅샷입니다(비교 sub-tab).
    SCE 처럼 fab map 전체가 곧 비교 집단이 됩니다.

  build_mdc_history(eqp_id, start, end) -> list[{...}]
    선택 장비 **하나만**, [start, end] 구간을 오름차순으로. beam_condition 당
    레코드 1건인 long format 입니다(시계열 sub-tab).

  상위 dispatcher 가 둘을 normalizers.settings_payload(settings + docs)로
  묶습니다. sce 와 같은 구조입니다.

CD-SEM / HV-SEM 구분은 이 sub-tab 에 별도로 걸려 있지 않습니다.
