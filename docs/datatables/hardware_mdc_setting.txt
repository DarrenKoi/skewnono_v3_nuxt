dict of dict format

{'eqp_id': {beam conditions: str}}

예를 들어,
{'4CCD6701': {
        '800V_HR_0Deg': '1.004984',
        '800V_HR_90Deg': '1.005625',
        '500V_HR_0Deg': '1.004096',
        '500V_HR_90Deg': '1.003888'
    }
}

each eqip id는 beam 종류과 값이 모두 다름
특정 장비는 더 많은 beam 종류를 가지고 있기도 함.
3000V, Valley 모드등 존재 

자주 바뀌지는 않지만 장비간 skew를 확인하는데 중요한 요소 

MDC : Meas Data correction

MDC 수치를 바꿈으로 인해 측정 결과값이 달라짐. result = MDC * actual measurement data

MDC는 절대 수치로 다른 장비의 수치와 같다고 해서 그 두 장비가 같다고 말할 수 없음
하지만 값이 비슷할 수록 장비의 h/w setting이 유사하다고 유추 가능.

MinIO에는 날짜별로 기록하여 추적 가능하도록 함
redis에는 가장 최근 mdc 값들을 fab_name 별로 저장

========================================================================
어댑터 소비 규약 (hardware/mdc office adapter)
========================================================================

★ 연결됨 — 사무실에서 구현 완료 (2026-07-27, 담당자 확인).
  구현체는 providers/mdc/office.py 이며 gitignore 대상이라 집(home) workspace 에는
  없습니다. 집에 있는 office_example.py 는 아직 stub 이므로, 이 문서가 사무실
  구현의 내용을 확인할 수 있는 유일한 기록입니다.
  ※ 템플릿(office_example.py)에 구현을 역반영하지 않으면 다음 사람은 stub 에서
     다시 시작하게 됩니다.

저장 위치 (담당자 확인 2026-07-27)

  1) 최신 스냅샷 — Redis hash, key = "mdc_setting"
     - field: fab_name ("M15A", "M14B", ...)
     - value: 해당 fab 의 {eqp_id: {beam_condition: value}} dict (위 형태)
     - 수집 시 덮어써지므로 항상 최신 값입니다.

  2) 이력 (trend) — MinIO, 기본 bucket/prefix (minio_handler/minio_config.py)
     - path: hitachi_sem/cdsem/mdc_setting/YYYY/MM/DD/{fab_name}.json
     - 각 JSON = 그 날짜의 fab 전체 dict of dict (Redis field 값과 같은 형태)

  ★ SCE 와 같은 2단 구조이며 이름만 다릅니다
    (hardware_sce_setting.txt: Redis "sce_info" + hitachi_sem/cdsem/sce_info/...).
    따라서 날짜 폴더를 **탐색**하고 기대 날짜를 계산하지 않는 규칙은 그대로
    적용됩니다 — 수집 주기가 규칙적이라는 보장이 없기 때문입니다.

  ★★ 다만 "빈 결과" 의 의미는 SCE 와 정반대입니다 (담당자 확인 2026-07-27).

    MDC 는 R3/R4 를 포함한 **모든 fab** 에 데이터가 있습니다. SCE 처럼 "이 fab 은
    원래 SCE 를 안 쓴다"(R3/R4) 거나 "아직 데이터가 없다"(M10) 는 예외가 없습니다.

    그러므로 SCE 의 graceful-empty 규칙을 여기로 그대로 복사하면 안 됩니다.
      SCE  : hash field 없음 / 아카이브 파일 없음  -> 정상적인 빈 상태. {} 나 [] 반환.
      MDC  : hash field 없음 / 아카이브 파일 없음  -> **비정상**. 수집이 실패했거나
             적재가 밀린 상태입니다.

    화면은 빈 상태로 렌더하더라도(502 로 탭을 죽일 이유는 없습니다) 로그나 health
    에는 반드시 드러나야 합니다. 그러지 않으면 실제 수집 장애가 "원래 이 fab 은
    데이터가 없나 보다" 로 조용히 묻힙니다 — MDC 는 장비간 skew 판단의 근거이므로
    낡은 값이나 없는 값을 눈치채지 못하는 것이 가장 나쁜 실패 방식입니다.

builder 2개

  build_mdc_settings(eqp_id, fab_name, as_of) -> {eqp_id: {beam_condition: str}}
    선택 장비 **와 같은 fab 의 형제 장비들**의 as-of 스냅샷입니다(비교 sub-tab).
    SCE 처럼 fab map 전체가 곧 비교 집단이 됩니다.

  build_mdc_history(eqp_id, start, end) -> list[{...}]
    선택 장비 **하나만**, [start, end] 구간을 오름차순으로. beam_condition 당
    레코드 1건인 long format 입니다(시계열 sub-tab).

  상위 dispatcher 가 둘을 normalizers.settings_payload(settings + docs)로
  묶습니다. sce 와 같은 구조입니다.

CD-SEM / HV-SEM 구분은 이 sub-tab 에 별도로 걸려 있지 않습니다.
