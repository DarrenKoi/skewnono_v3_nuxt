# AFM 실데이터 조사 요청 — Home → Office

- 작성일: 2026-10-02입니다.
- 수신자: 사내 AFM 원천 데이터와 기존 플랫폼을 조회할 수 있는 Office agent입니다.
- 목적: Home에서 실데이터의 구조·타입·결측·파일 연결 관계를 재현하여 현재 AFM 화면을 완성하기 위한 조사입니다.
- 회신 기한: 별도 날짜 기한은 없습니다. Home 구현을 시작하기 전에 P0 결과부터 회신해 주시면 됩니다.
- 부분 회신: 확인한 항목부터 답변하고, 나머지는 `미확인 / 필요한 접근 또는 담당자 / 다음 확인 방법`으로 남겨 주십시오.

## 1. 조사 범위와 현재 확인된 상태

현재 저장소에는 장비 선택, 측정 검색, 상세 표·차트·이미지, 그룹 시계열 비교,
Excel 내보내기가 있습니다. `backend/afm/providers/office_example.py`는 모든 함수가
`NotImplementedError`를 발생시키는 연결 전 stub입니다. Home은 사내 원천에 접근할 수
없으므로, 현재 mock의 값과 구조를 실데이터의 증거로 사용하면 안 됩니다.

이번 요청은 **원천 조회와 증거 수집**입니다. 아래 질문에 답하기 위해 운영 데이터를
변경하거나 어댑터를 먼저 구현할 필요는 없습니다. 이미 구현된 사무실 전용
`office.py`가 있다면 해당 구현의 존재와 실제 데이터 조회 결과를 함께 알려 주십시오.
원천 스키마와 현재 API 계약이 다르면 원천을 계약에 맞춘 것처럼 보고하지 말고,
차이와 필요한 변환을 구분해 주십시오.

우선 읽을 파일입니다.

- `CLAUDE.md`: 환경 전환, provider, 스키마와 mock 동기화 규칙입니다.
- `backend/afm/contracts.py`, `routes.py`, `data.py`: 현재 실행 코드의 계약과 호출 경로입니다.
- `backend/afm/providers/mock.py`: Home이 현재 재현하는 가정입니다.
- `frontend/app/composables/useAfmDetailApi.ts`: 프론트가 소비하는 필드와 API입니다.
- `docs/afm/개발요구.txt`, `tool_info.txt`: 과거 요구사항이며 현재 사실 확인이 필요합니다.
- `backend/afm/MIGRATION.md`, `docs/api-contracts/afm.yaml`: 참고 자료입니다. 실행 코드와 다른 설명은 차이로 보고해 주십시오.

## 2. 화면을 채우는 데 필요한 데이터

| 화면 기능 | 필요한 데이터 | 현재 소비 경로 | Office에서 확보할 근거 |
| --- | --- | --- | --- |
| `/afm` 장비 선택 | 장비 ID·이름·fab·concept | `useAfmToolData.ts`의 정적 목록 | 실제 장비 목록과 fab 매핑 |
| `/afm/<tool>` 검색·최근 측정 | 측정 식별자, 파일명, recipe, lot, slot, 날짜·시각, 반복 정보 | `GET /api/afm/files?tool=...` | 원천 index 구조와 대표 행 |
| 검색 결과 파일 보유 표시 | 여섯 종류 파일 목록, `has_*`, `point_count` | 목록 응답 | 실제 파일 존재 여부와 파생 규칙 |
| 상세 Information | `information`, 특히 `Recipe ID`, `Lot ID`, `Start Time` | `GET /api/afm/files/<filename>` | 상세 파일 구조와 정보 필드 |

| Measurement points 표 | `data`, `available_points`, validity·state·좌표 | 상세 응답 | 실제 상세 행과 Site 식별 규칙 |
| Heatmap·Histogram | 선택 위치의 `[{x, y, z}]` | `.../profile/<point>` | 실제 profile 구조·축·단위 |
| Profile image | 선택 위치의 이미지 | `.../image/<point>` → `.../image-file/<point>` | 대응 파일과 실제 이미지 형식 |
| Align·Tip·Capture·TIFF 갤러리 | `[{name, url}]` 및 이미지 본문 | `.../images/<image_type>` | 종류별 파일 목록과 읽기 결과 |
| See Together | 여러 측정의 동일 Site·통계·측정 컬럼, 측정 시각 | 그룹별 상세 API 조회 | 비교 가능한 연속 측정 샘플 |
| Excel 내보내기 | Information·Summary·Detailed·현재 Profile | 위 응답에서 클라이언트 생성 | 원천과 대조할 값·행 수·단위 |

조회 이력·그룹·최근 검색은 현재 브라우저 로컬 저장 상태입니다.
이 기능을 위해 별도 사내 DB를 찾을 필요는 없습니다.

## 3. P0 — 원천과 식별 관계

### Q01. 현재 사용할 AFM 원천은 무엇입니까?

DB·캐시·파일 저장소·기존 API 중 실제로 읽는 원천을 기능별로 적어 주십시오.
index/key/bucket/경로 규칙 또는 조회 함수·모듈 이름을 알려 주시되 비밀번호·토큰은 제외합니다.

필요한 이유: 사내 데이터 접근 방식과 기존 코드 재사용 가능 여부를 결정합니다.

> 답변: 미확인입니다. 조회 위치와 실행 근거를 기입합니다.

### Q02. 실제 장비와 fab 매핑은 무엇입니까?

현재 UI와 mock은 `R3 → MAP608`, `M12 → MAPC01`, `M15 → 5MAPT01`입니다.
과거 `tool_info.txt`는 `PKG → MAP608`, `R3 → MAPC01`, `M15 → 5EAP1501`입니다.
현재 운영 목록을 기준으로 ID·이름·fab·별칭·concept을 표로 회신해 주십시오.
현재 `Concept A`가 실제 분류인지도 확인해 주십시오.

필요한 이유: 장비 선택과 API의 `tool` 값이 실제 원천을 가리켜야 합니다.

> 답변: 미확인입니다. 기준 목록과 확인 날짜를 기입합니다.

### Q03. 측정 목록 원천 객체의 구조는 무엇입니까?

과거 요구사항의 `dict_merged = {tool: nested_dict}`가 현재도 맞는지 확인하고,
최상위부터 측정 한 건까지 이어지는 키·타입·값 샘플을 보내 주십시오.
DataFrame이면 shape, 컬럼, dtype, index, 직렬화 형식과 `to_dict` 방향을 기입합니다.

필요한 이유: 원천을 API의 행 배열로 변환하는 규칙을 재현합니다.

> 답변: 미확인입니다. 원천 객체의 구조와 대표 샘플을 기입합니다.

### Q04. 측정 한 건의 안정적인 식별자는 무엇입니까?

`unique_key` 또는 `uniquekey`의 실제 생성 규칙과 중복 범위를 알려 주십시오.
현재 UI는 같은 장비 안에서 `filename`으로 열기·그룹·이력을 식별합니다.
동명 파일이나 재측정·덮어쓰기 사례가 있으면 해당 충돌 사례를 포함합니다.

필요한 이유: 목록에서 선택한 측정과 상세·시계열이 다른 측정으로 연결되는 일을 방지합니다.

> 답변: 미확인입니다. 식별 규칙과 충돌 여부를 기입합니다.

### Q05. 파일명과 관련 파일을 연결하는 규칙은 무엇입니까?

실제 파일명 패턴별 샘플과 한 측정의 data/profile/tiff/align/tip/capture 연결표를
보내 주십시오. 확장자 제거, 경로 포함 여부, Site·Point No 해석 규칙도 연결표에 명시합니다.
`#`, 공백, 한글 등 실제 파일명 문자는 샘플에서 보존합니다.

필요한 이유: CSV·pickle·profile·이미지를 같은 측정으로 묶고 URL 인코딩을 재현합니다.

> 답변: 미확인입니다. 연결표와 패턴별 파일명을 기입합니다.

### Q06. 목록 필드의 실제 타입과 결측 표현은 무엇입니까?

각 필드를 `필드 → Python 타입 / 저장 dtype / null 가능 여부 / 대표값`으로 기입합니다.
대상은 `date`, `formatted_date`, `recipe_name`, `lot_id`, `slot_number`, `time`,
`measured_info`, 여섯 `*_dir_list`와 장비·fab 필드입니다.
과거 요구사항은 `time`·`measured_info`에 `None`을 허용하지만 현재 계약은 문자열입니다.
`None`, 빈 문자열, `[]`, `["no files"]`, 누락 키를 구분해 주십시오.

필요한 이유: null을 정상 값으로 꾸미지 않고 검색·표·JSON에서 같은 의미를 유지합니다.

> 답변: 미확인입니다. 필드 사전과 결측 샘플을 기입합니다.

### Q07. 날짜와 시각의 저장 규칙은 무엇입니까?

원천의 날짜·시각 및 상세 `Start Time`을 실제 값 그대로 제시하고, 시간대와
날짜만 존재하는 경우를 명시합니다. 선행 0, 초 생략, 자정 전후 사례가 있으면 포함합니다.

필요한 이유: 검색 표시와 See Together의 시간 정렬을 정확히 맞춥니다.

> 답변: 미확인입니다. 필드별 형식과 시간대를 기입합니다.

## 4. P0 — 상세와 Profile

### Q08. 상세 측정 파일을 읽은 결과는 어떤 구조입니까?

CSV면 인코딩·구분자·헤더·메타 정보 구간을, pickle이면 복원 객체의 키·타입·
DataFrame 컬럼과 dtype을 보내 주십시오. 같은 측정의 `information`, `summary`,
`data`, `available_points`로 이어지는 원천 위치를 표시합니다.

필요한 이유: Home 샘플이 정규화된 API뿐 아니라 실제 파일 구조도 재현하게 합니다.

> 답변: 미확인입니다. 파일 구조와 원천 → 응답 매핑을 기입합니다.

### Q09. 실제 측정 컬럼과 단위는 무엇입니까?

recipe·장비별 컬럼 사전을 보내 주십시오. 현재 프론트에는 `Left_H (nm)`,
`Right_H (nm)`, `Ref_H (nm)` 가정이 있고, 시계열 선택지는 이름에 `nm`가 있는
컬럼만 포함합니다. 다른 측정량·단위·수치 문자열·결측이 있으면 원래 형태로 알려 주십시오.

필요한 이유: 동적 컬럼과 단위가 다른 실제 recipe도 표시할 수 있게 합니다.

> 답변: 미확인입니다. 컬럼 사전과 recipe별 차이를 기입합니다.

### Q10. Site와 Point의 식별 관계는 무엇입니까?

`measurement_point`, `Site ID`, `Site X`, `Site Y`, `Point No`, `available_points`와
실제 profile·이미지 파일의 관계를 하나의 예로 보여 주십시오.
현재 상세 페이지는 Site 문자열만 선택하고 profile·이미지에 전달하며,
profile API의 선택적 `site_id/site_x/site_y/point_no`는 해당 화면에서 보내지 않습니다.
Site 문자열만으로 파일 하나를 결정할 수 있는지 확인합니다.

필요한 이유: 여러 Point가 있는 Site에서 임의 파일을 선택하는 일을 방지합니다.

> 답변: 미확인입니다. Site → Point → 파일 연결 예를 기입합니다.

### Q11. Summary의 통계 정의는 무엇입니까?

원천 요약을 그대로 읽는지 계산하는지 밝히고, `MEAN/STDEV/MIN/MAX/RANGE`의
집계 대상·유효값 제외 규칙·표준편차의 ddof를 명시합니다.
다른 `ITEM` 값이나 동일 `Site + ITEM`의 여러 행이 있으면 포함합니다.
가능하면 한 Site의 상세 행과 그 요약을 함께 보내 주십시오.

필요한 이유: mock의 요약과 상세가 수학적으로 일치하고 실데이터의 통계 의미를 보존합니다.

> 답변: 미확인입니다. 통계 정의와 대조 샘플을 기입합니다.

### Q12. Valid와 State의 의미와 실제 값은 무엇입니까?

`Valid`, 측정별 `*_Valid`, `State`의 값 목록·타입·실패 및 미확인 의미를 알려 주십시오.
현재 표의 Valid 수는 `Valid === true`인 행만 셉니다.

필요한 이유: `0/1`, 문자열, null 등을 잘못 해석하여 실패 값을 유효 측정으로 세지 않습니다.

> 답변: 미확인입니다. 값 사전과 실패·미확인 행을 기입합니다.

### Q13. 실제 Profile 데이터는 어떤 형태입니까?

한 파일의 헤더·shape·dtype·대표 행과 축 단위를 보내 주십시오.
1D 선형 profile인지 2D height map인지, 좌표가 실제 좌표인지 배열 index인지 명시합니다.
2D이면 격자 크기·순서·간격·원점·방향·결측을 포함합니다.
현재 mock의 20×20 XYZ 격자는 실데이터 근거가 아닙니다.

필요한 이유: 실제 profile이 지원하는 시각화를 결정하며 1D 데이터를 2D 표면으로 꾸미지 않습니다.

> 답변: 미확인입니다. 구조·단위·좌표 규칙과 작은 원본 샘플을 기입합니다.

### Q14. Profile 수치에는 어떤 전처리가 적용됩니까?

원본/leveling/flattening/필터링 중 저장된 데이터가 어느 단계인지, 높이 기준과
오류·포화·NaN·Inf 표현을 알려 주십시오. 실제 분포를 재현할 수 있도록
정상 및 이상 사례의 min/max/중앙값·분위수·결측 수를 함께 기입합니다.

필요한 이유: Heatmap·Histogram이 실제 수치 범위와 분석 의미를 재현합니다.

> 답변: 미확인입니다. 처리 단계와 분포 요약을 기입합니다.

## 5. P1 — 이미지, 비교, 조회 규모

### Q15. 종류별 실제 이미지 형식과 제공 방식은 무엇입니까?

Height·align·tip·capture·tiff 각각 실제 확장자·MIME·크기·읽기 경로와
기존 변환 함수가 있는지 기입합니다. 과거 요구사항은 WebP 등을 언급하지만
현재 이미지 provider와 route는 SVG 문자열 및 `image/svg+xml`을 사용합니다.
확장자가 아니라 실제 파일 내용으로 확인해 주십시오.

필요한 이유: 실이미지 제공에 계약 변경 또는 기존 변환 재사용이 필요한지 결정합니다.

> 답변: 미확인입니다. 종류별 메타데이터와 제공 가능한 샘플을 기입합니다.

### Q16. 파일 보유 표시와 실제 읽기 성공의 관계는 무엇입니까?

여섯 파일 목록에서 `has_profile/has_data/has_image/has_align/has_tip` 및
`point_count`를 만드는 규칙을 알려 주십시오. index에는 있지만 파일이 없거나
손상·권한 오류·업로드 중인 사례를 정상적인 빈 목록과 구분합니다.

필요한 이유: 파일 존재·미확인·조회 실패를 같은 빈 화면으로 처리하지 않습니다.

> 답변: 미확인입니다. 파생 규칙과 오류 사례를 기입합니다.

### Q17. 측정 간 비교가 가능한 조건은 무엇입니까?

동일 Site·측정 컬럼이 여러 recipe에서 같은 의미인지 알려 주십시오.
비교 가능한 측정 3건 이상의 연결된 샘플과, 비교하면 안 되는 사례가 있으면 보내 주십시오.

필요한 이유: See Together가 이름만 같은 서로 다른 측정량을 한 시계열로 연결하지 않습니다.

> 답변: 미확인입니다. 비교 조건과 샘플 식별자를 기입합니다.

### Q18. 장비별 데이터 규모와 갱신 주기는 어느 정도입니까?

조회 가능한 기간·총 건수·일별 증가량·파일당 상세/Profile 행 수·파일 크기의
대표값과 큰 사례를 알려 주십시오. 기존 조회의 제한·정렬·페이지 처리도 기입합니다.
현재 검색은 장비별 전체 목록을 받고 브라우저에서 필터링합니다.

필요한 이유: 전체 목록 조회를 유지할 수 있는지와 필요한 조회 범위를 결정합니다.

> 답변: 미확인입니다. 규모와 조회 제한을 기입합니다.

### Q19. 사무실 실행에 필요한 조건은 무엇입니까?

기존 클라이언트·파서·패키지 버전·환경 변수 이름·권한·네트워크 또는 mount 조건을
알려 주십시오. Phase 2 로컬 PC와 Phase 3 사내 클라우드의 접근 차이가 있으면 표시합니다.
자격 증명 값은 보내지 않습니다.

필요한 이유: Home에서 확인할 수 있는 범위와 Office에서만 확인할 연결 조건을 구분합니다.

> 답변: 미확인입니다. 실행 조건과 환경별 차이를 기입합니다.

## 6. 회신에 포함할 최소 샘플 묶음

기본 회신 파일은 `docs/afm/office-data-findings.md`로 작성해 주십시오.
샘플 파일을 공유할 수 없다면 구조·타입·대표 행을 해당 문서에 넣어도 됩니다.
식별자를 치환할 경우 같은 원본은 모든 샘플에서 같은 값으로 치환하고,
키·타입·null·선행 0·구분자·단위·파일 연결 관계는 유지합니다.

- [ ] 장비별 목록 대표 행 2건 이상과 원천의 최상위 구조를 포함합니다.
- [ ] 정상 측정 한 건의 index → 상세 → 두 Site 또는 Point의 Profile → 이미지 연결을 포함합니다.
- [ ] 실제로 관찰한 결측·실패·반복 측정 사례를 포함합니다. 없으면 `조회 범위 내 미관찰`로 적습니다.
- [ ] recipe별 컬럼·Site 구성이 다른 사례가 있으면 추가합니다.
- [ ] 시계열 비교 가능한 측정 3건 이상을 포함합니다.
- [ ] 이미지는 종류별 메타데이터와 가능한 샘플을 포함합니다. 이미지가 없어도 데이터 구조부터 회신합니다.
- [ ] 각 샘플에 원천 식별자, 조회 시각, 조회 방법, 전체 행 수, 발췌 여부를 적습니다.

      원래 값과 발췌 시 변환 규칙을 설명합니다.

## 7. Office 실행 증거와 Home의 후속 작업

### Office에서 남길 검증 근거

이미 연결된 어댑터가 있다면 `GET /api/health/providers`의 AFM 항목과 실제 API
응답을 함께 남겨 주십시오. 연결 전이면 원천 조회 결과만으로 충분합니다.
stub을 복사해서 office 모드를 켠 결과를 연결 검증으로 취급하지 않습니다.

실제 어댑터가 준비된 경우 아래 검증 결과를 남깁니다.

```bash
SKEWNONO_AFM_PROVIDER=office .venv/bin/python -m pytest backend/afm -q
```

통과·실패·skip 수와 원인을 기록합니다. 현재 갤러리 테스트에는 모든 행의 capture
존재와 네 종류 이미지 보유 등 mock에 의존하는 가정이 남아 있으므로,
실데이터와 충돌하면 사실을 바꾸지 말고 해당 테스트와 데이터 차이를 보고합니다.
빈 목록으로 skip된 계약 테스트는 상세/Profile 연결 증거가 아닙니다.

브라우저를 실행할 수 있다면 실제 측정으로 검색 → 상세 → Site 선택 → Profile·이미지
→ 그룹 시계열 → Excel 내보내기를 확인하고, 원천과 값·행 수가 일치하는지 기록합니다.
브라우저 확인을 못 했다면 그 범위를 명시합니다.

### Home에서 회신 후 채울 부분

1. 확인된 원천 사실은 `docs/datatables/<확인된-source>.txt`와
   `backend/afm/providers/mock.py`에 함께 반영합니다. source 이름은 조사 결과로 정합니다.
2. mock은 확인된 키·타입·결측·단위·분포·측정 간 연결 관계를 재현합니다.
   미확인 가정은 `OFFICE-VERIFY`로 표시합니다.
3. 장비/fab 목록, 동적 컬럼, Site/Point 선택, 이미지 형식 등 현재 UI·계약과
   충돌하는 부분을 실제 근거에 맞춰 수정합니다. `data.py`는 수정하지 않습니다.
4. 확인된 대표 샘플로 기존 테스트와 fixture를 보완하고 Home 화면을 검증합니다.
5. 실제 소스 연결과 사내 브라우저·클라우드 접근은 Office 검증으로 마무리합니다.

각 사실에는 `office 확인 YYYY-MM-DD`, 담당자 설명이면 `user-confirmed`,
추정이면 `OFFICE-VERIFY`를 붙입니다. 이 요청서 자체는 실데이터 확인 기록이 아닙니다.
