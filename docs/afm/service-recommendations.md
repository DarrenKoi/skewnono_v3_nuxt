# AFM 추가 서비스 추천 보고서

작성일: 2026-10-08

## 1. 보고서의 목적과 판단 기준

이 보고서는 현재 AFM 코드와 저장소에 기록된 사무실 데이터 확인 내용을 바탕으로 추가 서비스를 제안합니다. 신규 구현에 앞서 서비스의 목적, 필요한 데이터, 구현 범위, 검증 조건을 판단하는 문서입니다. 아래 구현 방식은 제안이며, 이미 구현된 동작과 구분하여 설명합니다.

사무실 데이터 근거는 2026-10-07까지의 확인 기록입니다. 이번 조사에서는 사무실 Redis와 MinIO에 접속하거나 브라우저에서 기능을 실행하지 않았습니다. mock 값은 실측 분포, 시간 형식, 인과관계의 근거로 사용하지 않습니다.

추천 순서는 다음과 같습니다.

| 순서 | 서비스 | 추천 이유 | 첫 구현 위치 |
| --- | --- | --- | --- |
| 1 | Lot·웨이퍼 이력 자동 연결 | 이전 측정을 찾고 그룹에 담는 수작업을 줄입니다. | 측정 상세와 검색 |
| 2 | 측정 소요시간 분석 | 같은 Recipe에서 오래 걸린 측정과 시간 분포를 찾습니다. | 선택 그룹 분석, 이후 가동 현황 |
| 3 | 팁 변경 전후 비교 | 팁 이력과 측정 결과를 연결하여 조사할 단서를 제공합니다. | 팁 모니터링과 시계열 비교 |
| 4 | 프로파일 비교·차이 보기 | 요약값만으로 보이지 않는 형상 변화를 비교합니다. | 측정 상세와 비교 화면 |
| 5 | 측정 항목 간 관계 분석 | 같은 위치의 여러 측정 항목이 함께 변하는지 확인합니다. | 상세 또는 시계열 비교 |
| 6 | 이상 측정 조사 묶음 | 값, 상태, 이미지, 프로파일을 같은 위치 기준으로 모읍니다. | 측정 상세 |
| 7 | 한 측정 안의 반복 회차 분석 | 같은 위치를 반복했을 때의 변화와 산포를 확인합니다. | 측정 상세, 회차 확인 이후 |

1번, 4번, 5번은 2026-10-09에 첫 범위를 구현했습니다. 구현한 범위와 남긴 범위는 3.5절에 있습니다.

7번은 필요성이 낮아서 마지막인 것이 아닙니다. 사무실에서 보고된 회차 표시 문제의 세부 답변을 먼저 받아야 합니다.

## 2. 현재 기능과 데이터 기반

### 2.1 이미 제공하는 기능

측정 검색·상세는 측정 목록, Info, Summary, 포인트별 값과 상태, 분석 이미지, 라인 또는 2D 프로파일, Excel 다운로드를 제공합니다.

시계열 비교는 선택한 측정의 추세, Recipe별 기준 범위(고정 기준선 포함), 포인트별 비교, 그룹 통계, 동일 sample 재측정 비교, 장비 건강을 제공합니다. 팁 모니터링, 가동 현황, Recipe 현황도 별도 페이지에 구현되어 있습니다.

추천 서비스는 이러한 기능을 재사용하거나 연결하는 방향입니다. 동일한 추세 차트와 이상치 표시를 새 페이지에 반복하는 것은 우선하지 않습니다.

### 2.2 확인된 데이터 종류

| 데이터 | 형태와 주요 내용 | 서비스 설계에 미치는 영향 |
| --- | --- | --- |
| 측정 목록 | Redis hash의 장비별 parquet. 측정키, 파일명, 날짜, Recipe, Lot, Slot, 측정 시각, 팁 요약, 파일 목록 | 목록만으로 후보 측정을 좁힐 수 있습니다. 상세 값은 별도 조회해야 합니다. |
| Info | MinIO의 name·value parquet. 13키 또는 15키 구성 | Sample ID와 팁 정보가 있습니다. 시작·종료 시각은 없는 측정도 있습니다. |
| Summary | method별 MEAN, STDEV, MIN, MAX, RANGE | 장비가 계산한 요약입니다. 빈 객체 또는 객체가 없는 측정도 있습니다. |
| 포인트 데이터 | method를 나타내는 Site, 위치 키, 측정값, State, Valid, Sample Count, Approach Count, Mileage | 위치별 비교와 반복 분석의 기반입니다. 측정하지 못한 위치는 행 자체가 없습니다. |
| 프로파일 | X·Y·Z parquet와 객체 metadata의 단위·DataSize·SurfaceSize | 파일마다 단위와 격자가 다릅니다. Z는 leveling하지 않은 원본이며 결측이 있습니다. |
| 이미지 | Result, align, tip, capture의 webp와 원본 | 위치별 자료와 측정 단위 자료가 섞입니다. 모든 위치에 모든 자료가 있지는 않습니다. |

다음 제약은 모든 서비스에 적용합니다.

- 목록은 30분마다 갱신되고 측정 시각 기준 3개월을 보존합니다. 실시간 상태나 전체 수명 이력으로 해석하지 않습니다.
- 웹은 저장된 측정 자료를 읽습니다. Redis와 MinIO 적재는 ETL이 담당합니다.
- MAP608의 목록 `time`은 세션 시각일 수 있습니다. 측정 시작 시각은 `measured_time` 또는 Info의 `Start Time`을 우선합니다.
- `point_count`는 실제 스캔 위치 수입니다. Recipe의 계획 위치 수나 반복을 포함한 데이터 행 수와 다릅니다.
- Summary의 `Site`는 method 이름이고 `Site ID`는 위치 식별자입니다.
- 서로 다른 Recipe의 같은 이름 컬럼이 같은 측정량이라는 근거는 없습니다.
- 추출 실패한 측정은 목록에 들어오지 않습니다. 목록만으로 전체 적재 성공률을 계산할 수 없습니다.
- 현재 상세 화면의 5~8초 지연 원인은 미해결입니다. 새 서비스가 전체 상세와 이미지를 미리 읽지 않도록 조회 범위를 제한합니다.

데이터 근거는 [Redis·MinIO 명세](../datatables/afm/afm_redis.txt), [원본 파일 명세](../datatables/afm/afm_raw_files.txt), [사무실 확인 기록](office-data-findings.md)입니다.

## 3. Lot·웨이퍼 이력 자동 연결

### 3.1 추천 목적

현재 사용자는 이전 측정을 검색한 뒤 그룹에 담아야 재측정 결과를 비교할 수 있습니다. 이 서비스는 상세 화면에서 같은 웨이퍼의 이전 측정을 찾고 비교까지 연결합니다.

예를 들어 같은 Lot·Slot의 측정 세 건을 시간순으로 놓고, 동일 Recipe의 이전 측정 대비 평균 변화와 팁 변경 여부를 함께 표시합니다. 다른 Recipe의 측정도 이력에는 표시하되 수치 비교는 분리합니다.

### 3.2 필요한 데이터

- 목록의 장비, `filename`, `unique_key`, `lot_id`, `slot_number`, `recipe_name`, 날짜와 `measured_time`입니다.
- 상세 Info의 `Sample ID`, `Lot ID`, `Start Time`입니다.
- 수치 비교에는 같은 block과 측정 항목의 Summary 또는 포인트 데이터가 필요합니다.
- 팁 표시에는 목록의 팁 식별 정보 또는 상세 Info를 사용합니다.

목록에는 Sample ID가 없습니다. 첫 단계는 같은 장비의 Lot·Slot으로 후보를 찾고, 사용자가 고른 후보의 상세에서 Sample ID를 확인하는 방식입니다. 전체 목록의 상세를 먼저 읽어 Sample ID 색인을 만들지 않습니다.

### 3.3 최소 구현 방식

1. 상세 화면에 같은 장비의 Lot·Slot 후보 목록을 표시합니다.
2. Slot이 없거나 Lot이 불명확하면 자동 연결 대신 추가 검색을 제공합니다.
3. Recipe 필터와 측정 시각 정렬을 적용합니다. 같은 시각이면 파일명 등으로 정렬을 고정합니다.
4. 사용자가 고른 후보만 상세 조회하고 Sample ID를 확인합니다.
5. 기존 비교 그룹에 담아 시계열 비교로 이동합니다. 그룹 한도 초과는 화면에서 명시합니다.
6. 동일 Recipe·block·컬럼의 이전 측정 대비 차이를 표시합니다.

기존 `prepareEntries`, `repeatPairs`, `useAfmCart`를 재사용합니다. 현재 그룹 한도는 `AFM_GROUP_MAX = 20`입니다. 파일 식별은 장비와 파일명을 함께 사용하며, 첫 범위는 같은 장비 안으로 제한합니다.

### 3.4 확인 사항과 검증 조건

Lot·Slot의 일치가 영구적인 동일 웨이퍼 식별을 보장하는지는 확인이 필요합니다. 첫 화면은 동일 웨이퍼 확정 이력보다 같은 Lot·Slot의 측정 후보로 설명합니다.

Slot의 선행 0 차이, Sample ID 불일치, 날짜 결측, 다른 Recipe, 다른 장비의 동명 파일을 검증합니다. 보존 기간 밖의 이력이 없다는 사실을 재측정이 없었다는 결론으로 바꾸지 않습니다.

근거: [목록 계약](../../backend/afm/contracts.py), [재측정 비교 로직](../../frontend/app/utils/afmTrend.ts), [비교 그룹](../../frontend/app/composables/useAfmCart.ts).

### 3.5 구현 상태 (2026-10-09)

측정 상세의 `같은 Lot·Slot 측정` 카드로 첫 범위를 구현했습니다. 화면 설명은 [기능 요약](feature-summary.md)의 3.2절에 있습니다.

| 3.3의 단계 | 상태 | 내용 |
| --- | --- | --- |
| 1. Lot·Slot 후보 목록 | 구현 | 같은 Slot 과 같은 Lot 의 다른 Slot 을 나누어 표시합니다. 숫자 Slot 은 선행 0 을 떼고 비교합니다. |
| 2. Slot·Lot 이 없을 때 | 일부 구현 | 자동 연결을 하지 않고 측정 검색에서 찾도록 안내합니다. 검색어를 채워 넘기는 연결은 만들지 않았습니다. |
| 3. Recipe 필터와 시각 정렬 | 구현 | 측정 시각순이며 같은 시각은 파일명으로 고정합니다. 그룹에 담는 기본 범위는 같은 Recipe 입니다. |
| 4. 후보의 Sample ID 확인 | 미구현 | 후보의 상세를 미리 읽지 않습니다. 사용자가 후보의 상세를 열어 확인합니다. |
| 5. 그룹에 담아 시계열 비교로 이동 | 구현 | 남은 자리를 넘으면 지금 연 측정에 가까운 순으로 담고 남은 건수를 표시합니다. |
| 6. 이전 측정 대비 차이 표시 | 미구현 | 수치 비교는 그룹에 담은 뒤 시계열 비교에서 봅니다. 팁 변경 표시도 같습니다. |

목록에 Sample ID 열이 생기면 4번을 상세 조회 없이 처리할 수 있습니다. 이 열의 추가는 적재 담당에 요청할 후속 항목입니다.

측정 항목 간 관계 분석(7절)도 같은 날 시계열 비교의 `06 측정 항목 간 관계` 구역으로 첫 범위를 구현했습니다. 화면 설명은 [기능 요약](feature-summary.md)의 3.3절에 있습니다.

| 7.3의 항목 | 상태 | 내용 |
| --- | --- | --- |
| X·Y 항목 선택기 | 구현 | 선택한 블록에서 숫자 값이 있는 측정 항목을 제공합니다. X 에는 행의 `Mileage` 와 `Approach Count` 도 제공합니다. |
| 같은 행의 두 값을 한 점으로 | 구현 | 그룹의 측정 전체에서 행 단위로 짝을 짓습니다. 반복 회차는 평균하지 않고 회차마다 한 점입니다. |
| 축의 컬럼 이름과 단위 | 구현 | 컬럼 이름을 그대로 씁니다. 측정 항목은 이름에 `(nm)` 가 있으며, `Mileage` 에는 단위를 붙이지 않습니다. |
| 완료·유효성 조건과 제외 행 수 | 구현 | 측정별 요약의 유효 행 규칙(COMPLETED 이고 Valid 가 FALSE 가 아님)을 그대로 씁니다. 제외한 행, 값이 없는 행, Valid 미상 행의 수를 표시합니다. |
| 표본 수와 상관계수 | 구현 | n 과 Pearson r 을 표시합니다. 3개 미만이거나 한 축의 분산이 0 이면 계산 불가로 표시합니다. |
| 항목 간 차이 | 7.3 그대로 | 내지 않습니다. 같은 단위라도 같은 측정량이라는 보장이 없으므로 차이를 지표로 제안하지 않습니다. |
| Recipe 혼합 | 구현 | 하나의 관계로 합치지 않습니다. 포인트별 비교와 같이 선택한 측정의 Recipe 만 사용합니다. |

회귀선, 규격·관리 한계 판정, 팁 변경 전후 구분, 위치(Site X·Y) 배치는 만들지 않았습니다. 컬럼별 `<측정명>_Valid` 는 제외 조건에 쓰지 않습니다. home mock 의 값은 지어낸 것이므로 집에서 보이는 관계는 실측 근거가 아닙니다.

같은 날 시계열 비교의 `02 포인트별 비교` 구역에 `FAILED · Valid FALSE 행` 의 `포함`·`제외` 선택을 더했습니다. 06 구역은 유효 행 규칙으로 행을 빼고 02 구역은 모든 행을 그려 두 구역이 같은 자료를 다르게 보여 주던 것을 사용자가 맞출 수 있게 한 것입니다. 기본은 이전과 같은 `포함` 입니다. `제외` 는 포인트 × 측정과 포인트 안정도에만 적용하며, 반복 측정 포인트는 마지막 유효 회차의 값을 쓰고 유효한 행이 없는 포인트는 그 측정에서 뺍니다. 해당하는 행 수를 선택 옆에 표시합니다. 01, 05, 06, 07 구역은 바꾸지 않았습니다.

측정 소요시간 분석(4절)에는 같은 날 포인트당 소요시간을 더했습니다. 시계열 비교의 `05 측정 소요시간` 구역에 표시합니다.

| 항목 | 상태 | 내용 |
| --- | --- | --- |
| 측정별 포인트당 시간 | 구현 | 소요시간을 그 측정의 data 행 수로 나눕니다. 나눈 행 수를 값 옆에 표시합니다. |
| 분모 | 4.4의 제외 사유 해소 | 목록의 `point_count` 를 쓰지 않습니다. 이미 읽은 상세의 data 행을 세므로 반복 회차가 들어갑니다. 블록이 여럿이면 행이 가장 많은 블록 하나만 세고, FAILED·STOPPED 행도 셉니다. |
| Recipe 별 중앙값 | 구현 | 포인트당 시간이 계산된 측정만으로 중앙값을 냅니다. |
| 계산하지 않는 경우 | 구현 | 소요시간이 없으면 기존 사유를 그대로 표시합니다. data 행이 없는 측정에는 포인트당 시간을 내지 않습니다. |

블록이 여럿인 측정에서 블록마다 다시 스캔하는지는 확인되지 않았습니다. 같은 측정값을 블록(method)별로 분석한다고 보고 한 블록만 셉니다. 이 값은 기록상 시작·종료 간 경과시간을 나눈 것이며 순수 스캔 시간, 가동률, OEE 로 해석하지 않습니다. P90 과 포인트당 시간 기준의 `중앙값의 N배` 는 만들지 않았습니다.

측정 상세에는 같은 날 `Site 인덱스 격자` 카드를 더했습니다. 이 보고서의 추천 항목에는 없던 기능이며, 7절에서 만들지 않았던 위치(Site X·Y) 배치를 한 측정 범위로 구현한 것입니다.

## 4. 측정 소요시간 분석

### 4.1 추천 목적

같은 Recipe의 측정이 보통 얼마나 걸리는지, 어느 측정이 평소보다 오래 걸렸는지 확인합니다. 측정 결과 변화와 함께 팁, Approach Count, 미완료 상태를 조사할 수 있습니다.

시작·종료 시각이 계산 가능한 측정만으로 서비스할 수 있습니다. 전체 장비 가동률이나 순수 스캔 시간으로 확대 해석하지 않습니다. 첫 지표 이름은 기록상 시작·종료 간 경과시간으로 정의합니다.

### 4.2 필요한 데이터와 현재 공백

15키 Info에는 `Start Time`과 `End Time`이 있습니다. 13키 Info에는 둘 다 없습니다. 장비별로 구성이 섞이므로 장비 이름만으로 계산 가능 여부를 정하지 않습니다.

Recipe, Lot, Slot, 상태, 반복 구성은 비교 대상을 나누는 데 사용합니다. 측정 순서로 정렬할 때는 목록의 세션 `time`이 아니라 `measured_time`을 사용합니다.

2026-10-08에 사용자가 전한 실측으로 다음이 확인되었습니다. 원문은 [사무실 확인 기록](office-data-findings.md)의 12차에 있습니다.

- 두 값의 표기는 `2026.10.01 00:13:58` 하나이며 날짜가 함께 기록됩니다.
- 두 값은 data CSV의 Info에만 있습니다. MAPC01은 현재 data CSV가 없어 계산할 수 없으므로 분석 대상에서 제외합니다. info CSV의 `Date`로 대신 계산하지 않습니다.
- `End Time`은 측정이 끝난 뒤에만 기록됩니다.
- 자정을 넘긴 측정이 실제로 있습니다(22:32:28 시작, 00:11:13 종료).
- MAP608에서 파일명의 측정 시각 자리가 `NA`인 측정은 `Start Time`이 유일한 시각 원천입니다.
- MAP608의 일부 측정에는 `End Time`이 아예 없습니다. 이런 측정은 분석하지 않고, 화면에 `End Time`이 없다는 것을 표시합니다.

두 값이 파일에 남는지는 AFM 장비의 설정에 달려 있습니다. 분석이 쓸모 있으면 엔지니어가 설정을 바꿀 수 있으므로, 지금 값이 있는 측정만 분석하고 계산 가능 여부는 장비 이름이 아니라 값의 유무로 판단합니다. 값이 생긴 장비는 코드 변경 없이 분석 대상이 됩니다.

mock의 소요시간 분포는 만들어 넣은 값입니다. 중단된 측정에서 `End Time`이 어떻게 기록되는지도 확인되지 않았습니다.

### 4.3 시간 형식 처리 제안

확인된 표기 `YYYY.MM.DD HH:mm:ss` 하나만 명시적으로 읽습니다. 다른 표기는 계산 불가로 분류하고 원문을 표시합니다. 브라우저의 `Date.parse`가 이 표기를 읽는 것은 표준이 보장하는 동작이 아니므로 파서가 자릿수를 직접 검증합니다.

시간대 표시가 없으므로 KST로 읽습니다. 브라우저나 서버의 로컬 시간대에 따라 결과가 달라지지 않게 계산합니다.

시작과 종료에 날짜가 있으므로 자정 통과는 보정 없이 계산됩니다. 종료가 시작보다 이르면 잘못된 기록으로 분류합니다. 시작과 종료가 같으면 0으로 계산하며, 결측을 0으로 바꾸지 않습니다.

### 4.4 최소 구현 방식

첫 구현은 이미 상세를 읽는 선택 그룹에 소요시간 표와 Recipe별 분포를 추가하는 것입니다. 전체 보존 기간의 모든 상세를 자동으로 읽지 않습니다.

파서의 결과는 계산 가능, 값 없음, 형식 미지원, 종료 역전으로 나눕니다. 계산 가능한 결과에는 원본 시각, 해석한 시작·종료, 초 단위 경과시간을 유지합니다.

Recipe별 중앙값, P90, 최솟값, 최댓값과 표본 수를 표시합니다. P90은 최소 표본 기준을 구현 시 정하고, 기준 미달이면 숨기거나 작은 표본임을 표시합니다. 정상 완료와 미완료를 분리하며 상태를 알 수 없는 측정도 별도로 표시합니다.

반복 횟수와 측정 구성이 다른 자료는 나누어 비교합니다. `point_count`는 반복 행 수가 아니므로 이를 단순 분모로 사용한 포인트당 시간은 첫 범위에서 제외합니다.

가동 현황 전체로 확장할 때는 ETL이 계산 가능한 소요시간과 계산 상태를 목록에 적재하는 방식이 적합합니다. 이 열은 현재 존재하지 않습니다. 전체 분석을 위해 이 적재 변경을 선택한다면 데이터 명세와 mock도 함께 갱신합니다.

### 4.5 검증 조건

- 확인된 표기와 그 밖의 표기(`-` 구분, 초 없음)를 검증합니다.
- 윤년, 존재하지 않는 날짜, 24시 이상, 60분 이상을 검증합니다.
- 자정 통과(22:32:28 → 00:11:13은 98분 45초), 종료 역전, 같은 시각, 결측을 검증합니다.
- MAPC01처럼 두 값이 없는 장비를 계산 불가로 표시하는지 확인합니다.
- MAP608의 세션 시작 시각을 측정 시작으로 쓰지 않는지 확인합니다.
- 13키 Info를 계산 불가로 표시하고 평균의 분모에서 제외하는지 확인합니다.
- 예를 들어 대상 100건 중 계산 가능 72건이라면 분석 표본이 72건임을 명시합니다.
- 사무실 표본으로 직접 계산한 시간과 화면 값을 대조합니다.

## 5. 팁 변경 전후 비교

### 5.1 추천 목적

팁 모니터링은 팁 상태를, 시계열 비교는 측정 결과를 보여 줍니다. 이 서비스는 두 정보를 연결하여 팁이 달라진 전후에 측정 결과와 경과시간이 어떻게 바뀌었는지 비교합니다.

결과는 원인 확정이 아니라 조사할 단서입니다. 제품이나 측정 조건이 함께 달라졌다면 팁 효과로 해석하지 않습니다.

### 5.2 필요한 데이터

팁 종류와 위치는 `Tip ID`, `Tip Cassette ID`, `Tip Port No`, `Tip Slot No`로 식별합니다. `Last Pick Up Time`과 Mileage는 같은 위치에 새 팁을 넣은 것으로 추정할 단서입니다.

측정 시각, Recipe, block, 측정 컬럼, Summary, Approach Count, State를 함께 사용합니다. 소요시간이 계산된 측정에는 경과시간도 연결합니다.

### 5.3 최소 구현 방식

기존 `healthSeries`와 `tipChanges`로 팁 변경 추정 시점을 구합니다. 선택한 시점의 전후에서 같은 Recipe·block·항목을 가진 측정만 비교합니다.

첫 화면은 사용자가 전후 측정을 선택하도록 하고, 기본 후보 수와 기간은 화면에서 조정할 수 있게 합니다. 전후 평균 또는 중앙값, 산포, 미완료가 있는 측정 비율, Approach Count를 표와 추세로 표시합니다. 전후 표본 수와 Lot·Slot 구성을 함께 보여 줍니다.

실제 교체 기록이 없으므로 이벤트 이름은 팁 변경 추정입니다. 같은 팁 정보에서 Mileage가 줄었다는 이유만으로 교체를 확정하지 않습니다. 기존 로직처럼 Pick Up 변경과 함께 해석합니다.

### 5.4 확인 사항과 검증 조건

Mileage 단위와 장비 재시작·수동 초기화 동작은 미확인입니다. MCNT 폭의 변동도 마모로 확정하지 않습니다.

팁 식별값 결측, 다른 Recipe 혼입, 전후 표본 부족, 같은 팁 위치의 재사용을 검증합니다. 미완료 비율은 그 값을 아는 측정만 분모로 사용합니다. 개별 위치 행의 실패율이 필요하면 상세의 행 수를 별도로 사용합니다.

## 6. 프로파일 비교·차이 보기

### 6.1 추천 목적

현재는 선택한 위치 하나의 프로파일을 확인합니다. 기준 측정과 현재 측정의 형상을 함께 보면 평균이 비슷해도 달라진 구간을 찾을 수 있습니다.

첫 범위는 같은 Recipe·block·위치의 1D 라인 두 개를 겹쳐 그리는 기능입니다. 2D 차이 맵은 좌표와 격자가 맞는 자료에서 후속으로 제공합니다.

### 6.2 필요한 데이터

선택한 두 측정의 X·Y·Z, 단위, DataSize, SurfaceSize와 위치 식별 정보가 필요합니다. 5EAP1501은 현재 확인된 데이터에 프로파일이 없습니다. 다른 장비도 모든 위치에 프로파일이 있는 것은 아닙니다.

프로파일 Z는 원본 높이입니다. leveling을 하지 않았고 결측값을 포함합니다. 단위는 파일마다 다르며 Pixel도 포함할 수 있습니다.

### 6.3 최소 구현 방식

사용자가 기준과 비교 측정, 위치를 고르면 두 프로파일만 조회합니다. 단위를 확인하고 같은 좌표의 값을 겹쳐 표시합니다. 물리 단위 변환은 확인된 대응만 사용하며 Pixel을 길이 단위로 바꾸지 않습니다.

처음에는 같은 좌표의 교집합으로 차이를 계산합니다. 좌표가 다르면 비교 불가 또는 공통 좌표 부족으로 표시합니다. 자동 정렬이나 보간은 실제 필요가 확인된 뒤 추가합니다.

원본 높이 비교를 기본으로 제공합니다. 평균 높이를 제거하는 보정 비교를 추가한다면 적용 여부와 보정량을 표시하고 원본을 보존합니다. 평면 leveling을 원본에 조용히 적용하지 않습니다.

평균 차이, 최대 절대 차이, RMSE는 비교에 사용한 유효 좌표 수와 함께 표시합니다. 수치 계산은 전체 프로파일을 읽는 백엔드에서 하고 차트용 결과만 솎는 방식이 적합합니다. API에 이미 있는 `full=1`은 원본 표본 접근 수단으로 재사용할 수 있지만, 큰 원본 두 개를 브라우저에 상시 보내지는 않습니다.

### 6.4 확인 사항과 검증 조건

단위 불일치, 1D·2D 혼합, 좌표 불일치, 결측, 파일 없음, 같은 프로파일의 차이 0을 검증합니다. 차트용으로 솎은 데이터에서 계산한 값을 전체 원본 통계로 표기하지 않습니다.

현재 화면은 최대 65,536점으로 솎은 프로파일을 받을 수 있습니다. Excel은 시트 한도 내에서 전체 표본을 다시 요청합니다. 원본 분석과 표시 표본을 구분하는 계약을 유지합니다.

근거: [프로파일 계약](../../backend/afm/contracts.py), [표시 표본 처리](../../backend/afm/profile_sampling.py), [현재 프로파일 화면](../../frontend/app/components/afm/detail/HeatmapChart.vue), [원본 조회 경로](../../backend/afm/routes.py).

## 7. 측정 항목 간 관계 분석

### 7.1 추천 목적

같은 위치에서 측정한 두 항목이 함께 변하는지 확인합니다. Left_H와 Right_H의 불균형, Ra와 Rq의 관계, 높이와 거칠기의 동반 변화가 조사 후보입니다. 해당 컬럼이 실제 존재하는 Recipe에만 제공합니다.

### 7.2 필요한 데이터

동일 Recipe·block의 포인트 행과 두 측정 컬럼, 위치 키, 상태, Valid가 필요합니다. 반복 자료를 포함하려면 회차도 구분해야 합니다.

컬럼 이름은 고정하지 않습니다. 실제 자료에는 1_Minimum부터 51_Minimum까지의 컬럼과 다양한 접두 이름이 있습니다.

### 7.3 최소 구현 방식

기존 컬럼 탐색과 숫자 변환 함수를 재사용하여 X·Y 항목 선택기를 만듭니다. 두 값이 모두 있는 같은 행을 산점도의 한 점으로 사용합니다. 각 축에 컬럼 이름과 단위를 표시합니다.

완료·유효성 조건을 명시하고, Valid 미상은 확정 유효와 구분합니다. 비교에서 제외한 행 수를 표시합니다. 동일 단위라도 서로 다른 측정량이면 항목 간 차이를 자동으로 의미 있는 지표라고 제안하지 않습니다.

첫 범위는 산점도와 표본 수입니다. 상관계수를 추가할 때는 표본 부족 또는 한 축의 분산이 0인 경우를 계산 불가로 표시합니다. 상관관계를 원인으로 설명하지 않습니다.

### 7.4 검증 조건

숫자 문자열, 결측, 상수 컬럼, 다양한 이름, block별 컬럼 차이와 반복 위치를 검증합니다. Recipe가 섞인 자료를 하나의 상관계수로 집계하지 않습니다.

## 8. 이상 측정 조사 묶음

### 8.1 추천 목적

관리선 밖의 측정이나 FAILED 위치를 선택하면 해당 위치의 값, 상태, 이미지와 프로파일을 한 화면에서 확인합니다. 기존 개별 조회와 다운로드를 조사 흐름으로 연결하는 서비스입니다.

현재 상세 화면에 자료들이 이미 있으므로 첫 단계는 새 저장 시스템보다 기준 측정과 비교 측정을 같은 위치로 동기화하는 것입니다.

### 8.2 필요한 데이터

파일·장비·Recipe·block·위치 식별자, 측정값, State, Valid와 각 이미지 목록을 사용합니다. 선택한 자료의 원본 다운로드 주소도 재사용합니다.

Result, point별 tip 이미지, capture는 위치와 연결될 수 있습니다. align과 측정 단위 C_Result는 위치별 자료가 아니므로 측정 전체 자료로 표시합니다.

### 8.3 최소 구현 방식

이상 측정에서 상세로 이동할 때 선택 위치와 이상 판단 항목을 전달합니다. 기준 측정을 고르면 같은 위치의 값과 이미지를 나란히 표시합니다. 사용자가 선택한 이미지 종류만 조회하고 모든 이미지를 미리 읽지 않습니다.

첫 범위는 조사 화면과 기존 링크·Excel·이미지 ZIP 활용입니다. 완성된 조사 보고서 파일 생성은 실제 공유 요구가 확인된 뒤 추가합니다.

### 8.4 확인 사항과 검증 조건

capture·Result·프로파일이 없다는 이유만으로 장비나 ETL 이상이라고 표시하지 않습니다. 자료 없음, 보존 기간에 따른 삭제, 조회 실패를 가능한 범위에서 구분합니다.

5EAP1501의 capture 꼬리 `_003`을 point 3으로 연결하는 것은 아직 가정입니다. 이 관계가 확인되기 전에는 확정 매칭 자료로 취급하지 않습니다. 반복 회차마다 별도 이미지가 있는 것처럼 표시하지 않습니다.

근거: [이미지 목록과 다운로드](../../backend/afm/routes.py), [분석 이미지 화면](../../frontend/app/components/afm/detail/AnalysisImages.vue), [파일과 위치 연결의 남은 확인](../datatables/afm/afm_redis.txt).

## 9. 한 측정 안의 반복 회차 분석

### 9.1 추천 목적

동일 웨이퍼의 서로 다른 측정 파일 비교와 구분되는 서비스입니다. 한 측정 파일 안에서 같은 위치를 여러 번 측정했을 때 회차별 값과 산포, 실패를 확인합니다.

같은 위치의 1회차·2회차 차이, 회차가 진행되면서 값이 한 방향으로 이동하는 현상, 일부 위치에서만 나타나는 불안정성을 찾습니다.

### 9.2 필요한 데이터와 선행 조건

`Site`로 block을 구분하고 `measurement_point`로 위치를 구분합니다. `Sample Count`, 행 순서, 측정 컬럼, 상태를 사용하여 회차를 해석합니다.

사무실 확인에 따르면 반복 Recipe는 모든 Site를 돈 뒤 다시 돌며 Sample Count가 바뀝니다. 그러나 Sample Count의 전체 의미는 미확인입니다. 반복이 없는 자료에서도 값이 있고, 시작값은 1로 고정되지 않습니다.

현재 `tagLaps`는 block·위치별 등장 횟수로 회차를 붙입니다. 사무실에서 회차가 기대와 달랐다는 보고가 있고 세부 답변을 받지 못했으므로, 실제 반복 표본으로 매핑 규칙을 먼저 확정합니다.

### 9.3 최소 구현 방식

회차별 원본 행 표를 먼저 제공합니다. 위치별 반복값, 첫 회차 대비 차이, 표본 수, 평균·표준편차·범위와 상태를 추가합니다. 불완전한 마지막 회차는 없는 위치를 결측으로 두며 0이나 앞 회차 값으로 채우지 않습니다.

현재 `measurementStats`의 포인트 Map은 같은 위치가 반복되면 마지막 값을 남깁니다. 회차 분석에서는 block·위치·회차를 구분하여 모든 반복을 보존해야 합니다. 장비 Summary와 회차별 재계산 통계는 출처를 구분합니다.

이미지와 프로파일은 반복마다 별도로 저장되지 않습니다. 반복 수치 분석에는 사용하지만 특정 회차의 이미지라는 설명을 붙이지 않습니다.

### 9.4 검증 조건

사무실에서 기대 회차를 표시한 표본과 결과를 대조합니다. 다중 block, 시작값이 1이 아닌 Sample Count, 반복 없음, 중단된 마지막 회차, 누락 위치와 동일 위치 반복값 보존을 검증합니다.

이 서비스의 결과를 정식 GRR로 부르지 않습니다. GRR에는 측정자, 부품, 반복 구성과 통제된 실험 계획이 추가로 필요합니다.

근거: [반복 행의 적재 규칙](../datatables/afm/afm_redis.txt), [현재 회차 부여](../../frontend/app/utils/afmPoints.ts), [현재 포인트 집계](../../frontend/app/utils/afmTrend.ts), [남은 사무실 질문](office-data-findings.md).

## 10. 공통 구현과 검증 원칙

기존 페이지, API, 컬럼 탐색, 통계 함수, 다운로드 기능을 먼저 재사용합니다. 프런트엔드 조회는 기존 `useAsyncData` 패턴을 따르고, 선택값이 바뀔 때 오래된 결과를 현재 선택의 값처럼 표시하지 않습니다.

전체 목록으로 후보를 좁히고 사용자가 고른 측정만 상세 조회합니다. 모든 측정의 프로파일과 이미지를 미리 읽는 방식은 피합니다. 목록 집계만으로 충분한 서비스는 목록을 사용하며, 장기간 전체 분석이 필요할 때만 ETL 요약 열을 추가합니다.

데이터 접근은 provider를 통합니다. 기존 dispatcher인 `backend/afm/data.py`는 수정하지 않습니다. API 확장이 필요하면 기존 provider 함수로 구성할 수 있는지 먼저 확인합니다. 현재 목록에 없는 분석 열을 추가한다면 계약, tracked office template, mock, 데이터 명세를 함께 맞춥니다. 사무실의 gitignored `office.py`는 template 갱신 이후 별도 동기화와 검증이 필요합니다.

검증은 서비스별 핵심 계산과 결측·형식·매핑 경계 사례에 집중합니다. UI 변경은 실제 실행 화면에서 로딩, 일부 조회 실패, 빈 결과, 선택 변경을 확인합니다. home mock의 통과를 사무실 데이터 검증으로 표현하지 않습니다.

## 12. 구현 순서 제안

첫 번째 단위는 Lot·Slot 후보 자동 연결과 기존 비교 그룹 이동입니다. 새 분석 계산을 많이 추가하지 않고 탐색 시간을 줄일 수 있습니다.

두 번째 단위는 실제 Start·End Time 표본에 맞춘 소요시간 파서와 선택 그룹 분석입니다. 표본 확인과 계산 제외 사유가 완성되면 가동 현황의 전체 기간 분석에 필요한 ETL 요약 적재를 판단합니다.

세 번째 단위는 팁 변경 추정 시점의 전후 비교입니다. 앞 단계의 경과시간 결과도 함께 연결합니다.

그다음 동일 좌표의 1D 프로파일 두 개를 비교합니다. 측정 항목 관계 분석과 조사 묶음은 기존 화면에 필요한 만큼 추가합니다. 반복 회차 분석은 실물 매핑 규칙이 확인된 뒤 진행합니다.
