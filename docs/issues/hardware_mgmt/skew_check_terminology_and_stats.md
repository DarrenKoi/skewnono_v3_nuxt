# 장비간 스큐 — 용어 정의와 통계 입도의 과학적 근거

- 작성일: 2026-05-31
- 상위 설계: `docs/superpowers/specs/2026-05-31-tool-skew-mgmt-design.md`
- 원천 이슈: `docs/issues/hardware_mgmt/skew_btw_tools.txt`
- 목적: 스큐 정량화 엔진(설계 스펙 §3)이 쓰는 **용어**와, 잔차·스큐를 **어느
  입도로 계산하는가**에 대한 결정 및 그 과학적 근거를 한곳에 고정합니다. office에서
  `data.py`를 실데이터로 스왑할 때 잘못된 단순화로 회귀하지 않도록 근거를 함께
  남깁니다.

## 1. 측정 데이터의 실제 구조

스큐를 어떻게 계산할지 정하기 전에, 한 번의 측정이 실제로 무엇을 만들어 내는지
확정합니다.

| 항목 | 값 | 비고 |
| --- | --- | --- |
| Wafer 당 site 수 | 9개 | Recipe가 지정하는 nominal 측정 위치 |
| site 당 측정점 | 보통 2개 | site 위치에서 **주변을 무작위로 접근**해 측정 |
| Wafer 1장·1장비 | 18점 | 9 site × 2점 |
| site index 매칭 | 가능 | 장비 간 같은 site index는 같은 nominal 위치 |
| 측정점 매칭 | **불가** | 같은 site라도 장비마다 무작위 위치를 찍음 |

핵심 사실 두 가지입니다.

- **site index는 장비 간 매칭됩니다.** 같은 Recipe·같은 Wafer이므로 site 1은 모든
  장비에서 같은 nominal 위치입니다.
- **측정점은 매칭되지 않습니다.** site 안에서 무작위로 접근하므로, 장비 A와 B가
  물리적으로 같은 점을 찍지 않습니다.

또한 CD_MONITORING조차 Wafer 안에서 CD 산포가 존재합니다(약 ±0.1nm 범위). 다른
Run Lot Recipe는 산포가 더 큽니다. 즉 "한 장비 = 한 숫자"가 아니라, 한 장비는 한
Wafer에서 **측정점 분포**를 만듭니다.

## 2. 용어 정의 (확정)

| 용어 | 한국어 라벨 | 정의 |
| --- | --- | --- |
| fleet | 함대 | **그날 그 cell을 실제로 측정한 장비들의 집합.** 등록된 전체 장비가 아니라 당일 측정분만. 항상 한 팹 내부로 한정합니다. |
| consensus | 기준값 | 같은 cell·같은 site·같은 날, fleet 장비들의 site 평균에 대한 **로버스트 중앙값**. 절대 진실값(true CD)이 아니라 fleet 스스로의 합의입니다. |
| 잔차(residual) | 잔차 | `tool − consensus` (부호 고정). 양수는 기준값보다 **높게 읽음**을 뜻합니다. 한 장비가 기준값에서 얼마나 벗어났는지의 상대 편차입니다. |
| skew | 스큐 | 윈도우 내 그 장비 잔차의 계통 평균(nm). 장비쌍 스큐 = `\|skew_i − skew_j\|`. |
| skew 윈도우 | — | 최근 10개 측정 **또는** 1주일. site당 점이 적어 하루치로는 불안정하므로 윈도우로 풀링합니다(§5). |
| TTTM | 상호 매칭 | Tool to Tool Matching. 두 장비의 장비쌍 스큐 ≤ tolerance이면 두 장비는 상호 TTTM입니다. |
| N배화 | N배화 | N개 장비가 서로 *모두* TTTM된 상태(N = 장비 수). 완전연결(clique)과 동치이며, 추천 그룹의 단위입니다. |

부호 규약 예시입니다.

```text
같은 cell · 같은 날, fleet의 장비들이 같은 Wafer를 측정:
  tool_A site평균 = 16.12,  tool_B = 16.05,  tool_C = 16.20

기준값(consensus) = 로버스트 중앙값 = 16.12

잔차 = tool − 기준값:
  A: +0.00,  B: −0.07(낮게 읽음),  C: +0.08(높게 읽음)
```

잔차는 최종 지표가 아니라 **재료**입니다. 잔차 → 스큐 → 장비쌍 스큐 순으로
쌓입니다.

## 3. 분산 분해 — 왜 입도가 문제인가

한 측정점의 CD를 다음과 같이 분해합니다.

```text
CD(tool t, site s, k번째 무작위점)
   = TrueCD(s)        ← site 간 변동 (Wafer 패턴, ±0.1nm 범위) — 보존 대상
   + LocalVar(s, ·)   ← site 내 무작위 변동 — 무작위 접근 때문
   + ToolSkew(t)      ← 측정 대상 (제거·관리하려는 장비 오염)
   + noise            ← 측정 잡음
```

북극성은 "장비 스큐가 결과를 오염시키지 않는(= Wafer 본연의 산포만 드러나는)
장비 조합"입니다. 즉 `TrueCD(s)`는 **보존**하고 `ToolSkew(t)`만 **분리**해야 합니다.

각 성분이 site-index 매칭에서 어떻게 행동하는지가 결정의 핵심입니다.

| 성분 | 성격 | site-index 매칭 시 | 처리 |
| --- | --- | --- | --- |
| `TrueCD(s)` | site 간, 구조적, 큰 신호 | 같은 site면 모든 장비에 공통 | **상쇄**로 제거 |
| `LocalVar` | site 내, 무작위, 작음 | 장비마다 다른 점 → 상쇄 안 됨 | **평균으로 감쇠**(상쇄 아님) |
| `ToolSkew` | 장비 고유 | 그대로 남음 | 측정 대상으로 유지 |
| `noise` | 무작위 | — | 평균으로 감쇠 |

따라서 입도는 "정확한 점 매칭"이 아니라 **"site-index로 묶고, site 안 무작위점을
평균"** 입니다. site 간 패턴은 상쇄로 완전 제거하고, site 내 무작위는 점 개수만큼
표준오차를 줄여 감쇠합니다.

## 4. 전체 평균은 무엇이 문제인가

"Wafer 전체를 평균낸 한 값으로 장비를 비교하면 안 되는가"라는 질문에 대한
정확한 답은 **조건부**입니다.

### 4.1 전체 평균이 괜찮은 경우

모든 장비가 같은 9개 site를 같은 횟수로 측정하면, Wafer 패턴 `TrueCD(s)`는 모든
장비의 전체 평균에 동일하게 들어가 장비 차에서 깨끗이 상쇄됩니다. 이 **완전 균형**
상황에서는 offset 스큐 값 자체는 site별 계산과 같게 나옵니다.

### 4.2 전체 평균이 깨지는 세 가지 경우

**① 공간적 어긋남을 숨깁니다 (가장 중요).** 평균은 부호가 다른 오차를 상쇄시켜,
*평균은 같지만 site마다 다른* 두 장비를 구분하지 못합니다.

```text
site:        1      2      3     전체평균
Tool A:   +0.10   0.00  −0.10  →   0.00
Tool B:    0.00   0.00   0.00  →   0.00
─────────────────────────────────────────
전체평균 차 = 0           → "두 장비 완벽 일치"라고 거짓 보고
site별 차  = +0.10, 0, −0.10  → 실제로는 전혀 일치하지 않음
```

A는 좌우로 기운 장비, B는 평평한 장비입니다. 어떤 Recipe가 주로 site 1 위치를
측정한다면 A·B 조합은 그 위치에서 0.1nm 스큐를 냅니다. 추천은 Wafer 전체가 아니라
**Recipe가 점유하는 site/대역의 일치도**를 기준으로 해야 하므로, 이 정보를 숨기는
전체 평균은 부적합합니다.

**② 무작위·불균형 샘플링에서 패턴이 새어듭니다.** site당 2점 무작위이므로 측정
실패·스킵·점 수 차이로 장비 간 site 커버리지가 조금만 어긋나도, `TrueCD(s)`
(±0.1nm — 찾으려는 스큐보다 큰 신호)가 평균 차에 불균형하게 섞입니다. 찾는 스큐가
~0.05nm인데 패턴이 0.2nm 범위면 작은 불균형이 신호만 한 편향을 만듭니다.
site-index로 묶어 공통 site만 비교하면 패턴은 정의상 상쇄되어 이 누수가 사라집니다.

**③ 추정 정밀도가 나빠집니다.** site 매칭은 통계의 블로킹(blocking·대응표본)으로,
site 간 큰 변동을 비교에서 제거해 스큐 추정의 신뢰구간을 좁힙니다. 점이 적을수록
중요합니다.

### 4.3 결론

완전 균형이면 offset 숫자는 같게 나오지만, 실제 데이터는 (a) site당 2점 무작위라
균형이 보장되지 않고, (b) 추천이 "특정 위치"를 향하며, (c) offset 가정 자체를
검증하려면 site별 분산이 필요합니다. 따라서 **site별 계산을 채택**합니다. v1이
"offset 스큐만" 다뤄도(설계 스펙 §7.2), site별 잔차는 계산해 두어야 offset 가정의
유효성을 검증하고 deferred 패턴 트랙으로 승급할 수 있습니다.

## 5. 확정된 계산 입도

계산은 **서로 다른 두 시간 척도**를 가지며, 각 척도는 다른 단계에 들어갑니다.
이 둘을 섞으면 안 됩니다.

| 척도 | 단계 | 이유 |
| --- | --- | --- |
| **하루(per day)** | 기준값·잔차 계산 | fleet = 그날 측정분. 기준값은 그 순간 공통 수준을 제거하는 **같은 날 상대 기준**입니다. |
| **윈도우(10측정/1주)** | 잔차 → skew 집계 | site당 2점의 무작위를 여러 날에 걸쳐 평균해 감쇠시킵니다. |

확정 절차입니다.

```text
1) site-index로 묶는다.

2) [하루 단위] 각 측정일 d에 대해:
     - 장비 site 평균(t,s,d) = 그날 그 site의 2점 평균
     - 기준값(s,d) = 그날 fleet 장비들의 site 평균에 대한 로버스트 중앙값
     - 잔차(t,s,d) = 장비 site 평균(t,s,d) − 기준값(s,d)

3) [윈도우 단위] 윈도우(최근 10측정/1주) 내 일별 잔차를 집계:
     skew(t,s) = 잔차(t,s,d)의 계통 평균
     → 하루 2점의 무작위가 윈도우(예 10일)에 걸쳐 평균되어 감쇠
       (site당 누적 2점 × 10측정 = 20점)

4) 9개 site의 skew(t,s)를 장비 skew로 집계한다.
```

핵심은 **풀링이 원시 측정점이 아니라 일별 잔차에서 일어난다**는 점입니다.

- **기준값은 반드시 하루 단위**입니다. 윈도우로 한 번에 기준값을 내면, 장비들이
  함께 표류한 공통 드리프트(common-mode drift)가 잔차에 남습니다. 장비가 표류하기
  때문에 모니터링하는 것이므로, 이 드리프트를 못 지우면 잔차가 오염됩니다.
- 원시점을 윈도우로 먼저 뭉치면(잘못된 방식) 여러 날을 한 기준값에 섞고, 날짜별
  커버리지가 다른 장비를 잘못 가중합니다.
- 희소성의 두 종류를 구분합니다. **그날 측정한 장비 수**는 매일 전 장비가 측정하므로
  적지 않아 하루치 기준값이 안정적입니다. 적은 것은 **장비당 site당 2점**이며, 이는
  fleet 정의가 아니라 잔차의 잡음 문제이므로 윈도우 잔차 풀링(3단계)으로 줄입니다.

### 5.1 per-day 기준값이 유효한 전제 (측정 cadence)

측정은 24시간에 걸쳐 1~2시간 간격으로 **한 번에 한 대씩** 이뤄집니다. 따라서 "같은
순간의 fleet 합의"는 물리적으로 불가능하며, 하루 단위 기준값은 *다른 시각에 찍힌
측정들*을 모읍니다. 이 묶음이 유효하려면 두 전제가 필요하고, 둘 다 확인되었습니다.

| 전제 | 확인 | 의미 |
| --- | --- | --- |
| 측정 스케줄이 **회전형** | 확인됨 | 측정 시각이 장비와 상관 없음 → 일주기 환경 드리프트가 장비 입장에서 무작위 |
| 하루 내 공통 변동 < 스큐 | 확인됨 | 교란의 크기 자체가 우리가 쫓는 스큐보다 작음 |

회전형이 핵심입니다. 시각이 장비와 고정 상관(예: A는 늘 02시 슬롯)이라면, 일주기
드리프트가 그 장비 잔차에 매일 같은 부호로 박혀 **스큐로 둔갑하는 지속 편향(alias)**
이 되고 윈도우 평균으로도 지워지지 않습니다. 회전형이면 측정 시각이 무작위가 되어
이 교란이 윈도우(약 1주 = 일별 측정 7회)에 걸쳐 평균되어 0으로 수렴합니다. 한 주면
각 장비가 여러 시각대를 골고루 밟으므로 시각 위상이 충분히 섞입니다.

> **office 검증 항목.** 회전 스케줄이 유지되는지와 하루 내 fleet 공통 변동이 스큐보다
> 작은지는 Phase-1 mock으로 증명할 수 없으므로, 실데이터로 확인합니다. 만약 향후
> 고정 슬롯으로 바뀌면 측정 timestamp 기반 detrend(하루 내 시간 추세 제거)가
> 필요합니다.

### 5.2 윈도우 절단 규칙 (장비 다운 대응)

장비는 부품 대기·네트워크 등으로 **MDC를 건드리지 않은 채** 며칠씩 측정을 쉴 수
있습니다(단순 다운). 이 경우 다운 전후는 같은 상태이므로 잔차를 이어서 풀링해도
정당합니다. 윈도우는 다음 세 한도의 **가장 빡빡한 쪽**에서 절단합니다.

| 한도 | 규칙 | 근거 |
| --- | --- | --- |
| epoch | 현재 epoch 내만 (cell 정의에 내재) | MDC 변경 전후는 baseline이 다름 |
| lookback | 최대 **2주** | 2주까지는 "같은 상태"로 간주 |
| count | 통상 ~1주(일별 7회) 목표, 부족 시 2주까지 확장 | 잔차 수가 곧 신뢰도 |

- **epoch 한도는 자동입니다.** `mdc_epoch`이 cell의 차원이므로(설계 스펙 §2), 한 cell
  안에서 잔차를 풀링하면 정의상 epoch을 넘지 못합니다. 별도 절단 단계가 아니라
  cell 구조가 보장합니다.
- **단순 다운은 epoch을 리셋하지 않습니다.** MDC 불변이므로 같은 cell·같은 epoch이
  유지되어, 2주 한도 내에서 다운 전 잔차를 이어 씁니다. 단 그 구간에 BM/PM 정비가
  있었다면 "유휴"가 아니라 "정비됨"이므로 §5.3의 소프트 마커 규칙을 적용합니다.
- **모자라면 신뢰도를 깎습니다.** 2주·현재 epoch 내에서 모은 잔차가 적으면(다운 복귀
  직후 등) 억지로 더 거슬러 가지 않고 신뢰도를 Low로 표시합니다(§7). 복귀 직후
  장비가 Low로 뜨는 것은 정직한 표시입니다.

**epoch 리셋 트리거.** epoch은 **MDC 수치가 과거와 다르게 바뀔 때**(보통 BM/PM 동반)
경계가 그어지고 baseline이 리셋됩니다(설계 스펙 §3.2). 다운·수리 자체가 아니라 *MDC
값 변경*만이 트리거입니다. MDC는 장비별(축·빔조건별)로 조정되므로 epoch 타임라인도
**장비별**입니다 — 한 장비의 MDC 변경은 그 장비 cell에만 새 epoch을 엽니다.

### 5.3 BM/PM 이벤트 — 하드 경계와 소프트 마커

BM/PM 실제 수행일 기록을 별도로 보유합니다. BM/PM이 **항상 MDC를 바꾸는 것은
아니므로**, 이벤트를 두 층으로 분리합니다.

| 층 | 트리거 | 효과 |
| --- | --- | --- |
| 하드 경계 | MDC 값 변경 (보통 BM/PM 동반) | epoch 리셋, 과거 잔차 풀링 금지 |
| 소프트 마커 | BM/PM 수행 (MDC 불변) | epoch 유지, 단 H/W를 건드린 **후보 불연속점**으로 표시 |

소프트 마커가 필요한 이유는, MDC가 안 바뀌어도 BM/PM은 물리적 개입(세정·부품·정렬)
이라 skew가 미세하게 step할 수 있기 때문입니다. 보정 모델 `A=(MDC)·B+C`에서 MDC는
그대로지만 raw 응답 `B` 자체가 달라질 수 있습니다.

- **§5.2의 "2주 same state"를 한정합니다.** 그 2주 안에 BM/PM 소프트 마커가 있으면
  다운 전후는 "유휴(idle)"가 아니라 "정비됨(serviced)"입니다. 기본 규칙은 **마커 이후
  데이터를 우선**하고, 부족할 때만 마커를 넘어 풀링하되 "정비 구간 포함"으로 신뢰도를
  낮춥니다. (마커를 넘는 step 검정으로 자동 판정하는 정교화는 office 몫입니다.)
- **진단 신호.** MDC를 안 바꾼 BM/PM 전후로 skew가 step하면, MDC가 못 잡은 H/W
  드리프트의 증거입니다 — 트렌드(대시보드 ③) 마커에서 바로 읽힙니다.
- **안정성 플래그 설명.** BM/PM 마커는 skew 점프의 원인을 설명해, 정비된 장비가
  "흔들리는 장비"로 오판되지 않게 합니다(설계 스펙 §3.2-4).

**계약 입력.** BM/PM 이벤트(수행일 + MDC 변경 여부 플래그)는 `mdc_history`와 별개의
입력입니다. 하드 경계는 `mdc_history`에서, 소프트 마커는 BM/PM 이벤트 로그에서
도출합니다(설계 스펙 §6 계약의 `epoch_markers`에 더해 추가 입력).

## 6. 직접 / 참고 tier 경계의 통계적 정당성

이 입도는 설계 스펙 §3.1의 3등급 신호 분리를 통계로 뒷받침합니다.

| tier | Wafer | site 패턴 `TrueCD(s)` | 분리 가능성 |
| --- | --- | --- | --- |
| 직접 | **같은** 물리적 Wafer | 장비 간 공통 → 상쇄 가능 | ToolSkew 깨끗이 분리 |
| 참고(양산) | **다른** Wafer | 장비마다 다름 → 상쇄 불가 | Wafer 산포와 엉켜 분리 불가 |

양산이 "직접"이 아니라 "참고"인 이유가 여기서 드러납니다. 다른 Wafer는
`TrueCD(s)`가 장비마다 달라 site 매칭으로도 상쇄되지 않으므로, Wafer-to-Wafer
산포가 ToolSkew와 분리되지 않습니다. 그래서 N배화 판정에 반영하지 않는 참고
신호로만 씁니다.

## 7. 신뢰도가 데이터 밀도의 함수인 이유

site 내 무작위는 상쇄가 아니라 평균이므로 추정 불확실성이 남고, 그 크기는 다음에
비례합니다.

```text
skew 추정 표준오차 ∝ 1 / √( site당 점수 × site수 × 윈도우 내 측정횟수 )
```

이것이 신뢰도 라벨(High/Med/Low)과 안정성 플래그를 수치로 정박할 근거입니다. 점이
많이 쌓인 셀일수록 High, 적으면 Low가 되며, 설계 스펙 §2의 "팹 간 차이는 tier별
데이터 밀도 차이로만 나타난다"가 여기서 구체화됩니다.
