# Research: Display approaches for optical metrology (film thickness + spectroscopic ellipsometry) in SKEWNONO — practical tradeoffs

## Summary

The repo's cheapest and strongest path is to treat optical metrology the way it already treats AFM: a measurement-list → detail → time-series-comparison feature, reusing skewvoir's comparison axes (time / lot / eqp_id / recipe / site) for **derived** values (thickness, n/k, MSE), and adding exactly two new view surfaces: a spectra detail view (Psi/Delta + model fit + residuals, per site) and a site-grid uniformity map. Imaging SE hyperspectral data (>10M spectra per acquisition in published systems) can never ship raw to a browser — the server must pre-reduce to per-pixel derived parameters and then bin/tile to map resolution; a raw-cube explorer is research-grade eye candy, not what fab engineers need. The single biggest quality trap is displaying derived thickness without fit-quality context (MSE/χ², residuals, parameter error limits/correlations) — every serious ellipsometry package (CompleteEASE, WVASE, DeltaPsi2, SpectraRay/4) shows these, and Horiba publishes the exact checklist.

## Findings

### 1. What products actually ship

This is the clearest public taxonomy of what a yield platform displays. **Sources:** [PDF Solutions wafer-map intro](https://www.pdf.com/understanding-semiconductor-data-visualization-with-wafer-maps-an-introduction/), [Exensio Manufacturing Analytics](https://www.pdf.com/products/exensio-analytics-platform/modules/manufacturing-analytics/). **Support:** direct evidence (fetched full article). **Confidence:** high.

4. **Claim:** yieldWerx and yieldHUB (SME-oriented yield platforms, closest analogues to SKEWNONO's scale) ship: lot/wafer/die-level yield views, per-site trend charts across lots ("Per Site Trend" — evaluates many lots for long-term patterns, flags deviating wafers, 5-lot trend graphs), defect/metrology/CD/image management modules. **Sources:** [yieldWerx product suite](https://yieldwerx.com/products/product-suite/), [yieldWerx FAQ](https://yieldwerx.com/faq/), [yieldHUB platform](https://www.yieldhub.com/platform). **Support:** direct evidence. **Confidence:** high.
5. **Claim:** Ellipsometer vendor software (J.A. ### 2. Imaging SE data volume — the hard constraint

8. **Claim:** A published full-wafer imaging Mueller-matrix SE system measures a 20×20 mm field at 3200×3200 pixels (6.5 µm resolution) across 35 wavelengths → **>10 million spectra per single acquisition**; a full wafer needs ~100–120 shots (~110 s each). Downstream products are per-pixel *derived parameter* maps: >10M overlay values, >10M CD points, >7M thickness points per wafer — a ~2000× increase over SEM data density. What the paper displays is never raw spectra: thickness/CD/overlay **wafer maps**, shot-level maps, histograms, and error maps. **Source:** [Ultra-wide-field imaging MMSE, Nature Communications (2025)](https://www.nature.com/articles/s41467-025-63511-1). **Support:** direct evidence (fetched, quoted numbers). **Confidence:** high.
9. **Claim:** A second SPIE 2025 paper on full-wafer imaging-ellipsometry 3D metrology (22×22 mm FOV, ML-based model from reference points) states the acquired spectra "generate a massive amount of measurement data exceeding 12…" — the sentence was truncated in every reachable copy (SPIE blocks fetch), most likely a TB-scale figure. **Sources:** [SPIE 13426-05](https://doi.org/10.1117/12.3051267). **Support:** partial direct evidence (abstract fragment only). **Confidence:** low for the exact number; high for the direction (raw imaging-SE cubes are enormous).
10. **Claim (researcher inference, arithmetic):** Even the *reduced* per-pixel product is too big for naive JSON→ECharts: 10M float values ≈ 100–200 MB JSON per wafer per parameter. A browser-viable map needs server-side binning/tiling to ≲10⁴–10⁵ cells (or a server-rendered raster + vector overlay). By contrast, a conventional point-SE wafer (e.g. 49 sites × ~1000 wavelengths × Psi/Delta × 2–3 AOIs) is ~10⁵–10⁶ floats ≈ 1–5 MB JSON — perfectly sane to ship per-measurement, especially fetched per site on demand. **Confidence:** high (order-of-magnitude arithmetic; no repo measurement taken).

### 3. ECharts 6 capability for these views

11. **Claim:** ECharts (installed: 6.1.0, verified in `frontend/node_modules/echarts/package.json`) supports all needed primitives: heatmap series on cartesian2d **with progressive rendering** (`HeatmapView.ts` implements incremental render; heatmap requires a `visualMap`), `large: true` scatter/line with typed-array rendering for 10⁵–10⁶ points, progressive rendering knobs (`progressive`, `progressiveThreshold`), and line `sampling: 'lttb' | 'minmax'` downsampling for dense spectra. Caveats: large mode disables per-item styling/interaction; animation auto-off above 2000 elements. **Sources:** [ECharts performance guide](https://www.mintlify.com/apache/echarts/guides/performance), [HeatmapView.ts](https://github.com/apache/echarts/blob/d6a812f8/src/chart/heatmap/HeatmapView.ts), [heatmap chart docs](https://www.mintlify.com/apache/echarts/charts/heatmap). **Support:** direct evidence. **Confidence:** high.
12. **Claim:** ECharts 6.0.0 had a large-scatter performance regression (issue #21434, closed as completed 2025-12-20); 6.1.0 postdates the fix window but the exact release containing the fix was not verified. **Source:** [apache/echarts#21434](https://github.com/apache/echarts/issues/21434). **Support:** direct evidence for the issue; inference for "6.1.0 is fine". **Confidence:** medium.
13. **Claim (researcher inference):** A spectra overlay (measured Psi/Delta + model + residual, ~1000-point lines × a handful of series per site) is trivially cheap in ECharts — no large-mode needed. The uniformity map is the only view where cell count matters: ≲10⁴ cells renders fine as heatmap; 10⁵ is the practical ceiling before switching to canvas-image or scatter-large tricks. **Confidence:** medium (no in-repo benchmark run).

### 4. The fit-quality trap

14. **Claim:** Horiba publishes the canonical "is my fit good?" checklist: check χ² first, then visually compare measured vs model, check that results are physical, examine **error bars on fitted parameters**, and examine the **correlation matrix** — large error bars or strong correlations mean the model/parameterization is under-determined even when the curve looks fine. **Source:** [Horiba SE Data Analysis FAQ](https://www.horiba.com/int/scientific/technologies/spectroscopic-ellipsometry/data-analysis/). **Support:** direct evidence. **Confidence:** high.
15. **Claim:** CompleteEASE defines MSE as the goodness-of-fit metric and offers global fitting that scans a parameter grid reporting the minimum MSE — i.e. the tool itself treats "MSE surface + parameter values" as the truth, not the single derived number. OptiLayer's OptiChar ships **partial discrepancies** (residuals) precisely because "a good-looking overlay alone can hide deviations, especially in Delta". The Laser Focus World article names the **correlation problem** (thickness↔n ambiguity) as the core extraction pitfall. **Sources:** [CompleteEASE manual](https://physlab.org/wp-content/uploads/2016/04/Ellipsometry_manual_2.compressed.pdf), [CompleteEASE](https://www.jawoollam.com/ellipsometry-software/completeease), [OptiLayer partial discrepancies](https://optilayer.com/optichar-module-of-optilayer-thin-film-software/partial-discrepancies/), [Multiwavelength ellipsometry (LFW)](https://www.laserfocusworld.com/test-measurement/test-measurement/article/16550827/multiwavelength-ellipsometry-fathoms-materials). **Support:** direct evidence. **Confidence:** high.
16. **Claim (researcher inference → design rule):** For SKEWNONO this means: any thickness value shown in a trend/map/table should carry its MSE (or fit-status flag) beside it; maps should offer an "MSE layer" (color = fit quality) or at least mark cells above a threshold; the spectra detail view should show residuals as a second panel, not just the Psi/Delta overlay; multi-angle or reference-measurement cross-check is the honest way to expose thickness/n correlation. **Confidence:** high as a recommendation grounded in 14–15.

### 6. Open-source references

21. **Claim:** Usable OSS: `wafertools/wafermap` (MIT, pure ES modules — wafer-map rendering, spatial stats, failure clustering, lot-level trends, reticle analysis; runs in browser), `cap1tan/wafermap` (Python/matplotlib wafer maps), `uia4w/uia-wafermap` (Apache-2.0 JS shot/wafer maps from STDF), and a single-file browser wafermap viewer for **parametric inline metrology** (`Lotheringer/wafermap-viewer`) — direct precedent that a no-install browser map is the expected UX for inline thickness data. ## Three biggest risks (plain language)

1. **Designing against guessed data.** No thickness/SE office source exists yet (`docs/datatables/` has no vendor for it). Every mocked schema decision (site layout, spectra sampling, fit metadata fields) is a guess that the real tool's export will contradict; the repo's own rule (mock must mirror office fidelity, unknowns marked `OFFICE-VERIFY`) limits the damage only if the UI is built against the *contract shape*, not the mock's conveniences. Skewvoir already learned this lesson — its readiness matrix gates whole views when site-layout identity is unknown.
2. **Showing derived thickness as bare truth.** A thickness number with no MSE/residual/correlation context looks identical whether the fit is excellent or degenerate (thickness↔n correlation). Every serious vendor tool shows fit quality; SKEWNONO must too, or engineers will trust bad numbers — and the bad numbers will be most convincing exactly when the model is wrong.
3. **Imaging-SE volume hubris.** Raw hyperspectral cubes (>10M spectra per acquisition; >10M derived values per wafer) cannot ride the repo's JSON/`$fetch`/50-req-per-5s SPA architecture. If the UI is designed assuming the browser gets dense data, the whole view collapses when the real tool arrives; the server-side reduction/binning contract must be decided before any pixel-grid UI is built.
