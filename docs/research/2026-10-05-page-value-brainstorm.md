# 화면별 가치 추가 검토 — 더 깊은 분석을 위해 무엇을 더할 것인가

- 작성일: 2026-10-05
- 질문: 각 화면에 무엇이 빠져 있고, 무엇을 더하면 사용자에게 더 깊은 분석을 줄 수
  있는가. 그리고 화면끼리 링크로 잇는 일이 나중의 리팩토링과 유지보수에 부담이 되지
  않는가.
- 방법: Claude(Opus 5.5)와 Codex(GPT-6.1-Sol, xhigh)가 Herdr 에서 3라운드로
  논의했습니다. 1라운드는 서로의 답을 보지 않은 독립 조사, 2라운드는 상호 반박,
  3라운드는 최종 서명입니다. 사용자에게 묻지 않고 둘이 결정했습니다.
- 조사 범위: 화면 컴포넌트, 각 기능의 `contracts.py`, provider 예시,
  `docs/datatables`, `CONTEXT.md` 를 읽었습니다. **사내 DB, 브라우저 화면, 실사용
  로그는 보지 않았고, 이 문서의 어떤 제안도 구현하거나 검증하지 않았습니다.**
- 후속(2026-10-06): 10번이던 포인트 축소 민감도(S15)는 사용자 결정으로
  목록에서 뺐습니다. 남은 9개의 실행 계획은
  [`2026-10-06-page-value-plans.md`](2026-10-06-page-value-plans.md) 에 있습니다.

## 요약

**1. 화면은 "보여 주기"는 이미 깊고, "따져 보기"가 얕습니다.** Recipe 현황에는
recipe 구성을 보정한 지수와 신뢰구간이 있고, TTTM 에는 최대 클리크가, 디바이스
통계에는 룰 엔진이, 스큐보아에는 강건 통계 기반 판정이 있습니다. 빠져 있는 것은
세 가지입니다.

- **비교 기준이 없습니다.** 지난 기간, 고정된 기준 집단, 정비 전후 가운데 어느
  것과도 비교하지 않습니다. 지금 통계는 "지금 고른 것" 안에서만 계산하므로 기준이
  데이터와 함께 움직입니다.
- **판정의 이유와 범위를 말해 주지 않습니다.** 왜 이 recipe 가 이 cap 으로
  판정됐는지, 이 알람이 장비 문제인지 recipe 문제인지, 평균이 높은 것이 전반적으로
  느려서인지 몇 건 때문인지는 사용자가 직접 찾아야 합니다.
- **진단에서 끝나고 다음 결정을 돕지 않습니다.** 룰을 바꾸면 무엇이 달라지는지,
  측정 포인트를 줄여도 되는지, 내린 결론을 어떻게 남길지에 대한 화면이 없습니다.

**2. 먼저 할 9개에 합의했습니다.** 모두 한 기능 폴더 안에서 끝나거나, 이미 있는
진입 계약을 쓰는 링크 하나만 필요합니다. 한 번에 하나씩 진행하는 순서입니다.

| 순위 | 화면 | 추가할 것 | 규모 | 답하게 되는 질문 |
| --- | --- | --- | --- | --- |
| 1 | Recipe 현황 | 이전 동일 기간 대비 증감 (S3) | S | 지난 기간보다 무엇이 변했는가 |
| 2 | 측정 이력 | 장비별 P50/P90 과 느린 실행 분리 (S4) | S | 전반적으로 느린가, 몇 건이 느린가 |
| 3 | 계측 룰 | 판정 근거 설명 (S5) | S | 왜 이 recipe 가 이 cap 인가 |
| 4 | 측정 이력 → 스큐보아 | 그 행의 MSR 을 바로 열기 (S2) | S | 이 실행의 원본 측정은 무엇인가 |
| 5 | 라이브 알람 | 사건 범위 묶어 보기 (S1) | M | 장비 문제인가, recipe 문제인가, lot 문제인가 |
| 6 | AFM 같이 보기 | 고정 기준 대비 비교 (S6) | M | 독립된 기준에서 얼마나 벗어났는가 |
| 7 | 스큐보아 | 기준·대상을 나눈 고정 비교 (S7) | M | 고정된 기준 집단보다 얼마나 움직였는가 |
| 8 | 계측 룰 | 저장하지 않는 cap 가정 계산 (S13) | M | 룰을 바꾸면 어떤 recipe 와 lot 이 영향을 받는가 |
| 9 | 스큐보아 | 검토 영수증 내려받기 (S8) | S/M | 이 결론과 근거를 어떻게 남기는가 |

순위 밖에서 함께 처리할 것은 세 가지입니다. 스토리지의 두 관측 시각 분리(S10)와
TTTM 의 양산 recipe 중복도 표시(S11)는 각 화면을 다음에 고칠 때 묶고, 장비 목록 →
H/W 링크 교체는 링크 정책이 요구하는 유일한 리팩토링입니다. 그다음 큰 과제는 H/W
화면의 정비 전후 비교(S9)입니다.

**3. 링크는 조건을 지킬 때만 안전합니다.** 대상 화면이 URL 로 받는 값을 스스로
정의해 두었고(이 문서에서는 "진입 계약"이라고 부릅니다), 출발 화면이 그 값을
추측 없이 갖고 있으며, 링크를 만드는 함수를 대상 화면 쪽이 소유할 때입니다. 이
조건으로 보면 **새로 만들 링크는 세 개, 고칠 링크는 하나**이고, 장비 요약 허브나
홈 브리핑처럼 여러 기능을 한 화면에 묶는 것은 만들지 않기로 했습니다. 자세한
판단은 1절에 있습니다.

## 표기

데이터 출처는 네 가지로 구분합니다.

| 표기 | 뜻 |
| --- | --- |
| 있음 | 이미 `contracts.py` 응답에 들어 있는 필드 |
| 계산 | 이미 받는 데이터에서 계산하거나 다시 묶을 수 있는 것 |
| 사내 확인 | 사내 소스는 `docs/datatables` 에 문서화돼 있으나 어댑터 확장과 실측 검증이 필요한 것 |
| 신규 수집 | 지금 어디에도 쌓이지 않아 새로 모아야 하는 것 |

규모는 S(0.5~2일), M(3~7일), L(수 주)이며 어림값입니다. "있음"과 "계산"은 집에서
mock 으로 동작을 확인할 수 있다는 뜻이지, 사내 데이터에서 같은 결과가 나온다는
보증이 아닙니다. 구현 규모와 사내 검증 위험은 따로 봐야 합니다.

## 1. 화면 간 링크: 유지보수 판단

### 1.1 지금 상태

링크의 안전성은 대상 화면이 무엇을 URL 로 받는지에 달려 있습니다. 화면마다 사정이
다릅니다.

| 화면 | URL 로 받는 값 | 근거 |
| --- | --- | --- |
| H/W 관리 | `eqp_id`, `start`, `end` (첫 진입 때만 읽음) | `frontend/app/components/ebeam/HardwareView.vue:54` |
| Recipe 검색 | `q`, `page`, `size` | `frontend/app/components/ebeam/RecipeSearchView.vue` |
| Recipe 상세 (열어보기·횡전개·측정 이력) | `recipe_name`, `fab_name` | `frontend/app/utils/recipeView.ts:261` |
| Recipe 현황 | `tab` | `frontend/app/components/ebeam/RecipeStatusView.vue` |
| 스큐보아 검색 | `q`, `fab` (한 번 쓰고 URL 에서 지움) | `frontend/app/components/ebeam/skewvoir/SearchLanding.vue:132` |
| 스큐보아 분석 | 선택 전체 (`lot`, `recipe`, `eq`, `mp`, `msr`, `cap`, `msrs`, `view` 등) | `frontend/app/utils/skewvoirAnalysis/routeQuery.ts:89` |
| AFM 상세 | 경로 `(tool, filename)` | `frontend/app/pages/afm/[tool]/[filename].vue` |
| 스토리지, TTTM, 라이브 알람, 장비 상태, 디바이스 통계, AFM 검색·같이 보기, Mag/Pixel | 없음 | `route.query` 를 읽는 코드가 없습니다 |

링크를 만드는 쪽에는 좋은 선례와 나쁜 선례가 함께 있습니다.

- **좋은 선례.** `skewvoirSearchRoute`(`frontend/app/utils/skewvoirLinks.ts:21`)와
  `recipeDetailRoute`(`frontend/app/utils/recipeView.ts:175`)는 대상 화면 쪽에 있는
  순수 함수가 `{ path, query }` 를 돌려주고 단위 테스트가 붙어 있습니다. 호출하는
  화면은 대상의 쿼리 키 이름을 몰라도 됩니다. 스큐보아 분석도
  `toAnalysisQuery` 와 `parseSelection` 을 같은 방식으로 갖고 있습니다.
- **나쁜 선례.** 장비 목록에서 H/W 로 가는 링크는 `setSelectedTool(eqpId)` 로
  메모리 상태를 바꾼 뒤 장비 정보 없이 `/hardware` 로 이동합니다
  (`frontend/app/components/ebeam/ToolInventoryView.vue:242`). 그 상태는 일반
  `useState` 라서 새로고침하면 사라지고, 새 탭으로 열거나 주소를 공유할 수
  없습니다. 정작 H/W 화면은 `?eqp_id=` 를 읽을 줄 아는데 이를 쓰는 호출부가
  하나도 없습니다.

### 1.2 위험이 실제로 생기는 곳

1. **쿼리 키 이름이 어긋나도 오류가 나지 않습니다.** 대상 화면이 키 이름을
   바꾸면, 손으로 문자열을 조립한 호출부는 타입 오류 없이 기본 화면을 엽니다. SPA
   라서 조용히 틀립니다.
2. **이름이 같아도 같은 식별자가 아닐 수 있습니다.** TAT·실패 순위의
   `recipe_name` 은 클래스가 붙은 `full_name` 과 다릅니다. 알람의 `recipe_id` 와
   `ppid` 는 서로는 같다고 문서화돼 있지만 `full_name` 과 정확히 대응한다는 근거는
   없습니다. 반대로 디바이스 통계의 `recipe_id` 는 `full_name` 과 같은 값이라고
   문서에 적혀 있습니다(`docs/datatables/hitachi/planstep_r3.txt:49`,
   `docs/datatables/hitachi/ebeam_tas_lot_hist.txt:34`).
3. **장비 ID 가 범위 없이는 고유하지 않을 수 있습니다.** sem_list mock 의 304행
   가운데 10개 ID 가 중복이고 그중 9개는 FAB 이나 모델이 서로 다릅니다. 코드
   주석은 사내에서는 고유하다고 적고 있으나(`HardwareView.vue:178`), 링크는
   계열과 FAB 범위를 함께 실어야 합니다.
4. **URL 값과 기억된 상태가 충돌합니다.** 화면은 마지막 선택을 기억하므로, 링크로
   들어온 값이 기억된 값을 정확히 한 번 이겨야 합니다. 스큐보아에서 라우터 교체
   두 개가 경쟁하던 문제가 이 부류였습니다.
5. **묶음 화면은 결합을 늘립니다.** 한 컴포넌트가 여덟 기능의 응답을 모아
   보여 주면, 어느 기능을 고치든 그 컴포넌트를 함께 고쳐야 합니다. 백엔드에서
   한 번에 모아 주는 엔드포인트로 옮겨도 결합은 자리를 옮길 뿐 사라지지
   않습니다. 게다가 새 기능 간 조인은 `validate_env()` 가 알아서 지켜 주지
   않습니다. 지금 선언된 의존은 pm_planning·storage·tttm 이 sem_list 에 기대는
   것뿐입니다(`backend/_runtime/data_provider.py:62`).

### 1.3 합의한 정책

**이름을 붙일 수 있는 이동은 다음 세 조건을 모두 만족할 때만 만듭니다.**

1. 대상 화면이 그 식별자와 범위를 URL 로 받는 계약을 이미 갖고 있습니다.
2. 출발 화면이 그 식별자를 추측 없이 갖고 있습니다. 표준 식별자가 아닌 값은
   사용자가 보고 고칠 수 있는 **검색어**로만 넘기고, 상세 화면을 정확히 여는
   데에는 쓰지 않습니다.
3. 링크는 대상 화면이 소유한 순수 함수로 만들고, 호출부가 전역 상태를 바꾸지
   않습니다. 식별자가 없거나 모호하면 첫 번째 장비를 고르거나 FAB 을 넓히지
   않고 그 사실을 화면에 보입니다.

버그가 전혀 없다는 약속이 아니라, 리팩토링 때 확인할 범위가 정해져 있다는
뜻입니다.

강제하는 방법은 세 가지이며 새 도구를 들이지 않습니다.

1. **대상 화면마다 계약 테스트 한 묶음.** 만들기 → 읽기 왕복, `/` 가 들어간
   이름, 다중 FAB 경로와 실제 소유 FAB, CD-SEM/HV-SEM, 빈 값과 모호한 식별자를
   기존 `node --test` 로 확인합니다. `recipeView.test.ts` 와
   `skewvoirAnalysis/routeQuery.test.ts` 가 이미 이 형태입니다.
2. **바뀐 파일에 대한 grep 을 리뷰 단서로.**
   `rg -n '/ebeam/|setSelectedTool|route\.query' <바뀐 파일>` 로 대상 소유 코드
   밖의 쿼리 문자열과 전역 상태 넘기기를 봅니다. `/ebeam/` 문자열 자체를
   금지하지는 않습니다. 지금도 29개 파일에 있고 대부분은 정상적인 내비게이션,
   빌더, 옛 주소 redirect 입니다.
3. **구현할 때 브라우저로 진입 확인.** 새 탭, 새로고침, URL 값 대 기억된 값,
   같은 화면 재진입, 뒤로 가기를 봅니다. 순수 함수 테스트로는 watcher 순서를
   증명할 수 없기 때문입니다.

모든 화면을 URL 과 동기화하도록 바꾸지는 않습니다. 구체적인 링크 하나가 요구하는
진입 계약만 더합니다.

### 1.5 결론

**새로 만들 링크 (모두 S):**

- **S2 측정 이력 행 → 스큐보아 분석.** 그 행의 정확한 MSR 을 엽니다. 스큐보아
  분석은 진입 계약이 있으나 `msrs` 만으로는 열리지 않습니다. `parseSelection` 이
  `lot` 을 요구하므로, 행에서 lot·장비·촬영 시각까지 담은 완전한 선택을 대상
  소유 함수로 만들어야 합니다.
- **S16 디바이스 통계 스텝 → 열어보기.** `recipe_id` 가 `full_name` 과 같은
  값이므로 R3 와 M-fab 모두 통과합니다. 여는 것은 현재 구성이지 그 스텝이 과거에
  쓴 버전이 아닙니다.
- **S17 알람 → 스큐보아 검색.** 운영자가 요청할 때만 장비·FAB·recipe 를 채운
  검색을 엽니다. 수정 가능한 검색어이며, 그 알람의 실행을 찾아 준다고 주장하지
  않습니다. 폴링 중에 측정 이력을 부르지 않습니다.

**고칠 링크 (S, 조건부):** 장비 목록 → H/W 를 `?eqp_id=` 를 쓰는 진짜 링크로
바꾸고 행의 실제 FAB 으로 보냅니다. 그러면 내비게이션 저장소의
`selectedToolId` 와 `setSelectedTool` 을 지울 수 있습니다. 쓰는 곳은 장비 목록
(쓰기)과 H/W 화면(읽고 지우기) 둘뿐입니다. 공유 상태로 값을 넘기는 규약이
하나 사라지므로 유지보수가 줄어드는 유일한 링크 변경입니다. 다만 빌더와 테스트가
더해지므로 줄 수가 줄어든다고 미리 말하지는 않습니다. 같은 범위 안에서 ID 가
겹치면 첫 번째를 고르지 말고 모호하다고 보여야 합니다.

**만들지 않는 것:** 장비 요약 허브, 홈 브리핑, 진입 계약이 없는 화면으로 가는
필터 링크, AFM 과 SEM 을 잇는 링크.
