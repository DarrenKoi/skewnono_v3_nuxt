## 2. 무엇을 계산해야 하는가 — 과학적으로

### 2.1 질문의 정체

"장비 A 와 B 가 얼마나 스큐되어 있는가"는 두 개의 다른 질문입니다.

- **크기**: 지금 이 순간 두 장비의 읽는 값이 몇 nm 차이 나는가.
- **성질**: 그 차이가 **재현되는 상수**인가, 아니면 매번 달라지는 잡음인가.

사용자가 실제로 필요로 하는 것은 두 번째입니다. 재현되는 상수라면 보정할 수 있고
다음 run 을 예측할 수 있지만, 잡음이라면 어떤 보정도 무의미하기 때문입니다.

### 2.2 관측 모형

셀 하나(= recipe × parameter × cd_band × beam_condition × mdc_epoch) 안에서

```text
y_ijk = μ + tool_i + lot_j + (tool×time)_it + site_k + ε_ijk
```

- `tool_i` — 재현되는 장비 offset (= 일관된 스큐)
- `lot_j` — 공정/lot 변동. **교란항이며, 이 항이 모형에 없으면 tool 효과가 식별되지
  않습니다.**
- `(tool×time)_it` — 장비 offset 자체가 시간에 따라 흔들리는 성분 (= 랜덤한 스큐)
- `site_k` — 웨이퍼 내 위치 효과
- `ε` — 반복 측정 잡음

여기서 나오는 기술통계가 **일관성 비율**입니다.

```text
일관성 = σ²_tool / (σ²_tool + σ²_tool×time)
```

1 에 가까우면 스큐는 장비의 성질이고, 0 에 가까우면 그날그날의 사정입니다.

### 2.3 그런데 답은 필터에서 나옵니다

위 비율은 **기술통계일 뿐 답이 아닙니다.** "다음 run 을 기대할 수 있는가"는 한 걸음
앞선 예측 구간을 요구하므로, 장비쌍 offset 시계열에 **국소선형추세 상태공간
모형(local linear trend)** 을 얹습니다. numpy 30줄이면 되며 새 의존성이 필요 없습니다.

```text
level_t = level_{t-1} + slope_{t-1} + w_t      (w ~ N(0, σ²_proc))
obs_t   = level_t + v_t                        (v ~ N(0, σ²_obs))
```

- `σ²_proc / (σ²_proc + σ²_obs)` 가 곧 **"일관 대 랜덤"** 비율입니다.
- one-step-ahead 예측 구간이 곧 **"다음 run 에 얼마를 기대하는가"** 입니다.
- `slope` 항이 있어야 **꾸준히 드리프트하는 장비**를 "일관됨"으로 오판하지 않습니다.
  국소수준(local level)만 쓰면, 60일 한 epoch 안에서 단조롭게 밀려가는 장비가
  σ²_tool 은 크고 σ²_tool×time 은 작게 나와 "안정적"으로 보고되며, 한 달 뒤 틀립니다.

판정은 학습된 분류기가 아니라 적합된 모수 위의 규칙으로 냅니다 — 일관 / 드리프트 중
(예측 가능하지만 이동 중) / 랜덤 / 점프. 라벨이 없는 데이터에 지도학습을 얹는 것보다
정직하고, 왜 그렇게 판정했는지 화면에서 설명할 수 있습니다.

### 2.4 반드시 피해야 할 함정 — 유사반복(pseudo-replication)

MSR 한 건에는 측정점이 수백 개 있습니다. 표본 수를 **점 개수**로 잡으면 표준오차가
10~25배 작게 나오고(`설계효과 = 1 + (m−1)ρ`, `m≈100~300`, `ρ≈0.8`), 그 결과
**모든 장비쌍이 유의하게 스큐된 것으로 나옵니다.** 유효 표본은 독립적인 **실행/lot
개수**이며, 군집-강건(cluster-robust) 표준오차를 써야 합니다.

이 한 가지만 틀려도 화면 전체가 조용히 거짓말을 합니다. 이번 검토에서 나온 가장
현실적인 실패 방식입니다.

### 2.5 MDC 는 추정 단계에서 되돌립니다

관측 CD 는 이미 보정된 값입니다(`result = MDC × actual`). MDC 는 **추정값이 아니라
알려진 설정**이므로, 역적용해도 분산이 늘지 않습니다. 따라서

- **추정할 때는 역적용**합니다. 그래야 MDC 변경이 60일 시계열 안의 설명 불가능한
  불연속이 되지 않고, epoch 을 넘어 비교할 수 있습니다.
- **표시할 때는 다시 적용**합니다. 현업이 실제로 겪는 것은 보정 후 잔차 스큐이기
  때문입니다.
- 역적용했는데도 경계에 점프가 남으면 그것은 잡음이 아니라 **신호**입니다 — MDC
  기록이 실제와 다르다는 뜻이므로 로그에 남겨야 합니다.
- 단, beam/Deg 키 재구성이 검증되기 전에는 역적용을 켜지 않습니다. 잘못된 계수를
  되돌리면 오차가 epoch 을 건너 곱셈으로 번집니다.

## 3. "recipe 를 더 많이 보면 스큐가 더 정밀해지는가"

**정밀해집니다. 다만 흔히 기대하는 이유 때문은 아니며, 순진하게 평균 내면 오히려
나빠집니다.**

### 3.1 스큐는 장비당 스칼라 하나가 아닙니다

장비 차이는 최소한 **offset 항**과 **CD 의존 gain 항**으로 나뉘고, 여기에 beam 조건과
edge 알고리즘(`meas_method` Score/Width/Edge, `object` Line/Space/MP)이 얹힙니다.
offset 오차와 gain 오차는 현장에서 대응 방법이 다르므로, 하나의 숫자로 뭉개면 답이
행동으로 이어지지 않습니다.

### 3.2 CD-gain 은 recipe 를 늘려서가 아니라 **한 실행 안에서** 잡습니다

처음에는 "recipe 하나는 CD 대역 하나이므로 offset 과 gain 이 구분되지 않는다"고
보았으나, 이는 틀렸습니다. **한 실행 안에 서로 다른 공칭 CD 를 가진 parameter 가 여러
개 들어 있습니다.** 같은 웨이퍼·같은 lot 이므로 이 대비에는 lot 분산이 섞이지 않으며,
CD-gain 을 깨끗하게 식별할 수 있는 유일한 경로입니다.

반대로 서로 다른 recipe 를 가로질러 CD 대비를 만들면, recipe 마다 도는 lot 이 다르므로
**gain 추정치가 lot 분산을 통째로 먹습니다.** 정밀해 보이지만 틀린 숫자가 됩니다.

### 3.3 그러면 recipe 를 늘리는 값어치는 무엇인가

세 가지입니다.

1. **beam·optics 조건의 레버리지.** CD 와 달리 가속전압·Optics 모드는 recipe 속성이므로,
   여러 recipe 를 봐야 조건별 스큐 구조가 드러납니다.
2. **장비쌍 연결.** 장비 A 와 B 가 공통으로 도는 recipe 가 없으면 그 쌍은 애초에 비교
   불가입니다. recipe 를 늘리는 것은 곧 비교 가능한 쌍을 늘리는 일입니다.
3. **부분 pooling 을 통한 축소(shrinkage).** 아래 3.4.

### 3.4 부분 pooling — 전부 합치지도, 전부 따로 두지도 않습니다

```text
장비 offset = δ_tool + γ_{tool,recipe},   γ ~ N(0, τ²)
```

- `τ²` 이 작으면 스큐는 장비의 성질이므로 합쳐도 되고, 정밀도는 대략 `√K` 로
  좋아집니다.
- `τ²` 이 크면 스큐는 (장비 × recipe) 의 성질이므로 **합치는 것이 적극적으로
  틀립니다.** 전 함대 평균 편향만 아주 정밀하게 얻고, 정작 필요한 recipe 별 스큐는
  지워집니다.
- 경험 베이즈 축소(BLUP)는 두 극단보다 기대오차가 작습니다. 각 recipe 추정치를 자기
  잡음과 `τ²` 의 비율만큼 장비 평균 쪽으로 당깁니다.

중요한 보정 한 가지: recipe 들은 **교환 가능(exchangeable)하지 않습니다.** CD 와 beam
조건은 **평균 구조에 공변량으로** 넣고, 구조화되지 않은 `γ` 는 그러고도 남는 잔차만
담아야 합니다. 그러지 않으면 축소가 향하는 중심이 앞서 "아무도 원하지 않는다"고 한
전 함대 평균이 되어 버립니다.

### 3.5 전제 조건 — 연결성은 epoch 단위로 확인합니다

여러 recipe 를 합치려면 장비×recipe 부속 그래프가 **연결**되어 있어야 합니다.
완전 그래프일 필요는 없습니다. A~B 가 recipe 1 을, B~C 가 recipe 2 를 공유하면 A–C 는
B 를 경유해 추정 가능하며, 이것이 계약의 `predicted` tier 가 뜻하는 바입니다.

다만 **그래프를 기간 전체로 뭉쳐서 그리면 가짜 안심을 줍니다.** A~B 가 1주차에,
B~C 가 4주차에 연결되었고 그 사이 B 가 PM 이나 MDC 변경을 겪었다면, B 는 두 링크에서
같은 물체가 아닙니다. 뭉친 그래프는 연결되어 보이지만 epoch 단위로는 끊겨 있고,
A–C 추정치는 B 의 점프만큼 편향된 채 "일관됨"으로 보고됩니다.

따라서 **연결성 검사는 epoch 단위**로 하고, 연결 성분과 경로 길이를 화면에 드러냅니다.
경로 길이가 곧 신뢰도의 근거입니다.

### 3.6 정밀도에는 바닥이 있습니다

recipe 를 아무리 늘려도 줄어드는 것은 **무작위 성분**뿐입니다. 모든 장비가 자기 MDC 를
거쳐 보정된다는 공통 계통 성분은 `√K` 로 줄지 않습니다. 화면은 통계적 표준오차와
계통 불확도를 **함께** 보여야 하며, 그러지 않으면 허용오차(tolerance) 비교가 허구가
됩니다.

## 5. 만들 순서

### 5.1 야간 rollup — 실행(run) 단위 grain (가장 먼저)

`back_dev_home/_scheduler/` 에 잡을 하나 추가하고, `(msr, eqp_id, recipe, parameter,
cell)` **한 행 = 한 실행**으로 강건 통계(중앙값·MAD·n·실행 내 산포)를 적재합니다.
`device_statistics` 의 weekly_trend 가 이미 쓰는 모양이며, parquet 로 하루 1 오브젝트면
됩니다.

**grain 을 일(day) 단위로 잡으면 안 됩니다.** `lot_id` 가 사라지면 lot 랜덤효과를 뺄 수
없고, 61일 뒤 원본이 삭제되면 **영원히 복구할 수 없습니다.** 그때는 이미 몇 달치 잘못된
이력이 쌓인 뒤입니다. 이번 검토에서 나온, 되돌릴 수 없는 유일한 실수 후보입니다.

부수 효과로 비용 문제도 함께 풀립니다. 장비 10대 × 60일 × recipe N 을 요청 때마다
계산하면 MinIO GET 이 수천 건이라 애초에 성립하지 않습니다.

### 5.2 생성형 mock

참값을 정해 두고 측정을 시뮬레이션합니다 — 장비 offset, 드리프트, lot 효과, site 효과,
잡음, MDC epoch 점프, 그리고 **`None` cd_value 와 빈 parameter 같은 결측**까지.
mock 이 결측을 내보내지 않아 office 의 null 경로가 집에서 한 번도 실행되지 않는
실패 방식을 여기서 되풀이하지 않아야 합니다. 참값을 알기 때문에 추정기가 σ² 들을
되찾아오는지 검증할 수 있고, 5.3 의 회귀 테스트가 성립합니다.

### 5.3 추정기 (2단계)

- **1단계** — 실행 단위 강건 장비쌍 offset + 군집-강건 관측분산.
- **2단계** — 그 시계열에 국소선형추세 필터. 1단계가 `σ²_obs` 를 공급하므로, 60점짜리
  짧은 시계열에서 두 분산을 동시에 분리하려다 병조건이 되는 상황을 피합니다.

단, `predicted` tier 에서는 1단계 SE 가 **lot 간 성분을 담지 않습니다.** 그대로 넘기면
lot 산포가 process noise 로 기입되어 드리프트가 과대평가되고, 60점으로는 잔차 백색성
검정이 이를 잡아내지 못합니다. lot 간 nugget 만큼 R 을 부풀리거나, R 의 **형태는
1단계로 고정한 채 스칼라 하나만** profile likelihood 로 공동추정합니다.

새 의존성은 필요 없습니다. numpy·pandas 로 충분하며, scikit-learn / statsmodels 는
클라우드 numpy 사고의 전례를 고려하면 지금 단계에서 감수할 이유가 없습니다.

### 5.4 화면

기존 `/ebeam/cd-sem/[fab]/skew-check.vue` 자리에 두되, 검증 전까지는 **실험실 메뉴**에서
들어가게 합니다(`app/utils/headerNav.ts` 의 `group: 'lab'`). 실험실은 "아직 확정이 아닌
계산 도구"라는 뜻을 이미 담고 있어, 정식 기능 탭보다 정직한 위치입니다.

## 6. 사무실에서 확인해야 할 것

집에서는 판정할 수 없는 항목입니다. 우선순위 순입니다.

1. **모든 장비를 도는 QC/매칭 recipe 가 실제로 있는가.** 있으면 `direct` tier 가 서고
   기능 전체가 성립합니다. 없으면 남는 것은 교란된 생산 데이터 추론뿐이며, 제품의
   가치가 크게 떨어집니다. **이 하나가 나머지 전부보다 중요합니다.**
2. **epoch 단위 장비×recipe 배정 행렬의 연결 성분 개수.** 3.5 의 이견을 가르는 유일한
   증거입니다. 성분이 하나면 브리징이 성립하고, 여러 개면 그 경계를 넘는 비교는
   화면에서 "비교 불가"로 막아야 합니다.
3. **실제 장비쌍 스큐의 크기 분포.** `tolerance_range` 를 정하는 근거입니다.
4. **MDC 의 `0Deg`/`90Deg` 가 `Image_rotation` 인가 측정 방향(X/Y)인가.** 계약의
   `Axis` 축이 여기에 걸려 있고, MDC 역적용을 켜도 되는지의 전제입니다.
5. **`Optics` 값의 전체 집합** (`'High Reso.'` 외에 Valley 등) 과 MDC 키 접미사의 대응.
6. 한 실행 내 parameter 들의 공칭 CD 분포 — 3.2 의 within-run CD-gain 대비가 실제로
   충분한 레버리지를 갖는지.

## 7. 화면은 어디에 두는가 — 스큐보아 렌즈 (2026-08-16 추가)

5.4 에서 독립 페이지를 전제했으나, 검토 중 **스큐보아 분석(`skewvoir/analysis`)의
렌즈로 넣는 쪽이 옳다**는 결론에 이르렀습니다. 그리고 그 렌즈는 이미 절반 존재합니다.

### 7.1 이미 있는 것

`timeseries/ToolSkewPanel.vue` + `timeSeries.ts` 의 `buildToolSkew` 가 지금 다음을
하고 있습니다.

- 장비별 n · 평균 · **recipe 별 중앙값으로 센터링한 offset** · σ
- offset 점추정과 ±σ 구간을 막대가 아니라 **추정치와 불확도**로 그리기
- **완전 교란 거부** — 모든 recipe 를 장비가 하나씩 나눠 측정한 세트에서는 숫자를
  내지 않고 이유를 말합니다 (`contrastRecipes === 0`). 센터링하면 전부 0.000 이
  나오는데, 그것은 "비교된 적 없는 장비들이 완벽히 일치한다"로 읽히는 **가장
  오해를 부르는 출력**이기 때문입니다.
- 다른 장비가 안 돈 recipe 만 측정한 장비는 `offset: null` → `—`, 0 이 아님

즉 2.2 의 lot/recipe 교란 문제와 3.5 의 연결성 문제를 **이 코드가 이미 1-hop
수준에서 정직하게 다루고 있습니다.** 추정기를 새로 짓는 것이 아니라 이것을
확장하는 일입니다.

또한 `TrendPoint` 한 개 = MSR 한 건이므로 `n` 은 점 개수가 아니라 실행 개수입니다.
**2.4 의 유사반복 함정을 이미 피해 있습니다.**

### 7.2 스큐보아가 구조적으로 유리한 이유

`/api/<tool>/skew/check` 계약은 **집계된** pairwise 행렬을 내려 줍니다. 반면
스큐보아는 **원본 점 데이터를 이미 로드**해 두고 있으므로, 집계 계약으로는 원리적으로
불가능한 것들을 할 수 있습니다.

- 3.2 의 **한 실행 안 CD-gain 대비** — 같은 웨이퍼의 여러 parameter 가 손에 있어야
  가능하며, 스큐보아는 이미 전부 들고 있습니다.
- 실행 내 산포를 이용한 **MSR 별 가중** (지금 `buildToolSkew` 는 `std` 를 버립니다)
- site 효과, 웨이퍼 내 위치별 스큐 — `position/` 렌즈의 자산을 그대로 씁니다

### 7.3 그래도 페이지가 남아야 하는 이유 — 두 질문의 분업

2.1 에서 스큐 질문을 **크기**와 **성질** 둘로 나눴습니다. 이 둘이 그대로 두 화면의
분업이 됩니다.

| | 스큐보아 렌즈 | 함대 스큐 페이지 |
| --- | --- | --- |
| 답하는 질문 | **크기** — 이 비교에서 얼마나 벌어져 있는가 | **성질** — 그 차이가 재현되는가 |
| 표본 | 사용자가 고른 MSR 세트 | 함대 × 60일 이상 rollup |
| 데이터 | 원본 점 | 집계 |
| 성격 | 확증 · 증거 열람 | 탐색 · 감시 |

**한 세트는 시간의 한 조각이므로, 세트 하나로는 일관성을 답할 수 없습니다.**
일관성은 여러 세트에 걸친 성질이고, 2.3 의 필터는 시계열을 요구합니다. 60일치 MSR 을
전부 고르면 되지 않느냐는 성립하지 않습니다 — 스큐보아는 수십 건 규모의 워크플로이고,
`/api/*` 는 5초당 50건 제한입니다.

따라서 페이지는 죽지 않고 **역할이 바뀝니다**: 함대에서 의심 쌍을 짚어 주고,
거기서 recipe·장비가 미리 선택된 스큐보아 세트로 넘겨 원본 증거를 보게 합니다.
단축 링크(`useShortLink` + `routeQuery.ts`)가 이미 그 연결을 실어 나를 수 있습니다.

### 7.4 렌즈를 완성하려면 메울 것

`buildToolSkew` 와 4·5장의 설계 사이의 간극입니다. 위에서부터 값어치 순입니다.

1. **pairwise 행렬 + N배화.** 지금은 기준선 대비 1:N 이라 "A 와 B 가 서로" 를
   말하지 못합니다. `skewGrouping.ts` 의 Bron–Kerbosch 그룹퍼는 이미 있는데
   스큐보아가 쓰지 않습니다 — 두 자산이 서로를 모른 채 놓여 있습니다.
2. **offset 과 CD-gain 분리.** 지금은 활성 parameter 하나에 대해서만 계산합니다.
   여러 parameter 를 함께 회귀해야 3.1 의 두 항이 갈립니다. 스큐보아만 할 수 있는
   일이므로 여기서 안 하면 아무 데서도 못 합니다.
3. **불확도가 판정에 들어가야 합니다.** 4장의 `buildAdjacency` 문제와 같은 뿌리입니다.
   허용오차와 비교할 때 점추정이 아니라 `offset + k·SE` 를 써야 합니다.
4. **MDC 역적용** (2.5). `mdc_setting` 을 `eqp_id` × 날짜로 조인해야 하므로 새 API
   의존이 생깁니다. beam 키 재구성(6장 4·5번)이 확인되기 전에는 켜지 않습니다.
5. **연결성을 1-hop 에서 그래프로.** `contrastRecipes` 는 사실상 1-hop 검사입니다.
   브리지 경로와 경로 길이까지 보여 주면 3.5 가 완성됩니다.

### 7.5 e-beam 효과 — 앞 장의 전제를 하나 무너뜨립니다

**SEM 은 측정 자체가 시료를 바꿉니다** (user-confirmed 2026-08-16). 레지스트
shrink·카본 오염 때문에 같은 점을 다시 재면 값이 달라지고, 그 차이는 잡음이 아니라
**측정 순서에 계통적인 편향**입니다.

그래서 2장·6장에서 "같은 웨이퍼를 2대 이상이 측정한 자료"를 표준(gold standard)처럼
쓴 것은 **틀렸습니다.** 나중에 측정한 장비는 이미 변화한 시료를 봅니다. 순서를
보정하지 않은 같은-웨이퍼 비교는 편향된 비교이며, 편향의 부호가 항상 같은 방향
(나중 장비 쪽)이라 **평균을 내도 사라지지 않습니다.**

### 7.6 두 가지 검증 방법

#### 방법 1 — A-B-B'-A' (장비 2대, 가장 확실)

같은 웨이퍼를 A → B → B' → A' 순서로 측정합니다(`'` 는 재측정). 슬롯 번호를
`t = 0,1,2,3`, 순서에 선형인 e-beam 성분을 `d` 라 하면

```text
y1 = A + 0d      y2 = B + 1d      y3 = B + 2d      y4 = A + 3d

스큐  = (y2 + y3)/2 − (y1 + y4)/2 = B − A      ← d 가 정확히 상쇄됩니다
e-beam = (y4 − y1)/3  =  y3 − y2  = d          ← 부산물로 함께 나옵니다
```

두 가지가 한 번에 나오는 것이 이 설계의 값어치입니다. **e-beam 효과 자체를 recipe 별로
정량화한 화면은 지금 앱에 없습니다** — 스큐를 재려다 얻는 덤이지만, 현업에는 그쪽이
더 쓸모 있을 수도 있습니다.

한계를 정확히 적어 둡니다. **ABBA 는 선형 성분만 상쇄합니다.** e-beam 영향은 보통
포화하므로(1회차→2회차 변화가 그다음보다 큼) 곡률 `c` 가 있고, 그때

```text
추정된 스큐 = (B − A) − 2c
```

즉 곡률의 2배만큼 편향됩니다. 더 나쁜 것은 **ABBA 4점으로는 이 편향을 진단할 수
없다**는 점입니다 — 미지수가 `A, B, d, c` 4개인데 관측도 4개라 잔차 자유도가 0입니다.
곡률을 보려면 다섯 번째 슬롯(A-B-B'-A'-B'')이나 반복이 필요합니다. 화면은 4점 세트에서
"선형 가정"이라고 명시해야 하며, 조용히 확정값처럼 내면 안 됩니다.

#### 방법 2 — 동일 recipe 다장비 일괄 검증 (N대, 넓게)

같은 recipe(가능하면 같은 웨이퍼)를 여러 장비가 측정한 자료를 한꺼번에 봅니다.
순서가 균형 잡혀 있지 않으므로 **측정 순번을 공변량으로 모형에 넣습니다.**

```text
y = tool_i + β · (누적 측정 순번) + (lot_j) + ε
```

- 웨이퍼가 하나면 `lot_j` 는 필요 없고, 순서 효과만 보정하면 됩니다.
- 웨이퍼가 여럿이면 `lot_j` 가 다시 들어옵니다(2.2).

**결정적인 전제 — 순서와 장비가 교락되면 안 됩니다.** 늘 A 가 먼저, B 가 나중이라면
`tool` 과 `순번` 열이 완전히 상관되어 설계행렬이 특이(singular)해지고, `β` 와 스큐를
분리할 수 없습니다. 웨이퍼마다 순서가 섞여 있어야 식별됩니다.

이것은 이미 `buildToolSkew` 가 하고 있는 거부와 정확히 같은 종류의 검사입니다.
지금 코드는 `contrastRecipes === 0` 일 때 숫자를 내지 않고 이유를 말합니다.
**같은 규율로 `orderBalance` 를 두 번째 거부 조건으로 추가해야 합니다** — 순서가
장비와 교락된 세트에서는 숫자 대신 "장비가 늘 같은 순서로 측정해 순서 효과와
장비 차이를 분리할 수 없습니다" 를 띄웁니다.

#### 두 방법과 계약의 tier

방법 1·2 가 계약의 `direct` / `predicted` 와 맞물립니다. 다만 2단이 아니라 3단이
정확합니다.

| 등급 | 조건 | 얻는 것 |
| --- | --- | --- |
| 확실 (`direct`) | 같은 웨이퍼 + A-B-B'-A' 순서 균형 | 스큐 + e-beam 효과. 선형 가정만 명시 |
| 보통 | 같은 웨이퍼 + 순서 불균형 | 순번 공변량 보정. 잔여 편향 경고 필요 |
| 약함 (`predicted`) | 다른 웨이퍼·lot, 같은 recipe | lot 항 필요. 지금 `buildToolSkew` 의 영역 |

교차-recipe 브리징(3.5)은 **주된 수단에서 내립니다.** 현업에서 어렵다는 것이
확인되었으므로, 3.4 의 부분 pooling 은 보조 신호로만 남기고 설계된 A-B-B'-A' 실행이
1순위 증거가 됩니다. 6장 확인 목록의 2번(연결 성분 개수)도 그만큼 순위가 내려가고,
**"A-B-B'-A' 세트가 meas_hist 에 남아 자동 판별 가능한가"** 가 그 자리를 차지합니다.

#### 순서 복원은 데이터로 가능합니다

`exe_detail_info.wafer_id` 와 `meas_hist` 의 `start_time` 이 있으므로, **같은
`wafer_id` 의 MSR 을 시간순으로 정렬하면 측정 순서가 그대로 나옵니다.** 즉 스큐보아는
사용자가 고른 세트가 A-B-B'-A' 인지 단순 나열인지 **자동으로 판별해 추정기를 고를 수
있습니다.** 별도 입력이 필요 없습니다.

### 7.7 순서 수정

5장의 순서를 다음으로 바꿉니다.

1. **순서 인식** — `wafer_id` × `start_time` 으로 세트의 측정 순서를 복원하고,
   A-B-B'-A' 인지 판별합니다. 나머지 전부의 전제이므로 이것이 먼저입니다.
   msr_file mock 에 e-beam 재측정 효과를 넣는 일이 여기 포함됩니다 — 지금 mock 은
   재측정 개념이 없어 보정 경로가 한 번도 실행되지 않습니다.
2. **두 추정기** (7.6) — ABBA 대비와 순번 공변량 모형. `orderBalance` 거부 조건 포함.
3. **스큐보아 렌즈 확장** (7.4 의 1·2·3) — pairwise 행렬 + N배화, offset/CD-gain 분리,
   불확도의 판정 반영. 집에서 전부 가능하고 원본 점 데이터가 이미 손에 있습니다.
4. **야간 rollup** (5.1) — 시간 축이 필요해지는 시점에.
5. **필터와 함대 페이지** (5.3, 5.4) — 1~3 에서 검증된 코어를 시계열에 얹습니다.

원래 순서는 "rollup 먼저"였습니다. 렌즈가 먼저인 편이 나은 이유는, **크기 추정기를
원본 데이터로 먼저 옳게 만들어 놓아야** rollup 이 무엇을 적재해야 하는지 알 수 있기
때문입니다. 반대로 하면 rollup 스키마를 추측으로 정하게 되고, 5.1 에서 지적한
"되돌릴 수 없는 grain 실수"의 위험이 바로 거기에 있습니다.

## 8. 결론

시작할 수 있습니다. 다만 순서는 **스큐보아 렌즈 → rollup → 필터 → 함대 페이지**이며,
"머신러닝"이라는 이름표는 떼는 편이 낫습니다. 물어보신 것은 예측 모델이 아니라
**분산이 어디서 오는가**이고, 그 질문에는 검증 가능한 답이 있습니다. 반대로 라벨 없는
데이터에 분류기를 얹으면, 맞는지 틀리는지 알 수 없는 숫자를 자신 있는 얼굴로 내놓게
됩니다.
