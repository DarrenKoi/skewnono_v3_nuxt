# 05: 권한 신청·승인 흐름

**What to build:** 권한이 없는 사용자가 탐색기를 열면 "권한 요청" 카드가 보이고, 사유 한 줄을 적어 신청합니다. 다시 열면 대기 중인지 거절되었는지 보이고, 거절되면 다시 신청할 수 있습니다. 관리자는 `/admin/access`에서 대기 신청을 승인하거나 거절하고, 같은 팀 신청은 "이 팀 전체 승인"으로 한 번에 처리합니다.

**Blocked by:** 04 (팀·사번 승인 저장소와 판정)

**Status:** ready-for-agent

- [ ] 신청은 신뢰 출처(cookie·local)에서만 받습니다. body에서는 `reason`만 받고 길이는 200자까지입니다. 사번과 dept_nm은 서버가 정합니다. 이미 `granted`인 사람이 신청하면 아무것도 하지 않습니다
- [ ] 신청할 때마다 새 `request_id`(uuid4 hex)를 발급합니다. `requested_at`은 표시용으로만 씁니다
- [ ] 승인과 거절은 둘 다 WATCH → `request_id` 비교 → MULTI → EXEC 순서로 처리합니다. `request_id`가 다르면 409 `request_changed`입니다. 승인 재시도에서 grant는 있고 신청이 없으면 no-op 성공으로 처리합니다
- [ ] `WatchError`는 `STORE_ERRORS`보다 먼저 잡습니다. 다시 읽어서 그 사번의 신청이 바뀌었으면 409를 내고, 무관한 변경이면 최대 3회까지 재시도합니다
- [ ] 팀 전체 승인은 트랜잭션 안에서 읽은 pending 신청 가운데 저장된 dept_nm이 같은 것만 지웁니다
- [ ] 응답이 끊겨 결과를 알 수 없으면 "결과 확인 불가, 새로고침"으로 안내합니다
- [ ] 탐색기 화면은 verdict별로 다음을 보여 줍니다: 신청 카드, 대기 안내, 거절 안내(재신청 가능), 신뢰 출처 안내, 소속 확인 불가 안내, 저장소 장애 안내
- [ ] 관리자 섹션에 대기 신청 칸을 만듭니다. 사번, 이름, 팀, 사유, 신청 시각을 보여 주고 승인·거절·팀 전체 승인 버튼을 둡니다. 사유는 HTML로 해석하지 않습니다
- [ ] 신청·승인·거절은 `logger.info`로 기록합니다
- [ ] HTTP 테스트로 확인합니다: 신청 → 승인 → 접근, 신청 → 거절 → 재신청, 승인 사이에 재신청이 끼면 409, 팀 전체 승인 정리, declared·token 신청 거부
- [ ] fake Redis가 `WatchError`를 던지게 해서 재시도와 409 분기를 확인합니다
- [ ] `browser-verify` 스킬로 비관리자 identity로 신청하고 관리자로 승인하는 흐름을 확인합니다
