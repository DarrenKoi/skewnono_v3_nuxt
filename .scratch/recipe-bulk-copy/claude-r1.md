# handoff.md 검토 (Claude, r1, 2026-10-17)

전제(사용자 추가): 대상 10대 이상, SKEWNONO는 2 CPU / 8 GiB, 별도 web app 할당 가능,
자원 증설 가능, **운행 중인 서비스에 영향 없음**이 최우선입니다.

## 1. 실행 장소: 별도 web app으로 확정 권고 (열린 질문 6 해소)

- SKEWNONO uWSGI 안의 스레드(`chat/orchestration.py`의 `_spawn_daemon` 선례)는
  탈락입니다. 00:05 `touch-reload`, `max-requests=1000` 재생성, harakiri가 다른
  요청의 SIGKILL로 워커를 통째로 죽일 때 복사가 중간에 끊깁니다. 분 단위 채팅 한 턴은
  견디지만, 10대 × 수백 파일은 수십 분 단위입니다.
- 같은 호스트의 별도 프로세스(`attach-daemon`)는 `wsgi.ini`가 번들 밖 영구 파일이라
  수작업 배포 단계가 늘고, 2 CPU / 8 GiB를 pandas 요청과 그대로 나눠 씁니다.
  "영향 없음"을 CPU·RAM 수준까지 보장하지 못합니다.
- 별도 web app이 가장 단순합니다. 복사기 버그·메모리 누수·FTP 행이 SKEWNONO
  프로세스에 닿지 않고, 배포 주기도 분리됩니다. SKEWNONO 증설은 구조 문제(재시작·
  주소공간 공유)를 풀지 못하므로 증설만으로는 부족합니다.
- 두 앱의 결합은 **Redis 키 공유**만으로 합니다. 둘 사이 HTTP 호출은 두지 않습니다.
  SKEWNONO = 계획 작성·승인·조회(읽기), worker app = 큐 소비·전송·상태 기록(유일한
  쓰기자). 단일 쓰기자이므로 잠금이 필요 없습니다.
- 이로써 handoff 64–65행의 SQLite 조건문은 삭제합니다. 호스트가 다르므로 공유 저장소가
  필요하고, 그 저장소는 이미 있는 office Redis입니다(`api_tokens`·`access_control`·
  `announcements`가 선례, 쓰기 선례는 `_scheduler/redis_jobs.py`).
- OFFICE-VERIFY: 그 web app이 (a) 장비 FTP 대역에 직접 닿는지, (b) 장시간 실행
  프로세스(비-WSGI 또는 `processes=1`)를 허용하는지, (c) 로컬 디스크가 재시작을 넘겨
  남는지(스냅샷 보관용; 아니면 MinIO), (d) 야간 재기동 정책이 있는지.
- worker가 여러 프로세스로 뜨는 플랫폼이면 `_scheduler/election.py`와 같은
  worker 1 선출을 재사용합니다.

## 2. 상태 모델이 없음 (가장 큰 공백)

handoff는 "영속 작업 기록"이라고만 하고 단위와 상태를 정하지 않았습니다. 재시작 복구는
상태 모델이 있어야 성립합니다.

- 단위: job → target(장비) → bundle(묶음) → file. 상태는 file에만 두고 bundle·
  target·job 상태는 집계로 계산합니다(별도 저장 안 함).
- file 상태: `planned → uploading → verifying → done | blocked_conflict |
  blocked_running | failed | uncertain`.
- 재시작 복구: worker 기동 시 `uploading`·`verifying`·`uncertain`인 파일을 찾아
  대상을 실제로 읽고 해시를 대조한 뒤 `done` 또는 `planned`로 되돌립니다. `put`의
  temp+rename 덕분에 반쯤 쓰인 원래 이름 파일은 없으므로 이 재판정이 안전합니다.
  `TransferUncertain`이 바로 `uncertain` 상태의 출처입니다.
- 저장: job 하나당 Redis hash 하나(`field = target/bundle/file`, 값 = 작은 JSON).
  큐는 `LPUSH`/`BRPOP` 리스트 하나. 취소는 job hash의 플래그를 worker가 파일 사이마다
  확인합니다. 그 이상(스트림, pub/sub)은 지금 필요 없습니다.

## 3. 묶음 단위 원자 교체를 기본안으로 검토 (열린 질문 3 단순화)

- 레시피 복사의 정상 경우는 **대상에 그 묶음 폴더가 없을 때**입니다. 그러면
  `<bundle>.sknn-tmp/`에 전부 올린 뒤 폴더를 `RNFR/RNTO`로 한 번에 바꿉니다.
- 효과: 충돌 검사가 "대상 폴더가 이미 있는가" 하나로 줄고(이미 확정한 덮어쓰기 차단과
  같은 뜻), "묶음 전체 보류"가 설계가 아니라 자연스러운 결과가 되며, 실행 중 레시피가
  반쯤 바뀐 상태를 볼 수 없습니다. 열린 질문 1의 경쟁 조건 노출 창이 파일 수백 개
  전송 시간에서 rename 한 번으로 줄어듭니다.
- OFFICE-VERIFY: 장비 FTP 서버가 디렉터리 rename을 지원하는지(Hitachi, AMAT 각각).
  안 되면 파일별 `put`으로 후퇴하고 보류 판정을 집계로 합니다. 설계는 두 경로를 다
  허용하되 **기본은 폴더 교체**로 둡니다.
- 대상에 같은 이름 폴더가 있으면 그 묶음은 `blocked_conflict`로 끝입니다. 파일 단위
  diff 보고는 v1에서 뺍니다(사용자가 탐색기로 직접 보면 됩니다).

## 4. 동시성·자원 (열린 질문 2 수치화)

- 파일은 KB–수 MB(ADR 0001의 프로파일)이므로 병목은 RAM이 아니라 **왕복 횟수와
  장비 FTP 세션 수**입니다. 장비당 제어 연결 1개로 고정하고(세션 상한 OFFICE-VERIFY,
  Hitachi 장비 FTP는 흔히 2–4), 장비 간 병렬 4–8입니다. 장비 10대 × 300파일이면
  장비당 300회 STOR + 300회 검증 ≈ 수 분, 장비 간 병렬로 전체도 수 분입니다.
- 원본 스냅샷은 **한 번** 받아 worker 로컬 디스크(또는 MinIO)에 두고 해시 목록을
  확정합니다. 수집 직후 원본 목록(크기·mtime)을 다시 읽어 수집 전과 다르면 한 번 더
  수집, 또 다르면 차단합니다. 이것으로 58–59행의 "수집 도중 변경"이 닫힙니다.
- 영속 스냅샷이 재시작 복구의 전제입니다. 메모리에만 두면 복구가 불가능합니다.

## 5. 검증 비용

- 재다운로드+해시는 파일이 작으므로 전송량 2배가 허용됩니다. 유지합니다.
- `SIZE`만으로는 불충분(확정 유지). `XMD5`/`XCRC` 확장 명령이 있으면 쓰되
  OFFICE-VERIFY. 없으면 재다운로드가 기본입니다.

## 6. 실행 중 레시피 경쟁 조건

- 잠금은 없습니다. 달성 가능한 최선: (a) 묶음의 첫 쓰기 **직전**에 상태 파일을 다시
  읽는다, (b) 폴더 교체로 노출 창을 rename 한 번으로 줄인다, (c) 교체 직후 상태 파일을
  한 번 더 읽어 그 사이 실행 대상이 바뀌었으면 `blocked_running`이 아니라 **경고**로
  보고한다(이미 바뀐 뒤라 되돌릴 수 없음).
- 잔여 위험을 스펙에 문장으로 남깁니다: "읽기와 rename 사이 수 초 안에 장비가 그
  레시피를 시작하면 새 파일로 실행될 수 있다." 이것을 없애려면 장비 쪽 잠금이
  필요하고 그것은 이 앱 범위 밖입니다.

## 7. handoff.md 자체의 문제

- 97–98행 "업로드 라우트가 이미 있습니다" vs 124행 "proxy에는 쓰기 라우트가
  없습니다"가 모순으로 읽힙니다. 사실은 fleet `upload()`는 있고(덮어씀), 탐색기용
  단일 클라이언트 라우트에만 쓰기가 없는 것입니다. 한 문장으로 고칩니다.
- Phase 2(office Windows, proxy 경유) 쓰기 경로는 **범위에서 뺍니다**. worker는
  클라우드에서만 돕니다. 집은 mock FTP, 사무실 검증은 클라우드 worker에 직접 합니다.
  proxy 쓰기+인증 설계 축 하나가 통째로 사라집니다.
- 55–57행 알림: 새 인프라를 만들지 말고 `announcements`(`/notices`) 저장소에 "개인
  대상 알림" 한 종류를 추가하는 쪽이 작습니다. 외부 알림(메일·Teams)은 v1 제외 유지.
- 53행 결과 CSV: v1에서 뺍니다. 작업 상세 화면의 문제 필터로 충분합니다.
- 42–48행 UI는 타당하나 "파일 수천 개"는 과장입니다(수백 개). 폴더 교체를 택하면
  작업 상세의 파일 단계는 접힌 기본값으로 두고 실패·불명확 파일만 펼칩니다.
- "다음 세션이 할 일"에 **먼저 답해야 할 OFFICE-VERIFY 묶음**을 한 번에 모아 두는 것이
  좋습니다: 디렉터리 rename 지원, FTP 세션 상한, 상태 파일 경로·형식, web app 네트워크·
  장시간 프로세스·디스크 정책. 이 넷은 설계 분기를 가르므로 한 장의 답안지로 받습니다.

## 8. 뺄 것 (YAGNI)

- SQLite 분기, proxy 쓰기 경로, CSV 내보내기, 파일 단위 diff 보고, 외부 알림,
  `BackgroundJobs` 재사용(메모리 기반이라 영속 큐와 역할이 겹치고 복구를 못 함).
  `FtpFleetDownloader`의 `upload`도 덮어쓰기라 그대로 못 쓰고, `FtpClient.put`만
  재사용합니다.
