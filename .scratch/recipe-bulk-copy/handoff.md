다시 미정으로 취급하지 않습니다. 구현이나 장비 검증은 수행하지 않았습니다.

## 이번 대화에서 확정한 결정 (user-confirmed)

- 추천 구조를 채택합니다. 웹은 계획·승인·조회를 담당하고, 실제 전송은 웹 요청 및
  웹 서버 재시작과 독립적인 전용 단일 worker가 수행합니다. 작업 기록은 영속 저장합니다.
- 레시피 하나는 여러 파일과 폴더의 묶음입니다. 묶음을 식별하는 경로 규칙은 미확정입니다.
- 운전 중인 대상 장비에도 복사할 수 있지만 현재 실행 중인 파일은 건드리면 안 됩니다.
- 현재 실행 중인 레시피·파일 정보는 장비의 상태 파일·로그에서 읽을 수 있습니다
  (user-confirmed). 로그에는 레시피 이름만 나오고 전체 경로는 나오지 않습니다
  (user-confirmed). 레시피 이름에 대응하는 경로는 API 또는 장비 내 txt 파일을 통해
  확인할 예정입니다(user-confirmed, 연동 수단의 세부사항은 미확정).
  이름으로 묶음 경로를 유일하게 찾을 수 있는지, API·txt 정보의 최신성은 미확인입니다.
  상태 파일·로그의 실제 경로, 형식, 갱신 주기와 최신성 판정 방법은 미확인입니다.
  관련 파일 보호 범위와 확인 후 실행 대상이 바뀌는 경쟁 조건의 방지 수단도
  아직 확인하지 않았습니다(`OFFICE-VERIFY`).
- 대상의 같은 경로에 내용이 다른 파일이 있으면 덮어쓰지 않고 차단하여 사용자에게
  알립니다(user-confirmed). 충돌이 있는 레시피 묶음의 처리 범위는 구체화해야 합니다.
- 개별 문제로 작업 전체를 조기 중단하지 않고, 전송 가능한 나머지 대상을 계속
  처리합니다. 마지막에 전체 계획 대비 결과를 검토하여 문제를 파악하고 사용자에게
  notification을 제공합니다(user-confirmed). 알림 채널과 상세 UI/UX는 미확정입니다.
  이 선호는 기존의 덮어쓰기 차단이나 실행 중인 파일 보호를 해제한다는 뜻이 아닙니다.
- SQLite 사용 조건과 부분 성공 유지는 앞선 추천의 기본안입니다.
  운영 조건과 세부 정책을 구체화해야 하며, 실제 장비 동작이 검증된 것은 아닙니다.

## UI/UX와 안전성의 제안안 (미확정)

사용자는 UI/UX와 별도 페이지 여부를 질문했습니다. 아래는 assistant의 추천이며,
사용자의 명시적 채택은 아직 없습니다. 다음 세션에서 확인한 뒤 스펙으로 옮깁니다.

- 파일 탐색기와 분리된 레시피 배포 전용 페이지를 만듭니다. URL·기능 slug는 미정입니다.
- 작업 목록: 실행자, 대상 장비 수, 진행 상태, 생성 시각을 보여줍니다.
- 새 배포: 원본 장비·레시피 묶음 선택 → 대상 장비 다중 선택 → 원본 스냅샷 수집·검증과
  대상별 차이 확인 → 고정된 계획 승인 순서입니다. 파일 수천 개를 직접 고르게 하지 않습니다.
- 작업 상세: 장비 → 레시피 묶음 → 파일 순서로 펼칩니다. 탭 종료와 무관하게 계속되며,
  재방문하면 서버에서 진행 상태를 조회합니다. 처리율 100%와 전체 성공을 구분합니다.
- 최종 검토: 승인 계획과 결과를 대조하여 누락, 내용 검증 실패, 충돌, 실행 중 보호,
  부분 반영 묶음, 결과 불명확을 표시합니다. 원인과 다음 행동을 제시합니다.
- 최종 검토는 안전 검사를 뒤로 미루는 것이 아닙니다. 쓰기 전 보호·충돌 검사와
  개별 전송 후 내용 검증은 계속 수행하고, 마지막에는 전체 결과를 대조합니다.
- 충돌이 하나라도 있으면 해당 레시피 묶음 전체를 보류하고, 다른 묶음은 계속 처리하는
  방식을 추천했습니다. 파일별 성공 기록과 별도로 묶음 전체의 완료 여부를 판정합니다.
- 결과 CSV와 문제 항목 필터를 제공합니다. 재시도는 현재 상태를 다시 확인한 새 계획으로
  진행하며, 반영 여부가 불명확한 파일은 재전송 전에 실제 상태를 대조합니다.
- 알림은 작업 상세로 연결되는 영속적인 앱 내부 알림 + 접속 중 토스트를 추천했습니다.
  메일·Teams·브라우저 푸시는 초기 범위에서 제외하는 제안입니다. 앱을 닫은 사용자에게
  즉시 전달되는 알림은 아니므로 외부 알림이 필요한지 확인해야 합니다.
- 원본을 한 번 수집해 해시 명세와 함께 고정하여 모든 대상에 동일한 바이트를 전달합니다.
  원본 수집 도중 변경되는 문제와 여러 파일의 일관성은 별도 확인이 필요합니다.
- 대상 파일의 내용 검증은 서버 해시가 가능하면 활용하고, 아니면 재다운로드 후 해시를
  비교하는 방식입니다. 크기 일치나 FTP 성공 응답만으로 완료 처리하지 않습니다.
- 상태·경로 조회 실패, 오래된 정보, 중복 매핑은 안전하다고 간주하지 않고 반영 보류를
  추천했습니다. 로그 조회는 잠금이 아니므로 실행 대상 변경 경쟁 조건은 여전히 미해결입니다.
- SQLite는 API와 worker가 단일 호스트의 로컬 영속 디스크를 공유할 때만 최소안입니다.
  별도 호스트·다중 worker라면 공유 DB가 필요합니다. 운영 저장소는 아직 확정하지 않았습니다.

## 지금까지 정해진 것 (2026-10-17, user-confirmed)

- 웹 파일 탐색기(`tool-files`)는 **한 장비에서 PC로 파일을 가져오는 일**만 합니다.
  스펙은 `.scratch/tool-files/spec.md`입니다.
- 디스크 일괄 정리와 장비 간 레시피 복사는 그 탐색기에서 **뺐습니다**. 레시피 복사는
  보통 파일 **수백 개**가 움직이는 일이라, HTTP 요청 하나에 태우면 불안정하다는 데
  사용자가 동의했습니다.
- 불안정의 원인은 웹 자체가 아니라 **오래 걸리는 일괄 작업을 요청 스레드에 태우는
  것**이라는 진단입니다(추론, 측정하지 않음). uWSGI 타임아웃이나 탭 종료로 중간에
  끊기면 어디까지 복사됐는지 알 수 없고, 재시도와 이어 하기가 없고, 작업 동안
  worker가 묶입니다(lot_hist 전체 다운로드의 Broken pipe와 같은 계열).

## 열린 질문

1. 레시피 묶음을 어떻게 식별하나요? 현재 실행 정보를 읽는 상태 파일·로그의 경로,
   형식, 갱신 주기와 최신성 판정 방법은 무엇인가요? 복사 중 실행 대상 변경 방지와
   관련 공유 파일의 보호 범위도 미확정입니다(`OFFICE-VERIFY`).
2. 대상 장비 수는 보통 몇 대인가요? 계열을 넘는 복사(HITACHI → AMAT)가 있나요?
3. 다른 내용의 동일 경로 파일은 차단·알림으로 확정했습니다. 다른 대상은 계속 처리합니다.
   충돌이 있는 묶음 전체를 보류하는 제안과 부분 반영 묶음의 처리 방법을 확정해야 합니다.
4. 개별 문제에도 나머지 전송을 계속하고 마지막 전체 검토 후 사용자에게 알리는 것으로
   확정했습니다. 부분 성공 유지·재시도와 중간 상태 묶음의 처리 방법은 구체화해야 합니다.
5. 누가 실행하나요? `tool-files`의 승인 목록(팀·사번)을 그대로 쓰나요?
6. 전용 worker를 어느 상시 실행 호스트에 배치하나요? 클라우드에서 장비 FTP로 직접
   닿는지, 별도 사내 호스트가 필요한지 확인해야 합니다. 웹 요청 내부 실행은 하지 않습니다.

## 이미 있는 재료 (다시 만들지 말 것)

- `ftp_handler/direct_downloader`의 `FtpFleetDownloader`: 여러 장비 동시 접속,
  `list_dirs`.
- `ftp_handler/proxy`: 방화벽 너머 클라이언트용 HTTP 전송. 서버(`flask_proxy.py`)에
  **업로드 라우트가 이미 있습니다**. `UploadSpec` wire 형식도 있습니다.
- `ftp_handler/web_app`의 `BackgroundJobs`: 웹 요청 밖에서 fleet 작업을 돌리고
  결과를 poll합니다. 다만 메모리 기반·단일 프로세스 범위라 재시작 복구와 WSGI
  프로세스 간 상태 공유를 보장하지 않습니다. 운영용 영속 작업 저장소를 대체하지 않습니다.
- `backend/_scheduler/`: 주기 작업은 정확히 한 프로세스만 실행합니다
  (`docs/deployment.md`의 `lazy-apps`, `enable-threads`).
- `ftp_handler/docs/adr/0001-proxy-batch-sizing.md`: proxy 배치 크기 결정 근거.
- 계열별 FTP 계정과 인코딩 설정은 msr_image config의 `SKEWNONO_TOOL_FTP_*`입니다.
  `tool-files` 작업에서 공용 위치로 옮겨질 예정입니다.
- `ftp_handler/`는 vendored copy입니다. 고치면 upstream `flask_modules`도 같이
  고쳐야 합니다.

## tool-files에서 재사용할 공용 부품 (다시 만들지 말 것)

`.scratch/tool-files/spec.md` r1은 다음 네 가지를 라우트 밖의 함수로 두기로 했습니다.
레시피 복사 job은 이 함수를 호출해서 씁니다.

1. 권한 판정: 팀(`dept_nm`) 승인과 사번 승인을 처리합니다. 쓰기 등급이 필요해지면
   grant 값에 `level` 필드를 추가합니다. 이 필드가 없으면 읽기 권한으로 봅니다.
2. 장비 해석: sem_list의 한 행에서 IP, fab, 모델, FTP 계정을 찾습니다.
3. 경로 검증: 경로 구성요소 단위로 루트를 검사하고 금지 문자를 막습니다.
4. 안전한 쓰기: `core.FtpClient.put`이 덮어쓰기를 거부하고, 임시 이름으로 올린 뒤
   rename합니다.

주의할 점이 두 가지 있습니다.

- proxy에는 쓰기 라우트가 없습니다. 레시피 복사를 Phase 2에서 돌리려면 proxy 쓰기와
  인증부터 설계해야 합니다. 기존 `upload_sknn_v3`는 덮어쓰기를 거부하지 않습니다.
- `ftp_handler`는 여러 서비스가 쓰고 있습니다. 기능은 추가만 하고 기존 동작은 바꾸지
  않습니다. 자세한 규칙은 spec r1의 "호환 규칙"에 있습니다.
