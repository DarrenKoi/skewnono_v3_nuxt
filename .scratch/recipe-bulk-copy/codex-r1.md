# 레시피 일괄 복사 설계 검토

판정은 보완 후 구현입니다. 새 제약을 기준으로 별도 앱의 독립 worker를 권고합니다. 현재 handoff만으로는 서비스 무영향, 묶음 일관성, 재시작 복구를 보장할 수 없습니다. 아래 경로와 줄 번호는 현재 체크아웃 기준입니다.

1. **[P0] worker의 위치보다 자원·수명 격리가 먼저입니다.**

   근거는 `handoff.md:15–16,90–103`, `backend/_scheduler/election.py:55–64`, `backend/chat/orchestration.py:69–78`, `docs/deployment.md:154–176,189–197`입니다. (a)는 요청 밖이어도 uWSGI worker의 메모리와 수명을 공유하므로 제외입니다. 선출은 중복 실행 방지일 뿐 격리가 아닙니다. harakiri는 배경 작업 자체의 타이머가 아니지만, 동승한 요청이 worker를 죽이거나 recycle·reload가 발생하면 작업도 사라집니다. (b)는 주소 공간만 분리하며 같은 2 CPU / 8 GiB의 CPU·메모리·I/O를 다툽니다. 일반 `attach-daemon`은 master reload에도 종료됩니다([uWSGI 공식 문서](https://uwsgi-docs.readthedocs.io/en/latest/AttachingDaemons.html)). 증설만으로도 무영향은 보장되지 않습니다.

   **권고:** (c)에 UI/API와 감독받는 단일 worker 프로세스를 두고, 독립 CPU·RAM 한도와 OOM 범위, SKEWNONO와 독립적인 재시작, 상시 실행·자동 재기동·배포 중 중복 방지, FTP 제어/수동 데이터 포트·Redis·MinIO 접근, 사내 identity 전달을 `OFFICE-VERIFY`로 확인해야 합니다. 단순히 URL만 다른 앱이면 부족합니다. 공유 Redis·MinIO·네트워크·장비 FTP의 경합도 남으므로 연결·요청·대역폭 상한과 기존 서비스 지연 확인이 필요하며, 이것도 불가능하면 무영향 요구를 충족했다고 판정할 수 없습니다.

2. **[P1] 영속 기록의 최소 단위는 job과 대상별 파일 task입니다.**

   근거는 `handoff.md:43–54,58–65`와 `ftp_handler/web_app/jobs.py:88–105,121–132`입니다. 메모리 job registry는 복구 원장이 될 수 없습니다. 최소 job 상태는 `planning / awaiting_approval / queued / running / paused / finished`이며, 종료 결과는 성공·부분 성공·실패를 별도로 집계하면 됩니다. task 키는 `(job_id, target_eqp, destination_path)`이고 상태는 `pending / in_progress / verified / blocked / failed / uncertain`이면 충분합니다. job에는 실행자·승인자·승인 시각·계획/manifest 해시·snapshot 위치·원본/대상 식별 정보가 필요합니다. task에는 기대 크기/해시·시도 ID·오류/이유·검증 시각·알려진 임시 경로가 필요합니다. 묶음 상태는 파일 결과에서 계산하면 됩니다.

   **권고:** API는 생성·고정 계획 승인·중지 요청만, worker는 계획 수집·task 결과·job 집계만 기록하고, 승인과 enqueue를 Redis 원자 연산으로 묶어야 합니다. 승인 요청 ID로 중복 제출을 막고, 큐는 Redis의 `queued` job 인덱스로 충분하며 별도 대형 작업 프레임워크는 필요하지 않습니다. `finished`와 알림 대기 표시도 함께 기록하고 job ID로 알림을 중복 제거해야 합니다.

3. **[P0] 재시작 시 재전송보다 실제 상태 대조가 먼저이며, lease만으로 단일 writer가 보장되지는 않습니다.**

   근거는 `handoff.md:53–54`, `ftp_handler/core/client.py:409–422,424–450`입니다. rename 직후 완료 기록 전에 죽는 경우는 `TransferUncertain`이 반환되지 않아도 발생합니다. 재기동 후 남은 `in_progress`는 모두 `uncertain`으로 취급해야 합니다. 대상 내용이 manifest와 같으면 `verified`, 다르면 `blocked`, 부재가 확인되면 보호 조건 재확인 후 재시도입니다. 조회 실패는 계속 `uncertain`입니다. 재개 때 기존 `verified`도 다시 대조하고, 달라졌다면 자동 복원하지 않고 보류해야 합니다. 같은 내용의 기존 파일은 '새로 복사함'과 구별해 검증된 건너뜀으로 기록하는 것이 적절합니다.

   **권고:** 쓰기 전에 시도 의도를 저장하고, 재개 때 최종 파일·확인 가능한 임시 파일을 대조해야 합니다. worker owner/heartbeat와 조건부 상태 갱신을 두되, lease 만료만 보고 후임을 시작하면 안 됩니다. 멈췄던 전임이 FTP 쓰기를 재개할 수 있고 FTP는 Redis 세대 번호를 검사하지 못하기 때문입니다. 전임 프로세스 종료 확인 후 인계하며, 확인 불가 시 보류해야 합니다. Redis 장애 시 새 쓰기를 멈추고 진행 중 파일은 복구 대상으로 남겨야 합니다. `put`의 무작위 임시 이름은 강제 종료 전에 기록되지 않을 수 있으므로 출처 불명 `.part`를 일괄 삭제하는 복구는 금지입니다.

4. **[P1] Redis에 접근할 수 있다는 사실은 영속성 보장이 아닙니다.**

   근거는 `handoff.md:33–34,64–65`입니다. SQL이 없는 새 조건에서는 SQLite와 '공유 DB 필요' 설명을 Redis 상태 원장으로 구체화해야 합니다. Redis는 영속성을 끌 수 있으며, AOF `everysec`도 장애 시 최근 약 1초의 기록을 잃을 수 있습니다([공식 영속성 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)). TTL이 없어도 `allkeys-*` 정책에서는 job이 퇴거될 수 있습니다([공식 eviction 문서](https://redis.io/docs/latest/develop/reference/eviction/)).

   **권고:** 실제 AOF/fsync·복구·백업·failover 손실 범위·퇴거 정책을 `OFFICE-VERIFY`로 확인하고, 미완료 job에는 TTL을 두지 않아야 합니다. snapshot 바이트는 MinIO에 불변 객체로 저장하고 Redis에는 참조와 해시만 둬야 합니다. 공유 Redis에는 job 수·파일 수·메타데이터·연결·조회 빈도 상한을 적용해야 하며, 전역 정책 변경으로 기존 앱에 영향을 주면 안 됩니다. 승인 기록 무손실을 요구한다면 그에 맞는 저장 확인 방식이 먼저이며, 소실된 승인을 원격 파일만 보고 재구성해 계속 실행하면 안 됩니다.

5. **[P0] 디렉터리 rename은 조건부 게시 수단이며, 기존 묶음의 원자적 교체 수단으로 일반화할 수 없습니다.**

   근거는 `handoff.md:17,27–28,51–52,119–120`과 `ftp_handler/core/client.py:409–416`입니다. 임시 묶음을 완성·검증한 후 아직 없는 최종 경로로 rename하는 방식은 부분 묶음 노출을 줄입니다. 그러나 기존 폴더를 backup으로 옮긴 뒤 새 폴더를 옮기는 두 rename은 원자적 swap이 아니며, 기존 다른 내용을 차단한다는 결정과도 충돌합니다. 여러 루트의 공유 파일을 포함하는 묶음은 디렉터리 하나로 게시할 수도 없습니다.

   **권고:** 단일 루트·장비가 staging을 무시함·디렉터리 rename의 지원/원자성/기존 대상 거부가 검증된 경우에만 새 묶음 게시에 사용해야 합니다. 미지원이면 per-file `put`으로 후퇴할 수 있지만 묶음 원자성은 포기한 것입니다. 장비가 불완전한 묶음을 선택하지 못하게 하는 활성화 절차나 정비 시간이 없다면 해당 장비의 자동 배포를 보류해야 합니다. 사전 충돌은 해당 대상 묶음 전체 보류, 도중 실패는 부분 반영 표시로 정하고 다른 묶음·장비는 계속 처리해야 합니다.

6. **[P1] 10대 이상이라는 규모가 파일별 연결이나 기본 동시성 48을 정당화하지는 않습니다.**

   근거는 `handoff.md:29–31,95–104`, `ftp_handler/direct_downloader/fleet_downloader.py:135–140,504–521,622–633`, `ftp_handler/docs/adr/0001-proxy-batch-sizing.md:15–22,37–54`입니다. 작은 파일은 연결·인증·FTP 명령 왕복과 장비 세션/디스크 한도가 먼저 병목이 될 가능성이 높습니다. 이는 측정 전 가설이며 CPU가 항상 여유롭다는 뜻은 아닙니다. 기존 ADR의 `harakiri=60`, RSS 한도와 배치 수치는 다른 proxy 앱의 조건이므로 현재 SKEWNONO 설정으로 옮기면 안 됩니다.

   **권고:** 단일 worker가 대상 장비별 연결 하나를 재사용하여 파일을 순차 처리하고, 장비 간 병렬도는 우선 2로 시작하는 `OFFICE-VERIFY` 제안입니다. 10대 이상은 제한된 슬롯으로 나누어 처리하면 됩니다. 다른 SKEWNONO 기능·외부 클라이언트의 세션까지 포함한 장비 한도와 서비스 지연을 확인한 뒤 올려야 합니다. 동일 장비의 job을 직렬화하고, 전송별 크기·시간·재시도·총 바이트 상한을 둬야 합니다. 전체 대상의 바이트를 `UploadSpec`/base64 JSON에 펼치지 말고 고정 snapshot에서 파일 단위로 공급해야 합니다.

7. **[P1] '한 번 수집해 고정'은 배포 바이트의 동일성만 보장하며 원본 묶음의 시점 일관성을 보장하지 않습니다.**

   근거는 `handoff.md:43–44,58–59`입니다. A 파일을 읽은 뒤 원본이 갱신되고 B 파일을 읽으면, 고정된 snapshot 자체가 서로 다른 버전의 조합일 수 있습니다. 목록·크기·mtime 전후 비교나 두 번의 동일 해시 수집은 탐지력을 높이지만 잠금/버전 없는 동시 수정에 대한 증명은 아닙니다.

   **권고:** 원본의 편집 중지·버전 고정 export·장비 제공 snapshot 중 가능한 수단으로 수집하고, 불변 MinIO 객체와 전체 파일 목록/상대 경로/크기/해시를 완성한 뒤 승인해야 합니다. 수집도 별도 worker에서 수행해야 합니다. 잠금이 불가능하면 전후 목록과 내용 재검사를 최소 완화책으로 삼되 한계를 명시해야 합니다. 재개 때 원본을 다시 읽어 누락 파일을 채우지 말고 같은 snapshot만 사용하며, 소실·변경 시 새 계획 승인이 필요합니다.

8. **[P1] 전체 내용 검증은 유지하되 서버 해시로 대체할 수 있는 경우만 비용을 줄여야 합니다.**

   근거는 `handoff.md:49–50,60–61`입니다. 수백 개 × 10대의 개수만으로 재다운로드가 과도하다고 결론낼 수 없습니다. 총 바이트·왕복 지연·장비 부하를 측정해야 합니다. 검증된 SHA-256 서버 해시가 있으면 본문 재전송을 줄일 수 있지만 SIZE/mtime, FTP 성공 응답, 표본 검사, 업로드 전 로컬 해시는 대상 내용의 동등성을 증명하지 못합니다.

   **권고:** 계열별 서버 해시 지원과 실제 바이트 해시 의미를 확인하고, 없으면 모든 대상 파일을 한 번 재다운로드해 SHA-256을 비교해야 합니다. staging 방식이면 게시 전 내용 검증과 게시 후 경로/목록 대조를 하고, rename 결과가 불명확하면 최종 경로를 다시 내용 검증해야 합니다. 현재 `FtpClient.download`는 bytes 전체 반환 방식이므로 파일 상한과 동시성으로 메모리를 제한해야 하며, 대용량이 확인될 때만 upstream에 스트리밍 검증을 추가하는 것이 적절합니다. 검증은 관찰 시점의 내용 보장이며 이후 장비의 수정까지 막지는 못합니다.

9. **[P0] 실행 로그 재확인은 경쟁 구간을 줄일 뿐 '실행 중인 파일 보호'를 충족시키지는 못합니다.**

   근거는 `handoff.md:18–26,62–63,81–83`입니다. 쓰기 직전 '현재 다른 레시피'라는 답을 얻어도 다음 순간 실행 대상이 바뀔 수 있습니다. 묶음에 없던 파일을 추가하는 행위도 실행 중 묶음의 동작에 영향을 줄 수 있어, 기존 파일을 덮어쓰지 않는 것만으로 충분하지 않습니다.

   **권고:** 잠금이 없다면 확인된 비활성 새 버전 경로에 staging하고, 운전 중 자동 활성화를 하지 않으며 장비 담당자가 정비 시간에 활성화하도록 분리하는 방식이 최선입니다. 이름의 유일한 경로 매핑·최신성·공유 의존 파일을 확인하고, 게시 직전/직후 상태 재확인·이상 시 해당 대상 보류를 추가해야 합니다. 그래도 장비가 staging 경로를 읽거나 검사 사이 실행 대상을 바꿀 위험은 남습니다. 장비 측 선택 금지·잠금·정지 확인 수단이 없으면 운전 중 배포의 절대 보호는 보장 불가이며, 기존 확정 요구를 조용히 완화하지 말고 자동 반영 조건 미충족으로 처리해야 합니다.

10. **[P1] 재사용 대상의 능력과 쓰기 권한이 handoff에서 과장되거나 상충합니다.**

    근거는 `handoff.md:97–98,112–127`입니다. 'proxy 업로드가 있음'과 '쓰기 라우트가 없음'은 fleet와 explorer를 구별해야 양립합니다. 실제 `ftp_handler/proxy/flask_proxy.py:276–288`의 fleet 업로드는 `fleet_downloader.py:888–913`의 덮어쓰기 STOR이며 안전한 `put` 대체물이 아닙니다. 인증 코드 자체는 `flask_proxy.py:139–147`에 있으나 토큰 미설정 시 허용하므로 실제 설정은 미확인입니다. 또한 현재 `tool_files/access.py:41–72`는 읽기 판정이며 쓰기는 `tool_files/routes.py:278–287`에서 플래그·관리자·transport를 따로 검사합니다. `put`도 best-effort이고 디렉터리 생성 API는 제공하지 않습니다.

    **권고:** Phase 2 UI는 별도 클라우드 worker에 작업을 제출하고 worker가 direct FTP를 사용하게 하면 새 proxy 쓰기 API는 생략할 수 있습니다. 필요할 때만 인증된 안전 쓰기 경로를 upstream에 추가해야 합니다. 초기 실행자를 관리자로 한정하면 `grant.level` 도입도 미룰 수 있습니다. 승인·실행·재개 시 권한과 쓰기 중지 설정을 재확인하고, worker는 서버측 장비 해석·경로 검증을 재사용해야 합니다. 계획에는 목적 장비/매핑과 계열 호환성, 대소문자·인코딩 충돌, 공유 파일, 폴더 생성 정책을 고정해야 하며, IP/계열/루트가 바뀌면 새 승인이 필요합니다. 경로 문자열 검사만으로 중간 링크를 막지 못하므로 FTP 계정의 서버측 쓰기 범위도 검증해야 합니다.

검증 범위는 지정 문서와 현재 코드의 정적 대조 및 공식 Redis/uWSGI 문서 확인입니다. 코드 수정·전송 시험·부하 시험은 수행하지 않았습니다. 실제 클라우드 자원 격리, Redis 내구성, FTP rename/해시/실행 상태 연동은 미검증이며 위 `OFFICE-VERIFY`가 해소되기 전에는 운영 안전성을 승인할 수 없습니다.
