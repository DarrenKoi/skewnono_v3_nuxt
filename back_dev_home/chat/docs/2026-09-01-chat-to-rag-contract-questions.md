# chat → RAG: `chat_rag_contract.txt` 중 코드가 검증할 수 없는 절반 (2026-09-01)

같은 날 보낸 [구조 변경 편지](2026-09-01-chat-to-rag-structure-changes.md)와
별개의 문서입니다. 그쪽은 **저희가 무엇을 바꿨는지**를 알리는 편지이고, 이
편지는 **저희가 확인할 수 없어 여쭙는 것**입니다.

## 왜 지금인가

`check_answer_contract --live` 가 사무실에서 통과했습니다. 이 검증이 닫아 준
것은 **모양**입니다 — 필수 키가 있는지, 서명이 맞는지, 인용이 5행 이하인지,
tool_trace 키가 갖춰졌는지.

닫지 못한 것은 **값의 의미**입니다. `source_id` 가 재색인 후에도 같은 chunk
를 가리키는지, `snippet` 이 노출 승인된 text 인지, 접근 권한 필터가 질의
안에 있는지 — 전부 통과한 검증 안에서 조용히 틀릴 수 있는 것들입니다. 저희
쪽에서는 관측할 수단이 아예 없습니다.

아래 6건이 그 목록입니다. 답을 주시면 `docs/datatables/hitachi/chat_rag_contract.txt`
와 mock 양쪽에 그대로 옮겨 적겠습니다(이 저장소의 규칙상 한쪽만 고치지
않습니다). 사내 식별자·host·credential 은 **적지 마십시오** — 필요한 것은
대부분 예/아니오이고, 이 저장소는 공개입니다.

## 질문

### Q1. `source_id` 는 재색인을 견딥니까

계약 문서는 "재색인 후에도 유지되는 stable ID, revision 이 바뀔 때만 변한다"
고 적혀 있습니다. 지금 배포된 인덱스가 실제로 그렇습니까?

**왜 묻는가.** chat 은 `source_id` 를 저장합니다 — 피드백 행과 30일 대화
기록이 이 값으로 근거를 되짚습니다. 재색인 때마다 id 가 움직이면 지난 답변의
인용이 조용히 다른 문서를 가리키거나 사라집니다. 오류가 나지 않으므로 아무도
알아채지 못합니다.

특히 id 가 chunk 순번이나 파일 offset 에서 파생된다면 문단 하나만 추가돼도
전부 밀립니다. 그런 파생이라면 **그렇다고 말씀만 해 주십시오** — 저희가 저장
정책을 바꾸면 되는 일이고, 계약을 어긴 것이 아닙니다.

### Q2. 실제 hit 에 `locator` 가 실립니까

2026-08-27 관측에서 `search_manuals` 는 `source_id, title, snippet, section,
page, figure_id, score, element_type` 8개만 돌려주었고, `locator` 는 저희 쪽
OFFICE-VERIFY 로 남아 있습니다. `agent_query` 의 sources 는 어떻습니까 —
`manual:<doc_id>#page=<page>` 형태를 채워 주십니까, 아니면 `None` 입니까?

**왜 묻는가.** 계약상 optional 이라 `--live` 는 없어도 통과합니다. 다만 SPA 가
인용을 어떻게 그릴지가 여기서 갈립니다: 값이 오면 "문서 · p.12" 참조를
보여주고, 안 오면 제목만 보여줍니다. 지금 mock 은 `None` 을 냅니다.

### Q3. AccessScope 는 질의 단계에 있습니까

계약 문서는 "검색 후 Python 필터링으로 보완하는 것은 계약 위반"이라고
적었습니다. 현재 `groups`/`fabs` 가 빈 list 인 상태에서,

1. `scope` 가 실제로 질의에 들어갑니까, 아니면 지금은 무시됩니까?
2. **빈 list 는 "제한 없음"입니까, "아무것도 매칭 안 됨"입니까?**

**왜 묻는가.** 2번이 특히 중요합니다. 매뉴얼은 현재 권한 제한이 없어 어느
쪽이든 결과가 같습니다. 그래서 회의록·메일을 붙이는 날 의미가 뒤집혀도
지금은 아무 신호가 없습니다. 지금 문장으로 받아 두는 것이 그때 회귀를
막습니다.

여전히 무시하고 계셔도 **문제가 아닙니다** — 그 사실을 적어 두면 됩니다.

### Q4. `snippet` 은 승인된 최소 근거 text 입니까

원문 body 를 그대로 자른 것입니까, 아니면 노출 승인 범위로 만든 발췌입니까?

**왜 묻는가.** snippet 은 화면에 그대로 그려지고 대화 기록에 저장됩니다.
매뉴얼 원문이 통째로 흘러나오는 경로가 되면 안 되는데, 저희 쪽에서는 길이도
출처도 볼 수 없습니다.

### Q5. 남은 OFFICE-VERIFY 3건은 그쪽에서 닫혔습니까

인덱스 이름, host, `safety_level`(매뉴얼이 ANSI Z535.6 계열 머리말
DANGER/WARNING/CAUTION/NOTICE 를 쓰는지) 세 가지입니다.

**값은 보내지 마십시오.** 이 저장소는 공개이고 사내 식별자는 commit 하지
않습니다. 필요한 것은 "닫혔다/아직이다" 뿐이며, 저희는 표시만 바꿉니다.

### Q6. 실제 `figure_id` 는 확정된 형식 그대로입니까 — 특히 파일 이름의 charset

`{stem}_p{page}_i{idx}` 이고 stem 이 매뉴얼 **파일 이름**이라는 것까지는
2026-08-19 에 확인했습니다(`CG6300_1.HHTSEM_SYSTEM_p100_i0`). 여쭐 것은
지금 색인된 전체 집합이 그 형식을 지키는지, 그리고 **점 말고 다른 문자**가
들어오는지입니다 — 공백, 한글, 괄호, `#`, `%` 같은 것들.

**왜 묻는가.** 이것이 이 편지에서 유일하게 **지금 당장 깨질 수 있는** 항목
입니다. 서버는 저장소에 닿기 전에 `^[A-Za-z0-9._-]{1,128}$` 로 검증하고,
걸리면 오류가 아니라 **그냥 그림이 안 뜹니다**. 2026-08-19 에 정확히 이
형태로 한 번 당했습니다 — mock id 에 점이 없어 charset 을 좁혔고, 집에서는
전부 통과하고 사무실에서만 모든 그림이 404 났습니다.

지금 mock fixture 에는 점 하나와 공백·한글 하나를 일부러 넣어 두었습니다
(`SYN 전자광학 조정 안내서 v2.1_p21_i0`). 실제 파일 이름에 그 밖의 문자가
있다면 저희가 charset 을 넓혀야 하니, **문자 종류만** 알려 주십시오. 파일
이름 자체는 필요 없습니다.

절로 기록한 뒤 `chat_rag_contract.txt` 와 mock 에 반영합니다. 문서 파일을
만드실 필요는 없습니다.

Q1·Q3·Q6 은 계약이 어긋나 있으면 **조용히 틀리는** 항목이라 우선입니다.
Q2·Q4·Q5 는 표시와 기록의 문제라 뒤에 답하셔도 됩니다.

## Q3 후속 — 규칙을 "질의 단계" 에서 "절단 전" 으로 바꿨습니다

계약 문서는 "검색 후 Python 필터링은 계약 위반" 이라고 적혀 있었습니다. faiss
에 native filter 가 없다면 **그 규칙은 지킬 수 있는 형태가 아니었습니다.**
저희 쪽 문장이 틀린 것이므로 저희가 고쳤습니다. 새 문장입니다:

> 접근 권한 필터는 **후보 pool 전체에 대해, 5행 절단 전에** 적용되어야 합니다.
> 절단 뒤에 거르는 것이 계약 위반입니다.

완화가 아니라 **관측 가능한 실패에 이름을 붙인 것**입니다. Python 필터인지
질의 절인지는 결과가 같지만, 자르기 전인지 후인지는 결과가 다릅니다 — 뒤에
거르면 권한 있는 근거가 순위 아래에 남아 있는데도 사용자는 5행보다 적게
받고, 오류가 없으므로 "권한 밖" 과 "정말 없음" 이 구분되지 않습니다.

mock 은 이미 이 순서입니다(`_has_access` 를 스캔 안에서 부르고 `[:limit]` 은
그 뒤). 그래서 여쭐 것이 하나 남습니다.

### ❓ Q7. 후처리 필터는 rerank·절단의 **앞**입니까 뒤입니까

후보 20~30건을 뽑고 rerank 한 뒤 5행으로 자르는 흐름에서, access 필터가 어느
지점에 들어갑니까?

지금은 전 문서가 `access IS NULL` 이라 **어느 쪽이든 결과가 같고, 그래서 지금
확인해 두지 않으면 나중에 확인할 기회가 없습니다.** 회의록·메일이 붙는 날
처음 드러나는데, 그때는 "검색이 원래 잘 안 되나 보다" 로 보입니다.

➡️ 절단 앞이 아니라면 **후보 pool 을 늘리는 것으로는 해결되지 않습니다** —
순서를 바꿔야 합니다.

## Q6 후속 — sanitization, 좁히지 마십시오

저희 serving charset 은 **이미 파일 이름이 담는 범위 전체**입니다:

```text
^[\w .-]{1,128}$      # str 패턴의 \w 는 Unicode — 한글 포함
+ ".." 를 포함한 id 거부
+ 앞머리 점(".", ".foo") 거부
```

공백·한글·점 전부 통과합니다. 2026-08-19 에 점을, 2026-09-01 에 공백과 한글을
넓혔고, 그때마다 이유는 같았습니다 — **charset 을 좁히면 오류가 나는 것이
아니라 그림이 그냥 안 뜹니다.**

### ❓ Q8. sanitization 을 넣으시면 어떤 문자를 바꾸십니까

➡️ 저희 권고는 **traversal 모양만** 거르는 것입니다: 경로 구분자(`/`, `\`),
`..`, 앞머리 점, 제어문자, 128자 초과. 공백·한글·점은 그대로 두십시오.

**이름을 바꾸는 sanitization 은 저장소까지 함께 바꾸는 변경입니다.**
`figure_id` 는 `source_id` 와 달리 내용 해시가 아니라 이름에서 파생되므로,
sanitizer 를 넣는 순간 id 가 달라지고 MinIO 객체 이름도 같이 달라져야 합니다.
인덱스만 다시 만들면 **모든 그림이 조용히 404** 납니다. 넣으신다면 그림
ingestion 과 같은 회차로 부탁드립니다.

## 새 질문 — Q3 의 답이 열어 준 것

"faiss" 라는 단어가 저희 문서 전체의 전제를 흔들었습니다. `chat_rag_contract.txt`
는 제목부터 "OpenSearch + MinIO" 이고, 2-leg hybrid 를 **Nori analyzer 를 쓰는
OpenSearch BM25** 로, 모델 호출을 **ML Commons remote connector(C1/C2)** 로
적어 두었습니다. 그런데 저희가 실제로 보는 것은:

| 관측 | 출처 |
|---|---|
| `index_dir` 의 네 파일 — db, vectors, faiss, bm25 | RAG 측 확인 2026-08-31 |
| faiss 에 native access filter 가 없어 Python 후처리 | RAG 측 확인 2026-09-01 |
| cloud preflight 가 `faiss-cpu`·`rank_bm25` 를 runtime 의존성으로 확인 | 이 저장소 |

전부 **클러스터가 아니라 프로세스 안의 파일 인덱스**를 가리킵니다.

### ❓ Q9. 배달된 파일 인덱스가 검색의 전부입니까

OpenSearch 클러스터를 함께 쓰십니까, 아니면 faiss + bm25 파일만으로 답하십니까?

➡️ 후자라고 짐작합니다만, 명시적으로 회신 받은 적이 없어 문서를 지우지 않고
"확인 필요" 표시만 달았습니다. 후자라면 저희 문서의 Nori·ML Commons·C1/C2 절은
현재 구현과 무관하므로 통째로 걷어내겠습니다.

### ❓ Q10. BM25 leg 는 한국어를 무엇으로 자릅니까

이것이 Q9 에서 파생되는 **진짜 위험**입니다. 저희 문서가 Nori 를 명시한 이유는
하나였습니다 — OpenSearch 기본 analyzer 가 한글을 한 글자씩 쪼개 쓸모 있는
매칭을 못 냅니다. `rank_bm25` 는 analyzer 가 없고 **넘겨준 토큰 리스트를 그대로
씁니다.** 그러니 무엇으로 토큰화하시는지가 그대로 한국어 recall 입니다.

공백 split 이면 "얼라인 알람을" 과 "얼라인 알람은" 이 다른 토큰이 되어 조사
하나에 매칭이 끊깁니다. 오류는 나지 않고 **빈 결과와 진짜 miss 를 구분할 수
없습니다** — 저희가 이 저장소에서 가장 경계하는 실패 모양입니다.

➡️ dense leg(BGE-M3)가 multilingual 이라 완전히 무너지지는 않겠습니다만, hybrid
의 절반이 한국어에서 놀고 있는 상태일 수 있습니다. 형태소 분석기든 n-gram 이든
**무엇을 쓰시는지 한 줄이면 됩니다.**
